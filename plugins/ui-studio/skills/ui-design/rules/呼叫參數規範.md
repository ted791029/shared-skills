# 呼叫參數規範

## Rule 1 -- 沒有參數時照預設執行

**強度：MUST**

使用者直接使用、呼叫者也沒有指定參數時，PRODUCT.md、DESIGN.md 與 tokens 一律讀寫專案根目錄的檔案，原型、局部示意、修改規格、方向選擇頁與方向候選.json 寫在專案根目錄的 `design/`，素材交由 ui-assets 依它的預設位置，截圖放在系統暫存資料夾，執行完整流程，缺少產品背景或設計方向時可以詢問使用者，檢查報告回覆在對話中。不得因為專案中有其他流程的資料夾，就自行改變讀寫位置或略過步驟。

### Good Example

這個範例在使用者直接要求收尾時，照預設讀專案根目錄的兩份文件並完整執行。

```text
使用者：「設定頁下週要上線，幫我弄好一點。」
參數：無 → 讀 PRODUCT.md、DESIGN.md（專案根目錄），用法判為收尾，寫出 design/修改規格-設定頁.md 後回覆檢查報告。
```

### Bad Example

這個範例看到專案有 `specs/` 資料夾，就自行把 DESIGN.md 寫進其中，使用者下次直接使用時讀不到它，又重新產出一份根目錄的 DESIGN.md。

```text
使用者：「設定頁下週要上線，幫我弄好一點。」
參數：無 → 專案有 specs/truth/，把 DESIGN.md 寫到 specs/truth/ui/DESIGN.md。
```

## Rule 2 -- 指定位置時只讀寫指定位置

**強度：MUST**

呼叫者指定 PRODUCT.md、DESIGN.md、tokens 輸出資料夾、原型、修改規格、選擇頁位置（方向選擇頁.html 與方向候選.json 所在的資料夾）、素材與素材清單、截圖、目標畫面或檢查報告的位置時，讀取與寫入都必須使用指定的位置，不得另在專案根目錄產出同名檔案；指定的檔案不存在時，視為該文件不存在。

### Good Example

這個範例依呼叫者指定的位置讀寫，選擇頁與候選也寫在指定的資料夾，專案根目錄沒有多出任何檔案。

```text
參數：PRODUCT.md = specs/truth/ui/PRODUCT.md、DESIGN.md = specs/truth/ui/DESIGN.md、選擇頁位置 = specs/plans/005-export/ui/、檢查報告 = specs/plans/005-export/ui/檢查報告.md
→ 讀 specs/truth/ui/DESIGN.md，候選寫入 specs/plans/005-export/ui/方向候選.json，選擇頁寫入 specs/plans/005-export/ui/方向選擇頁.html，檢查報告寫入 specs/plans/005-export/ui/檢查報告.md。
```

### Bad Example

這個範例忽略指定的位置，仍讀寫專案根目錄的 DESIGN.md，呼叫者維護的設計系統沒有被沿用，兩份 DESIGN.md 的值從此分歧。

```text
參數：DESIGN.md = specs/truth/ui/DESIGN.md
→ 專案根目錄沒有 DESIGN.md，判為沒有既有設計系統，在根目錄產出新的 DESIGN.md。
```

## Rule 3 -- 指定產品背景來源時只取自來源

**強度：MUST**

呼叫者指定產品背景的來源檔案時，PRODUCT.md 新增或修改的使用者、使用者要完成的任務、產品用途、使用情境、功能與限制，以及產品沒有的功能只能取自這些來源，不得向使用者詢問；來源沒有寫到的這類事實，不得從程式碼或常識推測補上：呼叫者帶入產品背景的異動時只列在回報，沒有帶入時標為待確認並列在回報中。指定的 PRODUCT.md 已有的內容是先前確認過的產品事實，不得因為這次的來源沒有提到就刪除、改寫或標為待確認。品牌個性、必須保留的品牌元素與設計禁區不在來源與既有 PRODUCT.md 中時，照常詢問使用者，不可詢問時標為待確認。

### Good Example

這個範例保留既有產品背景的族群，只從這次的規格書加入新的族群；呼叫者沒有帶入異動，規格書沒寫的使用頻率標為待確認。

```text
來源：specs/plans/006-hq-summary/spec.md、.claude/constitution/
既有 PRODUCT.md「使用者」：門市店長，月底對帳時匯出當月銷售。
PRODUCT.md「使用者」新增：總部會計，每季下載各門市彙總（來自 spec.md 使用者故事 US1）。
PRODUCT.md「待確認」新增：總部會計一季下載幾次，spec.md 沒有寫。
```

### Bad Example

這個範例把來源當成產品背景的全部，這次規格書沒提到門市店長，就把既有的族群刪除，之後店長使用的匯出頁失去產品背景的依據。

```text
來源：specs/plans/006-hq-summary/spec.md
PRODUCT.md「使用者」改為：總部會計（spec.md 只寫到總部會計，移除門市店長）。
```

## Rule 4 -- 帶入產品背景異動時只處理這些異動

**強度：MUST**

呼叫者帶入產品背景的異動（要新增、修改或刪除的節與事實，包括帶入「沒有異動」）時，只能處理這些異動，不得另外從來源整理其他節、補寫功能清單或新增「待確認」；處理異動時發現的需求缺口列在回報中，由呼叫者決定交給誰。異動涉及品牌個性、品牌元素或設計禁區，而既有 PRODUCT.md 沒有記錄、呼叫者也沒有帶入使用者先前的回答時，照常詢問使用者；已帶入回答時直接採用，不得重問。

### Good Example

這個範例只處理呼叫者帶入的一項異動，規格書沒寫的下載頻率列在回報。

```text
帶入的異動：「使用者」「使用情境」新增總部會計（US1）
→ 回報：「使用者」新增總部會計，每季下載各門市彙總；「使用情境」新增季末在總部辦公室下載。
→ 回報的缺口：總部會計一季下載幾次，spec.md 沒有寫。
```

### Bad Example

這個範例在帶入的異動之外，又從規格書整理出功能清單與待確認，呼叫者沒有盤點的節也被改動，產品背景累積了只屬於這次功能的內容。

```text
帶入的異動：「使用者」「使用情境」新增總部會計（US1）
→ 回報：另在「功能與限制」新增「已有功能：門市彙總下載」，「待確認」新增「總部會計一季下載幾次」。
```

## Rule 5 -- 指定執行範圍時只執行該範圍

**強度：MUST**

呼叫者指定執行範圍時，只能執行該範圍對應的部分，其餘步驟不得執行：

| 範圍 | 執行的部分 |
|---|---|
| 決定設計方向 | 判斷需求、整理產品背景的異動（含詢問品牌個性與設計禁區）、搜尋參考候選、判斷既有視覺世界與是否擲骰、推導候選並擲骰、產出選擇頁並等使用者選定或重擲、委派 ui-assets 選定素材來源，回報這次判定的範圍（建立、延伸、品牌不完整或取代）與理由、產品背景的異動（含使用者對品牌個性與設計禁區的回答）、產品的運作方式與受眾情境、方向候選（每個候選的來源類別、熟悉度、撐得住運作方式的理由、底色與主色、字體氣質、可辨識特徵、結果）、每一輪擲骰（模式、使用者的調整、擲中、挑戰者）、使用者選定的卡片與附帶的調整、選擇頁與方向候選.json 的路徑、參考資料候選與各自採用或排除的理由（沒有擲骰時寫出原因）、選定的方向與要新增或變更的設計系統值（含素材節）；不寫 PRODUCT.md 與 DESIGN.md、不撰寫原型 |
| 撰寫設計系統 | 依呼叫者帶入的產品背景、方向與異動撰寫 PRODUCT.md 與 DESIGN.md，並轉出 tokens 到指定的輸出資料夾；不撰寫原型 |
| 撰寫原型與檢查 | 以既有 PRODUCT.md、DESIGN.md 與 tokens 撰寫或修改原型、委派 ui-assets 取得素材、實測並撰寫檢查報告；不改寫 PRODUCT.md 與 DESIGN.md，需要新增或變更產品背景或 token 時列入回報 |
| 只實測與檢查 | 只對指定的原型或畫面實測、檢查並撰寫檢查報告；不撰寫或修改任何設計產物，包括 PRODUCT.md 與 DESIGN.md |

呼叫者同時指定用法（例如做新畫面或收尾）時，以指定的用法為準。呼叫者帶入設計方向的範圍（建立、延伸或取代）時，以帶入的範圍為準，但帶入建立時仍要依視覺方向規範讀既有程式碼與素材：程式碼已有一致的視覺時改判延伸，只有部分品牌素材時改判品牌不完整，並在回報寫出改判的理由。

### Good Example

這個範例的範圍是決定設計方向，等使用者在選擇頁選定後，回報判定、產品背景的異動、候選與擲骰、選定的方向與要新增的值就結束，PRODUCT.md 與 DESIGN.md 留給呼叫者盤點後再寫。

```text
範圍：決定設計方向；選擇頁位置 specs/plans/001-booking/ui/
→ 判定：建立（DESIGN.md 不存在，程式碼沒有既有視覺）。
→ 產品背景異動：新增「使用者」節（櫃台人員、看診民眾）；設計禁區：使用者說「不要像大醫院那樣冷冰冰」。
→ 運作方式：長輩在家用手機掛號，不必一早到櫃台排隊。
→ 候選 7 個（例：社區診所的櫃台｜場所｜熟悉｜長輩每次看診都會面對櫃台｜米白底、墨綠主色｜圓潤大字｜號碼牌造型的時段按鈕｜使用者選定）。
→ 擲骰：第 1 輪一般模式，擲中藥袋與處方箋，挑戰者診間衛教海報、候診椅號碼燈；第 2 輪保守一點，擲中社區診所的櫃台。
→ 使用者選定：第 2 輪第 1 張，附帶調整「字再大一點」。
→ 選擇頁：specs/plans/001-booking/ui/方向選擇頁.html；候選：specs/plans/001-booking/ui/方向候選.json。
→ 參考資料候選 Medical Clean 排除，醫療類別的預設長相。
→ 方向：「社區診所的櫃台」，新增色彩 --color-primary #1f6f5c、--color-surface #f7f5f0。
→ 不寫 PRODUCT.md 與 DESIGN.md、不修改畫面，回報結束。
```

### Bad Example

這個範例的範圍只是決定設計方向，卻接著寫入 DESIGN.md 並修改首頁，呼叫者還沒盤點的異動已經寫進設計系統，畫面也被改動。

```text
範圍：決定設計方向
→ 決定方向後寫入 DESIGN.md，並把首頁改成新的配色。
```

## Rule 6 -- 不可詢問時回報缺口

**強度：MUST**

呼叫者標明不可詢問時，原本要詢問使用者的問題不得自行選定答案：缺口會改變設計時，停止並在回報中列出問題、選項與推薦；不會改變設計時標為待確認後繼續。需要使用者在方向選擇頁選定時，產出選擇頁後停止，回報選擇頁的路徑、擲中的方向與「方向尚未選定」。再次執行時，選擇頁位置已有尚未選定的擲骰，就不得重新推導候選或擲骰：呼叫者帶入使用者的回覆時依視覺方向規範處理，沒有帶入時再請使用者選定。

### Good Example

這個範例在不可詢問時，把會改變版面的缺口列在回報中並停止，不影響設計的缺口標為待確認；需要選定方向時產出選擇頁後停止，再次執行時依帶入的回覆接續。

```text
參數：不可詢問
缺口 1：匯出頁的主要使用者是店長或總部會計，資訊密度完全不同 → 停止，回報：「A. 店長（推薦，spec.md 的 US1 是店長）B. 總部會計」。
缺口 2：品牌標語是否要出現在匯出頁 → 不改變版面，標為待確認。
缺口 3：設計方向要由使用者選定 → 產出 specs/plans/005-export/ui/方向選擇頁.html 後停止，回報：擲中「出貨單」，方向尚未選定。
再次執行：帶入使用者的回覆「選 3（倉庫料架標籤）」→ 方向候選.json 第 1 輪尚未選定，不重新擲骰，以 choose 記錄第 3 張後繼續。
```

### Bad Example

這個範例在不可詢問時自行選定使用者並完成畫面，選錯時整個畫面要重做，呼叫者也不知道有一個未經確認的決定。

```text
參數：不可詢問
缺口：匯出頁的主要使用者是店長或總部會計 → 選定店長，完成匯出頁。
```

## Rule 7 -- 委派 ui-assets 時原樣轉交參數

**強度：MUST**

委派 ui-assets 時，必須原樣轉交呼叫者指定的素材位置、素材清單位置、DESIGN.md 位置與「不可詢問」，並寫明這次的範圍（選定來源或取得素材）。找不到 ui-assets 時，不得自行選定來源或取得素材：需要素材的位置放上標示清楚的佔位圖，並在檢查報告列出缺少的素材。

### Good Example

這個範例把 SDD 呼叫者指定的位置與不可詢問原樣轉交給 ui-assets。

```text
委派 ui-assets：範圍 取得素材；素材位置 specs/plans/005-export/ui/prototype/assets/；素材清單 specs/plans/005-export/ui/prototype/素材清單.md；DESIGN.md specs/truth/ui/DESIGN.md；不可詢問
```

### Bad Example

這個範例沒有轉交位置與不可詢問，ui-assets 依預設把素材寫進專案根目錄的 design/assets/，並在 sub-agent 中停下來詢問使用者，整個 Wave 卡住。

```text
委派 ui-assets：取得首頁需要的圖示
```
