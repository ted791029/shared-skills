# 呼叫參數規範

## Rule 1 -- 沒有參數時照預設執行

**強度：MUST**

使用者直接使用、呼叫者也沒有指定參數時，PRODUCT.md、DESIGN.md 與 tokens 一律讀寫專案根目錄的檔案，原型、局部示意與修改規格寫在專案根目錄的 `design/`，素材交由 ui-assets 依它的預設位置，截圖放在系統暫存資料夾，執行完整流程，缺少產品背景或設計方向時可以詢問使用者，檢查報告回覆在對話中。不得因為專案中有其他流程的資料夾，就自行改變讀寫位置或略過步驟。

### Good Example

這個範例在使用者直接要求收尾時，照預設讀專案根目錄的兩份文件並完整執行。

```text
使用者：「設定頁下週要上線，幫我弄好一點。」
參數：無 → 讀 PRODUCT.md、DESIGN.md（專案根目錄），用法判為收尾，寫出 design/修改規格-設定頁.md 後回覆檢查報告。
```

### Bad Example

這個範例看到專案有 `specs/` 資料夾，就自行把 DESIGN.md 寫進其中，使用者下次直接使用時讀不到它，又重新產出一份根目錄的 DESIGN.md。

```text
使用者：「設定頁下週要上線，幫我弄好一點。」
參數：無 → 專案有 specs/truth/，把 DESIGN.md 寫到 specs/truth/ui/DESIGN.md。
```

## Rule 2 -- 指定位置時只讀寫指定位置

**強度：MUST**

呼叫者指定 PRODUCT.md、DESIGN.md、tokens 輸出資料夾、原型、修改規格、素材與素材清單、截圖、目標畫面或檢查報告的位置時，讀取與寫入都必須使用指定的位置，不得另在專案根目錄產出同名檔案；指定的檔案不存在時，視為該文件不存在。

### Good Example

這個範例依呼叫者指定的位置讀寫，專案根目錄沒有多出任何檔案。

```text
參數：PRODUCT.md = specs/plans/005-export/ui/PRODUCT.md、DESIGN.md = specs/truth/ui/DESIGN.md、檢查報告 = specs/plans/005-export/ui/檢查報告.md
→ 讀 specs/truth/ui/DESIGN.md，檢查報告寫入 specs/plans/005-export/ui/檢查報告.md。
```

### Bad Example

這個範例忽略指定的位置，仍讀寫專案根目錄的 DESIGN.md，呼叫者維護的設計系統沒有被沿用，兩份 DESIGN.md 的值從此分歧。

```text
參數：DESIGN.md = specs/truth/ui/DESIGN.md
→ 專案根目錄沒有 DESIGN.md，判為沒有既有設計系統，在根目錄產出新的 DESIGN.md。
```

## Rule 3 -- 指定產品背景來源時只取自來源

**強度：MUST**

呼叫者指定產品背景的來源檔案時，PRODUCT.md 的使用者、產品用途、使用情境與功能限制只能取自這些來源；來源沒有寫到的這類事實，不得從程式碼或常識推測補上，必須標為待確認並列在回報中。品牌個性與必須保留的品牌元素不在來源中時，照常詢問使用者，不可詢問時標為待確認。

### Good Example

這個範例只從指定的規格書與規範取得使用者與限制，規格書沒寫的使用頻率標為待確認。

```text
來源：specs/plans/005-export/spec.md、.claude/constitution/
PRODUCT.md「使用者」：門市店長，月底對帳時匯出當月銷售（來自 spec.md 使用者故事 US1）。
PRODUCT.md「待確認」：店長一個月匯出幾次，spec.md 沒有寫。
```

### Bad Example

這個範例從程式碼的路由推測出規格書沒有的使用者族群，PRODUCT.md 與規格書對使用者的認定不同，依規格書撰寫的驗收與依 PRODUCT.md 做的畫面互相矛盾。

```text
來源：specs/plans/005-export/spec.md
PRODUCT.md「使用者」：門市店長與總部會計（routes 中有 /hq/reports，推測總部也會使用）。
```

## Rule 4 -- 指定執行範圍時只執行該範圍

**強度：MUST**

呼叫者指定執行範圍時，只能執行該範圍對應的部分，其餘步驟不得執行：

| 範圍 | 執行的部分 |
|---|---|
| 決定設計方向 | 判斷需求、產出 PRODUCT.md、搜尋參考候選、委派 ui-assets 選定素材來源、決定視覺方向，回報方向與要新增或變更的設計系統值（含素材節）；不寫 DESIGN.md、不撰寫原型 |
| 撰寫設計系統 | 依呼叫者帶入的方向與異動撰寫 DESIGN.md，並轉出 tokens 到指定的輸出資料夾；不撰寫原型 |
| 撰寫原型與檢查 | 以既有 DESIGN.md 與 tokens 撰寫或修改原型、委派 ui-assets 取得素材、實測並撰寫檢查報告；不改寫 DESIGN.md，需要新增或變更 token 時列入回報 |
| 只實測與檢查 | 只對指定的原型或畫面實測、檢查並撰寫檢查報告；不撰寫或修改任何設計產物 |

呼叫者同時指定用法（例如做新畫面或收尾）時，以指定的用法為準。

### Good Example

這個範例的範圍是決定設計方向，回報方向與要新增的值後就結束，DESIGN.md 留給呼叫者盤點後再寫。

```text
範圍：決定設計方向
→ 產出 PRODUCT.md；方向：「社區診所的櫃台」，新增色彩 --color-primary #1f6f5c、--color-surface #f7f5f0。
→ 不寫 DESIGN.md、不修改畫面，回報結束。
```

### Bad Example

這個範例的範圍只是決定設計方向，卻接著寫入 DESIGN.md 並修改首頁，呼叫者還沒盤點的異動已經寫進設計系統，畫面也被改動。

```text
範圍：決定設計方向
→ 決定方向後寫入 DESIGN.md，並把首頁改成新的配色。
```

## Rule 5 -- 不可詢問時回報缺口

**強度：MUST**

呼叫者標明不可詢問時，原本要詢問使用者的問題不得自行選定答案：缺口會改變設計時，停止並在回報中列出問題、選項與推薦；不會改變設計時標為待確認後繼續。

### Good Example

這個範例在不可詢問時，把會改變版面的缺口列在回報中並停止，不影響設計的缺口標為待確認。

```text
參數：不可詢問
缺口 1：匯出頁的主要使用者是店長或總部會計，資訊密度完全不同 → 停止，回報：「A. 店長（推薦，spec.md 的 US1 是店長）B. 總部會計」。
缺口 2：品牌標語是否要出現在匯出頁 → 不改變版面，標為待確認。
```

### Bad Example

這個範例在不可詢問時自行選定使用者並完成畫面，選錯時整個畫面要重做，呼叫者也不知道有一個未經確認的決定。

```text
參數：不可詢問
缺口：匯出頁的主要使用者是店長或總部會計 → 選定店長，完成匯出頁。
```

## Rule 6 -- 委派 ui-assets 時原樣轉交參數

**強度：MUST**

委派 ui-assets 時，必須原樣轉交呼叫者指定的素材位置、素材清單位置、DESIGN.md 位置與「不可詢問」，並寫明這次的範圍（選定來源或取得素材）。找不到 ui-assets 時，不得自行選定來源或取得素材：需要素材的位置放上標示清楚的佔位圖，並在檢查報告列出缺少的素材。

### Good Example

這個範例把 SDD 呼叫者指定的位置與不可詢問原樣轉交給 ui-assets。

```text
委派 ui-assets：範圍 取得素材；素材位置 specs/plans/005-export/ui/prototype/assets/；素材清單 specs/plans/005-export/ui/prototype/素材清單.md；DESIGN.md specs/truth/ui/DESIGN.md；不可詢問
```

### Bad Example

這個範例沒有轉交位置與不可詢問，ui-assets 依預設把素材寫進專案根目錄的 design/assets/，並在 sub-agent 中停下來詢問使用者，整個 Wave 卡住。

```text
委派 ui-assets：取得首頁需要的圖示
```
