# 收尾規範

## Rule 1 -- 收尾只修飾不重新設計

**強度：MUST**

收尾只修正既有畫面的細節，以修改規格交付，不修改專案程式碼，也不得暗中重新設計。既有的視覺風格（配色、字體、圓角、間距系統）、內容、互動行為，以及不在這次範圍內的畫面與元件都必須保留。修改前先讀 DESIGN.md、既有 token、共用元件與相鄰畫面，以它們為基準。

### Good Example

這個範例只把散落的寫死數值換回既有 token、補上 focus 樣式，原本的圓角、配色與版面都沒變。

```css
/* 修改前：.toolbar { padding: 13px 15px; color: #4a4a4a; } */
.toolbar { padding: var(--space-3) var(--space-4); color: var(--text-muted); }
.toolbar button:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px; }
```

### Bad Example

這個範例以「收尾」為名把整個工具列換成新的配色與膠囊形狀，還改了不在範圍內的側邊欄，使用者拿到的是一個沒有同意過的新設計。

```css
.toolbar { background: linear-gradient(90deg, #0f172a, #1e3a8a); border-radius: 999px; }
.sidebar { width: 72px; }
```

## Rule 2 -- 概念有問題時明說並建議重新設計

**強度：MUST**

如果問題出在畫面的概念本身（流程方向錯、資訊架構不合使用者需要），不得在收尾裡偷偷換掉，必須用白話向使用者說明哪裡有問題、為什麼收尾解決不了，並建議改走「做新畫面」重新設計。說明時不使用設計術語。

### Good Example

這個範例用白話說明概念層級的問題，並建議重新設計，沒有自行動手替換。

```text
這次的修改規格列出了按鈕狀態、錯字和對齊的修正。另外有一個收尾解決不了的問題：
目前要先填完五個欄位才看得到價格，很多人可能在看到價格前就離開了。
這需要調整整個頁面的順序，建議另外用「做新畫面」重新設計這一頁。
```

### Bad Example

這個範例發現概念問題後，在收尾時自行把表單拆成三步驟精靈，沒有告知使用者，既有行為被改掉，也違反了收尾的範圍。

```text
已完成收尾的修改規格：修正對齊與錯字，並將表單改為三步驟精靈以改善轉換率。
```

## Rule 3 -- 先分類偏差再在最窄層級修正

**強度：MUST**

每個要修的偏差都必須先判斷屬於哪一類，再在最窄的正確層級修正：

| 類型 | 判斷方式 | 修正層級 |
|------|---------|---------|
| 缺少 token | 同一個數值在多處重複出現，系統需要可重用的值 | 新增 token 並替換各處 |
| 單次實作 | 已有共用元件或模式，這裡卻自己刻了一份 | 改用共用元件 |
| 概念不一致 | 流程、資訊架構或層級與產品中類似區塊不同 | 對齊相鄰區塊的作法 |
| 局部缺陷 | 單純寫得不完整或不一致 | 只改該處 |

不得為了單一例外建立系統層級的 token 或抽象。

### Good Example

這個範例判斷頁面自刻的確認對話框屬於「單次實作」，改用專案既有的共用元件，而不是修補自刻版本的樣式。

```jsx
// 類型：單次實作。專案已有 <ConfirmDialog>，移除自刻的 div 對話框
<ConfirmDialog
  open={open}
  title="刪除這個專案？"
  confirmLabel="刪除專案"
  onConfirm={handleDelete}
  onCancel={() => setOpen(false)}
/>
```

### Bad Example

這個範例只有一個按鈕需要特殊的 13px 間距，卻新增全域 token，系統多了一個只用一次的值，之後其他人會誤用它。

```css
:root { --space-checkout-promo-gap: 13px; }
.promo-apply { margin-inline-start: var(--space-checkout-promo-gap); }
```

## Rule 4 -- 依優先順序修正

**強度：MUST**

先把功能性缺陷與外觀問題分開，再依下列順序修正，前一級還有未處理的問題時，不得先做後一級：

1. 任務壞掉或被擋住、資料遺失、誤導人的狀態、無法以鍵盤或輔助科技走完的路徑。
2. 缺少的 loading、empty、error、success、disabled、權限不足狀態。
3. 流程與層級、響應式、與設計系統不一致之處。
4. 視覺與動態的不一致。
5. 程式碼與素材清理。

### Good Example

這個範例先修好送出後會清空表單的資料遺失問題，再補 loading 狀態，最後才調整按鈕陰影。

```text
1. [任務壞掉] 送出失敗時表單被清空 → 改為保留輸入並顯示錯誤
2. [缺少狀態] 送出中沒有 loading → 按鈕加上 aria-busy 與「送出中…」
3. [視覺] 主要按鈕陰影與其他按鈕不一致 → 改用 --shadow-sm
```

### Bad Example

這個範例花時間調整圖示對齊與陰影，卻沒處理送出失敗會清空表單的問題，畫面看起來更精緻，使用者仍然會遺失資料。

```text
1. [視覺] 圖示往下 1px 對齊文字
2. [視覺] 卡片陰影改柔和
（未處理：送出失敗時表單被清空）
```

## Rule 5 -- 整條使用路徑達到同一品質

**強度：MUST**

收尾必須涵蓋使用者完成任務的整條路徑（進入、操作、轉場、空狀態、錯誤恢復），每一段都要達到同一品質，不得只把其中一個角落修到完美。每一段都要以實測截圖確認手機、中間寬度與寬螢幕的版面，無法實測時改讀程式碼確認斷點樣式，並確認長內容、缺少內容等情況。

### Good Example

這個範例列出整條路徑每一段的檢查結果，每段都處理到同一水準。

```text
購物車 → 結帳 → 付款 → 完成
- 購物車：補空狀態、長商品名稱換行
- 結帳：表單錯誤訊息改為說明恢復方法、手機版欄位改單欄
- 付款：補 loading 與付款失敗狀態
- 完成：補「查看訂單」連結，避免停在死路
```

### Bad Example

這個範例只把購物車頁打磨到細節完美，結帳與付款頁仍缺少錯誤與 loading 狀態，使用者一離開第一頁就落回粗糙的品質。

```text
購物車：重新調整商品圖比例、價格字級、數量按鈕動畫、hover 效果
結帳、付款、完成：未檢查
```

## Rule 6 -- 不為了讓修飾看得見而加動畫

**強度：SHOULD**

收尾時保持既有動態的一致、可中斷與流暢，不得只為了讓使用者「看得出有修過」而新增動畫或特效。

### Good Example

這個範例只把各處不一致的轉場時間統一成既有 token，沒有新增效果。

```css
.menu, .tooltip, .drawer { transition-duration: var(--duration-fast); transition-timing-function: var(--ease-out); }
```

### Bad Example

這個範例在收尾時替所有卡片加上 hover 放大與發光，原本沒有這種動態，畫面變得浮躁，也偏離既有風格。

```css
.card:hover { transform: scale(1.05); box-shadow: 0 0 30px var(--accent); transition: all 0.3s; }
```

## Rule 7 -- 不得擅改事實性文案

**強度：MUST**

收尾可以統一用詞、大小寫與標點，但涉及產品事實的文案（價格、功能宣稱、數據、承諾）屬於產品事實，修改前必須用白話詢問使用者，不得自行改寫或新增宣稱。

### Good Example

這個範例只統一標點與用詞，並針對事實性文案向使用者確認。

```text
我把各頁的「登入／登錄」統一成「登入」，標點也改成全形。
首頁寫著「處理速度提升 3 倍」，這個數字我沒有改。請問這是目前正確的數字嗎？
```

### Bad Example

這個範例把「支援 Excel 匯入」改寫成「支援所有常見檔案格式」，替產品新增了沒有根據的功能宣稱，使用者可能因此誤信而客訴。

```diff
- <p>支援 Excel 匯入</p>
+ <p>支援所有常見檔案格式，一鍵匯入</p>
```

## Rule 8 -- 修改規格要列出清理項目

**強度：SHOULD**

收尾的修改規格必須把實作時要一併清除的項目列成獨立的清理項：除錯輸出、無用程式碼、沒用到的 import、被 token 取代的過時樣式與重複值。收尾結束前也要檢查這次寫入的局部示意，移除已被取代的示意檔與暫時檔案；實測截圖放在專案外，不算暫時檔案。

### Good Example

這個範例把要清除的舊樣式與除錯輸出列成清理項，實作時一併處理。

```markdown
| 優先 | 位置 | 現況 | 改成 | 依據 | 示意 |
|---|---|---|---|---|---|
| P4 | `src/pages/Cart.tsx` 第 12 行 | `console.log('cart', cart)` | 刪除 | 收尾規範 Rule 8 | — |
| P4 | `src/styles/cart.css` `.cart-total-old` | 已被 `--color-ink` 取代的舊樣式 | 刪除整條規則 | 收尾規範 Rule 8 | — |
```

### Bad Example

這個範例的修改規格只寫新的樣式，沒有列出被取代的舊 class，實作後新舊樣式並存，之後的人分不出哪一份才有效。

```markdown
| P3 | `.cart-total` | `color: #333` | `color: var(--color-ink)` | 收尾規範 Rule 3 | — |
```
