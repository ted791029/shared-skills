# 強韌規範

## Rule 1 -- 只補邊界情況不改設計

**強度：MUST**

強韌改善只能補上錯誤、空資料、載入中、超長內容、多語系、權限不足、重複操作等邊界情況的處理，不得改變正常情況下的版面、配色、字體與功能。新增的錯誤、空狀態與載入畫面要沿用既有的元件與樣式。

### Good Example

這個範例在既有卡片元件中補上錯誤狀態，沿用原本的卡片與按鈕樣式。

```jsx
if (error) return (
  <Card>
    <p>訂單清單載入失敗，請檢查網路後重試。</p>
    <Button variant="secondary" onClick={retry}>重新載入</Button>
  </Card>
);
```

### Bad Example

這個範例在補錯誤處理時順便換掉整頁的配色與卡片樣式，使用者只要求處理錯誤，卻得到一個面目全非的畫面。

```css
:root { --bg: #0b1020; --accent: #7c3aed; }
.card { border-radius: 24px; box-shadow: 0 20px 60px rgb(0 0 0 / .4); }
```

## Rule 2 -- 容器必須容納長文字與翻譯

**強度：MUST**

放文字的容器不得使用固定寬度，要能容納 100 個字元以上的名稱，以及比原文長 30–40% 的翻譯（德文常比英文長約 30%）。flex 與 grid 子項目要設 `min-width: 0` 以免撐破版面；需要截斷時用 `text-overflow: ellipsis` 或 `line-clamp`，並讓使用者仍能看到完整文字（例如 `title` 或展開）；可換行的文字加上 `overflow-wrap: break-word`。

### Good Example

這個範例讓按鈕依內容伸縮，清單名稱在 flex 中可縮小並截斷，完整名稱放在 `title`。

```jsx
<button className="px-4 py-2">送出申請</button>
<li className="flex gap-2">
  <span className="min-w-0 truncate" title={name}>{name}</span>
  <span className="shrink-0">{status}</span>
</li>
```

### Bad Example

這個範例把按鈕寬度寫死為 96px，換成德文或較長的名稱時文字溢出按鈕或被切掉，使用者看不懂按鈕在做什麼。

```jsx
<button className="w-24">送出</button>
<li className="flex"><span>{name}</span><span>{status}</span></li>
```

## Rule 3 -- 以邏輯屬性支援由右到左

**強度：SHOULD**

左右方向的間距、邊框與定位使用邏輯屬性（`margin-inline-start`、`padding-inline`、`border-inline-end`、`inset-inline-start`），有方向性的圖示在 `[dir="rtl"]` 下鏡像，讓阿拉伯文、希伯來文介面不需另寫一套樣式。

### Good Example

這個範例使用邏輯屬性，並在由右到左時鏡像箭頭。

```css
.item { padding-inline: 1rem; margin-inline-start: 0.5rem; border-inline-end: 1px solid var(--border); }
[dir="rtl"] .icon-arrow { transform: scaleX(-1); }
```

### Bad Example

這個範例寫死左右方向，切換成阿拉伯文時間距和邊框都在錯的一側，箭頭也指向反方向。

```css
.item { padding-left: 1rem; margin-left: 0.5rem; border-right: 1px solid var(--border); }
```

## Rule 4 -- 不得破壞阿拉伯字母文字

**強度：MUST**

處理波斯文、庫德文等阿拉伯字母文字時，不得在過濾或清理輸入時移除零寬不連字（U+200C），否則會改變字義。儲存時保留原本的字母形式；搜尋與驗證時把波斯文的 ی（U+06CC）、ک（U+06A9）與阿拉伯文的 ي（U+064A）、ك（U+0643）視為相同，不得拒絕其中一種。

### Good Example

這個範例只在搜尋比對時統一字母，儲存的原文不變，也保留零寬不連字。

```js
const normalizeForSearch = (s) => s.replace(/ي/g, 'ی').replace(/ك/g, 'ک');
const match = normalizeForSearch(record.name).includes(normalizeForSearch(query));
```

### Bad Example

這個範例在清理輸入時移除所有零寬字元，波斯文的複合詞被改成別的字，使用者的姓名或地址因此變得錯誤。

```js
const clean = input.replace(/[​-‍﻿]/g, '');
```

## Rule 5 -- 日期數字與複數交給 Intl

**強度：MUST**

日期、時間、數字、貨幣必須使用 `Intl.DateTimeFormat`、`Intl.NumberFormat` 並傳入正確的語系（包含不同曆法與數字字形，例如 `fa-IR`、`ar-SA-u-ca-islamic`），複數使用 i18n 函式庫處理。不得手寫格式或以英文規則拼接複數。

### Good Example

這個範例依語系格式化貨幣，複數交給 i18n 函式。

```js
new Intl.NumberFormat(locale, { style: 'currency', currency: 'TWD' }).format(total);
t('items', { count });
```

### Bad Example

這個範例手寫千分位與英文複數，德文使用者看到錯誤的千分位符號，其他語言的複數規則也全部錯誤。

```js
`$${total.toFixed(2).replace(/\B(?=(\d{3})+(?!\d))/g, ',')}`;
`${count} item${count !== 1 ? 's' : ''}`;
```

## Rule 6 -- 錯誤要說明並提供重試

**強度：MUST**

每個讀取資料的地方都必須處理網路失敗、逾時與 API 錯誤，說明發生什麼事並提供重試或下一步，不得只顯示「發生錯誤」。依狀態碼分別處理：400 顯示欄位驗證錯誤、401 導向登入、403 說明沒有權限、404 顯示找不到的狀態、429 說明操作太頻繁、500 顯示通用錯誤並提供客服管道。單一元件出錯時不得讓整個畫面無法使用。

### Good Example

這個範例依狀態碼給出不同處理，錯誤只影響這一個區塊。

```jsx
<ErrorBoundary fallback={<p>銷售圖表暫時無法顯示 <button onClick={retry}>重試</button></p>}>
  <SalesChart />
</ErrorBoundary>
{status === 403 && <p>你沒有查看此報表的權限，請聯絡管理員開通。</p>}
{status === 429 && <p>操作太頻繁，請稍候一分鐘再試。</p>}
```

### Bad Example

這個範例所有錯誤都只顯示同一句話並清空整頁，使用者不知道是沒權限、網路斷線還是系統問題，也沒有任何可以做的事。

```jsx
if (error) return <div>發生錯誤</div>;
```

## Rule 7 -- 驗證錯誤保留已輸入內容

**強度：MUST**

表單驗證錯誤要顯示在對應欄位旁，具體說明怎麼修正，並保留使用者已輸入的內容。不得在送出失敗後清空表單，也不得只依賴前端驗證，伺服器端的驗證錯誤同樣要對應回欄位。

### Good Example

這個範例在伺服器回傳錯誤時保留輸入，並把錯誤對應到欄位。

```jsx
const onSubmit = async (values) => {
  const res = await api.createAccount(values);
  if (res.status === 400) setFieldErrors(res.body.fields); // 值保留在表單中
};
<input aria-invalid={!!errors.email} aria-describedby="email-err" value={values.email} />
<p id="email-err">{errors.email}</p>
```

### Bad Example

這個範例在送出失敗後重置表單，使用者辛苦填完的十幾個欄位全部消失，只能從頭再填。

```js
catch (e) { form.reset(); alert('註冊失敗'); }
```

## Rule 8 -- 防止重複送出與殘留請求

**強度：MUST**

送出期間必須停用送出按鈕並顯示處理中，防止連點造成重複送出。元件卸載時要取消進行中的請求，並清除事件監聽、計時器與訂閱。

### Good Example

這個範例在送出期間停用按鈕，並在卸載時中止請求。

```jsx
<button disabled={submitting} aria-busy={submitting}>{submitting ? '付款處理中…' : '確認付款'}</button>

useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal }).then(setData);
  return () => ctrl.abort();
}, [url]);
```

### Bad Example

這個範例的付款按鈕在處理中仍可點擊，使用者以為沒反應多按幾次，就會被重複扣款。

```jsx
<button onClick={pay}>確認付款</button>
```

## Rule 9 -- 每份清單都有空狀態與載入狀態

**強度：SHOULD**

每份清單與資料區塊都要有空狀態（說明為什麼是空的並提供下一步）與載入狀態（說明正在載入什麼）。資料量可能很大時使用分頁或虛擬捲動，不得一次載入上萬筆。

### Good Example

這個範例分別處理載入、空資料與分頁。

```jsx
if (loading) return <Skeleton label="正在載入你的專案…" />;
if (projects.length === 0) return <EmptyState title="還沒有專案" action={<Button>建立第一個專案</Button>} />;
return <ProjectList items={projects} pageSize={50} />;
```

### Bad Example

這個範例沒有空狀態也一次抓取全部資料，沒有資料時畫面一片空白，資料多時頁面卡住數秒。

```jsx
const all = await fetch('/api/projects?limit=100000').then(r => r.json());
return <ul>{all.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
```

## Rule 10 -- 拖曳中斷時清除狀態

**強度：SHOULD**

自製的滑桿、拖曳區、可捲動控制列必須處理拖曳中斷：第二根手指落下時維持原本的指標；收到 `pointercancel`、`lostpointercapture`、在控制項外放開，或視窗 `blur` 時，清除拖曳狀態並釋放 pointer capture，讓下一次點擊或拖曳不需重新整理就能正常運作。

### Good Example

這個範例只追蹤第一個指標，並在各種中斷事件時結束拖曳。

```js
el.addEventListener('pointerdown', (e) => {
  if (activeId !== null) return;
  activeId = e.pointerId; el.setPointerCapture(e.pointerId);
});
const end = () => { activeId = null; el.classList.remove('dragging'); };
['pointerup', 'pointercancel', 'lostpointercapture'].forEach(t => el.addEventListener(t, end));
window.addEventListener('blur', end);
```

### Bad Example

這個範例只在 `pointerup` 結束拖曳，瀏覽器為了捲動取消手勢時狀態卡在拖曳中，之後的點擊都失效，只能重新整理頁面。

```js
el.addEventListener('pointerdown', () => { dragging = true; });
el.addEventListener('pointerup', () => { dragging = false; });
```
