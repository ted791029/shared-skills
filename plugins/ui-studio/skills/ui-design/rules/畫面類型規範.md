# 畫面類型規範

## Rule 1 -- 依這個畫面判斷類型

**強度：MUST**

畫面類型必須依「這次要做或要改的畫面」上的訪客要完成什麼來判斷，不得依產品整體的類別判斷。四種類型：說服型（訪客做決定並採取行動，例如首頁、行銷頁、活動頁、價格頁）、操作型（訪客完成一項工作，例如應用程式介面、儀表板、編輯器、後台、設定、工具）、閱讀型（訪客要理解某件事，例如文件、文章、教學、說明、更新紀錄）、體驗型（訪客沉浸在作品本身，例如作品集、藝廊、展示頁）。工具產品的行銷頁仍是說服型；時尚品牌的說明文件仍是閱讀型；文件的目錄首頁是閱讀型，不是說服型。

### Good Example

這個範例的產品是專案管理工具，但這次的畫面是對外的價格頁，因此依畫面判為說服型。

```text
這次要做的是 /pricing 價格頁，訪客在這裡比較方案並決定是否註冊，判為說服型。雖然產品本身是專案管理工具，但這個畫面的成功是「訪客按下開始試用」，不是「完成一項工作」。
```

### Bad Example

這個範例依產品類別把價格頁判為操作型，後續會套用後台的克制取捨，做出缺乏主張、看不出為什麼要買的價格頁。

```text
這是一個專案管理工具，屬於應用程式，所以 /pricing 頁面判為操作型，沿用後台的元件與密度。
```

## Rule 2 -- 說服型的取捨重點

**強度：MUST**

判為說服型時，取捨必須以「讓訪客看懂提供什麼、想要它、並採取行動」為優先：第一個畫面要說清楚提供的東西、露出一個明確的主要行動，並展示只有這個產品能證明的東西。主要行動必須是訪客來這裡真正要做的事的可用形式（例如航空公司的航線與日期搜尋、診所的可預約時段、商店的加入購物車），只放一個連到別處的裝飾連結不算。視覺表現要全力投入、有明確主張，不得退回「標題、副標、按鈕，下面一排等寬卡片」的通用樣板。

### Good Example

這個範例決定的取捨把可用的預約表單放在第一個畫面，並指出只有這家診所能證明的內容。

```text
畫面類型：說服型（診所官網首頁）。
取捨重點：第一個畫面直接放「選科別＋可預約時段」的預約表單，訪客不用往下捲就能掛號；主視覺用診所實際的看診環境照片，強調「週日也看診」這個鄰近診所沒有的事實。
```

### Bad Example

這個範例把主要行動做成一顆連到別頁的按鈕，並採用通用的卡片樣板，訪客在第一個畫面無法直接完成預約，頁面也看不出和其他診所有何不同。

```text
畫面類型：說服型（診所官網首頁）。
取捨重點：置中大標題「您的健康，我們守護」，下方一顆「立即預約」按鈕連到 /booking，再放三張等寬卡片介紹科別。
```

## Rule 3 -- 操作型的取捨重點

**強度：MUST**

判為操作型時，取捨必須以「好掃讀、前後一致、符合使用者已熟悉的慣例、貼合實際使用情境」優先於視覺表現。品牌只表現在字體、配色、密度與一個招牌細節上，不得改變版面組織、導覽方式或控制元件；按鈕、分頁、輸入框、下拉選單、篩選器、可排序的表格都必須使用平台的標準元件，不得為了風格重新發明標準操作（自製捲軸、怪異表單元件、非標準對話框）。

### Good Example

這個範例讓後台儀表板維持標準的導覽與元件，品牌只落在配色與一個招牌細節。

```text
畫面類型：操作型（倉儲後台的庫存儀表板）。
取捨重點：左側固定導覽列＋上方篩選列＋可排序表格，全部用標準元件；品牌色只用在側欄底色與「目前選取」狀態；招牌細節是把各倉庫的庫存水位畫成橫向貨架刻度。
```

### Bad Example

這個範例把操作型畫面做成「控制台」造型，用自製的功能鍵列取代導覽與按鈕，熟悉一般後台的使用者必須重新學習怎麼操作，掃讀速度也變慢。

```text
畫面類型：操作型（倉儲後台的庫存儀表板）。
取捨重點：整個畫面做成老式終端機，用底部 F1–F10 功能鍵列取代左側導覽，表格改成仿點陣印表紙的條紋文字區。
```

## Rule 4 -- 閱讀型的取捨重點

**強度：MUST**

判為閱讀型時，取捨必須以「讀者找得到答案、讀得懂、知道自己在哪裡與下一步去哪」為優先。品牌風格只能放在外框（頁首、導覽側欄、背景、標題與段落開頭、程式碼與表格的呈現方式），正文閱讀欄必須保持平靜：每行約 65–75ch、網頁正文約 16px、對比足夠、文字後方沒有裝飾。等寬字只用於程式碼、參數與小標籤，不得用於正文或標題；閱讀順序與導覽不得改成讀者需要重新學習的形式。

### Good Example

這個範例把風格放在外框，正文欄維持可讀寬度與字級。

```text
畫面類型：閱讀型（API 說明文件）。
取捨重點：左側章節樹＋右側本頁目錄＋上一頁／下一頁；品牌色用在頁首與側欄，章節編號用招牌的「里程碑」樣式；正文欄最大寬度 70ch、16px，程式碼區用等寬字。
```

### Bad Example

這個範例把風格延伸到正文欄，用等寬字排全文並在文字後方放紋理，讀者長時間閱讀會疲勞，也難以快速找到答案。

```text
畫面類型：閱讀型（API 說明文件）。
取捨重點：全文改用等寬字營造工程感，正文欄撐滿整個寬度，背景加上會緩慢移動的網格動畫。
```

## Rule 5 -- 體驗型的取捨重點

**強度：MUST**

判為體驗型時，取捨必須讓作品本身從第一個畫面就成為主角，介面（導覽、說明文字、按鈕）退到背景，只保留能操作所需的最少介面；不得讓介面元件或說明文字搶過作品的版面與注意力。

### Good Example

這個範例讓攝影作品集的第一個畫面由作品佔滿，導覽縮到角落。

```text
畫面類型：體驗型（攝影師作品集）。
取捨重點：第一個畫面是單張作品滿版呈現，左右鍵切換；導覽縮成右上角的小字選單，作品說明在捲動後才出現。
```

### Bad Example

這個範例讓自我介紹與服務卡片佔據第一個畫面，作品被擠到下方，訪客一進來看不到最能說服他的東西。

```text
畫面類型：體驗型（攝影師作品集）。
取捨重點：第一個畫面放大標題「用鏡頭說故事」和三張服務項目卡片，作品縮圖放在第二屏的格狀列表。
```

## Rule 6 -- 依白話描述判斷用法

**強度：MUST**

用法必須依使用者描述的目的判斷，不依使用者用了什麼術語：

| 用法 | 判斷依據 |
|------|----------|
| 做新畫面 | 要的畫面還不存在，或要整個換掉既有外觀（重新設計、換新風格） |
| 收尾 | 既有畫面大致完成，要在上線前把細節、間距、狀態修到位，不換外觀 |
| 技術檢查 | 只要知道有沒有無障礙、效能、響應式等問題，沒有要求改善 |
| 單項改善 | 只針對一個面向：版面、字體、配色、文案、響應式、效能、錯誤與空狀態、首次使用流程、動態 |

做新畫面產出原型；收尾與單項改善產出修改規格與需要的局部示意；技術檢查只產出檢查報告。任何用法都不修改專案程式碼。單項改善中，「加動態、讓互動有回饋」依動態規範，「要大膽、令人驚豔的效果」依突破規範，「加入個性與小驚喜」依驚喜規範。

### Good Example

這個範例依「上線前」與「怪怪的」這類白話描述判為收尾，並說明依據與產出。

```text
使用者說：「這個設定頁差不多了，下週要上線，可是看起來怪怪的，幫我弄好一點。」
判斷：用法為收尾。畫面已存在且要保留現有樣子，目的是上線前把細節修到位，沒有要換外觀，也沒有指定單一面向。產出修改規格，由實作流程修改程式碼。
```

### Bad Example

這個範例只因使用者提到「檢查」就判為技術檢查，結果只交出問題清單，沒有提出改成什麼，與使用者「弄好一點」的目的不符。

```text
使用者說：「幫我檢查一下這個設定頁，下週要上線，看起來怪怪的，幫我弄好一點。」
判斷：使用者說了「檢查」，用法為技術檢查，只產出問題清單，不提出修改規格。
```

## Rule 7 -- 換外觀時判為做新畫面

**強度：MUST**

收尾與單項改善必須保留既有的風格、行為、文案與範圍外的一切。使用者要求換掉現在的樣子（「整個改掉」「換一個風格」「不要再像現在這樣」）時，必須判為做新畫面，把舊外觀當成要避開的參考；不得判為收尾，在準備被取代的舊外觀上做細修。

### Good Example

這個範例在使用者表明不喜歡現有外觀時判為做新畫面。

```text
使用者說：「這個首頁太老氣了，我想整個換掉，但內容和功能不要動。」
判斷：用法為做新畫面（重新設計）。保留內容、功能與限制，舊外觀只當作「不要再像這樣」的參考。
```

### Bad Example

這個範例把換外觀的要求判為收尾，只調整舊外觀的間距與顏色，交出的仍是使用者已經說要換掉的樣子。

```text
使用者說：「這個首頁太老氣了，我想整個換掉，但內容和功能不要動。」
判斷：用法為收尾，保留現有版面，把字級調大一點、按鈕改成圓角、間距加寬。
```

## Rule 8 -- 缺 DESIGN.md 不代表全新

**強度：SHOULD**

判斷是否為做新畫面時，應以既有程式碼中的畫面與樣式為依據；專案沒有 DESIGN.md 本身不得作為判為做新畫面或換掉既有外觀的理由。既有畫面已有一致的配色、字體與元件時，應視為已有既定風格。

### Good Example

這個範例雖然沒有 DESIGN.md，仍依程式碼中既有的一致樣式判為單項改善。

```text
專案沒有 DESIGN.md，但 src/styles/tokens.css 已定義品牌色與字級，各頁元件一致。使用者只要求「錯誤訊息寫清楚一點」，判為單項改善（文案），沿用既有風格。
```

### Bad Example

這個範例只因沒有 DESIGN.md 就判為做新畫面，重新決定整套視覺，破壞使用者只想小修的既有畫面。

```text
專案沒有 DESIGN.md，視為全新專案，用法判為做新畫面，先決定新的配色與字體再改寫錯誤訊息。
```

## Rule 9 -- 用法不明時詢問

**強度：MUST**

兩種以上用法都說得通，或使用者沒有說要做什麼時，必須以白話列出可能的用法與各自會產生的結果，詢問使用者一次後停下等待；不得自行挑一種開始執行。

### Good Example

這個範例在「收尾」與「單項改善（配色）」都說得通時，用白話說明差別並詢問。

```text
你說「顏色看起來不太對，順便整理一下」，我想確認你要的範圍：
1. 只調整顏色，其他地方不動。
2. 顏色之外，連間距、按鈕狀態等細節一起整理到可以上線的程度。（推薦，你提到「順便整理」）
請回覆 1 或 2。
```

### Bad Example

這個範例在範圍不明時直接選了收尾並開始修改，可能動到使用者不想改的地方。

```text
我會把顏色和整個頁面的間距、字級、按鈕一起調整，現在開始修改。
```
