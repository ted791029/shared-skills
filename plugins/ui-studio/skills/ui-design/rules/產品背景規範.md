# 產品背景規範

## Rule 1 -- 只記錄產品事實

**強度：MUST**

PRODUCT.md 只能記錄長期有效、產品層級的事實：給誰用（使用者、所處情境）、他們要完成的主要工作、用途（產品做什麼、為什麼存在、怎樣算成功）、產品沒有的功能（刻意不做或還做不到、會改變整個產品能力邊界的事）、品牌個性（已確認的名稱、語氣、想給人的感覺、既有素材）、設計禁區與限制（平台、技術、法規、無障礙需求、必須保留的東西）。主要工作與沒有的功能都寫族群或整個產品的層級，不寫單一畫面的操作步驟、欄位或按鈕。這次任務的進度、討論過程與待辦事項不得寫入。

### Good Example

這個範例只記錄族群層級的主要工作與整個產品的能力邊界，都是長期有效的事實。

```markdown
使用者要完成的任務：門市藥師在櫃台尖峰時段一邊接待客人，一邊在 30 秒內查到庫存與處方紀錄。
產品沒有的功能：不提供線上下單與配送，客人只能到門市取藥。
```

### Bad Example

這個範例把這次對話的進度與單一畫面的操作寫進 PRODUCT.md，下次讀取時會把過期的任務進度誤當成產品事實，畫面細節也會讓每次改版都得改產品背景。

```markdown
今天和使用者討論過首頁，使用者說先做庫存頁，下週再處理處方頁。
使用者要完成的任務：在庫存頁點「篩選」→ 選分類 → 按「套用」。
產品沒有的功能：庫存頁還沒有匯出按鈕。
```

## Rule 2 -- 不含視覺決定

**強度：MUST**

PRODUCT.md 不得包含視覺決定：配色、色碼、字體、字級、元件樣式、版面、頁面概念、畫面類型、頁面的敘事順序；這些屬於 DESIGN.md 或這次畫面的設計。品牌個性只能寫成產品要給人的感覺，不得轉譯成具體的視覺做法。使用者親口說出的指定色、標誌與設計禁區是使用者給的限制，不是 Claude 的視覺決定，依本規範 Rule 3 記錄。

### Good Example

這個範例把品牌個性寫成想給人的感覺，沒有決定任何視覺做法。

```markdown
品牌個性：可靠、冷靜、不催促。使用者多半是在身體不適時使用，語氣要讓人安心，不用誇張的促銷說法。
```

### Bad Example

這個範例在 PRODUCT.md 決定了色碼、字體與版面，與 DESIGN.md 形成兩份互相競爭的視覺依據，之後改 DESIGN.md 時兩邊會不一致。

```markdown
品牌個性：可靠、冷靜。主色使用 #1E40AF，標題用 Noto Serif TC，首頁採左文右圖的版面，按鈕一律 8px 圓角。
```

## Rule 3 -- 使用者給的視覺限制照記不擴充

**強度：SHOULD**

使用者主動說出必須遵守的視覺限制（例如公司指定色、必須使用的標誌），或說出不想要的樣子（設計禁區）時，應照原話記錄；不得自行延伸成整套配色、字體或其他視覺決定，也不得把設計禁區改寫成 Claude 推測的具體禁令。

### Good Example

這個範例照原話記錄指定色、標誌與設計禁區，沒有延伸。

```markdown
## 必須保留的品牌元素
- 使用者表示公司標準色為 #E60012，對外頁面必須使用；Logo 檔案在 public/brand/logo.svg，不得變形或改色。

## 設計禁區
- 使用者說：「不要像農藥或肥料廣告那樣綠油油、很商業。」
```

### Bad Example

這個範例把一個指定色擴充成整套配色，又把設計禁區改寫成「禁用綠色」，把 Claude 自己的判斷寫成使用者確認過的限制，之後無法分辨哪些真的不能改，也會誤排除使用者沒反對的顏色。

```markdown
## 必須保留的品牌元素
- 主色 #E60012，輔助色 #FFB3B8 與 #7A0009，背景 #FFF5F5，搭配 Noto Sans TC 粗體標題。

## 設計禁區
- 全站禁用綠色與照片。
```

## Rule 4 -- 不得臆造事實

**強度：MUST**

PRODUCT.md 只能寫使用者確認過或專案中有實際證據的事實。不得自行編造客戶評價、客戶名單、使用人數、效能或成效數據、價格、授權條款、獲獎或媒體報導、部署環境等內容；專案中沒有這類素材時，必須寫明「目前沒有」，讓之後的工作不會捏造。

### Good Example

這個範例只寫專案中真的有的素材，並明確寫出沒有的東西。

```markdown
現有素材：docs/case-study-ntu.pdf 一份導入案例。
目前沒有客戶評價、使用人數統計與媒體報導，頁面上不得自行撰寫。
```

### Bad Example

這個範例編造了使用人數與客戶評價，這些內容之後會被寫進對外頁面，變成產品對外的不實宣稱。

```markdown
現有素材：已有超過 500 家企業使用，客戶評價「導入後效率提升 40%」——某科技公司資訊長。
```

## Rule 5 -- 不知道的標示待確認

**強度：MUST**

使用者沒有回答、專案中也找不到依據的產品事實，必須明確標示「待確認」並寫出缺的是什麼；不得用通用的推測句填補，也不得因此略過不寫而讓人誤以為已確認。

### Good Example

這個範例把未知的事實標為待確認，並寫出具體缺口。

```markdown
主要使用者：國中數學老師（已確認）。
是否也給學生直接使用：待確認，使用者尚未回答學生是否會登入系統。
```

### Bad Example

這個範例用通用說法補上不知道的事，讀者無法分辨這是確認過的事實還是猜測，之後可能為不存在的學生族群做設計。

```markdown
主要使用者：老師與學生，適合各年齡層使用，操作直覺簡單。
```

## Rule 6 -- 推測的事實標示來源

**強度：MUST**

從程式碼、文案或設定推得、但使用者沒有確認的事實，必須標示為推測並寫出依據；只有使用者確認過的內容可以不加標示。

### Good Example

這個範例標出推測與其依據。

```markdown
平台：web（推測，依據 package.json 使用 Vite + React，專案中沒有原生 App 程式碼；尚未經使用者確認）。
```

### Bad Example

這個範例把推測寫成確定事實，若推測錯誤，後續設計會以錯誤的平台為前提且無從察覺。

```markdown
平台：web。
```

## Rule 7 -- 不用通用套話填充

**強度：SHOULD**

每一句都應寫出這個產品特有、能影響之後設計決定的事實；套用在任何產品都成立的通用句（例如「以使用者為中心」「簡潔易用」「提供最佳體驗」）不得寫入。沒有可寫的內容時應省略該部分，而不是用通用句填滿。

### Good Example

這個範例寫出只屬於這個產品、會影響設計的事實。

```markdown
產品原則：查詢結果要能在櫃台螢幕上一眼看出「有貨／調貨中／缺貨」，藥師不需要點進細節頁才能回答客人。
```

### Bad Example

這個範例全是任何產品都適用的套話，對之後的設計決定沒有任何約束力。

```markdown
產品原則：以使用者為中心，提供簡潔、直覺、高效的最佳體驗。
```

## Rule 8 -- 以中文撰寫

**強度：MUST**

PRODUCT.md 的內容必須以中文撰寫；產品名稱、技術名稱、檔案路徑與專有名詞（例如 WCAG、React）保留原文。

### Good Example

這個範例以中文撰寫，只有專有名詞保留原文。

```markdown
無障礙需求：對外頁面須符合 WCAG 2.2 AA，因為客戶包含政府機關的採購單位。
```

### Bad Example

這個範例整段以英文撰寫，門外漢使用者無法閱讀與確認自己的產品背景是否寫對。

```markdown
Accessibility: Public pages must meet WCAG 2.2 AA because customers include government procurement units.
```
