# 響應式規範

## Rule 1 -- 只調整跨裝置的版面與互動

**強度：MUST**

響應式改善只能調整畫面在不同螢幕尺寸、方向與輸入方式下的版面結構、尺寸與互動方式，不得改變配色、字體風格、文案或功能。各裝置必須維持相同的資訊架構（相同的頁面、分類與名稱），不得為手機另做一套不同的導覽分類。

### Good Example

這個範例只改變導覽在手機上的呈現位置，項目與名稱和桌機相同。

```css
.nav { display: flex; gap: 2rem; }
@media (max-width: 767px) {
  .nav { position: fixed; inset: auto 0 0 0; justify-content: space-around; }
}
```

### Bad Example

這個範例在手機版把「訂單」「發票」合併成另一個名為「帳務」的分類，使用者在手機和電腦之間切換時找不到同樣的功能。

```jsx
{isMobile ? <NavItem>帳務</NavItem> : <><NavItem>訂單</NavItem><NavItem>發票</NavItem></>}
```

## Rule 2 -- 缺少目標裝置時白話詢問

**強度：MUST**

PRODUCT.md 或需求中沒有說明使用者主要用什麼裝置、在什麼情境下使用（例如外出單手操作、在辦公桌前專心處理、需要列印）時，Claude 必須以白話詢問使用者，不得自行假設。斷點、版面重組方式等設計判斷由 Claude 自行決定。

### Good Example

這個範例用白話詢問使用情境，沒有要使用者決定斷點。

```text
想先確認：使用這個畫面的人，大多是用手機在外面快速查看，還是用電腦坐著處理？需要列印出來嗎？
```

### Bad Example

這個範例把斷點這種設計判斷丟給使用者，門外漢無法回答。

```text
請問 breakpoint 要設在 640px 還是 768px？要用 container query 嗎？
```

## Rule 3 -- 由小螢幕往上寫樣式

**強度：SHOULD**

基礎樣式寫給手機，再用 `min-width` 媒體查詢往大螢幕疊加。預設避免以桌機為基礎再用 `max-width` 往下覆寫，除非既有程式碼已全面採用該寫法且改動範圍不允許重寫。

### Good Example

這個範例以單欄為基礎，在較寬的螢幕才加上多欄。

```css
.grid { display: grid; gap: 1rem; }
@media (min-width: 768px) { .grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 1024px) { .grid { grid-template-columns: repeat(3, 1fr); } }
```

### Bad Example

這個範例以三欄為基礎再往下覆寫，手機要先載入並推翻桌機樣式，規則越寫越多也越難維護。

```css
.grid { display: grid; grid-template-columns: repeat(3, 1fr); }
@media (max-width: 1023px) { .grid { grid-template-columns: repeat(2, 1fr); } }
@media (max-width: 767px) { .grid { grid-template-columns: 1fr; } }
```

## Rule 4 -- 斷點依內容破版處決定

**強度：SHOULD**

斷點放在內容開始破版的寬度，通常三個斷點就足夠（參考值 640px、768px、1024px；手機約 320–767px、平板 768–1023px、桌機 1024px 以上）。元件寬度隨容器變化時優先使用 container query，字級與間距用 `clamp()` 做流動縮放，減少斷點數量。不得照抄裝置型號尺寸設一大串斷點。

### Good Example

這個範例讓卡片依容器寬度切換排列，標題用 `clamp()` 流動縮放。

```css
.card-list { container-type: inline-size; }
@container (min-width: 36rem) { .card { display: grid; grid-template-columns: 8rem 1fr; } }
h1 { font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem); }
```

### Bad Example

這個範例依各家手機型號設斷點，新機型一出就不對，而且多數斷點和內容是否破版無關。

```css
@media (max-width: 375px) { … }
@media (max-width: 390px) { … }
@media (max-width: 414px) { … }
@media (max-width: 428px) { … }
```

## Rule 5 -- 觸控目標至少 44×44px

**強度：MUST**

觸控裝置上每個可點擊的元素至少 44×44px，相鄰目標之間要留間距，平板也維持 44×44px 但可以比手機排得密一些。手機上的內文字級不得小於 16px。

### Good Example

這個範例在粗指標裝置上把按鈕撐到至少 44px 並拉開間距。

```css
@media (pointer: coarse) {
  .toolbar button { min-width: 44px; min-height: 44px; }
  .toolbar { gap: 8px; }
}
body { font-size: 1rem; } /* 16px */
```

### Bad Example

這個範例的圖示按鈕只有 24px 且緊貼在一起，手指很容易按錯相鄰的按鈕。

```css
.toolbar button { width: 24px; height: 24px; padding: 0; }
.toolbar { gap: 0; }
```

## Rule 6 -- 依輸入方式而非螢幕大小判斷

**強度：MUST**

觸控與滑鼠的差異必須用 `pointer` 與 `hover` 媒體查詢判斷，不得用螢幕寬度或 User-Agent 推測裝置。任何功能都不得只能靠 hover 觸發，hover 效果要放在 `@media (hover: hover)` 內，觸控裝置要有點擊或常駐的替代方式。

### Good Example

這個範例的操作按鈕在觸控裝置上常駐顯示，只在可懸停的裝置才改為 hover 顯示。

```css
.row-actions { opacity: 1; }
@media (hover: hover) {
  .row-actions { opacity: 0; }
  .row:hover .row-actions, .row:focus-within .row-actions { opacity: 1; }
}
```

### Bad Example

這個範例的編輯與刪除按鈕只在 hover 時出現，手機和平板使用者永遠看不到，等於無法編輯資料。

```css
.row-actions { display: none; }
.row:hover .row-actions { display: flex; }
```

## Rule 7 -- 避開瀏海與系統列

**強度：MUST**

貼齊螢幕邊緣的元素（固定的頂部列、底部導覽、全螢幕區塊）必須以 `env(safe-area-inset-*)` 留出安全區域，並搭配不為 0 的最小值；viewport meta 必須加上 `viewport-fit=cover`。

### Good Example

這個範例讓底部導覽避開首頁指示條，並保留至少 1rem 的內距。

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
<style>
  .bottom-nav { padding-bottom: max(1rem, env(safe-area-inset-bottom)); }
</style>
```

### Bad Example

這個範例的底部導覽沒有處理安全區域，在有首頁指示條的手機上，按鈕會被指示條蓋住而點不到。

```css
.bottom-nav { position: fixed; bottom: 0; padding-bottom: 0; }
```

## Rule 8 -- 依裝置重組版面而非縮放

**強度：SHOULD**

不同裝置要重新安排版面，而不是等比縮放：手機改為單欄垂直堆疊、元件全寬、主要操作放在拇指容易碰到的下方，次要內容收進摺疊區或分頁；平板使用雙欄或「清單加詳情」；桌機善用寬度並以 `max-width` 限制，不得在 4K 螢幕上無限拉寬。多欄表格在手機上改為卡片。必須處理手機與平板的橫向畫面。

### Good Example

這個範例在手機上把表格列轉成卡片，以 `data-label` 保留欄位名稱，桌機內容限制最大寬度。

```css
.page { max-width: 1280px; margin-inline: auto; }
@media (max-width: 767px) {
  table, tr, td { display: block; }
  thead { display: none; }
  td::before { content: attr(data-label); font-weight: 600; display: block; }
}
```

### Bad Example

這個範例只把整個表格縮小塞進手機寬度，文字小到看不清，使用者必須放大並左右拖曳才能閱讀。

```css
@media (max-width: 767px) { table { transform: scale(0.5); transform-origin: top left; } }
```

## Rule 9 -- 小螢幕不得隱藏核心功能

**強度：MUST**

重要的功能在手機上必須能用，可以改變呈現方式（收進選單、抽屜、底部面板），但不得直接用 `display: none` 拿掉。

### Good Example

這個範例把篩選條件在手機上收進可展開的區塊，功能仍然存在。

```html
<details class="filters-mobile">
  <summary>篩選條件</summary>
  <div class="filter-panel">…</div>
</details>
```

### Bad Example

這個範例在手機上直接隱藏篩選面板，手機使用者完全無法篩選訂單，只能改用電腦。

```css
@media (max-width: 767px) { .filter-panel { display: none; } }
```

## Rule 10 -- 圖片依顯示寬度提供尺寸

**強度：SHOULD**

內容圖片要用 `srcset` 搭配寬度描述（`w`）與 `sizes`，讓瀏覽器挑選適合的檔案；不同裝置需要不同構圖時用 `<picture>`。不得只用 `display: none` 隱藏桌機大圖，因為被隱藏的圖片仍會下載。

### Good Example

這個範例提供多種寬度並告訴瀏覽器實際顯示寬度。

```html
<img src="hero-800.jpg"
     srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1200.jpg 1200w"
     sizes="(max-width: 768px) 100vw, 50vw"
     alt="倉庫人員正在掃描包裹">
```

### Bad Example

這個範例在手機上用 `display: none` 隱藏 2400px 大圖再另放小圖，手機仍會下載兩張圖，浪費流量並拖慢載入。

```html
<img class="desktop-only" src="hero-2400.jpg" alt="">
<img class="mobile-only" src="hero-600.jpg" alt="">
```

## Rule 11 -- 原生 App 依尺寸級別切換結構

**強度：MUST**

原生 App 必須依 size class（iOS）或 window size class（Android）切換版面結構，不得用裝置型號判斷。在平板上要重組（側邊欄、清單加詳情、多欄），不得直接放大手機版面；分割畫面與多視窗下的窄視窗也要正常運作。不得為了閃避版面錯誤而鎖定螢幕方向。

### Good Example

這個範例依 window size class 在寬螢幕改用清單加詳情。

```kotlin
when (windowSizeClass.windowWidthSizeClass) {
    WindowWidthSizeClass.EXPANDED -> ListDetailPane(list, detail)
    else -> ListScreen(onSelect = { navController.navigate("detail/$it") })
}
```

### Bad Example

這個範例用裝置型號判斷並鎖定直向，在平板分割畫面或折疊手機上版面錯亂，橫向使用者也被迫轉手機。

```swift
if UIDevice.current.model == "iPad" { layout = .wide }
AppDelegate.orientationLock = .portrait
```
