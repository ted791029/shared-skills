# 技術檢查規範

## Rule 1 -- 技術檢查不修改程式碼

**強度：MUST**

用法為「技術檢查」時只能讀程式碼、實測並記錄問題，不得修改任何程式碼、樣式或設定檔，也不得在專案內產生 PRODUCT.md、DESIGN.md、tokens、原型或截圖等任何檔案，即使問題很小、修法很明確也一樣。

### Good Example

這個範例發現問題後只記錄位置與修法，交由後續的收尾或單項改善處理。

```text
[P1] 刪除按鈕沒有可讀名稱
位置：src/components/FileRow.tsx 第 42 行
修法：在 <button> 加上 aria-label="刪除檔案"
（技術檢查只記錄，未修改程式碼）
```

### Bad Example

這個範例在技術檢查中直接改了程式碼，使用者只要求看問題，卻拿到未經同意的變更，報告中的問題也和實際程式碼對不上。

```text
已發現刪除按鈕沒有可讀名稱，已直接在 FileRow.tsx 加上 aria-label。
```

## Rule 2 -- 無障礙的檢查項目

**強度：MUST**

無障礙面向必須逐項檢查下列內容：

| 項目 | 從程式碼判斷的方式 |
|------|------------------|
| 對比 | 實測時採用畫面擷取的渲染後對比，圖示、元件邊框、疊在圖片上的文字與未實測時採用對比檢查腳本的結果；一般文字低於 4.5:1、大字低於 3:1 即為問題（AAA 為 7:1） |
| 減少動態 | 有動畫卻沒有 `prefers-reduced-motion` 替代；或用全域 `0.01ms` 一律關掉，連必要的狀態回饋也消失；閃爍超過門檻；動畫擋住 focus、閱讀或操作 |
| ARIA | 互動元件缺少 role、可讀名稱或狀態（如 `aria-expanded`、`aria-pressed`） |
| 鍵盤操作 | `outline: none` 且沒有替代 focus 樣式、`tabindex` 造成順序混亂、焦點被困在元件中出不來 |
| 語意 HTML | 標題層級跳號、缺少 `<main>`／`<nav>` 等地標、用 `<div onClick>` 代替 `<button>` |
| 替代文字 | `<img>` 缺少 `alt` 或 `alt` 內容無意義 |
| 表單 | 輸入欄位沒有 `<label>`、錯誤訊息不清楚、必填欄位沒有標示 |

### Good Example

這個範例對一段程式碼逐項比對表格，找出語意、鍵盤與替代文字三個問題。

```jsx
// 檢查對象
<div className="card" onClick={open}>
  <img src={cover} />
</div>
// 發現：
// 語意 HTML：可點擊的 <div> 應為 <button> 或 <a>
// 鍵盤操作：<div> 無法以 Tab 聚焦、無法用 Enter 觸發
// 替代文字：<img> 缺少 alt
```

### Bad Example

這個範例只檢查對比就判定無障礙沒問題，漏掉不能用鍵盤操作的卡片，鍵盤與螢幕閱讀器使用者根本打不開內容。

```text
無障礙：對比全部通過，沒有問題。
```

## Rule 3 -- 效能的檢查項目

**強度：MUST**

效能面向必須逐項檢查下列內容：

| 項目 | 從程式碼判斷的方式 |
|------|------------------|
| 版面抖動 | 迴圈中交錯讀取（`offsetHeight`、`getBoundingClientRect()`）與寫入版面屬性 |
| 昂貴動畫 | 隨意對 `width`、`height`、`top`、`left` 等版面屬性做動畫；沒有範圍限制的 blur、filter、陰影效果 |
| 缺少最佳化 | 首屏以外的圖片沒有 `loading="lazy"`、圖片未壓縮或尺寸遠大於顯示尺寸 |
| `will-change` 濫用 | 大範圍套用或在靜止時常駐；它只該用在已知昂貴的特定動畫 |
| 打包大小 | 不必要的 import、未使用的套件 |
| 重新渲染 | 不必要的重新渲染、缺少 memo 導致大型清單每次都重算 |

### Good Example

這個範例指出對 `height` 做動畫與常駐的 `will-change`，並說明影響。

```css
/* 檢查對象 */
.accordion-panel { transition: height 300ms; will-change: transform, opacity, height; }
/* 發現：
   昂貴動畫：對 height 做動畫，每一格都要重新計算版面，低階手機會卡頓
   will-change 濫用：靜止時也常駐，佔用額外記憶體 */
```

### Bad Example

這個範例把「沒有加 `will-change`」列為效能問題，把一個只該針對特定動畫的提示當成必備，會誤導開發者到處加上它反而拖慢頁面。

```text
[P2] .button 沒有設定 will-change: transform，建議所有互動元件都加上。
```

## Rule 4 -- 主題的檢查項目

**強度：MUST**

主題面向必須檢查：顏色是否寫死而沒有使用設計 token、暗色模式是否缺少對應值或暗色下對比不足、是否用錯 token 或混用不同類型的 token（例如把文字色 token 當背景用）、切換主題時是否有數值沒有跟著更新（例如寫在 inline style 或 JS 中的顏色）。

### Good Example

這個範例找出寫死的顏色與切換主題時不會更新的 inline style。

```jsx
// 檢查對象
<p style={{ color: '#1f2937' }}>本月營收</p>
<span className="badge" />  /* .badge { background: var(--text-primary); } */
// 發現：
// 寫死顏色：#1f2937 沒有使用 token，切到暗色模式時文字會幾乎看不見
// token 用錯：.badge 把文字色 token 當背景色
```

### Bad Example

這個範例只確認 `:root` 有定義 token 就判定主題沒問題，沒有檢查元件是否真的使用，暗色模式下寫死的深色文字仍然消失在背景裡。

```text
主題：已定義 --surface、--text 等 token，暗色模式完整。
```

## Rule 5 -- 響應式的檢查項目

**強度：MUST**

響應式面向必須逐項檢查下列內容：

| 項目 | 從程式碼判斷的方式 |
|------|------------------|
| 固定寬度 | 寫死的 `width: 960px` 等數值會在手機上撐破版面 |
| 觸控目標 | 互動元素建議至少 44×44px；低於 24×24 CSS px 即違反 WCAG 2.5.8，除非符合例外（間距足夠、有同功能的替代控制項、行內文字連結、瀏覽器預設樣式、尺寸本身必要）。間距例外的判定：以目標中心畫直徑 24px 的圓，不與其他目標或其他過小目標的圓重疊 |
| 觸控手勢 | 自訂滑桿、拖曳區、可橫捲的控制列只綁滑鼠事件；pointer 拖曳區沒有設定 `touch-action`；取消、失去 capture 或 blur 時沒有清除拖曳狀態 |
| 水平捲動 | 窄螢幕下內容溢出造成整頁可左右捲動 |
| 文字放大 | 文字放大後版面破掉（例如固定高度的容器） |
| 斷點 | 完全沒有手機或平板的斷點樣式 |

只憑程式碼無法確認的項目（例如觸控手勢的實際手感），必須註明「僅從程式碼判斷，未實際操作驗證」。

### Good Example

這個範例從程式碼找出只綁滑鼠事件的拖曳元件，並註明判斷依據的範圍。

```jsx
// 檢查對象
<div className="slider" onMouseDown={start} onMouseMove={move} onMouseUp={end} />
// 發現：觸控手勢只綁滑鼠事件，手機上無法拖曳；沒有 touch-action，拖曳時會帶動整頁捲動。
// 備註：僅從程式碼判斷，未實際操作驗證。
```

### Bad Example

這個範例看到斷點樣式存在就判定響應式通過，漏掉 20×20px 且彼此緊貼的圖示按鈕，手機使用者會一直按錯。

```text
響應式：已有 640px 與 1024px 斷點，通過。
```

## Rule 6 -- RTL 屬性只在宣告方向時檢查

**強度：MUST**

只有 `<html>` 或 `<body>` 宣告 `dir="rtl"` 的頁面，才檢查實體方向屬性（`margin-left/right`、`padding-left/right`、`text-align: left/right`、`float: left/right`、`border-left/right`、`left:`／`right:` 定位）是否該改用邏輯屬性，以及箭頭圖示方向是否相反；這些是需要確認的訊號，不是必然的缺陷。`[dir="rtl"]` 覆寫規則若沒有同時清除相反方向的基底值，兩邊都會生效，要列為問題。`left: 50%; transform: translateX(-50%)` 的置中寫法在兩種方向都正確，不得要求改成 `inset-inline-start`。只有 `lang` 是 RTL 語言（如 `ar`、`he`、`fa`）而沒有 `dir` 時，只需註記，不列為缺陷。

### Good Example

這個範例在宣告 `dir="rtl"` 的頁面中，指出覆寫規則沒有清除基底的左邊距，同時保留正確的置中寫法。

```css
/* <html lang="ar" dir="rtl"> */
.item { margin-left: 1rem; }
[dir="rtl"] .item { margin-right: 1rem; }   /* 問題：margin-left 沒清成 0，兩邊都有邊距 */
.toast { left: 50%; transform: translateX(-50%); }  /* 正確：置中寫法不受方向影響 */
```

### Bad Example

這個範例在沒有宣告 RTL 的中文頁面上，把所有 `margin-left` 列為缺陷，還要求改掉置中寫法，報告塞滿誤報，照改反而讓置中錯位。

```text
[P2] 共 48 處使用 margin-left，應改為 margin-inline-start。
[P2] .toast 使用 left: 50%，應改為 inset-inline-start: 50%。
（頁面為 <html lang="zh-Hant">，沒有 dir="rtl"）
```

## Rule 7 -- 實作完整性的檢查項目

**強度：MUST**

實作完整性面向必須讀程式碼找出：重複出現的實作捷徑（同一段樣式或元件到處複製）、偏離設計系統的寫法、誤導或純裝飾的內容（假數據、不能點的按鈕、佔位文字）、以及換成不相關的產品也能原封不動使用的結構。能從程式碼直接確認的事實（例如「12 個檔案寫死同一個顏色」）與主觀判斷（例如「版面像通用模板」）必須分開寫。

### Good Example

這個範例把可直接確認的事實與主觀判斷分開列出。

```text
可確認的事實：
- 相同的卡片樣式在 Home.tsx、Pricing.tsx、About.tsx 各複製一份，沒有共用元件
- Dashboard.tsx 的「本月成長 +128%」是寫死的假數字
主觀判斷：
- 首頁的三欄圖示卡片結構換成任何 SaaS 產品都能原封不動使用
```

### Bad Example

這個範例把主觀印象寫成確定的事實，又沒有指出位置，開發者無法判斷哪些是真的錯誤、該從哪裡改起。

```text
實作完整性：整體很像 AI 模板，到處都是重複程式碼。
```

## Rule 8 -- 嚴重度依影響判定

**強度：MUST**

每個問題都必須標註嚴重度，依對使用者的影響判定：

| 等級 | 判定標準 |
|------|---------|
| P0 阻斷 | 使用者無法完成任務 |
| P1 重大 | 造成明顯困難，或違反 WCAG AA |
| P2 次要 | 造成困擾，但有替代方式 |
| P3 細修 | 不影響實際使用，有空再修 |

拿不準時問自己：「使用者會不會因為這個問題去聯絡客服？」會的話至少是 P1。不得把所有問題都標成 P0，P3 只保留少數，避免次要問題淹沒真正重要的問題。

### Good Example

這個範例依影響分級：無法用鍵盤送出是 P0，對比不足違反 WCAG AA 是 P1，捲軸未主題化是 P3。

```text
[P0] 結帳按鈕是 <div onClick>，鍵盤使用者無法完成付款
[P1] 表單說明文字對比 3.2:1，低於 4.5:1
[P3] 自訂捲軸顏色未跟隨暗色主題
```

### Bad Example

這個範例把捲軸顏色和無法付款都標成 P0，開發者分不出哪個要先修，真正阻斷付款的問題被埋沒。

```text
[P0] 結帳按鈕無法用鍵盤操作
[P0] 自訂捲軸顏色未跟隨暗色主題
[P0] 頁尾連結底線位置太近
```

## Rule 9 -- 各面向依標準評 0～4 分

**強度：MUST**

五個面向各自依下表評 0～4 分，分數必須對得上該面向的問題清單：

| 面向 | 0 | 1 | 2 | 3 | 4 |
|------|---|---|---|---|---|
| 無障礙 | 無法使用（未達 WCAG A） | 重大缺口（幾乎沒有 ARIA、無法鍵盤操作） | 部分（有做但缺口明顯） | 良好（大致符合 WCAG AA，小缺口） | 優秀（完全符合 WCAG AA，接近 AAA） |
| 效能 | 嚴重（版面抖動、完全沒最佳化） | 重大（沒有延遲載入、昂貴動畫） | 部分（有最佳化但仍有缺口） | 良好（大致最佳化，可小幅改進） | 優秀（快速、精簡） |
| 主題 | 沒有主題（全部寫死） | 極少 token（大多寫死） | 部分（有 token 但使用不一致） | 良好（使用 token，少數寫死） | 優秀（完整 token 系統，暗色模式完全正常） |
| 響應式 | 只支援桌機（手機破版） | 重大問題（有斷點但多處失敗） | 部分（手機可用但有粗糙處） | 良好（響應式，少數觸控目標或溢出問題） | 優秀（流暢、各寬度正常、觸控目標與手勢正確） |
| 實作完整性 | 系統性偏離 | 重大且重複的失誤 | 數個已確認的問題 | 少數零星問題 | 一致且有意圖 |

宣告 `dir="rtl"` 的頁面若 RTL 呈現普遍錯誤，響應式分數再減 1。總分滿分 20，18–20 優秀、14–17 良好、10–13 尚可、6–9 差、0–5 危急。

### Good Example

這個範例的分數對得上問題清單：無障礙有一個 P1 對比問題、其餘符合 AA，給 3 分。

```text
無障礙：3 分
理由：鍵盤操作、語意標籤、表單標籤都正確；說明文字對比 3.2:1（P1）一處。
```

### Bad Example

這個範例在無障礙面向列出 P0 的鍵盤阻斷問題，卻給 4 分，分數和問題清單矛盾，使用者會誤以為畫面已經可以上線。

```text
無障礙：4 分
問題：[P0] 結帳按鈕無法用鍵盤操作
```

## Rule 10 -- 只列出經程式碼或實測確認的問題

**強度：MUST**

每個問題都必須指出具體位置才能列入：程式碼的檔案、元件與行號，或實測的截圖檔、寬度、狀態與選擇器；能從實測對回原始碼時兩者都寫。不得憑經驗猜測「可能有」的問題。疑似問題但無法從程式碼或實測確認時，必須註明無法確認的原因，不得當成已確認的問題計分。

### Good Example

這個範例的問題分別以程式碼位置與實測位置確認，無法確認的項目另外註明。

```text
[P1] 搜尋欄沒有 <label>（src/components/SearchBar.tsx 第 18 行）
[P1] 390px 時方案表格超出畫面 226px（light-390.png，.plan-table；src/pages/Pricing.tsx 第 44 行）
未能確認：圖片是否過大。圖片網址來自後端 API，未實測，無法從程式碼得知實際檔案大小。
```

### Bad Example

這個範例列出沒有位置、也沒有確認過的問題，開發者照著找卻找不到，報告失去可信度。

```text
[P2] 圖片可能沒有壓縮
[P2] 某些按鈕可能太小
```

## Rule 11 -- 每個問題用白話說明影響與修法

**強度：MUST**

每個問題都必須用白話寫出兩件事：這個問題會讓什麼樣的使用者遇到什麼困難，以及具體怎麼修。不得只丟出術語或標準編號，必須讓沒有 UI 背景的使用者看得懂；術語無法避免時，在同一句中解釋。

### Good Example

這個範例用白話說明誰會受影響、遇到什麼困難，並給出具體修法。

```text
[P1] 圖示按鈕太小（src/components/Toolbar.tsx 第 30 行）
影響：手機上這排按鈕每個只有 20×20 像素又緊貼在一起，手指很容易按到旁邊那顆，例如想按「編輯」卻按到「刪除」。
修法：把每個按鈕的可點範圍加大到至少 44×44 像素，按鈕之間留 8 像素間隔。
```

### Bad Example

這個範例只寫術語與標準編號，沒有說明影響，也沒有具體修法，使用者看不懂問題有多嚴重，也不知道該怎麼改。

```text
[P1] 違反 WCAG 2.5.8 Target Size (Minimum)。
```
