# 原生平台規範

## Rule 1 -- 結構遵循平台，品牌只走開放層

**強度：MUST**

原生 App（SwiftUI、UIKit、Jetpack Compose、Android Views、React Native、Expo、Flutter）的結構、導覽與互動必須遵循該平台規範：iOS 依 Human Interface Guidelines，Android 依 Material Design 3。品牌風格只能透過平台開放的層次表現：iOS 的 tint 色、字體點綴、動態與內容；Android 的 Material 主題（色彩角色、字級、形狀、動態）。不得為了品牌感重做導覽列、返回方式或系統控制項。同一個跨平台 App 在 iPhone 上仍要遵守 iOS 的安全區域、減少動態與邊緣滑動返回。

### Good Example

這個範例以 tint 色表現品牌，導覽結構仍用系統的 NavigationStack。

```swift
NavigationStack {
    OrderList()
        .navigationTitle("訂單")
}
.tint(Color("BrandGreen"))
```

### Bad Example

這個範例為了品牌感自製頂部導覽列與返回按鈕，iPhone 使用者熟悉的大標題、返回手勢與動畫全部消失，會覺得像套殼的網頁。

```swift
VStack {
    HStack { Button("‹ 返回") { dismiss() }; Spacer(); Text("訂單").font(.custom("Brand", size: 22)) }
    OrderList()
}
.navigationBarHidden(true)
```

## Rule 2 -- 使用平台原生元件

**強度：MUST**

必須使用平台提供的控制項：iOS 的 Toggle、Segmented Picker、Stepper、系統選擇器、Action Sheet、Alert、Context Menu、Swipe Actions 與 SF Symbols；Android 的 Material 按鈕（filled、tonal、outlined、text）、FAB、Switch、Chip、Snackbar、Bottom Sheet、Material Dialog 與 Material Symbols。不得自製等價控制項，不得混用網頁圖示庫，不得把 iOS 控制項搬到 Android 或反之。設定類內容在 iOS 用分組列表，不用自製卡片堆疊。

### Good Example

這個範例在 Android 使用 Material 3 的 Switch 與 Snackbar。

```kotlin
Switch(checked = notify, onCheckedChange = { notify = it })
scope.launch { snackbarHostState.showSnackbar("已更新通知設定", actionLabel = "復原") }
```

### Bad Example

這個範例在 Android 上使用 iOS 風格的開關與網頁圖示庫，Android 使用者會覺得陌生，系統的無障礙與主題也套用不到。

```kotlin
CupertinoSwitch(checked = notify, onCheckedChange = { notify = it })
Icon(painterResource(R.drawable.fontawesome_bell), contentDescription = null)
```

## Rule 3 -- 觸控目標依平台最小尺寸

**強度：MUST**

每個可點擊的控制項，iOS 至少 44×44 pt 並與相鄰目標保留間距；Android 至少 48×48 dp，目標之間至少 8 dp。

### Good Example

這個範例讓 Android 圖示按鈕達到 48 dp 並保留 8 dp 間距。

```kotlin
Row(horizontalArrangement = Arrangement.spacedBy(8.dp)) {
    IconButton(onClick = onEdit, modifier = Modifier.size(48.dp)) { Icon(Icons.Outlined.Edit, "編輯") }
    IconButton(onClick = onDelete, modifier = Modifier.size(48.dp)) { Icon(Icons.Outlined.Delete, "刪除") }
}
```

### Bad Example

這個範例的 iOS 圖示按鈕只有 24 pt 且緊貼，手指很容易誤觸到旁邊的刪除。

```swift
HStack(spacing: 0) {
    Button(action: edit) { Image(systemName: "pencil") }.frame(width: 24, height: 24)
    Button(action: delete) { Image(systemName: "trash") }.frame(width: 24, height: 24)
}
```

## Rule 4 -- 避開安全區域與系統列

**強度：MUST**

iOS 的控制項必須放在安全區域內，不得被瀏海、動態島、首頁指示條或圓角遮住。Android 採全螢幕繪製時必須套用狀態列、導覽列、螢幕挖孔與鍵盤（IME）的 window insets，內容不得被系統列或鍵盤蓋住。

### Good Example

這個範例在 Compose 中套用系統列與鍵盤的 insets。

```kotlin
Scaffold(contentWindowInsets = WindowInsets.safeDrawing) { padding ->
    Column(Modifier.padding(padding).imePadding()) { CheckoutForm() }
}
```

### Bad Example

這個範例讓底部按鈕忽略安全區域，在有首頁指示條的 iPhone 上，「結帳」按鈕被指示條壓住而難以點擊。

```swift
CheckoutButton()
    .ignoresSafeArea()
```

## Rule 5 -- 系統返回必須可用

**強度：MUST**

iOS 的左邊緣滑動返回不得被停用或被其他手勢覆蓋；Android 必須支援預測式返回手勢與返回鍵，不得攔截返回讓使用者卡住。只有在會遺失未儲存資料時，才可以在返回前詢問確認。

### Good Example

這個範例只在有未儲存資料時攔截 Android 返回並詢問。

```kotlin
BackHandler(enabled = hasUnsavedChanges) { showDiscardDialog = true }
```

### Bad Example

這個範例無條件攔截返回，使用者按返回鍵完全沒反應，只能強制關閉 App。

```kotlin
BackHandler(enabled = true) { /* 不做任何事 */ }
```

## Rule 6 -- 導覽結構依平台與尺寸

**強度：MUST**

iOS 頂層用 Tab Bar 放 2～5 個區塊（只放區塊，不放動作），層級用 Navigation Stack，獨立任務用 Sheet；頂層畫面用大標題並在捲動時收合，深層詳情頁用一般標題。Android 在窄螢幕用底部導覽列（3～5 個目的地），寬螢幕改用 Navigation Rail 或 Drawer，不得把手機底部導覽原封不動放到平板。Android 一個畫面只放一個 FAB，且只給主要動作。

### Good Example

這個範例在 Compose 依寬度自動切換底部導覽列與 Rail，並只有一個 FAB。

```kotlin
NavigationSuiteScaffold(navigationSuiteItems = {
    destinations.forEach { item(selected = it == current, onClick = { current = it }, icon = { Icon(it.icon, null) }, label = { Text(it.label) }) }
}) {
    Scaffold(floatingActionButton = { FloatingActionButton(onClick = onCreate) { Icon(Icons.Filled.Add, "新增訂單") } }) { … }
}
```

### Bad Example

這個範例在 iOS 的 Tab Bar 中放了「新增」動作並塞了 6 個分頁，使用者點下去不是切換區塊而是跳出表單，違反預期也放不下。

```swift
TabView {
    Home().tabItem { Label("首頁", systemImage: "house") }
    NewOrderForm().tabItem { Label("新增", systemImage: "plus") }
    // …另外 4 個分頁
}
```

## Rule 7 -- 字級跟隨系統設定

**強度：MUST**

iOS 必須使用系統文字樣式（Large Title 到 Caption）以支援 Dynamic Type，內文為 17 pt，最小不得低於 11 pt；介面文字與控制項使用 SF Pro，品牌字體只能用在展示性的標題。Android 必須依 Material 字級角色（Display、Headline、Title、Body、Label）設定，字級單位用 sp，不得用固定 px 或 dp，也不得每個畫面各自挑字級。

### Good Example

這個範例在 iOS 使用系統文字樣式，在 Android 使用字級角色。

```swift
Text(order.title).font(.headline)
Text(order.note).font(.body)
```

```kotlin
Text(order.title, style = MaterialTheme.typography.titleMedium)
```

### Bad Example

這個範例寫死字級，使用者把系統字體調大後文字仍然很小，視力不好的人無法閱讀。

```swift
Text(order.title).font(.system(size: 15))
```

```kotlin
Text(order.title, fontSize = with(LocalDensity.current) { 15.dp.toSp() })
```

## Rule 8 -- 使用語意色彩並支援深色模式

**強度：MUST**

顏色必須使用平台的語意色彩：iOS 的 label、secondaryLabel、systemBackground、separator 與單一 tint 色（tint 只用在可互動元素，不做裝飾）；Android 的 Material 色彩角色（primary、onPrimary、surface、surfaceVariant、secondaryContainer、outline、error）。不得寫死 hex 色碼。深色模式必須完整設計，不得只做反色。iOS 的模糊與半透明用系統材質，不自製毛玻璃；Android 的層次用標準的 tonal elevation，不加任意陰影。Android 12 以上可使用 Dynamic Color，但要有靜態色彩的備援。

### Good Example

這個範例在 Compose 使用色彩角色，並在支援時套用 Dynamic Color、否則使用靜態配色。

```kotlin
val scheme = if (Build.VERSION.SDK_INT >= 31) dynamicLightColorScheme(context) else BrandLightColors
MaterialTheme(colorScheme = scheme) {
    Surface(color = MaterialTheme.colorScheme.surface) { Text("待出貨", color = MaterialTheme.colorScheme.onSurface) }
}
```

### Bad Example

這個範例寫死白底黑字並自製毛玻璃，切換到深色模式時整片仍是刺眼的白色，高對比設定也不會生效。

```swift
Text("待出貨").foregroundColor(Color(hex: "#222222"))
    .background(Color.white.opacity(0.7).blur(radius: 20))
```

## Rule 9 -- 系統轉場並尊重減少動態

**強度：MUST**

轉場必須符合平台導覽模型：iOS 推入從右滑入、Sheet 從下升起、關閉時反向；Android 使用 container transform、shared axis、fade through 等 Material 動態與標準時長。使用者開啟 iOS 的「減少動態效果」或 Android 的「移除動畫」時，必須改為淡入淡出或直接切換，不得保留視差與大幅滑動。

### Good Example

這個範例在使用者開啟減少動態時改用淡入淡出。

```swift
@Environment(\.accessibilityReduceMotion) var reduceMotion
DetailView()
    .transition(reduceMotion ? .opacity : .move(edge: .trailing))
```

### Bad Example

這個範例無視減少動態設定，固定使用大幅縮放與視差，對動態敏感的使用者會感到暈眩不適。

```swift
DetailView()
    .transition(.scale(scale: 0.3).combined(with: .offset(y: 400)))
```

## Rule 10 -- 跨平台轉換換成對方的慣例

**強度：SHOULD**

把畫面從 iOS 轉到 Android、從 Android 轉到 iOS，或從網站轉成原生 App 時，必須把導覽與控制項換成目標平台的對應元件，只保留品牌的配色意圖、字體點綴與動態個性。網站轉原生時，網頁導覽換成平台導覽，hover 互動換成觸控互動，px 字級換成 Dynamic Type 或 sp。以下 Example 皆對照此對照表：

| iOS | Android |
|---|---|
| Tab Bar | Navigation Bar／Rail／Drawer |
| 邊緣滑動返回、返回箭頭 | 預測式返回手勢／返回鍵 |
| Toggle、Segmented Control、系統選擇器 | Material Switch、Chip、Material 選擇器 |
| Action Sheet | Bottom Sheet／Material Dialog |
| SF Symbols、SF Pro、Dynamic Type | Material Symbols、Roboto、sp |
| 語意系統色、材質 | Material 色彩角色、tonal elevation |
| 系統推入與 Sheet 轉場 | Container transform、shared axis、fade through |

### Good Example

這個範例把 iOS 的 Action Sheet 轉成 Android 的 Modal Bottom Sheet。

```kotlin
if (showActions) ModalBottomSheet(onDismissRequest = { showActions = false }) {
    ListItem(headlineContent = { Text("分享") }, modifier = Modifier.clickable(onClick = onShare))
    ListItem(headlineContent = { Text("刪除") }, modifier = Modifier.clickable(onClick = onDelete))
}
```

### Bad Example

這個範例把 iOS 的 Segmented Control 直接仿製到 Android，Android 使用者看到不熟悉的控制項，主題色與無障礙行為也與系統其他地方不一致。

```kotlin
IosStyleSegmentedControl(options = listOf("全部", "未付款", "已出貨"), selected = tab, onSelect = { tab = it })
```

## Rule 11 -- 確認外觀與字級設定

**強度：SHOULD**

完成後 Claude 必須讀原型、修改規格或程式碼逐條確認：深色模式下每個顏色都來自語意色彩或色彩角色；系統字級調到最大時，沒有固定高度或單行限制會截斷文字；App 支援的每種裝置（手機、平板）與方向都有對應的版面分支。發現不符就寫進修改規格，並告知使用者手勢、效能與折疊手機姿勢需要在實機上確認。

### Good Example

這個範例讓列表列高度隨字級增長，並允許文字換行。

```swift
HStack(alignment: .firstTextBaseline) {
    Text(item.name).font(.body).lineLimit(nil)
    Spacer()
    Text(item.price).font(.body.monospacedDigit())
}
.padding(.vertical, 12)
```

### Bad Example

這個範例寫死列高並限制單行，系統字級調大時商品名稱被截斷成「不鏽鋼保…」，使用者看不出是哪個商品。

```swift
HStack { Text(item.name).lineLimit(1); Spacer(); Text(item.price) }
    .frame(height: 44)
```
