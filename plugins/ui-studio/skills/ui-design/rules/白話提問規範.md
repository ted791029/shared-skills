# 白話提問規範

## Rule 1 -- 提問寫在對話文字中

**強度：MUST**

提問必須直接寫在對話文字中，以一般文字列出問題與選項；不得使用彈出式的提問工具或對話框。

### Good Example

這個範例把問題與選項直接寫在回覆文字中。

```text
開始之前想先確認一件事：
1. 這個頁面主要是給誰看的？
   A. 第一次聽說這個產品的新客人（推薦，頁面上有「免費試用」按鈕）
   B. 已經在用的老客戶
請直接回覆 A 或 B。
```

### Bad Example

這個範例改用彈出式提問工具，違反使用者要在對話中直接看到並回覆問題的偏好，提問也不會留在對話紀錄裡。

```text
（呼叫 AskUserQuestion，question: "這個頁面主要是給誰看的？", options: ["新客人", "老客戶"]）
```

## Rule 2 -- 問完停下等待回覆

**強度：MUST**

送出提問後必須停下等待使用者回覆，不得在同一則回覆中接著依自己的推薦開始撰寫檔案或修改畫面。

### Good Example

這個範例在提問後結束回覆，等使用者回答。

```text
以上兩題回覆後，我再開始做頁面。
```

### Bad Example

這個範例提問後沒有等待就先照推薦動手，使用者的回答若不同，已完成的工作就得重做。

```text
以上兩題你可以晚點回覆，我先照推薦的選項把頁面做出來了，檔案在 src/pages/landing.tsx。
```

## Rule 3 -- 一次最多四題

**強度：SHOULD**

一輪提問應最多 4 題，並挑出最會改變結果的問題先問；只有回答暴露出重大缺口時才追加下一輪，不得一次丟出整份問卷。

### Good Example

這個範例只問三題最會改變設計的問題。

```text
想先確認三件事：
1. 主要使用的人是誰？
2. 他們通常在什麼情況下打開這個頁面？
3. 有沒有一定要保留的東西，例如公司標誌或某句標語？
```

### Bad Example

這個範例一次丟出八題，使用者難以逐題回答，常會略過或隨便選，得到的答案反而不可靠。

```text
請回答以下問題：
1. 主要使用者？ 2. 使用情境？ 3. 想要的感覺？ 4. 競爭對手？
5. 預算？ 6. 上線日期？ 7. 有幾個頁面？ 8. 未來會加什麼功能？
```

## Rule 4 -- 只問會改變設計的問題

**強度：MUST**

每一題都必須是答案不同就會讓畫面做法不同的問題；不改變設計的問題（例如上線日期、團隊人數）不得問。答案明顯的事不得做成選項題，應直接說出推測並請使用者需要時更正。

### Good Example

這個範例問的是會直接改變畫面密度與排版的使用情境，並把明顯的事直接說出來。

```text
看起來這是給門市店員用的點餐畫面，我會照這個方向做，不對再告訴我。
想問一題：店員通常是站著用平板單手點，還是坐在櫃台用電腦？這會決定按鈕要多大、一個畫面放多少品項。
```

### Bad Example

這個範例問了不會改變畫面做法的事，也把明顯的事做成選項，浪費使用者的回答次數。

```text
1. 這個系統預計什麼時候上線？
2. 你們團隊有幾位工程師？
3. 這是點餐系統嗎？ A. 是 B. 不是
```

## Rule 5 -- 程式碼可得知的事不問

**強度：MUST**

提問前必須先讀專案的程式碼、文案與設定；能從其中得知的事（例如產品名稱、使用的框架、現有頁面與功能、既有品牌色）不得再問使用者。

### Good Example

這個範例先從程式碼得知框架與產品名稱，只問程式碼無法回答的事。

```text
我從專案看到這是用 Next.js 做的「好食記」訂餐網站，已經有菜單、購物車與會員頁。
想問一題：最常來訂餐的是哪一種人？
```

### Bad Example

這個範例問了 package.json 與頁面文案就能回答的事，讓使用者重複說明已知資訊，也顯得沒有先看過專案。

```text
1. 你的網站是用什麼技術做的？
2. 產品名稱是什麼？
3. 目前有哪些頁面？
```

## Rule 6 -- 從程式碼推得的事請使用者確認

**強度：SHOULD**

從程式碼推得、但使用者沒有親口確認的產品事實，應以一句話說出推測並請使用者更正，不得直接當成已確認的事實使用。

### Good Example

這個範例把從路由推得的使用者族群說出來，請使用者確認。

```text
從 /admin 與 /teacher 兩組頁面看起來，主要使用者是學校老師，管理員是次要的，對嗎？不對的話告訴我。
```

### Bad Example

這個範例把推測直接當成事實，推測錯誤時後面的設計會整個做給錯的人。

```text
主要使用者是學校老師，我會以老師的需求來設計。
```

## Rule 7 -- 每題附具體選項與推薦

**強度：MUST**

每一題都必須附 2～4 個具體選項，並標出推薦的選項與一句白話理由；不得只丟出開放式問題讓使用者自己想答案。

### Good Example

這個範例每個選項都具體，並標出推薦與理由。

```text
這個頁面想給人什麼感覺？
A. 專業可靠，像銀行或保險公司（推薦，你們的客戶是企業財務人員）
B. 親切輕鬆，像生活類 App
C. 高級精緻，像精品品牌
```

### Bad Example

這個範例只有開放式問題，沒有選項與推薦，門外漢使用者不知道該怎麼回答，常只能回「都可以」。

```text
你希望這個頁面給人什麼感覺？
```

## Rule 8 -- 不用設計術語

**強度：MUST**

問題與選項必須用日常用語描述，不得出現設計或前端術語（例如 hero、CTA、留白、層級、字重、對比、grid、RWD、無襯線體）；需要描述效果時，改用使用者看得到的結果或熟悉的例子。

### Good Example

這個範例用使用者看得到的結果描述兩種做法。

```text
畫面上的資訊你希望怎麼排？
A. 一次看到很多筆資料，像 Excel 表格（推薦，你提到每天要對上百筆訂單）
B. 一次只看幾筆，每筆大一點、看得比較清楚
```

### Bad Example

這個範例充滿術語，UI 門外漢看不懂選項的差別，只能亂選或回「你決定」。

```text
資訊密度要 compact 還是 comfortable？hero 區要不要放 CTA？列表要用 card grid 還是 table？
```

## Rule 9 -- 問產品事實不問設計判斷

**強度：MUST**

只能問產品事實：誰會用、在什麼場合用、想給人什麼感覺、有什麼必須保留（標誌、標語、指定顏色、既有功能）、有什麼限制。設計判斷（用哪種字體、哪個色碼、哪種版面、元件長什麼樣子）由 Claude 依產品事實決定，不得丟回給使用者選。

### Good Example

這個範例問的是使用場合這個產品事實，字體與版面由 Claude 自行決定。

```text
大家通常在哪裡看這個頁面？
A. 通勤時用手機滑（推薦，你說客人多半從 LINE 連結點進來）
B. 上班時用電腦看
```

### Bad Example

這個範例把字體與色碼的設計判斷丟給門外漢使用者，使用者沒有能力判斷，選出的結果也不會比 Claude 依產品事實決定的更好。

```text
標題要用哪一種字體？
A. Noto Serif TC
B. Noto Sans TC
主色要用 #2563EB 還是 #0F766E？
```
