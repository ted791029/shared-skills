# 依差異範圍規範

## Rule 1 -- 範圍依差異的來源判定

**強度：MUST**

呼叫者以原始碼段入口交辦時依 Rule 2，check 的 `kind` 為技術修正時依 Rule 3。其餘情況下，本 plan 還沒有本 skill 的紀錄時照完整流程；已有紀錄時，這次的範圍只由下表各來源的差異決定；完整流程中途出現 Planner 回報的上游問題時，修正後只重跑它的差異判定的端點，再接著執行完整流程還沒執行的 Wave。每個差異都必須判斷是連帶異動（寫出要改的介面列、Wave 或原始碼段，以及要重跑的端點）或不受影響（寫出理由）。範圍外的介面列、Wave、原始碼段與既有的介面 ID 不改，範圍外的端點不重跑；重跑的端點結果為改了時，後面 Wave 中相依它的端點也加入範圍。

| 差異來源 | 判斷的節 | 重跑的端點 |
|---|---|---|
| check 的 `self.changes`：spec.md 的需求單位、research.md、techstack.md、truth-changes 的 technical-research 一節、技術項.md 中「修正：system-analysis」的行 | 引用該需求的介面列與它們所在的 Wave，新增的需求另判斷要新增的介面列；技術與 workspace 的差異另判斷原始碼段與結構決策 | 介面列或 Wave 被修正的端點 |
| Planner 回報的上游問題（Wave 中的回傳，或呼叫者轉交） | 問題在 plan.md 時是回報指出的介面列、Wave 或原始碼段，指向同一處的回報合併成一次修正；問題在前置端點的產出時不改 plan.md | 被修正的端點、收到回報的前置端點與回報的 Planner 所屬的端點 |
| check 的 `pending` 中的 Planner（via 為本 skill 的依差異入口） | 端點沒有排進 Wave、前置端點這次的異動使它的介面新增或修改時，新增它的介面列與 Wave；其餘不改 plan.md | 該端點 |
| wave-report.md 中狀態不是「完成」的端點 | 無 | 該端點 |

以下 Example 皆對照此情境：

```text
check：self.changes 為 ADD spec.md＞FR-009（結果畫面也要列出置頂訊息）；pending 另有 data-plan（本 plan 沒有紀錄，契約 ChatMessage.yaml 變了，via：/system-analysis 的依差異入口只重跑資料庫端）
plan.md：UI-01 聊天區介面（FR-001～FR-005）、UI-02 結果畫面聊天介面（FR-006）、API-01 聊天訊息 API（FR-001～FR-005）；沒有 DB 介面列，Wave 1 前端、Wave 2 後端
truth-changes ＞ api-plan：MOD components/schemas/ChatMessage.yaml，新增要持久化的欄位 pinned（FR-003）
```

### Good Example

這個範例逐項判斷兩個差異並寫出理由，只修正受影響的介面列，為沒有排進 Wave 的資料庫端新增介面列與 Wave，其他列與既有的介面 ID 不變，重跑的端點只有範圍內的前端與資料庫端。

```markdown
| 差異 | 判斷 | 範圍 |
|---|---|---|
| ADD FR-009 | 連帶異動 | UI-02 依據需求加 FR-009，重跑前端；API-01 不受影響：訊息已帶 pinned，不需要新的資料 |
| data-plan 待補跑 | 連帶異動 | pinned 要持久化，資料庫端的聊天訊息資料表要改：新增 DB-01（MOD，FR-003）與 Wave 3 資料庫端，重跑資料庫端 |

UI-01、API-01、原始碼段與既有的介面 ID 不改；前端重跑的結果為改了時，相依它的 Wave 2 後端也加入範圍。
```

### Bad Example

這個範例無視差異的來源，重新執行完整流程並重新編號，ui-contract 以 UI-02 引用的段落對不上新編號，兩個 Wave 全部重跑，沒有排進 Wave 的資料庫端卻仍沒有人判斷 pinned 要不要持久化。

```text
system-analysis 有差異 → 重新盤點全部介面（原 UI-02 改為 UI-03）→ 重跑 Wave 1、Wave 2 → 重寫 wave-report.md
```

## Rule 2 -- 原始碼段入口只改原始碼段與結構決策

**強度：MUST**

呼叫者以原始碼段入口交辦原始碼段以外的產品檔時（implement 轉交 bdd 綠燈、重構回報，或直接實作的任務列出的產品檔），只能在 plan.md 的 `### 原始碼（repo 根目錄）` 補上這些檔案與它們所在的目錄，並刪去或改寫被它們取代、實作沒有使用的檔案與職責說明，新的目錄或分層使結構決策的理由改變時才修改結構決策；介面盤點、分析 Wave 與 wave-report.md 不改，也不重跑任何 Planner。檔案的位置違反專案結構規劃規範或 plan.md 適用的憲法條款時，不修改原始碼段，結果為不能改，交給 task 排任務把檔案移到原始碼段列出的位置。以下 Example 皆對照此交辦：

```text
原始碼段入口：原始碼段以外的產品檔
- backend/app/services/chat_pin.py（bdd 綠燈 T014，置頂與取消置頂）
- tools/pin_cache.py（bdd 綠燈 T014，置頂快取）
plan.md 原始碼段：backend/app/services/ 只列 rooms.py、snapshot.py；結構決策：後端分為路由 → 服務 → 資料存取三層
techstack.md 套件安裝清單的 workspace：backend、frontend
```

### Good Example

這個範例只在原始碼段補上服務層的新檔案，檔案仍在既有的服務層，結構決策不變；不在任何 workspace 的檔案不補進原始碼段，回報不能改並交給 task；介面盤點、分析 Wave 與 wave-report.md 都沒有動，也沒有重跑 Planner。

```text
backend/app/services/
├── rooms.py
├── snapshot.py
└── chat_pin.py          # 本功能新增：置頂與取消置頂
結構決策：不改（仍在服務層）
tools/pin_cache.py：不在任何 workspace，違反專案結構規劃規範 → 不補進原始碼段；不能改，交給 task 排任務把它移到 backend/app/services/
介面盤點、分析 Wave、wave-report.md：不改；不重跑 Planner
check_plan.py：0 個問題
```

### Bad Example

這個範例為了一個檔案的位置重新盤點介面，並重跑三個 Wave 的 Planner、重寫 wave-report.md，工作量與實際影響不成比例，Planner 還可能改到這次沒有原因的介面文檔。

```text
原始碼段補上 chat_pin.py → 重新盤點介面 → 重跑 Wave 1～3 的 ui-ux-plan、api-plan、data-plan → 重寫 wave-report.md
```

## Rule 3 -- 技術修正 plan 只判斷點名本 skill 的技術項

**強度：MUST**

check 的 `kind` 為「技術修正」時，plan 沒有 spec.md 與 plan.md，判斷技術項.md 中「修正：system-analysis」的行與 check 列出的其他差異（例如 technical-research 清理了 techstack.md；技術修正 plan 沒有介面列、Wave 與原始碼段可以受影響，這些差異都是不受影響），不得為它們撰寫 plan.md、wave-report.md 或執行 Planner。system-analysis 的事實只有有需求的 plan 中的 plan.md 與 wave-report.md，已交付 plan 的 plan.md 也不修改，所以這些行的結果為不能改，交給 dev-finding 把這一行的「修正：」改寫成出錯那份資料的擁有者；沒有這些行時結果為不用改。以下 Example 皆對照此技術項：

```text
plan：005-chat-fix（技術修正）
技術項.md：- 契約 ChatMessage.yaml 的 pinned 是字串，資料模型 chat_messages.pinned 是布林（使用者；`specs/truth/contracts/components/schemas/ChatMessage.yaml` 與 `specs/truth/data/聊天.dbml`；修正：system-analysis）
```

### Good Example

這個範例判定這一行錯的是契約或資料模型，不是 system-analysis 的事實，沒有撰寫 plan.md，回報不能改並交給 dev-finding 改寫修正的擁有者；dev-finding 改寫後已沒有點名本 skill 的行，下一次的結果為不用改。

```text
不能改：技術修正 plan 沒有 plan.md，這一行錯的是契約或資料模型，不是 system-analysis 的事實。
交給：dev-finding 依出錯那份資料的擁有者，把「修正：system-analysis」改寫成「修正：api-plan」或「修正：data-plan」。
這次沒有記錄，system-analysis 仍是待補跑。
（dev-finding 改寫後再執行：技術項.md 已沒有「修正：system-analysis」的行 → 不用改，依 plan-package 記錄）
```

### Bad Example

這個範例為了這一行在技術修正 plan 撰寫 plan.md 與兩個 Wave，plan 變得像有需求的 plan，dsl-refine 與 task 會要求它沒有的 acceptance 與 spec.md，契約與資料模型的擁有者也從沒被點名。

```text
建立 plan.md：API-01 聊天訊息 API（MOD，技術：pinned 型別不一致）、DB-01 聊天訊息資料表（MOD）；Wave 1 後端、Wave 2 資料庫端 → 依序執行 api-plan、data-plan
```
