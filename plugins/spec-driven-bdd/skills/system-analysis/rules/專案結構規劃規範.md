# 專案結構規劃規範

## Rule 1 -- 文件樹只列 plan 資料夾中已確定的文件

**強度：MUST**

文件（這個 plan）的目錄樹只能列出 plan 資料夾中檔名已確定的文件：spec.md、research.md、truth-changes.md、plan.md 與 tasks.md，並以註解說明內容；由其他指令產生的文件必須在註解標示來源指令。不得列出 `specs/truth/` 的文件，也不得列出各端點的介面文檔，介面文檔的位置、檔名與格式由負責該端點的 Planner 決定。

### Good Example

這個範例只列出 plan 資料夾中檔名已確定的文件，並標示每份文件的來源指令。

```text
specs/plans/001-photo-album-organizer/
├── spec.md              # 功能規格（由 /specify 產生）
├── research.md          # 技術決策與理由（由 /technical-research 產生）
├── truth-changes.md     # 這個 plan 對 truth 的異動紀錄（由修改 truth 的各個指令記錄）
├── plan.md              # 本文件
└── tasks.md             # 實作任務（由後續任務拆解產生，不由本指令建立）
```

### Bad Example

這個範例列出 `data-model.md`，資料庫端的 Planner 實際把資料模型寫進 `specs/truth/data/` 時，文件樹指向不存在的檔案，後續任務拆解依文件樹讀取會找不到資料模型。

```text
specs/plans/001-photo-album-organizer/
├── plan.md              # 本文件
├── data-model.md        # 資料表欄位、索引與交易邊界
└── tasks.md             # 實作任務（由後續任務拆解產生，不由本指令建立）
```

## Rule 2 -- 原始碼樹必須依端點與 workspace 分目錄

**強度：MUST**

原始碼（repo 根目錄）的目錄樹必須讓 techstack.md 套件安裝清單的每個 workspace 對應到同路徑的目錄（`.` 對應 repo 根目錄），每個需要程式碼的端點放在它所屬 workspace 的目錄內；多個端點共用同一個 workspace 時，各端點在其中分開子目錄。資料庫端與檔案系統端放在存取它們的端點目錄內。

### Good Example

這個範例依 techstack.md 的 frontend、backend、e2e 三個 workspace 建立頂層目錄，資料庫遷移與儲存目錄放在後端內。

```text
backend/
├── src/db/migrations/001_init.sql
└── storage/                 # 執行期產生（.gitignore）
frontend/
e2e/
```

### Bad Example

這個範例把資料庫與儲存區另開頂層目錄，名稱也與 workspace 不一致，npm workspaces 找不到 `client`，資料庫遷移與存取它的後端程式分離。

```text
client/
server/
database/
storage/
```

## Rule 3 -- 結構決策必須說明理由

**強度：MUST**

結構決策必須寫出採用的結構與至少一個取自 spec.md 或 constitution 的理由，不得只重述目錄樹。

### Good Example

這個範例說明三層分層是為了讓服務層可獨立測試並達成覆蓋率要求。

```markdown
**結構決策**：採用前端 ＋ 後端兩個專案的 Web 應用程式結構，並以 npm workspaces 管理，另加 `e2e` 驗收測試專案。
後端分為路由 → 服務 → 儲存庫三層，讓核心商業邏輯（服務層）可以獨立測試，並達到 90% 覆蓋率要求。
```

### Bad Example

這個範例只重述目錄樹，看不出為什麼這樣分，後續調整結構時無法判斷哪些分層不能拆。

```markdown
**結構決策**：有 frontend、backend、e2e 三個資料夾。
```
