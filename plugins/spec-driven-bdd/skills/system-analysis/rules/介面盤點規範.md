# 介面盤點規範

## Rule 1 -- 端點必須是獨立的技術系統

**強度：MUST**

端點是本次需求涉及、可獨立運作或保存資料的技術系統，例如前端、後端、資料庫、檔案系統、手機 App、硬體裝置、雲端服務、第三方服務。必須從 spec.md 的需求與 techstack.md 的技術判斷涉及哪些端點；同一端點內的程式分層（如路由、服務、儲存庫）不得當成端點。

### Good Example

這個範例依 techstack.md 選用的 MySQL 與本機檔案系統儲存，把資料庫與檔案系統各列為獨立端點。

```markdown
端點：前端、後端、資料庫端、檔案系統端
```

### Bad Example

這個範例把後端的程式分層列成端點，卻漏掉保存原始檔與縮圖的檔案系統，Wave 會為分層各開 sub-agent，檔案系統的介面則沒人分析。

```markdown
端點：前端、路由層、服務層、儲存庫層、資料庫端
```

## Rule 2 -- 介面必須歸屬提供它的端點

**強度：MUST**

介面是端點提供給使用者或其他端點使用的部位，所屬端點必須填提供方，不得填使用方。兩個端點之間的連線只能列成一個介面，不得在兩端各列一次。

### Good Example

這個範例把前端呼叫的相簿 API 歸屬於提供它的後端，只列一次。

```markdown
| API-02 | 相簿 API（列表、排序） | 後端 | ADD | FR-006、FR-007、FR-013、FR-015、FR-016、NFR-010 |
```

### Bad Example

這個範例在前端與後端各列一次相簿 API，同一份契約會被兩個 sub-agent 各寫一份，內容容易互相矛盾。

```markdown
| UI-05 | 相簿 API 呼叫 | 前端 | ADD | FR-007、FR-013 |
| API-02 | 相簿 API（列表、排序） | 後端 | ADD | FR-007、FR-013 |
```

## Rule 3 -- 介面粒度依使用部位切分

**強度：SHOULD**

介面應依端點被使用的部位切分：前端依畫面或畫面區塊（如工作區、圖片預覽區），後端依資源分組的 API，資料庫依資料表，檔案系統依儲存區。介面名稱後應以括號列出該部位涵蓋的元素。不應把整個端點列成一個介面，也不應細到單一欄位或單一 HTTP 路徑。

### Good Example

這個範例把前端依畫面切成介面，並以括號列出涵蓋的元素。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | ADD | FR-007、FR-013 |
| UI-03 | 相簿平鋪預覽介面（縮圖格線、佔位載入、刪除） | 前端 | ADD | FR-010、FR-017 |
```

### Bad Example

這個範例把整個前端列成一個介面，依據需求塞滿所有前端需求，無法看出每個畫面對應哪些需求。

```markdown
| UI-01 | 前端介面 | 前端 | ADD | FR-001、FR-006～FR-014、FR-016～FR-020 |
```

## Rule 4 -- 介面必須由需求開出

**強度：MUST**

每個介面的依據需求必須列出促使它存在或這次改變它的 FR、NFR 或 SC 編號，連續編號以「～」表示範圍；促使它的是本 plan acceptance 中標 `@開發發現` 的 AC（例如依憲法改正會改變 PM 看得到的行為，記成了開發發現的 AC）時，寫該 AC 編號。只因 PM 看不到差異的技術原因而新增、修改或刪除、沒有需求可引用的介面，例如技術項.md 點名的問題，或依憲法改正先前 plan 留下、PM 看不到差異的內容，在依據需求的最後寫「技術：<原因>」，原因沿用技術項的問題，或寫「依憲法 <條款 ID> 改正」。找不到依據需求、也沒有技術原因的介面不得列入。

### Good Example

這個範例的燈箱介面列出要求放大檢視、返回平鋪與刪除的需求；設定 API 這次只因先前 plan 留下的回應沒有包成 data 與 meta 而依憲法改正，沒有需求可引用，依據需求寫出技術原因。

```markdown
| UI-04 | 燈箱放大檢視介面（上一張／下一張、返回平鋪、刪除） | 前端 | ADD | FR-011、FR-012、FR-017、NFR-007 |
| API-04 | 設定 API（排序模式） | 後端 | MOD | 技術：依憲法 C-API-01 改正 |
```

### Bad Example

這個範例列出 spec.md 沒有要求的相簿分享介面，Wave 會為不存在的需求安排分析。

```markdown
| UI-05 | 相簿分享介面（分享連結、權限） | 前端 | ADD | — |
```

## Rule 5 -- 每條功能需求必須被介面涵蓋

**強度：MUST**

spec.md 的每一條 FR 必須至少出現在一個介面的依據需求中。全域 FR 必須列在所有實際落實它的介面上。

### Good Example

這個範例把要求繁中訊息的全域 FR-020 列在會顯示錯誤、空狀態與載入狀態的三個畫面。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | ADD | FR-007、FR-020 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | ADD | FR-001、FR-020 |
| UI-03 | 相簿平鋪預覽介面（縮圖格線、佔位載入、刪除） | 前端 | ADD | FR-010、FR-020 |
```

### Bad Example

這個範例沒有任何介面引用 FR-020，後續 sub-agent 只依各自介面的依據需求分析，繁中訊息的要求會被所有介面文檔遺漏。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | ADD | FR-007 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | ADD | FR-001 |
```

## Rule 6 -- 介面 ID 使用端點前綴

**強度：MUST**

介面 ID 固定為 `<端點前綴>-<兩位流水號>`，流水號在端點內從 01 依序遞增。前綴必須依端點類型取下表，任何功能的同類型端點都使用相同前綴，因為 planner-provisioning 以前綴對照負責的 Planner；表中沒有的端點類型自訂一個大寫英文前綴。表格列必須依端點由外而內排列，同一端點的介面相鄰。

| 端點類型 | 前綴 |
|---|---|
| 前端 | `UI` |
| 後端 | `API` |
| 資料庫端 | `DB` |
| 檔案系統端 | `FS` |
| 手機 App | `APP` |
| 硬體裝置 | `HW` |
| 第三方服務 | `EXT` |

### Good Example

這個範例同一端點共用前綴、流水號連續，且由外而內排列。

```markdown
| UI-01 | 主頁相簿列表介面（相簿卡片、空狀態、拖放與鍵盤排序） | 前端 | ADD | FR-007 |
| UI-02 | 匯入對話框介面（選取檔案、進度、略過結果） | 前端 | ADD | FR-001 |
| API-01 | 匯入 API | 後端 | ADD | FR-001～FR-004 |
| DB-01 | 相簿資料表（含自訂排序） | 資料庫端 | ADD | FR-003 |
```

### Bad Example

這個範例為前端自訂 `FE` 前綴並混用全域流水號，planner-provisioning 依前綴找不到 `ui-ux-plan`，會判定缺少並重建一個職責重複的 Planner；資料庫又排在前端之間，Wave 標題無法以範圍引用同一端點的介面。

```markdown
| FE-1 | 主頁相簿列表介面 | 前端 | ADD | FR-007 |
| DB-01 | 相簿資料表 | 資料庫端 | ADD | FR-003 |
| FE-2 | 匯入對話框介面 | 前端 | ADD | FR-001 |
```

## Rule 7 -- 每個介面必須標示這次的異動

**強度：MUST**

「異動」欄必須填這次迭代對該介面的異動，只能是下表四個值之一，並對照 `specs/truth/` 的現況判定：有介面文檔的端點對照它的介面文檔，truth 沒有介面文檔的端點（例如前端）對照 `specs/truth/features/` 中該端點的 feature。這次的需求移除的既有介面也必須列入表中並標 `DEL`，依據需求填要求移除它的需求；專案的第一個 plan 沒有既有介面，全部為 `ADD`。以下 Example 皆對照此需求與 truth 現況：

| 異動 | 判定 |
|---|---|
| `ADD` | truth 沒有這個介面，這次新增 |
| `MOD` | truth 已有這個介面，這次的需求改變它的操作、資料或呈現 |
| `DEL` | truth 已有這個介面，這次的需求移除它 |
| `無` | truth 已有這個介面，這次的需求用到它但不改變它 |

```text
FR-021：照片可以加上標籤，並依標籤篩選
FR-022：移除燈箱放大檢視，點擊縮圖改為直接下載原圖
truth 現況：有平鋪預覽與燈箱兩個畫面、照片 API（列表、前後張、刪除、原圖與縮圖取得）；沒有標籤的畫面、API 與資料表
```

### Good Example

這個範例的標籤是新介面標 ADD，被 FR-022 移除的燈箱列入表中標 DEL，少了前後張的照片 API 標 MOD。

```markdown
| 介面 ID | 介面 | 所屬端點 | 異動 | 依據需求 |
|---|---|---|---|---|
| UI-01 | 標籤篩選介面（標籤清單、篩選結果、空狀態） | 前端 | ADD | FR-021 |
| UI-02 | 相簿平鋪預覽介面（點擊縮圖下載原圖） | 前端 | MOD | FR-022 |
| UI-03 | 燈箱放大檢視介面 | 前端 | DEL | FR-022 |
| API-01 | 標籤 API（新增、移除、依標籤列出照片） | 後端 | ADD | FR-021 |
| API-02 | 照片 API（移除前後張，原圖取得不變） | 後端 | MOD | FR-022 |
| DB-01 | 照片標籤資料表 | 資料庫端 | ADD | FR-021 |
```

### Bad Example

這個範例只列新增的介面，被 FR-022 移除的燈箱與要修改的照片 API 都不在表中；沒有任何 Wave 會分析它們，後端的 Planner 不會刪除前後張的契約，truth 會留下已經不存在的操作。

```markdown
| 介面 ID | 介面 | 所屬端點 | 異動 | 依據需求 |
|---|---|---|---|---|
| UI-01 | 標籤篩選介面（標籤清單、篩選結果、空狀態） | 前端 | ADD | FR-021 |
| API-01 | 標籤 API（新增、移除、依標籤列出照片） | 後端 | ADD | FR-021 |
| DB-01 | 照片標籤資料表 | 資料庫端 | ADD | FR-021 |
```

## Rule 8 -- 異動要對照涵蓋需求的 AC

**強度：MUST**

判定既有介面是 `MOD` 還是 `無` 時，除了 spec.md 的 FR、NFR，也必須讀 acceptance 中涵蓋這些需求的 AC：AC 的步驟或斷言要求既有介面多一個操作、資料或呈現（例如畫面多一個標示、回應多一個欄位）時，即使 FR 的文字沒有提到，該介面也是 `MOD`，依據需求寫 AC 涵蓋的需求編號。以下 Example 皆對照此需求、AC 與 truth 現況：

```text
FR-005：客人可以取消自己的預約
AC-02（# 涵蓋：US1、FR-005）："王小明" 按 "取消預約" → 看到 "預約已取消"，而且預約清單仍列出這筆預約並標為 "已取消"
truth 現況：預約清單畫面只列出成立中的預約，取消後的預約會從清單消失
```

### Good Example

這個範例讀到 AC-02 要求清單保留已取消的預約，既有的清單畫面要多一個標示，判定為 MOD。

```markdown
| UI-02 | 預約清單介面（已取消的預約標示） | 前端 | MOD | FR-005 |
```

### Bad Example

這個範例只看 FR-005 的文字，認為清單不用改；ui-ux-plan 不會為清單撰寫已取消的標示，dsl-refine 衍生 AC-02 時才發現 UI 契約沒有這個呈現，要經 dev-finding 回到 system-analysis 改為 MOD 再重跑 ui-ux-plan，多走一輪。

```markdown
| UI-02 | 預約清單介面 | 前端 | 無 | FR-005 |
```

## Rule 9 -- 共用 schema 的修改歸在驅動它的介面列

**強度：MUST**

多個介面的操作共用的 schema（例如多個 API 都回傳的狀態結構）沒有自己的介面列。這次的需求要改共用 schema 時，只把需求要求改變的介面標為 `ADD` 或 `MOD`；只因共用 schema 附帶多了或少了欄位、操作與用途都沒有改變的其他介面，維持原本的異動，不必改標 `MOD`。以下 Example 皆對照此需求與契約：

```text
FR-001：對局結束後，結果畫面顯示雙方的勝場排名
契約：`components/schemas/RoomState.yaml` 被 API-01 房間 API（取得目前房間）與 API-02 對戰 API（猜測、認輸）的回應引用；結果畫面的排名由 API-01 取得
```

### Good Example

這個範例只把結果畫面取得排名的房間 API 標為 MOD，RoomState 加上排名的修改歸在它的列；對戰 API 的操作與用途沒有改變，維持「無」。

```markdown
| API-01 | 房間 API（目前房間的勝場排名） | 後端 | MOD | FR-001 |
| API-02 | 對戰 API（猜測、認輸） | 後端 | 無 | FR-001 |
```

### Bad Example

這個範例因為對戰 API 的回應也引用 RoomState 就改標 MOD；猜測與認輸的操作沒有任何改變，卻要有 Rule 驅動它的異動，task 找不到驅動它的 Rule 時判為案例缺口而停下。

```markdown
| API-01 | 房間 API（目前房間的勝場排名） | 後端 | MOD | FR-001 |
| API-02 | 對戰 API（猜測、認輸的勝場排名） | 後端 | MOD | FR-001 |
```
