# 端點分派規範

## Rule 1 -- 端點資料夾必須對應 plan.md 的介面前綴

**強度：MUST**

plan.md「介面盤點」中每種介面 ID 前綴各對應一個端點資料夾，資料夾名稱用小寫英文：UI 對應 `frontend`、API 對應 `backend`、DB 對應 `database`、FS 對應 `filesystem`；其他前綴取「所屬端點」欄的英文小寫（例如 MQ 的訊息佇列端為 `queue`），並在用語表「端點」登記前綴與資料夾。前端只有一個 `frontend` 資料夾，不分畫面元件測試與系統測試。不得把兩種前綴併成一個資料夾，也不得為 plan.md 沒有的前綴建資料夾。儲存端點（使用 `templates/database/` 或 `templates/filesystem/` 樣板的端點）沒有分到任何補充案例時，不建立資料夾、不登記在用語表「端點」，並在回報寫明 plan.md 有該前綴但沒有 feature 的原因；`specs/truth/features/` 已有的端點資料夾沿用，不因這次沒有案例而刪除。以下 Example 皆對照此介面盤點與補充案例的分派結果：

```text
| UI-01～UI-05 | 前端 |
| API-01～API-03 | 後端 |
| DB-01～DB-03 | 資料庫端 |
| FS-01～FS-02 | 檔案系統端 |
補充案例分派到 database：NFR-013（技能剩餘次數上限）；分派到 filesystem：無
```

### Good Example

這個範例為有案例的三種前綴各建一個端點資料夾，前端只有一層；filesystem 沒有分到案例，不建資料夾，回報寫明原因。

```text
specs/plans/002-battle-skills/features/acceptance/   ← spec-by-example 的產物，只讀
specs/truth/features/
├── frontend/
├── backend/
└── database/

回報「未產生的端點」：FS（filesystem）：spec.md 沒有檔案路徑、命名或其他儲存約束的需求，檔案寫入的結果由 backend 查證
```

### Bad Example

這個範例把前端拆成兩層，又為沒有案例的 FS 建了空的 filesystem 並登記在用語表，同一組 When 在前端要寫兩次，filesystem 寫不出任何 Rule 與 dsl.md，task 卻會依用語表找這個資料夾的 feature。

```text
specs/truth/features/
├── frontend/
│   ├── component/
│   └── e2e/
├── backend/
├── database/
└── filesystem/   ← 空資料夾
```

## Rule 2 -- AC 的動作只分派到畫面與 API 端點

**強度：MUST**

AC 每組 When 的每個動作，依介面文檔分派到該動作有行為的端點：使用者在畫面上的操作一律分派到 `frontend`；ui-contract.md 或 openapi.yaml 寫明該操作呼叫的 API，分派到 `backend`；不呼叫任何 API 的操作只分派到 `frontend`。AC 的動作與斷言一律不分派到儲存端點，API 寫進資料表或檔案的結果由 `backend` Then 的查證斷言讀取。畫面斷言的內容來自 API 的回應欄位或推播事件時（例如對手畫面播放特效來自推播），`backend` 必須另衍生驗該回應欄位或推播事件的 Example；只在畫面上產生、不經任何 API 的斷言只分派到 `frontend`。每組 When 至少有一個動作分派到某個端點。以下 Example 皆對照此 When 組與介面文檔：

```text
AC-01 第 1 組：甲開啟改答案、甲送出新答案 4567 → 甲的畫面顯示目前答案、雙方畫面播放改答案特效、乙的畫面看不到答案
ui-contract.md：開啟改答案只顯示輸入框，不呼叫 API；送出新答案呼叫 POST /api/rooms/{room_id}/skills/change-secret；收到 skill_effect 推播時播放特效
openapi.yaml：該 API 更新 rooms 的 host_secret、host_original_secret 與 host_change_left，成功後向雙方推播 skill_effect
```

### Good Example

這個範例把畫面操作留在 frontend，只把呼叫 API 的送出新答案分派到 backend；特效來自推播，backend 另驗推播事件；資料表的答案與次數由 backend 的查證斷言讀取，不分派到 database。

```text
frontend ← 開啟改答案、送出新答案 4567：甲的畫面顯示目前答案、雙方畫面播放改答案特效、乙的畫面看不到答案
backend  ← 送出新答案 4567：甲的目前答案為 4567、雙方收到改答案的特效事件、乙的房間狀態看不到答案
```

### Bad Example

這個範例因為 API 會更新 rooms 就把送出新答案分派到 database，又漏了特效依賴的推播；database 的測試得先打 API 再查資料表，與 backend 的查證重複，後端沒實作時也只能一起失敗；前端的特效則沒有任何後端 Rule 驅動推播。

```text
backend  ← 送出新答案 4567：甲的目前答案為 4567、乙的房間狀態看不到答案
database ← 送出新答案 4567：rooms 的答案、原答案與改答案剩餘次數
```

## Rule 3 -- 補充案例依能直接驗證它的端點分派

**強度：MUST**

依 AC 衍生規範挑出的補充案例，分派到能直接觸發並驗證該需求的端點：輸入格式、權限與狀態前置條件的拒絕放 `backend`，畫面有同樣的防呆時 `frontend` 另加一組；畫面狀態（載入、空狀態、無障礙）放 `frontend`；儲存端點只接儲存結構與約束的案例（唯一與主鍵、CHECK、型別範圍、外鍵、索引、檔案路徑與命名），以直接讀寫資料表或檔案就能觸發。只能透過 API 觀察的業務結果，即使最後寫進資料表或檔案，也放 `backend`。不得把補充案例分派到驗證不了它的端點。以下 Example 皆對照此 spec.md 需求與 data-model.dbml：

```text
FR-003 新答案不符合四碼規則時，系統不接受並顯示四碼規則提示
FR-006 改答案之前已送出的猜測與回報必須保留原樣
FR-028 每位玩家每局有改答案與連猜三次各 1 次使用次數
data-model.dbml：ck_rooms_skill_counts（四個技能剩餘次數皆介於 0 與 1，擋下超用，NFR-013）
```

### Good Example

這個範例把四碼規則的拒絕放後端、提示放前端；改答案前的猜測保留原樣要經 API 改答案才看得到，放後端；技能次數的上限是資料表的 CHECK 約束，放資料庫端。

```text
FR-003 → backend（系統拒絕、答案不變）、frontend（顯示四碼規則提示）
FR-006 → backend（改答案後查詢猜測歷史，回報不變）
FR-028 → database（技能剩餘次數不能超過 1）
```

### Bad Example

這個範例把 FR-006 也放進 database，資料庫端得先打 API 改答案再查 guesses，驗的是後端的業務規則，與 backend 的同一條規則重複，後端沒實作時也無法先通過。

```text
FR-006 → database（改答案之前已寫入的猜測紀錄，A、B 數欄位不得因改答案而改變）
```

## Rule 4 -- step 目錄依測試設定判斷

**強度：MUST**

每個端點資料夾的 step 目錄與目錄下既有的模組，必須從專案測試設定載入 feature 與 step 的路徑判斷。判斷結果只寫進委派簡報，不得寫進用語表、feature、dsl.md 或回報，也不得為設定中找不到或多端點共用的目錄另行擬定目錄；設定沒有載入本端點時，委派簡報寫「測試設定未載入本端點」。以下 Example 皆對照此專案測試設定：

```text
frontend/playwright.config.js：
  features: ['../specs/truth/features/frontend/*.feature']
  steps: ['tests/e2e/support/fixtures.js', 'tests/e2e/steps/**/*.js']
backend/tests/behave_runner.py：
  SUITES = {"api": "backend", "database": "database"}；step 從 backend/tests/<套件>/steps 載入，未指定 feature 時收集 specs/truth/features/<端點資料夾>
backend/tests/api/steps/modules/：對戰、對戰紀錄、房間、推播、準備、玩家、維運
```

### Good Example

這個範例依 playwright 設定與 runner 的套件對照找出各端點的 step 目錄與既有模組，結果只寫進委派簡報，用語表的端點表維持原欄位。

```markdown
委派 frontend：
- **step 目錄**：`frontend/tests/e2e/steps`（既有模組：對戰、對戰紀錄、房間、推播、準備、維運）

委派 backend：
- **step 目錄**：`backend/tests/api/steps`（既有模組：對戰、對戰紀錄、房間、推播、準備、玩家、維運）
```

### Bad Example

這個範例沒有讀測試設定，依資料夾名稱猜了一個不存在的 step 目錄，寫 step 的人會把檔案放到 runner 不會載入的位置；又把 step 目錄寫進用語表，專案層級的設定多了一份會過時的副本。

```markdown
委派 backend：
- **step 目錄**：`backend/tests/steps`（依端點名稱推測）

用語表「端點」：
| 介面前綴 | 資料夾 | 測試名稱與工具 | 樣板資料夾 | step 目錄 | 可用起點 |
|---|---|---|---|---|---|
| API | `backend` | … | `templates/backend/` | `backend/tests/steps` | … |
```
