# 跨端點一致規範

## Rule 1 -- 共用句子必須以用語表為準

**強度：MUST**

不同端點表達同一件事的步驟，必須改成用語表登記的同一句文字，而用語表的寫法以 acceptance 的 AC 句型為準，AC 沒有的句子才由合併階段統一；各端點 dsl.md 中的這個句型也改成相同的句型文字。端點為了沿用或避開本端點既有的句型而改用的句型，已登記在涵蓋表「AC 句型對照」的，維持該端點的寫法，不改回用語表的共用寫法。只有測試撰寫語意可以依各端點的測試層不同。儲存端點直接寫入資料的句子與畫面、API 端點的業務動作句不是同一件事，不改成相同文字。

### Good Example

這個範例依用語表把後端的同義句改成用語表的文字；前端沿用前端既有句型的寫法已登記在 AC 句型對照，維持不改；資料庫端直接寫入的句子不是匯入動作，保留原文。

```text
用語表：匯入拍攝於 {日期} 的照片 {照片}
AC 句型對照：`匯入拍攝於 {日期} 的照片 {照片}` | frontend | `上傳拍攝於 {日期} 的照片 {照片}`
backend：匯入拍攝於 "2026-10-01" 的照片 "P1"   ← 原為「新增拍攝於 2026-10-01 的照片 P1」
frontend：上傳拍攝於 "2026-10-01" 的照片 "P1"   ← 沿用前端既有的句型，不改回
database：照片 "P1" 的紀錄已存在   ← 直接寫入資料表，維持不改
```

### Bad Example

這個範例保留兩種說法，又把資料庫端的直接寫入改成業務動作句；讀者跨端點比對時以為前後端是兩種不同的前提，資料庫端的 step 則被誤導去走匯入流程。

```text
frontend：匯入拍攝於 "2026-10-01" 的照片 "P1"
backend：新增拍攝於 "2026-10-01" 的照片 "P1"
database：匯入拍攝於 "2026-10-01" 的照片 "P1"   ← 原為「照片 "P1" 的紀錄已存在」
```

## Rule 2 -- 同一條規則的 Rule 名稱必須一致

**強度：MUST**

不同端點驗證同一條業務規則時，Rule 名稱必須逐字相同，以用語表的寫法為準；只有規則本身不同時才使用不同名稱。

### Good Example

這個範例的後端與前端驗同一條規則，Rule 名稱逐字相同。

```gherkin
backend/相簿排序.feature：  Rule: 儲存排序失敗時，相簿順序必須維持不變
frontend/相簿排序.feature：  Rule: 儲存排序失敗時，相簿順序必須維持不變
```

### Bad Example

這個範例兩端用不同說法描述同一條規則，追溯規則時要靠人判斷「還原」與「不變」是否同義，搜尋 Rule 名稱也只會找到其中一端。

```gherkin
backend/相簿排序.feature：  Rule: 儲存排序失敗時，相簿順序必須維持不變
frontend/相簿排序.feature：  Rule: 排序失敗必須還原畫面
```

## Rule 3 -- 新出現的共用句子與技術說法必須補進用語表

**強度：MUST**

合併時發現兩個以上端點使用、但用語表沒有登記的句子，統一文字後補進用語表「共用句子」，標明使用的端點；只有一個端點使用的句子不登記。sub-agent 回傳的新增技術說法一律補進用語表「技術說法對照」，標明使用的端點；同一個技術說法在各端點採用不同業務說法時，統一成一種並改寫各端點的 feature。

### Good Example

這個範例把前端與後端都用到的新句子補進共用句子，並把前端回傳的新增技術說法補進技術說法對照。

```markdown
| 刪除照片 {照片} | frontend、backend |

| role="alert" | 會被螢幕閱讀器立即朗讀 | frontend |
```

### Bad Example

這個範例沒有補進用語表，下一個 plan 執行時 sub-agent 看不到這句的統一寫法與 `role="alert"` 的業務說法，同一件事又會出現新的說法，check_features.py 也抓不到這個技術說法。

```markdown
（用語表維持原樣；frontend 與 backend 各自使用「刪除照片 "P1"」；frontend 回傳的 role="alert" 沒有登記）
```

## Rule 4 -- 被依賴的入口與事件必須有 Rule 驅動

**強度：MUST**

逐一檢查每個端點 dsl.md 的測試撰寫語意與它對應的介面文檔（ui-contract.md、openapi.yaml 的請求、回應欄位與推播事件），列出該端點的結果依賴的其他端點入口、回應欄位與推播事件；dsl.md 沒有寫出名稱、但介面文檔寫明畫面結果來自某個事件時也要列入。每一項都必須在被依賴端點有一條 Rule 以它為 When 或在 Then 驗證它；缺少時，能從 AC 的斷言或 spec.md 需求追溯來源，就依該端點的規則補上 Rule 並登記在涵蓋表的 AC 涵蓋表或補充案例，追溯不到時列入待確認事項「跨端點依賴缺口」。dsl.md 的技術對應與介面文檔不符（路徑、方法、欄位或事件名稱不同）也列入「跨端點依賴缺口」。以下 Example 皆對照此前端 Rule、介面文檔與後端 feature：

```text
frontend/改答案.feature：Rule: 改答案後，雙方畫面必須在時限內播放寫明角色與技能名稱的特效（AC-01 第 1 組）
ui-contract.md：收到 skill_effect 推播時播放特效
openapi.yaml：change-secret 成功後先向雙方推播 skill_effect（skill: change_secret，不含答案），再推播 room_state
frontend/dsl.md 起點：以 `POST /api/rooms/{room_id}/secret` 設定答案；openapi.yaml 為 `PUT /api/rooms/{room_id}/secret`
backend/改答案.feature：沒有任何 Rule 驗 skill_effect
```

### Good Example

這個範例找出前端特效依賴的推播，在後端補上可追溯到 AC-01 的 Rule 並登記；起點的方法與介面文檔不符，列入跨端點依賴缺口。

```markdown
backend/改答案.feature 補上：
  Rule: 改答案後，系統必須向雙方推播寫明技能與使用者角色、不含答案的特效事件
涵蓋表 AC 涵蓋表：| AC-01 | 1 | backend | `改答案.feature` | 改答案後，系統必須向雙方推播寫明技能與使用者角色、不含答案的特效事件 | ADD |
待確認事項「跨端點依賴缺口」：
- `frontend/dsl.md` 的 `系統處於 {前置狀態}`：以 `POST /api/rooms/{room_id}/secret` 設定答案，openapi.yaml 為 `PUT`
```

### Bad Example

這個範例只核對 dsl.md 有寫出名稱的 API，前端 dsl.md 沒寫 `skill_effect` 就判定沒有依賴；前端特效的 Rule 沒有任何後端 Rule 驅動推播，前端綠燈會因為後端從未實作推播而停下。

```markdown
跨端點依賴：frontend/dsl.md 用到的 API（`GET /api/me/room`、`POST /api/rooms/{room_id}/guesses`）在 backend 都有 Rule → 無缺口
```
