# 異動判斷規範

## Rule 1 -- 依差異時只把連帶異動列入範圍

**強度：MUST**

check 回報 dsl-refine 有紀錄且是待補跑、被交辦修正（dev-finding 回覆的應修正的擁有者是 dsl-refine，或 implement、bdd 交來的問題），或目標是技術修正 plan 時，這次的差異只有 check 的 `self.changes`、交辦內容，以及 `技術項.md` 中「修正：dsl-refine」的行。每個差異都要判斷「連帶異動」並寫出要改的 Rule、句型或用語表項目，或「不受影響」並寫出理由：AC 的差異依 plan_cases.py diff 對應的 Rule 判斷；需求的差異對照涵蓋表補充案例登記的需求編號；介面文檔、上游 truth 異動與 plan.md 介面列的差異，以它的識別碼（介面 ID、testid、API 路徑、欄位、錯誤碼、資料表）搜尋 dsl.md、feature 與用語表的引用處判斷，UI 契約的 MOD 一節另以它修改的先前 plan 介面 ID（例如 002/UI-01）搜尋引用改變部分的地方；技術項與交辦點名的 Rule 或句型直接列入，點名的是被取代的舊編號（例如以本 plan 的研究決策取代已交付 plan 的 002/R-08，或以新的介面 ID 取代已交付 plan 的 UI 介面）時，以舊編號搜尋 dsl.md、feature 與用語表，引用它的每一處都列入。範圍以外的 Rule、Example、句型與用語表項目不得改寫；AC 沒有變時，不得重新衍生任何 AC 的 Rule。以下 Example 皆對照此 check 結果、上游異動與 dsl.md：

```json
{"self": {"owner": "dsl-refine", "recorded": true, "pending": true, "changes": [
  {"status": "MOD", "unit": "truth:contracts/components/schemas/SkillCounts.yaml"},
  {"status": "MOD", "unit": "plan:truth-changes.md＞api-plan"},
  {"status": "MOD", "unit": "plan:plan.md＞API-03"}]}}
```

```text
api-plan 的表格：| MOD | `contracts/components/schemas/SkillCounts.yaml` | `change_answer_left` 的型別由字串改為整數 | 技術：契約的型別與程式不一致 |
plan.md：API-03 的依據需求補上 NFR-012，介面與異動不變
frontend/dsl.md 的「雙方畫面顯示下列技能剩餘次數：」：再讀確認以整數比較 `state.skills.mine.change_answer_left` 與表格
backend/dsl.md 的「雙方的技能剩餘次數如下：」：回應斷言把 `change_answer_left` 當字串與表格比較
```

### Good Example

這個範例逐項判斷三個差異，以欄位名稱找出兩個引用處，只把以字串比較的後端句型列入範圍，其他 Rule 與句型不動。

```markdown
| 差異 | 判斷 | 說明 |
|---|---|---|
| MOD `contracts/components/schemas/SkillCounts.yaml` | 連帶異動 | `backend/dsl.md` 的句型「雙方的技能剩餘次數如下：」改為以整數比較；`frontend/dsl.md` 的句型「雙方畫面顯示下列技能剩餘次數：」本來就以整數比較，不受影響 |
| MOD `truth-changes.md` ＞ api-plan | 連帶異動 | 同上一列，api-plan 記錄的就是這個型別 |
| MOD `plan.md` ＞ API-03 | 不受影響 | 只補依據需求，介面的行為與欄位不變，沒有 Rule 或句型引用依據需求 |
```

### Bad Example

這個範例看到契約變了就依目前的 acceptance 重新規劃全部端點，先前 plan 留下的 Rule 被改寫成另一種說法，truth-changes 多出這次的差異沒有要求的修改，task 會為沒有變的行為排紅燈。

```text
dsl-refine 待補跑：重新執行完整流程，委派 frontend、backend、database 三個 sub-agent 依目前的 acceptance 重寫所有 feature 與 dsl.md。
```

## Rule 2 -- 技術修正 plan 只依點名的技術項修正

**強度：MUST**

check 回報種類為「技術修正」時，plan 本來就沒有 spec.md、acceptance、plan.md 與 wave-report.md，不得因此要求使用者先補上；範圍只有 `技術項.md` 中「修正：dsl-refine」的行點名的 Rule、句型與用語表項目，端點資料夾沿用 `specs/truth/features/` 既有的，只委派範圍涉及的資料夾。truth-changes 的原因寫「技術：」加該技術項的問題。涵蓋表仍依樣板撰寫：AC 的兩張表只留表頭，技術項新增或修改的 Rule 登記在「補充案例」，來源需求寫同一個原因。以下 Example 皆對照此技術修正 plan：

```text
plan：005-dsl-cleanup（種類 技術修正），沒有 spec.md、features/acceptance/、plan.md 與 wave-report.md
技術項.md：
- `specs/truth/features/用語表.md` 的參數合法值「改答案」「連猜三次」的意義重述 002/FR-028 的每局 1 次（使用者；`specs/truth/features/用語表.md:41` 與 `:42`；修正：dsl-refine）
- `specs/truth/features/backend/連猜三次.feature` 的 Rule「三次內猜中時必須立刻結束」有一個 Example 含兩句 When（使用者；check_features.py 的 multi_when；修正：dsl-refine）
```

### Good Example

這個範例不要求 acceptance 與 plan.md，只改兩行點名的用語表項目與 Rule、只委派 backend，原因寫技術項的問題，拆開 When 的 Rule 登記在涵蓋表的補充案例。

```markdown
truth-changes：
| MOD | `features/用語表.md` ＞ 參數合法值 `{技能}` | 只改說明：「改答案」「連猜三次」的意義刪除「每局 1 次」，改寫使用次數依 002/FR-028 | 技術：用語表的參數合法值「改答案」「連猜三次」的意義重述 002/FR-028 的每局 1 次 |
| MOD | `features/backend/連猜三次.feature` ＞ Rule「三次內猜中時必須立刻結束」 | 含兩句 When 的 Example 拆成兩個各一句 When 的 Example，斷言不變 | 技術：backend/連猜三次.feature 的 Rule「三次內猜中時必須立刻結束」有一個 Example 含兩句 When |

涵蓋表「補充案例」：
| 技術：backend/連猜三次.feature 的 Rule「三次內猜中時必須立刻結束」有一個 Example 含兩句 When | backend | `連猜三次.feature` | 三次內猜中時必須立刻結束 | MOD |
```

### Bad Example

這個範例因為技術修正 plan 沒有 acceptance 就停下，要使用者先執行 spec-by-example 與 system-analysis，點名 dsl-refine 的技術項沒有人修，這個 plan 也無法交付。

```text
缺少 features/acceptance/、plan.md 與 wave-report.md，請先執行 spec-by-example 與 system-analysis 後再繼續。
```

## Rule 3 -- 技術修正 plan 不得改變 PM 看得到的行為

**強度：MUST**

技術修正 plan 的修改只能改測試的寫法、說明、引用與結構（句型、Example 的拆分、Background、用語表的文字，以及陳述同一條規則的 Rule 名稱，例如把寫進名稱的文案換成它的意思），不得改變 Rule 陳述的規則，也不得改變 Example 驗證的、使用者看得到的結果（畫面、訊息、操作結果）。技術項要求這類修改時，不修改那一項，這次的結果是「不能改」：寫出擋住的技術項與「技術修正 plan 不得改變 PM 看得到的行為」，交給使用者以有需求的 plan 處理。以下 Example 皆對照此技術項：

```text
- `specs/truth/features/frontend/改答案.feature` 的 Rule「改答案次數用完後不能再改答案」的停用說明寫「本局次數已用完」，與 002 ui-contract.md 的 UI-01 文案「這局的改答案已經用完」不同（使用者；`specs/truth/features/frontend/改答案.feature:88`；修正：dsl-refine）
```

### Good Example

這個範例看出修改會換掉玩家看到的停用說明，不修改 feature，回報不能改並交給使用者。

```text
不能改：技術項要把 frontend/改答案.feature 的停用說明由「本局次數已用完」改為 UI 契約的文案，會改變玩家看到的訊息，技術修正 plan 不得改變 PM 看得到的行為。
交給：使用者以 /specify 開立有需求的 plan，由 PM 決定採用哪一句文案。這次沒有記錄，dsl-refine 仍是待補跑。
```

### Bad Example

這個範例在技術修正 plan 直接把 Example 的停用說明換成 UI 契約的文案並記錄改了，PM 核准過的文案在沒有人決定的情況下被換掉，task 依它排出改畫面文字的任務。

```markdown
| MOD | `features/frontend/改答案.feature` ＞ Rule「改答案次數用完後不能再改答案」 | 停用說明由「本局次數已用完」改為「這局的改答案已經用完」 | 技術：frontend/改答案.feature 的停用說明與 002 ui-contract.md 的 UI-01 文案不同 |
```

## Rule 4 -- 合併重複的句型保留 step 已實作的寫法

**強度：MUST**

兩個句型代入合法值後會同時符合同一句、而且測試撰寫語意相同時，合併成一個句型：保留 step 目錄中既有 step definition 已經註冊的那一個寫法（含它的參數名稱），刪除另一列，Step 檔對照只留保留的句型，其他句型的測試撰寫語意（例如「保存 → 給…」）與用語表「共用句子」中引用被刪句型的地方一併改為保留的句型；feature 的步驟同時符合兩者時不改步驟。測試撰寫語意不同時不得合併，改依句型收斂規範修改其中一個句型的固定文字。保留的句型記一列 MOD，摘要以「只改說明：」開頭並寫出併入的句型；被併入的句型記一列 DEL，寫出併入哪一個與步驟要不要改。以下 Example 皆對照此 dsl.md、既有 step 與 feature：

```text
frontend/dsl.md：`進入第 {數字} 輪，輪到玩家 {玩家} 猜測` 與 `進入第 {輪次} 輪，輪到玩家 {玩家} 猜測` 兩列的測試撰寫語意相同，Step 檔對照兩者都登記在 `modules/對戰/猜測.js`
frontend/tests/e2e/steps/modules/對戰/猜測.js：Then("進入第 {數字} 輪，輪到玩家 {玩家} 猜測", …)；參數型別只註冊了 {數字}
feature：互猜對戰.feature、改答案.feature、連猜三次.feature 共 4 個步驟（例如「進入第 2 輪，輪到玩家 "甲" 猜測」）同時符合兩列
```

### Good Example

這個範例保留 step 已註冊的 `{數字}`，刪除 `{輪次}` 那一列並從 Step 檔對照移除，步驟與 step 都不用改，保留的句型記為只改說明，task 會讓用到它的 4 個 Example 重新執行。

```markdown
| MOD | `features/frontend/dsl.md` ＞ 句型「進入第 {數字} 輪，輪到玩家 {玩家} 猜測」 | 只改說明：併入測試撰寫語意相同的「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」，原本同時符合兩列的 4 個步驟改由這一列比對 | 技術：frontend/dsl.md 的兩個句型意思相同，有 4 個步驟同時符合 |
| DEL | `features/frontend/dsl.md` ＞ 句型「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」 | 併入「進入第 {數字} 輪，輪到玩家 {玩家} 猜測」，feature 的步驟不用改 | 技術：frontend/dsl.md 的兩個句型意思相同，有 4 個步驟同時符合 |
```

### Bad Example

這個範例保留 step 沒有註冊的 `{輪次}`，step definition 的寫法與參數型別都要改，原本只要重新執行的 4 個 Example 變成要重做紅燈；紀錄只寫一列刪除，task 以為用到它的 Example 都已改寫，找不到要重新驗證的 Example。

```markdown
| DEL | `features/frontend/dsl.md` ＞ 句型「進入第 {數字} 輪，輪到玩家 {玩家} 猜測」 | 刪除重複的句型 | 技術：frontend/dsl.md 的兩個句型意思相同，有 4 個步驟同時符合 |
```

## Rule 5 -- 修改既有句型必須標明只改說明或改測試寫法

**強度：MUST**

修改 dsl.md 既有的句型列時，truth-changes 的對象寫成 `features/<端點>/dsl.md ＞ 句型「<句型>」`（句型的固定文字改了時寫改後的句型，摘要寫出原句型），改動摘要以下列其中一種開頭：「只改說明：」表示只改了說明、引用或參數名稱，依新的寫法既有的 step 不用改，例如把引用的舊編號改為取代它的新編號，而測試用到的內容沒有變；「改測試寫法：」表示動作、等待、保存或斷言的做法改了，step 要跟著改，例如取代舊編號的新決策改了測試用到的時限。拿不準既有 step 要不要改時寫「改測試寫法：」。修改 feature 的 Background、起點句上方的 `# 預設值：` 註解、dsl.md 的參數對照或用語表時，對象寫到該 Background、feature、參數對照的型別或用語表的節，摘要同樣以這兩種之一開頭。新增與刪除句型不加開頭。不得只寫「修改句型」或只以檔案為對象，也不得把 step 要改的修改寫成只改說明。以下 Example 皆對照此三個修改：

```text
1. frontend/dsl.md 的 `系統處於 {前置狀態}`：刪除說明中重述需求數值的「新對局的雙方技能剩餘次數由後端給定為各 1 次」，建立對局的 API 與順序不變
2. backend/dsl.md 的 `雙方的技能剩餘次數如下：`：回應斷言由「`change_answer_left` 等於各列的字串」改為「等於各列的整數」
3. frontend/dsl.md 的 `玩家 {玩家} 的裝置無法播放特效`：引用的 002/R-08 已由 005/R-01 取代，兩者判定無法播放的條件相同
```

### Good Example

這個範例以句型為對象，第一列只刪說明、第三列只改引用的編號，既有 step 都不用改，task 只排重新執行；第二列改了斷言的比較方式，task 會為用到它的 Example 排紅燈。

```markdown
| MOD | `features/frontend/dsl.md` ＞ 句型「系統處於 {前置狀態}」 | 只改說明：刪除說明中重述需求數值的「新對局的雙方技能剩餘次數由後端給定為各 1 次」，建立對局的 API 與順序不變 | 技術：frontend/dsl.md 的起點句型說明重述 002/FR-028 的技能次數 |
| MOD | `features/backend/dsl.md` ＞ 句型「雙方的技能剩餘次數如下：」 | 改測試寫法：回應斷言的 `change_answer_left` 由字串比較改為整數比較 | 技術：契約的型別與程式不一致 |
| MOD | `features/frontend/dsl.md` ＞ 句型「玩家 {玩家} 的裝置無法播放特效」 | 只改說明：引用由 002/R-08 改為取代它的 005/R-01，判定無法播放的條件不變 | 技術：frontend/dsl.md 引用被 005/R-01 取代的 002/R-08 |
```

### Bad Example

這個範例以檔案為對象、摘要沒有標明是哪一種修改，task 分不出改了哪個句型、step 要不要改，只能為整個前端資料夾用到任何句型的 Example 全部排紅燈。

```markdown
| MOD | `features/frontend/dsl.md` | 修改起點句型的說明 | 技術：frontend/dsl.md 的起點句型說明重述 002/FR-028 的技能次數 |
```
