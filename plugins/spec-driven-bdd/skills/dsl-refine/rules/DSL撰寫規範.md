# DSL 撰寫規範

## Rule 1 -- 每份 dsl.md 必須能單獨讀懂

**強度：MUST**

每個端點一份 dsl.md，只收該端點 feature 用到的句型。兩個端點都用到的句型，各自寫一列完整內容，依各自的測試層寫測試撰寫語意；不得寫「同後端」或連到其他端點的 dsl.md。

### Good Example

這個範例在前端與後端各寫一列，兩列的測試撰寫語意依各自的測試層撰寫。

```markdown
frontend/dsl.md：
| `刪除照片 {照片}` | … | … | 不支援 | 動作：在 `photo-tile` 中點該照片的 `photo-delete` 並在 `confirm-dialog` 點確認<br>等待：該照片的 `photo-tile` 消失 |

backend/dsl.md：
| `刪除照片 {照片}` | … | … | 不支援 | 動作：`DELETE /api/photos/{photoId}`<br>保存：回應 → 給「相簿 {相簿} 有 {張數} 張照片」 |
```

### Bad Example

這個範例在前端只寫「同後端」，寫前端測試的人被導向直接打 API，畫面上的刪除按鈕與確認對話框完全沒有被測到。

```markdown
frontend/dsl.md：
| `刪除照片 {照片}` | … | … | 不支援 | 同 backend/dsl.md |
```

## Rule 2 -- 範例句必須逐字出現在 feature

**強度：MUST**

範例欄以 `{}` 標出被替換的部分，拿掉大括號後必須與 feature 中某一句完全相同；句型改了或 feature 改了值，範例要一起改。

### Good Example

這個範例拿掉大括號後，就是 feature 中「以不同檔名匯入與 P1 相同內容的照片」那個 Example 的一句。

```markdown
| `以檔名 {檔名} 匯入與 {照片} 相同內容的照片` | 以檔名 {"P1-副本.jpg"} 匯入與 {"P1"} 相同內容的照片 | … |
```

### Bad Example

這個範例的值在 feature 裡從沒出現過，寫測試的人無法從範例找到對應的 Example 對照實際用法，也看不出這個句型是否還有人使用。

```markdown
| `以檔名 {檔名} 匯入與 {照片} 相同內容的照片` | 以檔名 {"test.jpg"} 匯入與 {"X"} 相同內容的照片 | … |
```

## Rule 3 -- 句型參數只寫型別與核心語意

**強度：MUST**

句型參數欄每個參數寫一行 `・**名稱** \`{型別}\`（字串／整數／小數）：核心語意`，多個參數以 `<br>` 分隔；不列出所有合法值，也不寫「列舉」。合法值有固定對照時寫在參數對照，不寫在這裡。

### Good Example

這個範例每個參數一行，只寫型別與它在句子中代表什麼。

```markdown
・**相簿** `{相簿}`（字串）：被移動的相簿<br>・**相簿** `{相簿}`（字串）：放在它之前的目標相簿
```

### Bad Example

這個範例把所有合法值列在參數欄，新增相簿時每個用到 `{相簿}` 的句型都要改，值也和參數對照表重複兩處。

```markdown
・**相簿**：列舉，A、B、C、2026年10月1日（星期四）、2026年10月2日（星期五）
```

## Rule 4 -- Data Table 參數必須宣告欄位

**強度：MUST**

Data Table 參數欄只能寫「不支援」；橫式表格逐欄寫 `・**欄位**（字串／整數，必填或選填）：語意`，選填欄位寫出沒寫時的預設值；直式表格寫 `直式表格，每一列是「欄位｜值」，欄位：A、B（沒寫的欄位如何處理）`。feature 中帶表格的步驟，表頭必須只用這裡宣告的欄位，而且包含所有必填欄位。

### Good Example

這個範例的橫式表格宣告兩個欄位的必填與選填，選填欄位寫出預設值；直式表格列出允許的欄位與沒寫時的處理。

```markdown
・**相簿**（字串，必填）：相簿名稱<br>・**照片數**（整數，選填）：沒寫時不檢查照片數
直式表格，每一列是「欄位｜值」，欄位：相簿名稱、照片數（只檢查有寫的欄位）
```

### Bad Example

這個範例只寫「表格」，沒有宣告欄位，寫測試的人不知道要讀哪些欄、哪些可以省略，feature 也可能出現任意表頭。

```markdown
表格：相簿資料
```

## Rule 5 -- 測試撰寫語意必須具體到可寫程式

**強度：MUST**

測試撰寫語意要寫到直接寫得出程式的程度：後端寫打哪個 API 與帶什麼，前端寫操作哪個 testid，資料庫寫以資料庫驅動直接寫入或查詢哪張表的哪些欄位，檔案系統寫以 fs 或擁有被測路徑與命名的儲存模組讀寫哪個路徑。儲存端點的動作不得呼叫產品 API、WebSocket、服務層，或含業務規則的 repository 方法（同時改多個欄位、依業務條件決定寫入內容的方法）。只寫容易做錯的決策點，不寫程式碼、SQL、例外處理或共用抽象。

### Good Example

這個範例的後端寫明 API、上傳內容與容易做錯的地方；資料庫端寫明以資料庫驅動直接寫哪張表、哪些欄位與預期觸發的約束，都沒有程式碼。

```markdown
backend：動作：`POST /api/photos`，以 multipart 上傳與該照片位元組完全相同、但檔名不同的檔案（檔名不得影響判斷）
database：動作：以 pymysql 直接新增一筆 `photos`，`content_hash` 與已存在的照片相同，其他欄位取合法值；預期被 `uk_photos_hash` 拒絕，攔截錯誤
```

### Bad Example

這個範例的後端寫成程式碼，換測試框架就得重寫 DSL，真正容易做錯的「位元組要完全相同」反而沒有寫出來；資料庫端呼叫服務層，驗到的是匯入流程而不是唯一索引，索引漏建時服務自己的重複檢查也會讓測試通過。

```markdown
backend：動作：`const res = await request(app).post('/api/photos').attach('file', buf, name); ctx.res = res;`
database：動作：`photoService.importPhoto`，重複時由服務回傳 duplicate
```

## Rule 6 -- Given 與 When 寫成動作、等待、保存

**強度：MUST**

Given 與 When 的測試撰寫語意依序寫「動作：」「等待：」「保存：」，沒有等待或保存時省略該項。保存必須寫成「存什麼 → 給哪一句 Then 讀」，沒有 Then 會讀的資料不寫。一組 When 有多個動作時，只有最後一個動作保存回應給 Then；前面的動作不攔截錯誤，失敗就讓測試直接失敗。只有預期會被拒絕的動作才攔截並保存錯誤，成功路徑的動作不得把錯誤存起來留給 Then 判斷。

### Good Example

這個範例寫出動作、要等的畫面，以及存下的資料給哪一句 Then 使用。

```markdown
動作：在主頁把相簿卡片 `album-card` 拖放到目標卡片之前<br>等待：卡片順序改變<br>保存：送出的請求 → 給「系統收到 {次數} 次移動相簿的要求」
```

### Bad Example

這個範例只寫「保存：回應」，沒說存什麼、給誰讀，寫 Then 的人只能猜資料放在哪裡、叫什麼名字。

```markdown
動作：拖放相簿<br>保存：回應
```

## Rule 7 -- Then 每列同時寫回應斷言與查證斷言

**強度：MUST**

Then 的測試撰寫語意依序寫「回應斷言：」與「查證斷言：」。查證斷言標明管道（權威狀態、再讀確認、跨視角、不該發生），只寫 1 到 2 個管道，讀取的位置不得與回應斷言相同；資料庫端的查證一律開新的連線查詢，確認資料已經提交。只有一種斷言時，另一種寫成「無，因為<理由>」。查證需要先做動作時，在管道下先寫「動作：」再寫要驗的結果，並寫明這個動作不算進這次操作、不更新回應。

### Good Example

這個範例第一列是後端，回應讀這次請求的回應，查證以雙方身份重新查詢；第二列是資料庫，回應讀攔截到的約束錯誤，查證開新連線查資料表。

```markdown
| `雙方的技能剩餘次數如下：` | … | … | … | 回應斷言：狀態碼 200，回應 `state.skills` 的 `change_left`、`burst_left` 等於各列<br>查證斷言：<br>・再讀確認：雙方各以自己的身份 `GET /api/me/room`，`state.skills` 同名欄位等於各列 |
| `資料庫拒絕這次寫入，因為 {原因}` | … | … | … | 回應斷言：攔截到的錯誤是 `ck_rooms_skill_counts` 的檢查約束錯誤，沒有錯誤或其他錯誤都算失敗<br>查證斷言：<br>・權威狀態：開新的資料庫連線查 `rooms`，該玩家該技能的剩餘次數仍為寫入前的值 |
```

### Bad Example

這個範例的資料庫查證沿用寫入時的同一個連線，同一個連線看得到自己還沒提交的資料，寫入其實沒被拒絕、只是還沒提交時測試照樣通過。

```markdown
| `資料庫拒絕這次寫入，因為 {原因}` | … | … | … | 回應斷言：攔截到的錯誤是 `ck_rooms_skill_counts` 的檢查約束錯誤<br>查證斷言：<br>・權威狀態：以寫入時的同一個連線查 `rooms`，該玩家該技能的剩餘次數仍為寫入前的值 |
```

## Rule 8 -- 參數對照只放查不到的共用對照

**強度：MUST**

型別同時符合三個條件才放進參數對照：業務用詞對到的技術值在介面文檔查不到（例如中文錯誤原因對到狀態碼與錯誤代碼）、值是封閉集合、dsl.md 中有三列以上句型使用（以 dsl.md 的句型列數計算，不是 feature 中出現的次數）。測試資料本身（例如猜測的四碼、照片檔）、一句話就能說明的換算（例如秒換毫秒）、介面文檔已有的對應（testid、API 路徑）都不放，介面文檔已有的對應在該列寫「依 <文檔名稱>」。對照表只列本端點 feature 用到的值，每個值的對應必須明確，不得寫「通常」「大致」。沒有任何型別符合條件時，刪除整個「參數對照」段落，不留標題與說明。以下 Example 皆對照此後端 dsl.md 的使用情形：

```text
{原因}：重複的照片、不支援的格式，4 列句型使用，介面文檔只有錯誤代碼、沒有中文原因
{格式}：JPEG、PNG、HEIC，1 列句型使用
{照片}：P1、P3，測試資料
```

### Good Example

這個範例只把 `{原因}` 放進參數對照，`{格式}` 只有一列使用、`{照片}` 是測試資料，都寫在該列。

```markdown
### `{原因}`

| 值 | 狀態碼與 `code` |
|---|---|
| 重複的照片 | 409 `duplicate_photo` |
| 不支援的格式 | 415 `unsupported_format` |
```

### Bad Example

這個範例把測試資料與只有一列使用的格式也做成對照表，每個值的「對應」都沒有技術資訊，dsl.md 變長，寫測試的人也得不到任何幫助。

```markdown
### `{照片}`

| 值 | 對應 |
|---|---|
| P1 | 照片 |
| P3 | 照片 |

### `{格式}`

| 值 | 對應 |
|---|---|
| JPEG | 格式 |
| PNG | 格式 |
| HEIC | 格式 |
```

## Rule 9 -- 每一列必須寫完整

**強度：MUST**

每一列的五個欄位都要寫出該句型自己的內容，不得寫「同上」「同 XX 句型」或留空；參數對照表除外。

### Good Example

這個範例的兩個相近句型各自寫完整的測試撰寫語意。

```markdown
| `刪除照片 {照片}` | … | … | 不支援 | 動作：`DELETE /api/photos/{photoId}`<br>保存：回應 → 給「系統回覆…」 |
| `刪除相簿 {相簿} 的唯一照片` | … | … | 不支援 | 動作：先 `GET /api/albums/{albumId}/photos` 取得唯一照片，再 `DELETE /api/photos/{photoId}`<br>保存：回應 → 給「系統回覆…」 |
```

### Bad Example

這個範例的第二列寫「同上」，寫測試的 AI 只讀這一列時不知道要先查出唯一照片，可能直接以相簿 id 呼叫刪除。

```markdown
| `刪除照片 {照片}` | … | … | 不支援 | 動作：`DELETE /api/photos/{photoId}` |
| `刪除相簿 {相簿} 的唯一照片` | … | … | 不支援 | 同上 |
```

## Rule 10 -- 起點句只寫建立規則

**強度：MUST**

建立起點的起點句，測試撰寫語意必須寫「只寫在 Background 或 Example 的第一句 Given」，參數說明列出本端點允許的起點名稱；內容寫「依該 feature 起點句上方的 `# 預設值：` 註解建立」，acceptance 的起點與端點自訂的起點都一樣：feature 的預設值註解是 truth 中起點內容的家，acceptance 屬於 plan、交付後就是歷史紀錄，不得指向它；不得在 DSL 再列一次每個狀態的內容。前端的起點依前端測試規範寫明以 API 建立與開啟的瀏覽器情境。

### Good Example

這個範例只寫建立規則與允許的名稱，狀態內容交給該 feature 的預設值註解；第二列是前端，寫明以 API 建立後開兩個瀏覽器情境。

```markdown
| `系統處於 {前置狀態}` | 系統處於 {"對戰開始輪到甲"} | ・**前置狀態** `{前置狀態}`（字串）：起點名稱，只限 對戰開始輪到甲 | 不支援 | 動作：只寫在 Background 或 Example 的第一句 Given。在測試行程內建立應用程式並清空測試資料庫，依該 feature 起點句上方的 `# 預設值：` 註解以 API 建立對局；其他狀態由 Example 的差異句推進 |
| `系統處於 {前置狀態}` | 系統處於 {"對戰開始輪到甲"} | ・**前置狀態** `{前置狀態}`（字串）：起點名稱，只限 對戰開始輪到甲 | 不支援 | 動作：只寫在 Background 或 Example 的第一句 Given。後端與 MySQL 已實際啟動；先 `POST /api/test/reset`，依該 feature 起點句上方的 `# 預設值：` 註解以 API 建立對局，再為甲、乙各開一個瀏覽器情境進入對戰畫面<br>等待：兩個情境的 `game-board` 出現 |
```

### Bad Example

這個範例在 DSL 重抄狀態內容，acceptance 調整起點的祕密答案時，兩處內容不一致，寫測試的人不知道該信哪一份。

```markdown
| `系統處於 {前置狀態}` | … | … | 不支援 | 動作：建立狀態。對戰開始輪到甲＝甲答案 0123、乙答案 5678、第 1 回合輪到甲；雙方各猜兩次＝再猜 1234、0132、1357、3210… |
```

## Rule 11 -- 推測的技術對應必須標擬定

**強度：MUST**

測試撰寫語意或句型參數中的技術對應（API 欄位、testid、等待上限、量測輸出格式、測試工具的用法），在介面文檔、acceptance 與 techstack.md 都查不到、由撰寫者自行推測時，必須緊接在該對應後面標「（擬定）」；有來源的不標。標了擬定的對應都要列出：家在 dsl.md 的（等待上限、量測輸出格式、測試工具的用法）列入回報的「推測的技術對應」；家在介面文檔的（testid 在 UI 契約，API 的路徑、欄位、錯誤碼與推播事件在契約，資料表、欄位與約束在資料模型）列入回傳的「上游的事實問題」，交回該文檔的擁有者。

### Good Example

這個範例的 `lightbox` 出自 ui-contract.md，不標；關閉按鈕的 testid 在介面文檔查不到，標了擬定，並因為 testid 的家是 UI 契約而列為上游的事實問題。

```markdown
動作：點選 `photo-tile` 的第 N 個<br>等待：`lightbox` 出現
回應斷言：`document.activeElement` 是 `lightbox-close`（擬定）

上游的事實問題：`frontend/dsl.md` 的「開啟照片 {照片}」用到 ui-contract.md 沒有的 testid `lightbox-close`（擬定），testid 的家是 UI 契約
```

### Bad Example

這個範例自行推測了關閉按鈕的 testid 卻沒有標示，寫測試的人以為它出自介面文檔，照抄後找不到元素，review 的人也無從得知要確認哪一處。

```markdown
回應斷言：`document.activeElement` 是 `lightbox-close`
```

## Rule 12 -- 每個句型登記一個 Step 檔

**強度：MUST**

dsl.md 最後的「Step 檔對照」必須涵蓋本份所有句型，每個句型只出現在一列。模組欄填用語表「模組」段的模組名稱，或填 `shared`；句型依它操作或查證的領域物件歸屬模組，不依使用它的 feature 歸屬，只有不屬於任何模組領域的句型（起點句、時鐘）才填 `shared`。能力用繁體中文短名，只能包含中文字、英文字母、數字與底線，不得含空白或標點符號。Step 檔寫相對於委派簡報列出的本端點 step 目錄（專案測試設定載入本端點 step 的目錄）的路徑：模組句型為 `modules/<模組名稱>/<能力>.<副檔名>`，shared 句型為 `shared/<能力>.<副檔名>`，副檔名依 techstack.md 的測試語言；句型已有 step 實作時（dsl.md 既有的列，或 step 目錄中既有的 step definitions），Step 檔填它已在的檔案，不另開一份。以下 Example 皆對照此後端 dsl.md 的句型、用語表模組段與既有 step：

```text
句型：系統處於 {前置狀態}、匯入拍攝於 {日期} 的照片 {照片}、系統回覆照片已新增、查詢相簿列表、共有 {相簿數} 本相簿
模組：相簿、照片；測試語言 JavaScript
step 目錄既有：shared/系統狀態.js 已實作「系統處於 {前置狀態}」；modules/相簿/列表.js 已實作「共有 {相簿數} 本相簿」
```

### Good Example

這個範例的五個句型各登記一次；相簿列表的查詢與斷言操作相簿，即使匯入照片的 feature 也使用，仍歸相簿，也正是既有 step 所在的檔案；起點句不屬於任何領域，歸 shared 的既有檔案；模組與能力都是繁體中文。

```markdown
| 模組 | 能力 | Step 檔 | 句型 |
|---|---|---|---|
| shared | 系統狀態 | `shared/系統狀態.js` | `系統處於 {前置狀態}` |
| 照片 | 匯入 | `modules/照片/匯入.js` | `匯入拍攝於 {日期} 的照片 {照片}`<br>`系統回覆照片已新增` |
| 相簿 | 列表 | `modules/相簿/列表.js` | `查詢相簿列表`<br>`共有 {相簿數} 本相簿` |
```

### Bad Example

這個範例漏登「查詢相簿列表」，又因為匯入照片的 feature 用到相簿數查詢就把它歸到照片，寫 step 的人不知道漏登的句型該放哪裡；相簿數的句子已實作在 `modules/相簿/列表.js`，卻登記到照片模組，寫 step 的人會在照片模組再實作一份，同一句註冊兩次而無法執行。

```markdown
| 模組 | 能力 | Step 檔 | 句型 |
|---|---|---|---|
| shared | 系統狀態 | `shared/系統狀態.js` | `系統處於 {前置狀態}` |
| 照片 | 匯入 | `modules/照片/匯入.js` | `匯入拍攝於 {日期} 的照片 {照片}`<br>`系統回覆照片已新增`<br>`共有 {相簿數} 本相簿` |
```

## Rule 13 -- 前端測試撰寫語意寫瀏覽器情境與定位

**強度：MUST**

`frontend` 的 Given 與 When 測試撰寫語意必須寫出在哪位參與者的瀏覽器情境執行、操作哪個 testid（依 ui-contract.md）與等待哪個畫面變化；Then 寫出在哪個情境讀取哪個區塊，跨視角的查證寫明讀另一個情境。注入故障的句型以「注入故障：」開頭。不得寫成元件渲染、假 API 或請求紀錄。

### Good Example

這個範例寫明情境、testid 與等待，跨視角寫明讀另一位玩家的情境。

```markdown
| `{玩家} 送出新答案 {四碼}` | {"甲"} 送出新答案 {"4567"} | ・**玩家** `{玩家}`（字串）：在誰的情境操作<br>・**四碼** `{四碼}`（字串）：新答案 | 不支援 | 動作：在該玩家的情境於 `change-answer-input` 輸入四碼並點 `change-answer-submit`<br>等待：該情境的 `skill-effect` 播放結束 |
| `{玩家} 的畫面看不到 {玩家} 的新答案與舊答案` | {"乙"} 的畫面看不到 {"甲"} 的新答案與舊答案 | ・**玩家** `{玩家}`（字串）：讀誰的畫面<br>・**玩家** `{玩家}`（字串）：被改答案的玩家 | 不支援 | 回應斷言：在第一位玩家的情境，整頁文字不包含第二位玩家的新舊答案<br>查證斷言：<br>・跨視角：第二位玩家的情境 `current-answer` 顯示新答案（確認答案確實存在而不是沒有更新） |
```

### Bad Example

這個範例寫成元件渲染與請求紀錄，與前端測試規範要求的真實後端執行方式矛盾，step definition 依這一列寫出來的測試根本不會開瀏覽器。

```markdown
| `{玩家} 送出新答案 {四碼}` | {"甲"} 送出新答案 {"4567"} | … | 不支援 | 動作：`render(<ChangeAnswerDialog />)` 後 `fireEvent.submit`<br>保存：假 API 收到的請求 → 給「系統收到…的要求」 |
```

## Rule 14 -- dsl.md 只描述現況，引用編號必須帶 plan 前綴

**強度：MUST**

dsl.md 是全專案共用的一份，標題與內容只描述系統現在的句型，不得寫「本功能」「這次新增」「沿用 002」這類只在某個 plan 才成立的說法。測試撰寫語意引用 plan 的決策、需求或介面編號時，必須寫成 `<plan 編號>/<編號>`，例如 `002/R-08`。

### Good Example

這個範例的標題不帶功能名稱，引用的研究決策與 UI 介面都寫出所屬的 plan。

```markdown
# 前端 DSL

| `{玩家} 的畫面播放 {技能} 的特效` | … | … | 不支援 | 回應斷言：在該玩家的情境 `skill-effect` 出現並顯示技能名稱（依 002/UI-05）<br>查證斷言：<br>・跨視角：對手的情境在 2 秒內也出現 `skill-effect`（時限依 002/R-08） |
```

### Bad Example

這個範例的標題帶著某個 plan 的功能名稱，引用的編號沒有 plan 前綴；下一個 plan 也有自己的 R-08 與 UI-05，讀者無法知道這一列依據的是哪一份研究紀錄與 UI 契約。

```markdown
# 前端 DSL：對戰技能

| `{玩家} 的畫面播放 {技能} 的特效` | … | … | 不支援 | 回應斷言：本功能新增的 `skill-effect` 出現並顯示技能名稱（依 UI-05）<br>查證斷言：<br>・跨視角：對手的情境在 2 秒內也出現 `skill-effect`（時限依 R-08） |
```

## Rule 15 -- 不重述需求、UI 契約與起點的內容

**強度：MUST**

測試撰寫語意、句型參數與用語表只寫它們自己擁有的事實（句型、參數、測試的做法與決策點、測試的等待上限），不得重述需求的數值與規則（每局次數、字數上限、倒數秒數、輪數上限、勝負規則，包括只由其他端點驗證的數值），不得重抄 UI 契約的文案（標題、提示、按鈕、錯誤訊息與說明的文字），也不得重抄起點的預設值；要用到時以識別碼引用它的家：需求寫 `<plan>/FR-xxx`，文案寫 ui-contract.md 的 `<plan>/UI-xx` 與文案名稱或 testid，API 與資料寫契約、資料模型的路徑、欄位或約束名稱，起點內容寫「依該 feature 起點句上方的 `# 預設值：` 註解」。feature 步驟帶的值（參數、Data Table）是測試資料，在測試撰寫語意中以參數名稱指稱。以下 Example 皆對照此需求、UI 契約與 feature：

```text
002/FR-028：每位玩家每局有改答案與連猜三次各 1 次使用次數
002/UI-05 的文案「玩法說明 5」：每局各有 1 次「改答案」：輪到你時，可以在猜測前換掉自己的答案，之後同一輪仍可以猜。
frontend/改答案.feature：Then 雙方畫面顯示下列技能剩餘次數：（表格：甲 改答案 0、連猜三次 1）
```

### Good Example

這個範例的起點句只寫建立方式、不寫次數；玩法說明以介面 ID 與文案名稱引用；剩餘次數以表格的欄位比較；用語表的意義欄以需求編號引用使用次數。

```markdown
| `系統處於 {前置狀態}` | … | … | 不支援 | 動作：…依該 feature 起點句上方的 `# 預設值：` 註解以 API 開房、加入、設定答案、準備與開始，技能剩餘次數由開始遊戲的 API 給定，不另外寫入… |
| `玩家 {玩家} 看到玩法說明介紹改答案與連猜三次` | … | … | 不支援 | 回應斷言：該玩家情境的 `entry-howto` 第 5、6 項文字分別等於 ui-contract.md 002/UI-05 的「玩法說明 5」「玩法說明 6」… |
| `雙方畫面顯示下列技能剩餘次數：` | … | … | … | 回應斷言：動作者情境的 `skill-count-self`、`skill-count-opponent` 與表格的「改答案」「連猜三次」欄相同… |

用語表：| 改答案 | 換掉自己的祕密答案（使用次數依 002/FR-028） | frontend、backend |
```

### Bad Example

這個範例在起點句、玩法說明句與用語表重抄「各 1 次」與文案全文；需求改成每局 2 次或 ui-ux-plan 改寫文案時，這三處不會跟著改，測試照舊的數字與文案驗證，與核准的需求不一致，修正時還得逐一找出每個複本。

```markdown
| `系統處於 {前置狀態}` | … | … | 不支援 | 動作：…新對局的雙方技能剩餘次數由後端給定為各 1 次… |
| `玩家 {玩家} 看到玩法說明介紹改答案與連猜三次` | … | … | 不支援 | 回應斷言：…第 5 項文字為「每局各有 1 次「改答案」：輪到你時，可以在猜測前換掉自己的答案，之後同一輪仍可以猜。」… |

用語表：| 改答案 | 換掉自己的祕密答案，每局 1 次 | frontend、backend |
```
