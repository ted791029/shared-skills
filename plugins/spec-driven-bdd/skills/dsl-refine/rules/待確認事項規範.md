# 待確認事項規範

## Rule 1 -- 必須列出所有自行補上的內容

**強度：MUST**

回報必須逐項列出 acceptance 與 spec.md 沒有寫、由產生過程自行補上的內容，每項寫出 `端點/feature::Rule::Example 標題`、補了什麼與依據；沒有內容的類別寫「無」，不得省略該類別。

### Good Example

這個範例逐項寫出位置、補上的內容與依據，沒有的類別寫「無」。

```markdown
- 自補的資料：backend/改答案.feature::送出新答案後，雙方的技能剩餘次數必須同步更新::甲送出新答案 4567 補上乙的連猜三次剩 1 次（AC 表格只列改答案欄）
- 補上的查證斷言：frontend/改答案.feature::送出新答案後，畫面必須顯示新答案::甲送出新答案 4567 補上「重新開啟頁面後仍顯示 4567」（AC 只驗當下畫面）
- 只有一種斷言的句型：frontend 的「{玩家} 的猜測欄仍為 {四碼}」查證為無（猜測欄內容只存在該玩家的瀏覽器）；filesystem 的「{照片} 的 {檔案種類} 不在正式路徑」回應為無（`fileStore.removeFiles` 沒有回傳值）
- 隱含預設值：無
```

### Bad Example

這個範例只寫一句概括，使用者無法知道要去哪個 Example 確認、補了什麼，自補的資料可能與實際需求不符卻沒人發現。

```markdown
- 有部分資料與斷言是自行補上的，請檢查。
```

## Rule 2 -- 規格沒寫的行為交由 dev-finding，不自行補成 Rule

**強度：MUST**

feature 為了涵蓋規則而需要、但 spec.md 與 acceptance 都沒有寫的行為（追溯不到需求的失敗、邊界或分支），不得自行寫成 Rule 或 Example，也不得直接修改 spec.md、acceptance 或 plan.md。主 agent 委派 dev-finding 記錄；sub-agent 在回傳的「規格沒寫的行為」寫出位置、行為與依據，由主 agent 委派。依 dev-finding 的回覆處理：新增的 AC 依一般的 AC 衍生並登記到涵蓋表；判為直接修時，依回覆寫出的需求編號衍生（違反 AC 的依 AC 衍生，違反 FR、NFR 的寫成該編號的補充案例）。回報的「開發發現」逐項列出發現的內容、dev-finding 回覆的分類、新增的 AC 編號、技術項或被違反的需求編號，以及應修正的擁有者。

### Good Example

這個範例把 spec 沒寫的界限交由 dev-finding 記錄，再依新增的 AC 衍生，回報列出分類、AC 編號與應修正的擁有者。

```markdown
- FR-003 只寫「不符合四碼規則」，沒寫長度或字元不符（12、abcd）是否也算：PM 看得到的行為，dev-finding 新增 AC-07（`@開發發現`），已衍生 `backend/改答案.feature::不符合四碼規則的新答案必須被拒絕` 的 Outline，應修正的擁有者 dsl-refine
```

### Bad Example

這個範例自行把 12、abcd 寫進 Outline，只在回報建議使用者修改 spec；這兩個案例沒有任何 AC 或需求可追溯，PM 沒有機會在拆任務前看到它們，實作者卻要為它們寫程式。

```markdown
- 建議加到 spec 或 acceptance：FR-003 加入「12、abcd 等長度或字元不符也視為不符四碼規則」，feature 已以 Outline 涵蓋 1123、12、abcd
```

## Rule 3 -- 增量衝突必須並列兩邊內容

**強度：MUST**

這次的異動遇到使用者手改過的 Example 時，回報必須並列這次的變更（AC 變更前後的原文，或盤點列出的修改）與目前的 Example 內容，並寫明這個 Example 沒有被修改，請使用者決定保留哪一邊。

### Good Example

這個範例並列兩邊內容並寫明未修改，使用者可以直接決定。

```markdown
- 增量衝突：backend/改答案.feature::不符合四碼規則的新答案必須被拒絕::甲送出新答案 1123（未修改）
  - acceptance：AC-02 第 1 組「送出新答案 "1123"」→「送出新答案 "12"」
  - 目前的 Example（手改過）：When "甲" 送出新答案 "11234"
```

### Bad Example

這個範例只寫有衝突，使用者得自己翻 acceptance 與 feature 比對差異，也不知道 Example 是否已被改動。

```markdown
- 增量衝突：改答案的四碼規則 Example，請確認。
```

## Rule 4 -- 補充案例必須與 AC 衍生分開列出

**強度：MUST**

回報的「補充案例」必須逐項列出來源需求編號、端點、feature 與 Rule，與 AC 衍生的 Example 分開；AC 涵蓋表只列 AC 衍生的 Example。沒有補充案例時寫「無」。

### Good Example

這個範例把補充案例獨立成一段，每項都有來源需求。

```markdown
### 補充案例

- FR-003：backend/改答案.feature::不符合四碼規則的新答案必須被拒絕
- FR-003：frontend/改答案.feature::不符合四碼規則的新答案必須被拒絕
- NFR-003：database/對戰紀錄.feature::明細查詢必須使用索引
```

### Bad Example

這個範例把補充案例混進 AC 涵蓋表，使用者以為 AC-02 要求了四碼規則的三種輸入，PM 沒審過的案例被當成驗收標準。

```markdown
| AC-02 | 1 | backend | 改答案 | 不符合四碼規則的新答案必須被拒絕（含 12、abcd） |
```

## Rule 5 -- 上游的事實錯了或缺了必須交回擁有者

**強度：MUST**

本 skill 只寫 `specs/truth/features/` 與 plan 的 `features/涵蓋表.md`；不論是否發現問題，都不得修改 acceptance、spec.md、plan.md 與介面文檔，連格式或補定位這類順手的修改也不例外。衍生需要的事實在上游錯了或缺了時，包括介面文檔或 plan.md 與 acceptance 不一致，以及 dsl.md 用到的識別碼在介面文檔查不到（testid 的家是 UI 契約，API 的路徑、欄位、錯誤碼與推播事件的家是契約，資料表、欄位與約束的家是資料模型），不得只在 dsl.md 標擬定或只列在待確認事項：主 agent 委派 dev-finding 以 record 記錄並取得應修正的擁有者（sub-agent 在回傳的「上游的事實問題」寫出位置、內容、依據與出錯的文檔，由主 agent 委派），回報的「開發發現」寫出應修正的擁有者。應修正的擁有者不是 dsl-refine 時，衍生照常依 AC 完成，但這次的結果是「不能改」：不記錄，寫出擋住的事實與應交給的擁有者，等擁有者改正後再執行。只有家在 dsl.md 的對應（測試的等待上限、量測輸出格式、測試工具的用法）可以只標擬定並列入「推測的技術對應」。以下 Example 皆對照此情境：

```text
1. sub-agent 回傳的上游的事實問題：frontend/dsl.md 的「玩家 {玩家} 取消連猜三次」用到 UI 契約沒有的 testid `triple-guess-cancel`（擬定）；本 plan 的介面盤點把該畫面標為「無」
2. AC-03 第 1 組「甲送出新答案後仍輪到甲」；`contracts/paths/技能/api_rooms_{roomId}_skills_change-answer.yaml` 的 description 寫「回合轉移給對手」
3. frontend/dsl.md 的「雙方畫面在 1 秒內依序顯示下列猜測紀錄：」：從點擊送出開始計時、以最後一列出現為結束（擬定；acceptance 只寫 1 秒內，沒有寫量測的起訖點）
```

### Good Example

這個範例把前兩項交給 dev-finding，依回覆寫出 UI 契約與契約的擁有者，結果判為不能改、不記錄；第三項的家在 dsl.md，只列入推測的技術對應。

```markdown
### 推測的技術對應

- `frontend/dsl.md` 的 `雙方畫面在 1 秒內依序顯示下列猜測紀錄：`：從點擊送出開始計時、以最後一列出現為結束（acceptance 只寫 1 秒內，沒有寫量測的起訖點）

### 開發發現

- `frontend/dsl.md` 的「玩家 {玩家} 取消連猜三次」用到 UI 契約沒有的 testid `triple-guess-cancel`（擬定）：看不到的技術問題，已加入技術項，應修正的擁有者 ui-ux-plan
- AC-03 第 1 組「甲送出新答案後仍輪到甲」與改答案契約的「回合轉移給對手」衝突：直接修（違反 AC-03），不留紀錄，應修正的擁有者 api-plan

不能改：UI 契約缺 `triple-guess-cancel` 的定位（交 ui-ux-plan），改答案契約與 AC-03 衝突（交 api-plan）。這次沒有記錄，dsl-refine 仍是待補跑。
```

### Bad Example

這個範例只把 testid 列在推測的技術對應、只把衝突寫在對話裡就記錄改了；testid 只存在 dsl.md，下一個 plan 的 ui-ux-plan 讀不到它，契約也沒有人去改，測試照 AC 通過，交付時契約與程式互相矛盾。

```markdown
### 推測的技術對應

- `frontend/dsl.md` 的「玩家 {玩家} 取消連猜三次」：testid `triple-guess-cancel`（UI 契約沒有列出）

### AC 與產物衝突

- AC-03 第 1 組「甲送出新答案後仍輪到甲」；改答案契約「回合轉移給對手」。衍生 Example 依 AC 撰寫

結果：改了，已記錄。
```
