# 前端測試規範

## Rule 1 -- 前端 feature 以 Playwright 對實際啟動的後端執行

**強度：MUST**

`frontend` 資料夾的 feature 以 techstack.md 的 Playwright 操作真實瀏覽器，後端與資料庫實際啟動並連通；不使用元件測試模式，也不以假 API 取代後端。dsl.md 起點句的測試撰寫語意必須寫明這個執行方式。

### Good Example

這個範例的起點句寫明後端實際啟動、以 API 建立資料後開瀏覽器，Example 操作的是整套系統。

```markdown
| `系統處於 {前置狀態}` | 系統處於 {"對戰開始輪到甲"} | … | 不支援 | 動作：只寫在 Background 或 Example 的第一句 Given。後端與 MySQL 已實際啟動；先 `POST /api/test/reset` 清空資料，再依該 feature 起點句上方的 `# 預設值：` 註解以 API 建立對局，最後為甲、乙各開一個瀏覽器情境進入對戰畫面 |
```

### Bad Example

這個範例以假 API 與元件渲染建立起點，Example 只驗到元件，前後端串接的錯誤在這份 feature 永遠測不到，與 AC 要驗收的整套流程脫節。

```markdown
| `系統處於 {前置狀態}` | 系統處於 {"對戰開始輪到甲"} | … | 不支援 | 動作：重設假 API 回傳對戰中的房間後 `mount(<GameBoard />)` |
```

## Rule 2 -- 起點以 API 建立，不走畫面

**強度：MUST**

起點與需要多步才能到達的前置狀態，以後端 API（含契約 `specs/truth/contracts/paths/測試輔助/` 的測試輔助端點，以路徑引用）直接建立，再開啟瀏覽器進入對應畫面；只有 Example 的 Given 差異句才在瀏覽器中以 When 句型操作。不得以一連串畫面操作建立起點。

### Good Example

這個範例的起點全部以 API 建立，重置資料以契約的測試輔助端點路徑引用，瀏覽器開啟時畫面已在對戰中。

```markdown
動作：`POST /api/test/reset`；以 API 依序開房（甲）、加入（乙）、雙方設定答案、準備、開始遊戲；為甲、乙各開一個瀏覽器情境並開啟對戰畫面<br>等待：兩個情境的 `game-board` 出現
```

### Bad Example

這個範例在瀏覽器中逐步點擊建立起點，每個 Example 多花十幾秒，首頁或準備畫面的小改動也會讓全部對戰 Example 的起點壞掉。

```markdown
動作：甲開啟首頁、輸入暗號、按開房；乙開啟首頁、輸入暗號、按加入；雙方輸入答案、按準備；甲按開始
```

## Rule 3 -- 每位參與者一個瀏覽器情境

**強度：MUST**

AC 中以名稱區分的參與者（甲、乙、房主、加入者）各開一個獨立的瀏覽器情境，各自保存身份；步驟中的參與者名稱決定在哪個情境執行動作或讀取畫面，「雙方畫面」的斷言在每個情境各讀一次。不得讓兩位參與者共用同一個情境或分頁。

### Good Example

這個範例依參與者名稱選情境，雙方畫面的斷言在兩個情境各讀一次。

```markdown
| `{玩家} 猜 {四碼}` | {"甲"} 猜 {"5679"} | … | 不支援 | 動作：在該玩家的瀏覽器情境中於 `guess-input` 輸入四碼並點 `guess-submit`<br>等待：該情境的 `guess-log` 多一列 |
| `雙方畫面顯示輪到 {玩家}` | 雙方畫面顯示輪到 {"乙"} | … | 不支援 | 回應斷言：動作所在情境的 `turn-indicator` 文字為該玩家<br>查證斷言：<br>・跨視角：另一個情境的 `turn-indicator` 文字也為該玩家 |
```

### Bad Example

這個範例用同一個分頁改寫身份來切換玩家，推播與連線狀態只剩一個，「雙方畫面同時更新」的規則根本沒有被測到。

```markdown
動作：在同一個分頁把 localStorage 的 token 換成乙的再重新整理
```

## Rule 4 -- 查證斷言用另一方畫面或重新查詢

**強度：MUST**

前端 Then 的查證斷言只從兩個管道挑：跨視角（另一位參與者的畫面，或重新開啟頁面後的畫面）、再讀確認（以 API 重新查詢）；不得以攔截到的請求紀錄作為查證。

### Good Example

這個範例以重新開啟頁面後的畫面查證答案真的被保存。

```gherkin
      When "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
      And "重新開啟頁面後"，"甲" 的畫面顯示目前答案 "4567"
```

### Bad Example

這個範例以攔截到的請求作查證，請求送出不代表後端接受了，答案沒被保存這個 Example 照樣通過。

```gherkin
      When "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
      And 系統收到 1 次更改答案的要求
```

## Rule 5 -- 只有真實後端做不出的失敗才注入故障

**強度：MUST**

網路中斷、回應逾時、伺服器錯誤這類真實後端在測試中做不出來的情況，才以 Playwright 的路由攔截注入故障，寫成 Given 差異句，dsl.md 在該句型的測試撰寫語意開頭標「注入故障：」。真實後端做得出來的拒絕（格式錯誤、狀態不符）一律讓後端實際回應，不得攔截。

### Good Example

這個範例只攔截「沒有回應」這種後端做不出來的情況，並標明注入故障。

```markdown
| `伺服器在 {玩家} 送出猜測時沒有回應` | 伺服器在 {"甲"} 送出猜測時沒有回應 | … | 不支援 | 注入故障：在該玩家的情境以 `page.route` 攔截 `POST /api/rooms/*/guesses`，不回應直到測試結束 |
```

### Bad Example

這個範例攔截了四碼規則的拒絕，後端本來就會回應這個錯誤，攔截後測的是攔截器而不是系統，後端把規則改壞了也測不到。

```markdown
| `伺服器以 {原因} 拒絕新答案` | 伺服器以 {"四碼規則不符"} 拒絕新答案 | … | 不支援 | 注入故障：`page.route` 攔截 `POST …/change-answer` 回 400 |
```

## Rule 6 -- 每個 Example 之間必須重設資料

**強度：MUST**

每個 Example 開始前透過測試重置端點，或使用獨立的房間、帳號等資料隔離，使 Example 之間不共享狀態、可以在多個 worker 平行執行；dsl.md 的起點句必須寫明重設方式。不得依賴 Example 的執行順序。

### Good Example

這個範例每個 Example 都先重置再建立自己的對局，平行執行也互不影響。

```markdown
動作：只寫在 Background 或 Example 的第一句 Given。每個 Example 先 `POST /api/test/reset`，再以 API 建立本 Example 自己的對局
```

### Bad Example

這個範例第二個 Example 假設第一個 Example 開的房間還在，單跑第二個或平行執行時起點不存在，測試隨機失敗。

```markdown
動作：沿用上一個 Example 建立的房間
```
