# 步驟與斷言規範

## Rule 1 -- 步驟與標題只寫業務語意

**強度：MUST**

Given、When、Then、Data Table 與 Examples 的儲存格、Rule 名稱、Example 標題與 feature 檔名，只寫使用者或產品負責人看得懂的業務語意，不得出現下列技術說法：API 路徑、HTTP 方法與狀態碼、testid、CSS 選擇器與 HTML 屬性（role、aria-*、value）、資料表、欄位與索引名稱、英文錯誤代碼、測試替身（假 API、假 WS）、請求與連線機制、身份與儲存機制（權杖、localStorage）、內部資料結構（快照）。秒、毫秒等時間限制是業務要求，可以寫。這些技術對應只寫在 dsl.md 的測試撰寫語意。

### Good Example

這個範例只寫業務動作與結果，`POST /api/rooms/{id}/skills/change-answer` 與回應欄位留給 dsl.md；「3 秒內」是使用者感受得到的時間要求，照寫。

```gherkin
      When "甲" 送出新答案 "4567"
      Then 系統回覆答案已更改
      And 雙方畫面在 3 秒內播完改答案特效
```

### Bad Example

這個範例把 API 路徑、回應欄位與 HTML 屬性寫進步驟，產品負責人讀不懂，改版 API 時 feature 也得跟著改，業務規則與實作綁在一起。

```gherkin
      When 呼叫 POST /api/rooms/{id}/skills/change-answer 帶 answer=4567
      Then 回應 200 且 skill_change_left 為 0
      And "特效區塊" 的屬性 "aria-busy" 為 "true"
```

## Rule 2 -- 步驟優先逐字沿用 AC 句型

**強度：MUST**

衍生 Example 中語意與 AC 某一句相同的步驟，逐字沿用 AC 的句子，只替換參數值；只有本端點讀不到 AC 所說的對象（例如後端讀不到畫面），或只有本端點能表達的動作與結果，或本端點 dsl.md 既有的句型已用另一句表達同一件事、或已把同一句用在另一件事時，才使用與 AC 不同的句型，並在涵蓋表「AC 句型對照」登記 AC 句型與本端點句型的對應；本端點沒有行為的步驟登記為「本端點不適用」。不得為同一件事另造一句與 AC 不同的說法，也不得在句首加「系統回覆中」「重新查詢後」這類讀取位置，讀取位置寫在 dsl.md 的回應與查證斷言。以下 Example 皆對照此 AC 句子：

```gherkin
      When "甲" 開啟改答案
      And "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
      And 雙方的猜測歷史依序為：
        | 回合 | 玩家 | 紀錄       |
        | 1    | 甲   | 使用改答案 |
```

### Good Example

這個範例的後端逐字沿用讀得到的猜測歷史句，只因讀不到畫面而把目前答案改成本端點句型，開啟改答案登記為本端點不適用，三項都記在 AC 句型對照。

```gherkin
# backend/改答案.feature
      When "甲" 送出新答案 "4567"
      Then "甲" 的目前答案為 "4567"
      And 雙方的猜測歷史依序為：
        | 回合 | 玩家 | 紀錄       |
        | 1    | 甲   | 使用改答案 |
```

```markdown
| `{玩家} 開啟改答案` | backend | 本端點不適用 |
| `{玩家} 的畫面顯示目前答案 {四碼}` | backend | `{玩家} 的目前答案為 {四碼}` |
```

### Bad Example

這個範例的後端在句首加上讀取位置，同一件事拆成「重新查詢後」與 AC 原句兩種說法，PM 對照 AC 時以為是兩件事，回應與查證也被拆到兩個句型。

```gherkin
# backend/改答案.feature
      When "甲" 送出新答案 "4567"
      Then 系統回覆答案已更改
      And "重新查詢後"，猜測歷史依序為：
        | 回合 | 玩家 | 紀錄       |
        | 1    | 甲   | 使用改答案 |
```

## Rule 3 -- Given 以差異句推進到需要的狀態

**強度：MUST**

Example 的 Given 只寫與該 Example 起點（Background 或 Example 第一句起點句）不同的部分，用動作句把狀態推進到案例需要的樣子；畫面與 API 端點的動作句可以使用 dsl.md 的 When 句型。儲存端點（使用 `templates/database/` 或 `templates/filesystem/` 樣板的端點）的差異句寫成直接寫入的資料內容（某筆紀錄已存在、某個欄位的值、某個檔案已在某處），不得沿用 AC 或後端的業務動作句。不得在 Given 重寫起點已建立的內容，也不得用一句狀態名稱代替多個差異。以下 Example 皆對照此起點與要推進到的狀態：

```text
起點：系統處於 "對戰開始輪到甲"
backend 要推進到：雙方依序猜過 1234、0132、1357、3210
database 要推進到：甲的連猜三次剩餘次數為 0（原本由甲確認使用連猜三次造成）
```

### Good Example

這個範例的後端以一句帶表格的猜測推進到雙方各猜兩次，讀者看得到每次猜測；資料庫端直接寫入要的剩餘次數，不經過確認連猜的業務動作。

```gherkin
# backend/改答案.feature
    Example: 雙方各猜兩次後甲送出新答案 1123
      Given 雙方依序猜下列號碼：
        | 玩家 | 猜測 |
        | 甲   | 1234 |
        | 乙   | 0132 |
        | 甲   | 1357 |
        | 乙   | 3210 |
      When "甲" 送出新答案 "1123"

# database/連猜三次.feature
    Example: 甲的連猜三次剩 0 次時寫成 2 次
      Given "甲" 的 "連猜三次" 剩餘次數為 0
      When 把 "甲" 的 "連猜三次" 剩餘次數寫成 2
```

### Bad Example

這個範例的後端用一句自創的狀態名稱代替四次猜測，寫測試的人只能猜雙方各猜了什麼；資料庫端沿用業務動作句推進，資料庫測試得等後端的確認連猜實作完才能執行。

```gherkin
# backend/改答案.feature
    Example: 雙方各猜兩次後甲送出新答案 1123
      Given 已進行到第 3 回合
      When "甲" 送出新答案 "1123"

# database/連猜三次.feature
    Example: 甲用過連猜三次後把剩餘次數寫成 2 次
      Given "甲" 確認使用連猜三次
      When 把 "甲" 的 "連猜三次" 剩餘次數寫成 2
```

## Rule 4 -- When 一句寫一個動作

**強度：MUST**

每句 When 只寫一個動作；AC 的一組 When 有多個動作時，第一個用 When，其餘依序用 And。不得把多個動作塞進同一句。

### Good Example

這個範例把開啟改答案與送出新答案寫成兩句，各自對應一個句型。

```gherkin
      When "甲" 開啟改答案
      And "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
```

### Bad Example

這個範例把兩個動作塞進一句，句型字典得為「開啟並送出」另外定義一個只用一次的句型，開啟與送出也無法各自重用。

```gherkin
      When "甲" 開啟改答案後送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
```

## Rule 5 -- 字串參數加雙引號

**強度：MUST**

步驟中可替換的字串參數一律加雙引號，數字參數不加引號；固定的句型文字不加引號。

### Good Example

這個範例的玩家與四碼加雙引號，次數不加。

```gherkin
      When "甲" 猜 "5679"
      Then "甲" 的改答案剩餘次數為 0
```

### Bad Example

這個範例的字串參數沒有加引號，句型無法分辨參數從哪裡開始，「甲 猜 5679」可能被整段當成同一個參數。

```gherkin
      When 甲 猜 5679
```

## Rule 6 -- 該合併的步驟必須用 Data Table

**強度：MUST**

同一句型連續三行以上、只差參數值時，必須寫成一句帶 Data Table 的步驟。只有一欄、而且值是玩家、照片這類短名稱的序列時不用表格，寫成以「、」分隔的列表參數。

### Good Example

這個範例把同一句型的三列猜測合成一張表，讀者一眼看出是同一組猜測。

```gherkin
      Given 雙方依序猜下列號碼：
        | 玩家 | 猜測 |
        | 甲   | 1234 |
        | 乙   | 0132 |
        | 甲   | 1357 |
```

### Bad Example

這個範例把同一句型連寫三行，Given 拉長成三句，讀者要逐行比對才看得出是在建立同一組猜測，再多一列時還得再加一句。

```gherkin
      Given "甲" 猜 "1234"
      And "乙" 猜 "0132"
      And "甲" 猜 "1357"
```

## Rule 7 -- 影響閱讀的預設值必須註解

**強度：MUST**

步驟沒有寫出、但會影響讀者判斷結果的預設值（例如祕密答案、猜測對新舊答案各算幾 A 幾 B），在該步驟上方加一行 `# 預設值：…`，只寫業務語意；AC 已有的預設值註解逐字沿用。不影響判斷的預設值不寫。

### Good Example

這個範例沿用 AC 的註解說明乙兩次猜 3210 對新舊答案的回報不同，讀者才看得懂為什麼第二次是 0A0B。

```gherkin
      # 預設值：乙兩次猜 3210，改答案前對 0123 為 0A4B，改答案後對 4567 為 0A0B
      When "乙" 猜 "3210"
      Then 系統回覆 "0A0B"
```

### Bad Example

這個範例沒有註解，讀者以為乙猜 3210 本來就是 0A0B，看不出這個 Example 是在抓「改答案後仍用舊答案計算」的錯誤。

```gherkin
      When "乙" 猜 "3210"
      Then 系統回覆 "0A0B"
```

## Rule 8 -- Then 句型必須同時有回應斷言與查證斷言

**強度：MUST**

每個 Then 句子在 dsl.md 的測試撰寫語意都同時含回應斷言與至少一個從其他管道讀取的查證斷言：回應斷言驗這次 When 最後一個動作的直接結果，而且必須反映這條 Rule 要驗的結果；查證斷言從權威狀態、再讀確認、跨視角、不該發生中挑 1 到 2 個，不得與回應斷言讀同一個地方。各端點的回應與查證依下表。不得把回應與查證拆成兩個句子，也不得讓回應斷言驗與這條 Rule 無關的結果。

| 端點 | 回應斷言 | 查證斷言 |
|---|---|---|
| frontend | 這次操作在畫面上造成的變化（動作者或對手的畫面） | 另一位參與者的畫面、重新整理後的畫面，或以 API 重新查詢 |
| backend | 這次請求的回應 | 以同一或另一位使用者身份重新查詢、推播，或查資料庫 |
| database、filesystem | 直接寫入或儲存模組呼叫的結果；預期被拒絕時為攔截到的錯誤類型；成功且沒有與這條 Rule 相關的回傳值時寫「無，因為…」 | 以新的連線查詢資料表，或直接讀檔案系統 |

### Good Example

這個範例的 Rule 驗次數用完後不能再改答案，When 就是再送一次新答案；一句 Then 的回應驗這次被拒絕，查證以重新查詢確認答案沒被改掉。

```gherkin
  Rule: 改答案次數用完後不能再改答案

    Example: 甲已把答案改為 4567 後再送出新答案 1357
      Given "甲" 送出新答案 "4567"
      When "甲" 送出新答案 "1357"
      Then 系統拒絕這次"改答案"，因為 "本局次數已用完"
```

```markdown
回應斷言：狀態碼 409，`code` 為 `skill_exhausted`<br>查證斷言：<br>・再讀確認：以該玩家身份 `GET /api/me/room`，`state.my_secret` 仍為上一次成功送出的答案
```

### Bad Example

這個範例把回應與查證拆成兩個句型，feature 只寫第一句時就只驗回應，實作回覆 200 卻沒有存下新答案，這個 Example 照樣通過。

```markdown
| `系統回覆答案已更改` | … | 回應斷言：狀態碼 200 |
| `"重新查詢後"，{玩家} 的答案為 {四碼}` | … | 查證斷言：・再讀確認：`GET /api/me/room` 的 `state.my_secret` |
```

## Rule 9 -- 只有一種斷言時必須寫明理由

**強度：MUST**

只有兩種情況可以只寫一種斷言：本端點的動作沒有與這條 Rule 相關的回應（資料庫、檔案系統的操作成功，且沒有回傳與這條 Rule 相關的值），或確實找不到第二個有意義的管道（前端的焦點位置、無障礙屬性、只存在本機畫面的欄位內容）。這時 dsl.md 把另一種寫成「無，因為<理由>」，並列入待確認事項；找得到第二管道時不得只寫一種，也不得為了湊數補上與結果無關的查證。

### Good Example

這個範例的猜測欄內容只存在甲的瀏覽器，沒有送到後端也不會出現在對手畫面，因此查證寫明理由，並列入待確認事項。

```markdown
| `{玩家} 的猜測欄仍為 {四碼}` | … | 回應斷言：該玩家情境的 `guess-input` 值等於四碼<br>查證斷言：無，因為猜測欄內容只存在該玩家的瀏覽器，不會送到後端或對手畫面 |
```

### Bad Example

這個範例宣稱特效只有畫面能驗，但對手畫面也會播放同一個特效，跨視角查證其實存在，只驗甲的畫面時，特效只在甲端出現的錯誤測不出來。

```markdown
| `特效顯示技能名稱 {技能} 與使用者 {角色}` | … | 回應斷言：甲的情境 `skill-effect` 顯示技能名稱與角色<br>查證斷言：無，因為只有畫面能驗 |
```

## Rule 10 -- 技術說法依用語表改寫

**強度：MUST**

從介面文檔補到步驟中的技術說法，依用語表「技術說法對照」的業務說法改寫；用語表沒有的技術說法，自訂業務說法寫進 feature，並在回傳的「新增技術說法」逐項列出技術說法與採用的業務說法，不得沿用原文。無障礙屬性改寫成使用者感受得到的效果，例如「標示為輸入錯誤」「會被螢幕閱讀器立即朗讀」。以下 Example 皆對照此用語表與介面文檔：

```text
用語表「技術說法對照」：
| 錯誤碼 INVALID_FOUR_CODE | 四碼規則不符 | backend、frontend |
| aria-invalid="true" | 標示為輸入錯誤 | frontend |

ui-contract.md：新答案欄位驗證失敗時 aria-invalid 為 true，錯誤訊息具 role="alert"
```

### Good Example

這個範例依用語表改寫第一項；`role="alert"` 不在用語表，自訂為「會被螢幕閱讀器立即朗讀」並在回傳中列出。

```gherkin
      When "甲" 送出新答案 "1123"
      Then "新答案欄位" 標示為輸入錯誤
      And "四碼規則提示" 會被螢幕閱讀器立即朗讀
```

```markdown
- 新增技術說法：`role="alert"` → 會被螢幕閱讀器立即朗讀
```

### Bad Example

這個範例照抄介面文檔的技術原文，也沒有回傳新增的技術說法；其他端點遇到同一個屬性會各自想一種說法，用語表也不會補上。

```gherkin
      When "甲" 送出新答案 "1123"
      Then "新答案欄位" 的屬性 "aria-invalid" 為 "true"
      And "四碼規則提示" 的屬性 "role" 為 "alert"
```

## Rule 11 -- 多個動作時回應只驗最後一個動作

**強度：MUST**

When 有兩個以上動作時（前端整組保留 AC 的操作），回應斷言只驗最後一個動作的結果；前面的動作失敗必須讓 Example 失敗，dsl.md 不得攔截這些動作的錯誤。前面動作的結果需要驗時，另立以它為 When 的 Example，不得在同一個 Example 以多句回應斷言分別指名各個動作。以下 Example 皆對照此動作：

```gherkin
      When "甲" 開啟改答案
      And "甲" 送出新答案 "4567"
```

### Good Example

這個範例的回應只驗送出新答案後的畫面，開啟改答案若失敗，送出那一步就找不到輸入框而讓 Example 失敗。

```gherkin
      When "甲" 開啟改答案
      And "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
```

### Bad Example

這個範例在同一個 Example 分別指名兩個動作的回應，一個 Example 驗了兩件事，第一句失敗時第二句不會執行，報告也看不出是哪個動作壞了。

```gherkin
      When "甲" 開啟改答案
      And "甲" 送出新答案 "4567"
      Then "開啟改答案的畫面中"，出現新答案輸入框
      And "送出新答案的畫面中"，目前答案為 "4567"
```

## Rule 12 -- 需要動作的查證寫進同一句的查證斷言

**強度：MUST**

查證要先做一個或多個動作才能驗證時（例如以對手再猜一次確認新答案已生效），把動作寫在該 Then 句型 dsl.md 查證斷言的「動作：」，並寫明這個動作不算進這次操作；不得另寫一句只有查證的 Then，也不得另開一組 When。以下 Example 皆對照此 AC 片段：

```gherkin
      When "甲" 送出新答案 "4567"
      Then "甲" 的畫面顯示目前答案 "4567"
      When "乙" 猜 "4567"
      Then 系統回報 "4A0B"
```

### Good Example

這個範例在後端用一句 Then 同時驗回應與「乙再猜一次得到 4A0B」，再猜的動作寫在查證斷言，When 只有這次要測的改答案。

```gherkin
      When "甲" 送出新答案 "4567"
      Then "甲" 的目前答案為 "4567"
```

```markdown
回應斷言：狀態碼 200，`state.my_secret` 為四碼<br>查證斷言：<br>・再讀確認：動作：以乙的身份猜該四碼，不算進這次操作；回報為 4A0B
```

### Bad Example

這個範例為了查證另寫一句只有查證的 Then，這句沒有回應斷言，讀者還以為乙的猜測也是這次要驗的行為。

```gherkin
      When "甲" 送出新答案 "4567"
      Then "甲" 的目前答案為 "4567"
      And "乙" 之後猜 "4567" 會得到 "4A0B"
```
