# 句型收斂規範

## Rule 1 -- 語意完全一致才合併句型

**強度：MUST**

把步驟中可替換的值換成參數後比對，文字相同、而且測試要做的事完全相同的步驟，才合併成同一個句型。文字相近但測試動作不同的（例如一個打 API、一個只改資料表），必須維持不同句型。

### Good Example

這個範例把只差相簿與照片數的兩句合併成同一個句型，兩句都是驗這次回應的相簿內容再重新查詢相簿列表。

```text
相簿 "2026年10月1日（星期四）" 有 1 張照片
相簿 "2026年10月3日（星期六）" 有 3 張照片
→ 相簿 {相簿} 有 {張數} 張照片
```

### Bad Example

這個範例把「匯入照片」（打匯入 API）與「資料表已有照片」（直接寫資料表）合成同一個句型，step definition 只能擇一實作，另一邊的測試就用錯了測試層。

```text
匯入拍攝於 "2026-10-01" 的照片 "P1"
資料表已有拍攝於 "2026-10-01" 的照片 "P1"
→ {方式}拍攝於 {日期} 的照片 {照片}
```

## Rule 2 -- 能拆成核心句型就拆

**強度：MUST**

一個句型若由兩個以上可以單獨使用的句型組成，必須拆成核心句型，讓 feature 用 And 串接；只有拆開後語意會改變時才保留組合句型。Then 句型的回應斷言與查證斷言屬於同一句的語意，不得拆成兩個句型。

### Good Example

這個範例把「匯入並開啟相簿」拆成兩個核心句型，各自可在其他 Example 重用。

```text
匯入測試資料 {測試資料}
開啟相簿 {相簿}
```

### Bad Example

這個範例保留組合句型，只想開啟相簿的 Example 也必須重新匯入，或另外再定義一個「開啟相簿」句型，兩個句型的開啟邏輯會重複。

```text
匯入測試資料 {測試資料} 後開啟相簿 {相簿}
```

## Rule 3 -- 參數使用領域命名的型別

**強度：MUST**

句型參數的型別使用規格用詞的繁體中文名稱，例如 `{相簿}`、`{照片}`、`{日期}`、`{原因}`；不得使用 `{string}`、`{int}` 這類通用型別。

### Good Example

這個範例的型別名稱直接說出參數的業務意義。

```text
把相簿 {相簿} 移到相簿 {相簿} 之前
```

### Bad Example

這個範例使用通用型別，寫測試的人看不出兩個參數是相簿還是照片，也無法為相簿建立專屬的合法值對照。

```text
把相簿 {string} 移到相簿 {string} 之前
```

## Rule 4 -- 同一句不得同時符合兩個句型

**強度：MUST**

把型別的合法值代入後，feature 中任何一句都只能符合一個句型。新增句型前要確認它不會和既有句型同時符合同一句；會同時符合時，修改其中一個句型的固定文字。

### Good Example

這個範例的兩個句型固定文字不同，「相簿依序是」與「相簿數」不會同時符合同一句。

```text
相簿依序是 {相簿列表}
共有 {相簿數} 本相簿
```

### Bad Example

這個範例的第二個句型把文字也做成參數，「相簿依序是 "C、A、B"」同時符合兩個句型，測試框架會回報 ambiguous step 而無法執行。

```text
相簿依序是 {相簿列表}
相簿{描述}
```

## Rule 5 -- 先沿用端點資料夾既有的句型，意思不同才新增

**強度：MUST**

一個端點資料夾只有一份 dsl.md 與一套 step definitions，同一句只能對應一份 step 實作。收斂句型時必須讀該端點 dsl.md 既有的句型與 step 目錄中既有的 step definitions：測試要做的事相同，就逐字沿用既有的句型；測試要做的事不同，就使用固定文字不同的新句型，直到新舊句型不會同時符合同一句。沿用句型時，新增的參數值（例如起點名稱）不得與既有的同名值代表不同內容。不得為了這次的 Example 改變既有句型的測試撰寫語意；既有句型的行為確實因這次的需求而改變時，使用它的既有 Example 必須已列在委派簡報的異動範圍。以下 Example 皆對照此既有的 backend dsl.md 與這次要寫的步驟：

```text
既有的 backend/dsl.md：
  `玩家 {玩家} 猜 {四碼}`：動作 POST /api/rooms/{room_id}/guesses
  `系統處於 {前置狀態}`：依前置狀態名稱建立房間，已用名稱有 "AB 對戰中"
這次要寫：
  1. AC 句型 `{玩家} 猜 {四碼}`：動作同樣是 POST /api/rooms/{room_id}/guesses
  2. 連猜三次中的一次猜測：動作是 POST /api/rooms/{room_id}/skills/triple-guess
  3. 起點：雙方都已設定答案、輪到房主、尚未使用任何技能
```

### Good Example

這個範例同義的猜測沿用既有的句型，異義的連猜改寫固定文字避開，起點沿用句型但取一個新名稱。

```text
1. 同義 → 沿用 `玩家 {玩家} 猜 {四碼}`
2. 異義 → `玩家 {玩家} 在連猜三次中猜 {四碼}`
3. 同義句型、新內容 → 沿用 `系統處於 {前置狀態}`，前置狀態取名 "房主輪到且尚未使用技能"
```

### Bad Example

這個範例另寫同義的 `{玩家} 猜 {四碼}`，同一個猜測動作在同一個資料夾有兩個句型、兩份實作；連猜沿用 `玩家 {玩家} 猜 {四碼}` 卻要打另一支 API，既有的 Example 會跟著改打新的 API；起點重用 "AB 對戰中" 卻代表不同的房間狀態，既有的 Example 會從錯的狀態開始。

```text
1. `{玩家} 猜 {四碼}`
2. `玩家 {玩家} 猜 {四碼}`（打 /skills/triple-guess）
3. 系統處於 "AB 對戰中"（這次定義為尚未使用技能、輪到房主）
```
