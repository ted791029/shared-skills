# 增量更新規範

## Rule 1 -- spec.md 沒變動的旅程必須原樣保留

**強度：MUST**

既有 `features/acceptance/` 中，對應的使用者故事與 FR 在 spec.md 沒有變動的 Example，必須原樣保留，包括 PM 手改過的步驟、表格與註解；不得為了統一寫法而重寫。

### Good Example

這個範例只有 FR-016 變動，只更新涵蓋 FR-016 的 AC-07，PM 手改過的 AC-05 原樣保留。

```text
spec.md 變動：FR-016
AC-05（涵蓋 FR-013、FR-015）→ 保留
AC-07（涵蓋 FR-016）→ 更新
```

### Bad Example

這個範例重新產生整份相簿排序 feature，PM 在 AC-05 手改的表格被覆蓋，PM 得重新檢查每一個旅程。

```text
spec.md 變動：FR-016
相簿排序.feature → 全部重新產生
```

## Rule 2 -- 新增的 AC 必須接續既有最大編號

**強度：MUST**

新增的 Example 從既有 AC 的最大編號往後接續，不得重編既有 AC 的編號，也不得重複使用已被刪除的編號，讓已經在討論或追溯中使用的編號維持不變；編號取 check_acceptance.py 輸出的 `next_ac`，它已算入開發發現的 AC 與 `truth-changes.md` 引用過的編號。

### Good Example

這個範例既有 AC-01 至 AC-09，新增的旅程編為 AC-10。

```gherkin
    Example: AC-10 自訂順序後一次匯入 10 月 5 日與 10 月 6 日的照片
```

### Bad Example

這個範例把新旅程插進相簿排序後重編為 AC-08，原本的 AC-08、AC-09 變成 AC-09、AC-10，PM 先前針對「AC-08」的回饋就對不上旅程。

```gherkin
    Example: AC-08 自訂順序後一次匯入 10 月 5 日與 10 月 6 日的照片
    Example: AC-09 在相簿頁刪除 10 月 1 日相簿的 P3
```

## Rule 3 -- 與既有步驟矛盾才算衝突

**強度：MUST**

只有 spec.md 的變動會讓既有 Example 的步驟、表格或結果變成錯誤時才算衝突；只需新增旅程、或既有旅程仍然正確的變動不算衝突，直接處理不詢問。列出衝突時寫出 AC 編號、既有寫法與 spec.md 的新內容。以下 Example 皆對照此變動：

```text
既有 AC-06：相簿放到另一本相簿上時插在它之前
spec.md 新 FR-014：相簿放到另一本相簿上時，依放開位置決定插在之前或之後
```

### Good Example

這個範例判斷既有的「插在之前」在新規則下不一定成立，列為衝突並寫出雙方內容。

```text
衝突：AC-06
- 既有寫法：放到 10 月 3 日相簿上後，10 月 1 日相簿排在它之前
- spec.md 新內容：FR-014 依放開位置決定插在之前或之後
```

### Bad Example

這個範例把只新增 FR-021 的變動也列為衝突，使用者被迫逐一確認與既有旅程無關的項目，真正矛盾的 AC-06 被淹沒在清單中。

```text
衝突：AC-06、AC-07、AC-08（spec.md 新增 FR-021）
```

## Rule 4 -- 覆蓋只改使用者確認的衝突步驟

**強度：MUST**

使用者確認以 spec.md 為準後，只修改該衝突涉及的步驟與表格，Example 的其他步驟、標題與註解維持原樣；使用者選擇保留既有寫法時依 Rule 6 處理。

### Good Example

這個範例在使用者確認以 spec.md 為準後，只改寫 AC-06 的拖放步驟與其後的順序表格。

```gherkin
      # 預設值：放開位置在 10 月 3 日相簿的左半部
      When 把相簿 "2026年10月1日（星期四）" 拖放到相簿 "2026年10月3日（星期六）" 上
      Then 主頁依序顯示下列相簿：
        | 相簿                    | 照片數 |
        | 2026年10月1日（星期四） | 5      |
        | 2026年10月3日（星期六） | 2      |
        | 2026年10月2日（星期五） | 3      |
```

### Bad Example

這個範例在使用者確認後重寫整個 AC-06，連 PM 手改過的「按下取消鍵」段落也被換掉，修改超出使用者確認的範圍。

```text
使用者確認：AC-06 以 spec.md 為準
處理：重新產生 AC-06 全部步驟
```

## Rule 5 -- 不得改動開發發現的 AC

**強度：MUST**

標 `@開發發現` 的 AC 是開發中發現、由 dev-finding 新增的驗收案例，連同它上方的 `# 開發發現：` 註解與它所在的 Rule 一律不得修改、搬移或刪除，也不計入每份 feature 2 至 3 個 Example 的限制。spec.md 的變動與它矛盾時，在回報的「與 spec.md 不一致之處」列出，由 dev-finding 的 review 決定去留。以下 Example 皆對照此變動與既有的 AC：

```text
spec.md 變動：FR-014 改為相簿放到另一本相簿上時一律插在它之後
既有 AC-06（涵蓋 FR-014）：放到 10 月 3 日相簿上後，10 月 1 日相簿排在它之前
既有 AC-10（@開發發現，dsl-refine）：拖放到第一本相簿上時，排在第一本之前
```

### Good Example

這個範例把衝突的 AC-06 列給使用者確認，開發發現的 AC-10 原樣保留，並在回報中列出它與新的 FR-014 矛盾。

```text
衝突：AC-06（依 Rule 3 列給使用者確認）
AC-10：原樣保留
回報「與 spec.md 不一致之處」：AC-10：拖放到第一本相簿上時排在第一本之前；spec.md：FR-014 一律插在它之後
```

### Bad Example

這個範例依新的 FR-014 改寫 AC-10，PM 沒有在 review 中看到這個開發發現被推翻；`truth-changes.md` 中以 AC-10 為原因的列也與 AC 對不上。

```text
AC-10（@開發發現）→ 改為「拖放到第一本相簿上時，排在它之後」
```

## Rule 6 -- 保留與 spec.md 矛盾的 AC 時這次不能改

**強度：MUST**

使用者選擇保留與 spec.md 新內容衝突的既有寫法時，不修改那個 AC；這種情況，以及依 Rule 8 改寫後的 AC 仍與 spec.md 的需求矛盾時，都在回報的「與 spec.md 不一致之處」列出，這次的結果是「不能改」：擋住的是那條需求（寫出編號），交給 clarify-over-specs 依 AC 改寫，改寫後再執行本 skill。不得自行改寫那條需求來消除矛盾，也不得記錄為「不用改」。以下 Example 皆對照此衝突與回覆：

```text
衝突：AC-06
- 既有寫法：放到 10 月 3 日相簿上後，10 月 1 日相簿排在它之前
- spec.md 新內容：FR-014 相簿放到另一本相簿上時一律插在它之後
使用者的回覆：AC-06 保留既有寫法
```

### Good Example

這個範例保留 AC-06 並列出不一致，以不能改停下，寫出擋住它的 FR-014 與要交給的 clarify-over-specs。

```text
AC-06：保留既有寫法，不修改
與 spec.md 不一致之處：AC-06：放到 10 月 3 日相簿上後排在它之前；spec.md：FR-014 一律插在它之後
不能改：FR-014 與使用者保留的 AC-06 矛盾 → 交給 clarify-over-specs 依 AC-06 改寫 FR-014，改寫後再執行 /spec-by-example
這次沒有記錄，spec-by-example 仍是待補跑。
```

### Bad Example

這個範例只在回報列出不一致就記錄為不用改，spec-by-example 不再是待補跑；下游依 FR-014 規劃介面、依 AC-06 衍生測試，兩者互相矛盾，交付前沒有任何擁有者會再發現。

```text
AC-06：保留既有寫法，不修改；與 spec.md 不一致之處已列在回報
結果：不用改（已記錄）
```

## Rule 7 -- 依差異逐項判斷新增、修改或不受影響

**強度：MUST**

check 回報本 skill 有紀錄且是待補跑時，`self.changes` 列出的每個需求單位都要依下表判定一個結果並寫出理由，只改判定為新增或修改的 AC，其餘 AC 依 Rule 1 原樣保留；同一個需求變更造成的多個單位（例如新增的 FR 與故事中補上的驗收情境）一起判定。標 `@開發發現` 的 AC 不列為修改的對象。全部判定為不受影響時不改 feature，這次的結果是「不用改」。

| 判定 | 條件 |
|---|---|
| 修改 AC | 變動會改變某個既有 AC 的步驟、表格、結果或涵蓋（通常是涵蓋列出它、或旅程依它撰寫的 AC；讓既有步驟變成錯誤時依 Rule 3 列為衝突）；或它是 PM 在 Demo 看得到的新行為，能在既有旅程經過的畫面或步驟驗證 |
| 新增 AC | 它是 PM 在 Demo 看得到、Demo 必看的新行為，沒有既有旅程經過能驗證它的地方 |
| 不受影響 | PM 在 Demo 看不到（容量、壓力、無障礙掃描、只能從系統內部確認的結果）、是成功標準，或不改變任何既有 AC 的步驟與結果、也不需要新的旅程 |

以下 Example 皆對照此 check 結果、需求與既有 AC：

```json
{"self": {"owner": "spec-by-example", "recorded": true, "pending": true, "changes": [
  {"status": "MOD", "unit": "plan:spec.md＞使用者情境與測試 （必填）＞使用者故事 2"},
  {"status": "ADD", "unit": "plan:spec.md＞FR-021"},
  {"status": "ADD", "unit": "plan:spec.md＞NFR-024"}]}}
```

```text
FR-021：相簿頁的標題下方必須顯示這本相簿的照片數
使用者故事 2：驗收情境補上「開啟相簿時，標題下方顯示照片數」
NFR-024：照片庫有 10,000 張照片時，開啟相簿頁必須在 2 秒內顯示第一屏縮圖
既有 AC-03（涵蓋 US2、FR-010、FR-011、FR-012）：從主頁開啟 10 月 1 日相簿，放大 P3 後前後切換
既有 AC-04（涵蓋 US2、FR-010、FR-011、NFR-007）：10 月 1 日相簿的 P2 原始檔案已遺失
```

### Good Example

這個範例逐項判定三個差異，只在 AC-03 補上照片數的驗證，AC-04 原樣保留，PM 看不到的 NFR-024 不受影響。

```markdown
| 差異 | 判定 | 說明 |
|---|---|---|
| ADD `FR-021` | 修改 AC-03 | PM 開啟相簿就看得到照片數；AC-03 已開啟 10 月 1 日相簿，在開啟後的 Then 補上「相簿頁顯示 5 張照片」，涵蓋加上 FR-021 |
| MOD `使用者故事 2` | 修改 AC-03 | 補上的驗收情境就是 FR-021，與上一列一起改 |
| ADD `NFR-024` | 不受影響 | 要準備 10,000 張照片並量測時間，PM 在 Demo 看不到 |
```

### Bad Example

這個範例無視差異重寫整份 feature，與 FR-021 無關的 AC-04 也被改寫，dsl-refine 與 task 得為它重做 Rule 與任務；為 PM 看不到的 NFR-024 另寫的旅程也無法在 Demo 現場確認。

```text
瀏覽相簿待補跑，重新挑選全部旅程：改寫 AC-03、AC-04，並為 NFR-024 新增 AC-10「照片庫有 10,000 張照片時開啟相簿」
```

## Rule 8 -- 保留並取代只改寫與保留的 AC 矛盾的部分

**強度：MUST**

dev-finding 的 review 交辦保留並取代時，PM 已決定保留那個開發發現的 AC：交辦的 AC 不再列為衝突詢問使用者，同一個交辦造成的 spec.md 變動也不再詢問。只改寫交辦的 AC 中與保留的 AC 矛盾的步驟與表格，以及寫出被取代內容的 Example 標題或 Rule 名稱，讓兩個 AC 同時成立；AC 編號與其他步驟維持原樣，保留的開發發現 AC 與交辦以外的 AC 一律不改。保留的開發發現 AC 已完整取代交辦的 AC（兩者驗收同一段旅程，交辦的 AC 改寫後已沒有要另外驗的步驟）時，刪除交辦的 AC，回報寫出被刪除的 AC 與取代它的開發發現 AC。改寫後仍與 spec.md 的需求矛盾時依 Rule 6 處理。以下 Example 皆對照此交辦與既有內容：

```text
交辦：PM 保留 AC-10（@開發發現）「把相簿拖放到主頁第一本相簿上時，排在它之前」，請依它改寫 AC-06 拖放到 10 月 3 日相簿上之後的相簿順序，使它不再與 AC-10 矛盾
spec.md：clarify-over-specs 已依同一個交辦把 FR-014 改為「相簿放到第一本相簿上時插在它之前，放到其他相簿上時插在它之後」
```

```gherkin
  Rule: 拖放相簿只能改變順序

    # 涵蓋：US3、FR-014、FR-019
    Example: AC-06 把 10 月 1 日相簿拖到 10 月 3 日相簿上，再拖曳 10 月 2 日相簿後取消
      When 把相簿 "2026年10月1日（星期四）" 拖放到相簿 "2026年10月3日（星期六）" 上
      Then 主頁依序顯示下列相簿：
        | 相簿                    | 照片數 |
        | 2026年10月3日（星期六） | 2      |
        | 2026年10月1日（星期四） | 5      |
        | 2026年10月2日（星期五） | 3      |
      When 開始拖曳相簿 "2026年10月2日（星期五）"
      And 按下取消鍵
      Then 主頁依序顯示下列相簿：
        | 相簿                    | 照片數 |
        | 2026年10月3日（星期六） | 2      |
        | 2026年10月1日（星期四） | 5      |
        | 2026年10月2日（星期五） | 3      |
```

### Good Example

這個範例沒有再詢問使用者，只把 AC-06 兩個順序表格改為 10 月 1 日相簿排在第一本的 10 月 3 日相簿之前，標題、Rule 名稱、拖放與取消的步驟都不變，AC-10 也不動。

```gherkin
      When 把相簿 "2026年10月1日（星期四）" 拖放到相簿 "2026年10月3日（星期六）" 上
      Then 主頁依序顯示下列相簿：
        | 相簿                    | 照片數 |
        | 2026年10月1日（星期四） | 5      |
        | 2026年10月3日（星期六） | 2      |
        | 2026年10月2日（星期五） | 3      |
      When 開始拖曳相簿 "2026年10月2日（星期五）"
      And 按下取消鍵
      Then 主頁依序顯示下列相簿：
        | 相簿                    | 照片數 |
        | 2026年10月1日（星期四） | 5      |
        | 2026年10月3日（星期六） | 2      |
        | 2026年10月2日（星期五） | 3      |
```

### Bad Example

這個範例把 PM 在 review 已經決定的事再問一次，又藉機改了 AC-06 的標題、刪掉取消拖曳那一段；取消後順序不變從此沒有旅程驗收，PM 審過的內容被改動也沒有人告知。

```text
衝突：AC-06 與 AC-10 矛盾，請確認以哪一個為準。
（PM 回覆以 AC-10 為準）
AC-06 重寫為「AC-06 把 10 月 1 日相簿拖到第一本相簿上」，刪除取消拖曳的步驟
```
