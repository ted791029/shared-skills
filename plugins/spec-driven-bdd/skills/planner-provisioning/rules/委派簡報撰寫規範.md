# 委派簡報撰寫規範

## Rule 1 -- Artifact 敘述涵蓋端點的全部產出

**強度：MUST**

Artifact 敘述必須為此端點的 Planner 要產出的每一份文檔各寫一節，讓 artifact-to-skill-engineering 一次從全部 Artifact 建出 Planner。產出文檔由簡報決定，plan.md 不指定；端點有多種介面形式（如 REST API 與 WebSocket）時各寫一份。不得只寫其中一份、留待之後補建。

### Good Example

這個範例為資料庫端決定產出 `data/data-model.md`，並為它寫了一節。

```markdown
## Artifact 敘述

### `data/data-model.md`

- 歸屬：truth
- 格式：Markdown
- 記載資訊：
  - 每張資料表的欄位、型別、約束與預設值
  - 索引與唯一鍵
- 範例取材：照片相簿整理器 `plan.md` 介面盤點的 DB-01 相簿資料表、DB-02 照片資料表
```

### Bad Example

這個範例的負責端點是後端，簡報卻沒有任何 Artifact 敘述，artifact-to-skill-engineering 沒有範例可寫，建出的 Planner 沒有樣板。

```markdown
## Artifact 敘述

（無）
```

## Rule 2 -- 只有範例取材可寫入功能專屬內容

**強度：MUST**

負責端點、記載資訊與流程需求會成為 Planner 的樣板骨架、SOP 與 rules，必須能套用到任何功能中同類型的端點，不得出現特定功能的業務名詞（如相簿、照片、匯入）、需求編號（如 FR-007）或介面 ID（如 API-02）。功能專屬內容只能寫在範例取材，作為範例的素材來源。

### Good Example

這個範例的記載資訊只描述任何後端都會記載的項目，相簿與介面 ID 只出現在範例取材。

```markdown
- 記載資訊：
  - 每個外層介面操作對應的 API 路徑、方法與用途
  - 分頁、排序與篩選的參數
- 範例取材：照片相簿整理器 `plan.md` 介面盤點的 API-02 相簿 API
```

### Bad Example

這個範例在記載資訊寫入相簿業務名詞與需求編號，抽出的骨架只適用於照片相簿整理器，換到其他功能就要重建 Planner。

```markdown
- 記載資訊：
  - 相簿列表與拖放排序的 API（FR-007、FR-013）
  - 照片前後張的取得方式
```

## Rule 3 -- 格式使用業界標準，路徑依歸屬與介面類型命名

**強度：MUST**

每份文檔的格式必須選用該介面類型的業界標準規格並寫出版本，如 OpenAPI 3.1；沒有業界標準規格的介面類型使用 Markdown。文檔路徑的基準依歸屬決定：歸屬為 plan 的相對於 plan 資料夾，歸屬為 truth 的相對於 `specs/truth/`。路徑應依介面類型命名：資料模型為 `data/data-model.<副檔名>`，REST API 為 `contracts/openapi.yaml`，WebSocket 等事件介面為 `contracts/asyncapi.yaml`，前端為 `ui/ui-contract.md`，其他端點為 `<端點英文短名>/<端點英文短名>-contract.md`。歸屬為 truth 的文檔必須放在這個 Planner 自己的資料夾，不得放進其他 Planner 寫入的資料夾，truth 異動的核對以資料夾判定是誰的異動。

### Good Example

這個範例寫出標準規格與版本，路徑依 REST API 的命名。

```markdown
### `contracts/openapi.yaml`

- 歸屬：truth
- 格式：OpenAPI 3.1（YAML）
```

### Bad Example

這個範例沒有寫出規格與版本，並以 Wave 編號命名路徑，產出的 Planner 每次可能寫成不同結構，後續任務拆解也無法從檔名看出是哪個端點的契約。

```markdown
### `wave2.yaml`

- 格式：YAML
```

## Rule 4 -- 記載資訊必須包含對內層的需要

**強度：MUST**

非最內層端點的 Planner，記載資訊必須包含一項「此端點需要內層端點提供什麼」，讓下一個 Wave 的 Planner 能從產出文檔推導介面。

### Good Example

這個範例要求後端記載每個 API 讀寫的資料與檔案，資料庫端與檔案系統端的 Planner 能據此分析。

```markdown
- 記載資訊：
  - 每個外層介面操作對應的 API 路徑、方法與用途
  - 每個 API 需要讀寫的資料與檔案，供內層端點分析
```

### Bad Example

這個範例只記載後端自身的 API 設計，產出的 `openapi.yaml` 看不出要讀寫哪些資料，資料庫端的 Planner 只能自行猜測欄位。

```markdown
- 記載資訊：
  - 每個外層介面操作對應的 API 路徑、方法與用途
  - 錯誤回應的狀態碼與錯誤訊息結構
```

## Rule 5 -- 記載資訊只寫項目不寫設計

**強度：MUST**

記載資訊必須寫成文檔要記載的資訊項目，不得預先寫出設計決定，如特定驗證機制、路徑命名或欄位型別。

### Good Example

這個範例只要求記載檔案上傳的請求與回應形式，由 Planner 依各功能的 techstack 決定。

```markdown
- 記載資訊：
  - 檔案上傳與二進位內容的請求與回應形式
```

### Bad Example

這個範例在簡報中定下 multipart 與路徑前綴，改用其他上傳方式或路由慣例的功能也被迫套用。

```markdown
- 記載資訊：
  - 一律以 `multipart/form-data` 上傳，路徑以 `/api/v1` 為前綴
```

## Rule 6 -- 不在範圍必須指出負責者

**強度：MUST**

不在範圍的每一項必須寫出負責的 Planner 或後續流程，且必須涵蓋相鄰端點的 Planner 會分析的內容，避免兩個 Planner 寫出重疊的文檔。

### Good Example

這個範例把相鄰端點的分析內容逐項指給對應的 Planner。

```markdown
### 不在範圍

- 資料表欄位、索引與交易邊界（交由 data-plan）
- 原始檔與縮圖的目錄結構與命名規則（交由 storage-plan）
```

### Bad Example

這個範例沒有指出負責者，也沒有排除資料表設計，`api-plan` 會在 `openapi.yaml` 中定義資料表欄位，與 `data-plan` 的 `data-model.md` 重疊且容易矛盾。

```markdown
### 不在範圍

- 其他端點的內容
```

## Rule 7 -- 每份文檔必須標示歸屬

**強度：MUST**

每份文檔必須寫出歸屬，只能是 plan 或 truth。描述系統目前的介面、之後的 plan 會在同一份文檔上增修、下游與之後的迭代都要引用的文檔歸屬 truth；只描述這次迭代的設計、交付後不再修改的文檔歸屬 plan。有任何一份文檔歸屬 truth 時，流程需求必須保留「truth 異動」與讀取 `specs/truth/` 既有文檔的兩行；全部歸屬 plan 時刪除這兩行。不得把歸屬留給 Planner 執行時自行判斷。

### Good Example

這個範例的儲存契約描述系統目前的目錄結構，之後的 plan 會繼續增修，歸屬 truth，流程需求保留「truth 異動」一行。

```markdown
### `storage/storage-contract.md`

- 歸屬：truth
- 格式：Markdown
```

```markdown
- truth 異動：修改 truth 前委派 truth-changes 的 inventory 盤點這次的新增、修改與刪除，修改後委派 truth-changes 的 record 記進 plan 的 `truth-changes.md` 並核對
```

### Bad Example

這個範例沒有寫歸屬，流程需求也沒有「truth 異動」一行；建出的 Planner 會把整份儲存契約寫在 plan 資料夾，下一個 plan 看不到它，修改既有的儲存區時也不會盤點與記錄異動。

```markdown
### `storage/storage-contract.md`

- 格式：Markdown
```

## Rule 8 -- Planner 必須與 planner-provisioning 同層

**強度：MUST**

Planner 的存放位置必須與 planner-provisioning 的資料夾同層。Planner 會以相對連結使用 plan-package、truth-changes 與 constitution 的 SKILL.md 與 RuleFile，檢查腳本也只在同層尋找 Planner。planner-provisioning 位於 plugin 的安裝目錄（例如 `~/.claude/plugins/cache/`）時，存放位置改為該 plugin 原始 repo 中 planner-provisioning 的同層；不得寫進安裝副本，也不得另放到專案的 skill 目錄。

### Good Example

這個範例的 planner-provisioning 由 plugin 安裝，Planner 建立在原始 repo 的同層，更新 plugin 後連結與檢查腳本都找得到。

```text
planner-provisioning：~/.claude/plugins/cache/shared-skills/spec-driven-bdd/3618568e6551/skills/planner-provisioning/
原始 repo：D:/repo/shared-skills
存放位置：D:/repo/shared-skills/plugins/spec-driven-bdd/skills/storage-plan/
```

### Bad Example

這個範例把 Planner 放到專案的 skill 目錄，它連到 `../plan-package/SKILL.md` 的連結失效，check_findings.py 也找不到這個 Planner，把它回報為未知的擁有者。

```text
planner-provisioning：~/.claude/plugins/cache/shared-skills/spec-driven-bdd/3618568e6551/skills/planner-provisioning/
存放位置：D:/work/report/.claude/skills/storage-plan/
```
