# 發現分類規範

## Rule 1 -- 違反已核准需求的發現直接修

**強度：MUST**

發現的現象違反本 plan 中 PM 已經核准的需求（spec.md 的 FR、NFR，或 acceptance 中 PM 提出的 AC）時，判定為「直接修」，在回覆中寫出被違反的編號，不新增 AC；應修正的擁有者不是呼叫者自己、不會在這次執行中改正時，在技術項.md 記一行（問題寫出被違反的編號）並寫上「修正：<應修正的擁有者>」，讓該擁有者成為待補跑，交辦不因對話中斷而遺失。發現者有理由認為已核准的需求本身應該改變（例如做不到、會造成其他問題，或想改成另一個看得到的結果）時不是直接修，依 Rule 2 分類，並在依據寫出理由與矛盾的需求編號，由 PM 在 review 決定。以下 Example 皆對照此現象與需求：

```text
現象一：客人取消預約後，沒有收到取消通知
現象二：implement 認為用餐前 24 小時以上取消的客人不需要通知，想改成只在用餐前 24 小時內取消時才寄送
spec.md：FR-004 取消預約時必須寄送取消通知給客人
```

### Good Example

這個範例比對出現象一違反已核准的 FR-004，判定為直接修並寫出編號，修正要改程式、不是呼叫者這次能改的，記一行技術項交給 task；現象二是要改變已核准的行為，不當成直接修，交給 PM 決定。

```text
現象一 判定：直接修（違反 FR-004），不新增 AC
  技術項.md：- 取消預約後沒有寄送取消通知，違反 FR-004（implement；`backend/app/services/bookings.py` 的取消流程；修正：task）
現象二 判定：要改變 FR-004 → 依 Rule 2 分類（PM 看得到，新增 AC，依據寫出理由與「與 FR-004 矛盾」）
```

### Bad Example

這個範例為已核准的需求再加一個開發發現的 AC，PM 要重複確認自己提過的需求，列出時也被不需要決定的項目占滿。

```text
現象一 判定：PM 看得到 → 新增標 @開發發現 的 AC-09
```

## Rule 2 -- 以 PM 能否在 Demo 看到結果分類

**強度：MUST**

沒有違反已核准需求的發現，以「能不能寫成一個 PM 現場操作產品就看得到差異的驗收案例」判定：寫得出來的是 PM 看得到的行為，新增標 `@開發發現` 的 AC；寫不出來的是看不到的技術問題（資料結構、約束、命名、內部一致性），列入技術項。判定依據是處理結果會不會改變使用者看到的畫面、訊息或操作結果，不是問題出現在哪一層；使用者在產品中操作不到的情況（畫面上沒有對應的入口）寫不成這樣的驗收案例，屬於技術項。

### Good Example

這個範例三個發現都以使用者操作得到、看到的結果會不會不同來判定。

```text
現象：用餐前 2 小時內呼叫取消預約，程式會拒絕，契約沒有寫這個回應；訂位頁在這段時間仍顯示「取消預約」按鈕
判定：客人按「取消預約」會看到被拒絕的提示 → PM 看得到 → 新增 AC

現象：用餐開始後直接呼叫取消預約會被拒絕，契約沒有寫這個回應；訂位頁在用餐開始後不顯示「取消預約」按鈕
判定：客人在畫面上操作不到，PM 現場 Demo 看不到 → 技術項

現象：資料模型宣告了外鍵 fk_bookings_slot_id，實際的資料庫沒有建立
判定：補不補外鍵，客人操作任何畫面都看不出差異 → 看不到 → 技術項
```

### Bad Example

這個範例以問題所在的層次分類，忽略客人按下取消時看到的結果會不同，這個行為沒有讓 PM 看過就被定案。

```text
現象：用餐前 2 小時內呼叫取消預約，程式會拒絕，契約沒有寫這個回應；訂位頁在這段時間仍顯示「取消預約」按鈕
判定：問題出在 API 契約，屬於後端的技術問題 → 技術項
```

## Rule 3 -- 拿不準時當作看得到

**強度：MUST**

無法確定 PM 看不看得到差異時，一律新增標 `@開發發現` 的 AC，不得以發生機率低或影響小為由列入技術項。

### Good Example

這個範例無法排除兩位客人看到的結果會不同，判定為看得到。

```text
現象：兩位客人同時預約最後一個名額時，誰會預約成功沒有定義
判定：多數時候看不出差異，但兩位客人看到的結果可能與送出的先後不符，無法確定 → 新增 AC
```

### Bad Example

這個範例以機率低為由列入技術項，PM 沒有看過的行為被當成技術細節定案，上線後客人看到後送出的人反而訂到位時才發現沒有人決定過。

```text
現象：兩位客人同時預約最後一個名額時，誰會預約成功沒有定義
判定：同時送出的機率很低 → 技術項
```

## Rule 4 -- 一個發現只含一個可獨立決定的行為

**強度：MUST**

交來的現象包含多個 PM 可以分別保留或不要的行為時，必須拆成多個發現，各自分類與記錄。以下 Example 皆對照此現象：

```text
現象：用餐前 2 小時內取消預約會被拒絕；另外，候補成功時客人沒有收到任何通知
```

### Good Example

這個範例把兩個可以分別決定的行為拆成兩個發現。

```text
- 用餐前 2 小時內按「取消預約」會被拒絕 → 新增 AC
- 候補成功時客人沒有收到通知 → 新增 AC
```

### Bad Example

這個範例把兩個行為寫成一個驗收案例，PM 想留下其中一個、不要另一個時無法回覆。

```text
- 用餐前 2 小時內不能取消，且候補成功時沒有通知 → 新增一個 AC
```

## Rule 5 -- 已記錄的發現不得重複記錄

**強度：MUST**

記錄前必須比對 acceptance 中標 `@開發發現` 的 AC 與 `技術項.md`，確認是否已有描述同一個行為或問題的紀錄。已有時回覆既有的 AC 編號或那一行，不新增。以下 Example 皆對照此既有紀錄與現象：

```text
既有紀錄：AC-08「"王小明" 在用餐前 1 小時取消預約」（標 @開發發現，api-plan 記錄）
現象：dsl-refine 交來「用餐前 2 小時內不能取消預約，規格沒有寫」
```

### Good Example

這個範例比對出同一個行為已有紀錄，回覆既有的編號。

```text
回覆：已記錄為 AC-08，不新增
```

### Bad Example

這個範例為同一個行為再加一個驗收案例，PM 會被問兩次，兩個案例的結果不同時下游無法判斷以哪一個為準。

```text
回覆：新增 AC-10
```

## Rule 6 -- 技術修正 plan 只記錄看不到的技術問題

**強度：MUST**

plan-package 的 check 回報目標是技術修正 plan 時，判定為 PM 看得到的發現（含依 Rule 3 拿不準的）不新增 AC，也不改列為技術項：這個發現的結果是「不能改」，回覆寫明擋住它的是「技術修正 plan 不得改變 PM 看得到的行為」，需在這個 plan 交付或放棄後，以 /specify 開立有需求的 plan 處理，它沒有寫入任何紀錄（dev-finding 沒有被追蹤的輸入，不會因此成為待補跑）。同一次交來的看不到的技術問題照常列入技術項並記錄；使用者直接交來的發現，發現的 skill 寫「使用者」。以下 Example 皆對照此情境：

```text
plan：005-dsl-cleanup（技術修正 plan）
現象一（使用者）：`specs/truth/features/frontend/dsl.md` 第 42 行「客人 {客人} 按 {按鈕}」與第 57 行「客人 {客人} 點選 {按鈕}」意思相同
現象二（使用者）：取消成功的提示「預約已取消」想改成「已為你取消預約」
```

### Good Example

這個範例把看不到的現象一列入技術項並以使用者為發現者，看得到的現象二回覆不能改與處理方式，沒有新增 AC。

```text
- 現象一：看不到 → 技術項「- `specs/truth/features/frontend/dsl.md` 的「客人 {客人} 按 {按鈕}」與「客人 {客人} 點選 {按鈕}」兩個句型意思相同（使用者；`specs/truth/features/frontend/dsl.md:42` 與 `:57`；修正：dsl-refine）」
- 現象二：PM 看得到 → 不能改：技術修正 plan 不得改變 PM 看得到的行為。請在 005-dsl-cleanup 交付或放棄後，以 /specify 開立有需求的 plan 處理；這個發現沒有寫入任何紀錄。
```

### Bad Example

這個範例在技術修正 plan 新增開發發現的 AC；這種 plan 沒有 spec.md 與需求的核准流程，提示文字的改變卻隨技術修正交付，commit 訊息的需求寫「無（技術修正）」，之後追溯不到有人以需求核准過這個改變。

```text
- 現象二：PM 看得到 → 在 features/acceptance/取消預約.feature 新增 AC-01（@開發發現）
```
