# 修正擁有者規範

## Rule 1 -- 應修正的擁有者是出錯資料的擁有者

**強度：MUST**

直接修、新增 AC、技術項三種分類的回覆都要寫出應修正的擁有者與要修正的內容：找出現象中錯了或缺了的那份資料，依下表寫出它的擁有者。擁有者不一定是發現它的 skill，也不得寫表外的 skill（例如 bdd、implement、analyze）。新增 AC 時，規格沒有寫這個行為正是開發發現的來由，spec.md 與 acceptance 不算出錯；寫出為了做到這個 AC 還要改的資料的擁有者，只缺 truth 的測試案例時是 dsl-refine。

| 出錯的資料 | 應修正的擁有者 |
|---|---|
| spec.md 的使用者故事、FR、NFR、SC 等需求 | clarify-over-specs |
| acceptance 中 PM 提出的 AC | spec-by-example |
| acceptance 中標 `@開發發現` 的 AC | dev-finding |
| research.md、`specs/truth/techstack.md` | technical-research |
| plan.md、wave-report.md | system-analysis |
| `ui/` 的 UI 契約與原型 | ui-ux-plan |
| `specs/truth/contracts/` | api-plan |
| `specs/truth/data/`、data-migration.md | data-plan |
| 其他端點的介面文檔 | 該端點的 Planner |
| `specs/truth/features/` 的 feature、dsl.md、用語表，plan 的涵蓋表 | dsl-refine |
| tasks.md | task |
| 文件都正確，只有程式要改 | task（排任務，由 implement 實作） |

以下 Example 皆對照此發現：

```text
發現的 skill：dsl-refine
現象：acceptance 的 AC-03 寫客人取消後看到「預約已取消」，預約仍列在清單中並標為已取消；`specs/truth/contracts/paths/預約/api_bookings_{bookingId}_cancel.yaml` 的 description 寫取消後直接刪除預約
判定：直接修（違反 AC-03）
```

### Good Example

這個範例找出錯的是契約，寫出契約的擁有者 api-plan 與要改的內容，而不是發現它的 dsl-refine。

```text
直接修（違反 AC-03），不留紀錄。
應修正的擁有者：api-plan。`contracts/paths/預約/api_bookings_{bookingId}_cancel.yaml` 的 description 改為取消後保留預約並標為已取消，與 AC-03 一致。
```

### Bad Example

這個範例把發現它的 dsl-refine 寫成擁有者；dsl-refine 依 AC-03 衍生完測試，契約仍寫直接刪除，沒有人交給 api-plan，依契約實作的程式與測試互相矛盾，錯的契約也隨交付留在 truth。

```text
直接修（違反 AC-03），不留紀錄。
應修正的擁有者：dsl-refine（發現它的 skill）。
```

## Rule 2 -- 不一致時先判斷錯在哪一邊

**強度：MUST**

現象是兩份資料互相不一致時，先判斷錯的是哪一份，再對照擁有者。依序判斷：與本 plan 已核准的需求（spec.md 的 FR、NFR，acceptance 的 AC）或依據引用的憲法條款不符的一方是錯的；兩方都符合時，發現者能以程式現況以外的依據（例如其他文件的用法、型別或命名）說明哪一方不是原本的設計，就採用它的判斷；仍分不出時以產出在前的一方為準，文件之間以被依據的上游文件為準，文件與程式之間以文件為準。不得只因為程式已經這樣運作就判定文件錯。以下 Example 皆對照此發現：

```text
發現的 skill：implement
現象：`specs/truth/data/預約.dbml` 的 Table `bookings` 宣告了外鍵 `fk_bookings_slot_id`，`backend/migrations/0003_bookings.sql` 沒有建立；spec.md 與 acceptance 都沒有提到這個外鍵，implement 也沒有說明資料模型哪裡不對
```

### Good Example

這個範例依序判斷：兩方都不違反需求，發現者沒有說明資料模型不是原本的設計，以文件為準，錯的是程式。

```text
看不到的技術問題。錯的是程式，以資料模型為準。
應修正的擁有者：task，排補上外鍵 `fk_bookings_slot_id` 的遷移任務，由 implement 實作。
```

### Bad Example

這個範例只因為程式已經在跑就判定資料模型錯，請 data-plan 刪掉外鍵；沒有人決定過的設計改變被當成修正，資料庫也從此少了這個約束。

```text
看不到的技術問題。程式實際沒有外鍵，以程式為準。
應修正的擁有者：data-plan，刪除 Table `bookings` 的外鍵宣告。
```

## Rule 3 -- 多份資料出錯時只寫最上游的擁有者

**強度：MUST**

同一個發現有多份資料錯了或缺了時，只寫產出順序最上游那一份的擁有者，技術項的「修正：」也只寫這一個。產出順序為 spec.md → acceptance → research.md 與 techstack.md → plan.md → UI 契約 → 契約 → 資料模型與其他端點的介面文檔 → truth 的 feature、dsl.md 與用語表 → tasks.md → 程式。要改的介面文檔所屬的介面在本 plan 的 plan.md 標「無」或沒有列時，plan.md 也缺了（介面要改為 MOD 或新增一列），最上游的擁有者是 system-analysis，由它改列後在 Wave 重跑該端點的 Planner；技術修正 plan 沒有 plan.md，不適用這一點。下游的擁有者在上游改完後由 plan-package 的 check 列為待補跑，自行判斷連帶異動，不在回覆中另外點名。以下 Example 皆對照此發現：

```text
發現的 skill：dsl-refine
發現一：新增的 AC-08 要客人在用餐前 1 小時按「取消預約」時看到「用餐前 2 小時內無法取消」；`ui/ui-contract.md` 的 UI-03 沒有這段提示，`specs/truth/contracts/paths/預約/api_bookings_{bookingId}_cancel.yaml` 也沒有這個錯誤回應
發現二：`specs/truth/features/frontend/dsl.md` 擬定了候補確認視窗取消鈕的 testid `waitlist-cancel`，UI 契約沒有；這個視窗所在的 UI-04 在本 plan 的介面盤點標「無」
```

### Good Example

這個範例在發現一只寫最上游的 UI 契約的擁有者，契約由 api-plan 在 UI 契約改完、成為待補跑後自行判斷；發現二的 UI-04 在 plan.md 標「無」，最上游缺的是 plan.md，寫 system-analysis。

```text
發現一：PM 看得到 → 新增 AC-08。
應修正的擁有者：ui-ux-plan，在 UI-03 補上「用餐前 2 小時內無法取消」的提示與它出現的狀態。
發現二：看不到的技術問題 → 技術項。
應修正的擁有者：system-analysis，把 UI-04 改為 MOD（技術：補上 dsl.md 擬定的定位 waitlist-cancel），在 Wave 重跑 ui-ux-plan 補上定位。
```

### Bad Example

這個範例只寫下游的擁有者。發現一的 api-plan 補上錯誤回應後，UI 契約仍沒有這段提示，ui-ux-plan 的輸入沒有變、不會成為待補跑，要等 dsl-refine 衍生前端 Example 時才再交辦一次；發現二的 ui-ux-plan 因 UI-04 標「無」只能回報不能改，再交給 system-analysis 改列，兩個發現都多走一輪。

```text
發現一：PM 看得到 → 新增 AC-08。
應修正的擁有者：api-plan，在取消預約的契約補上「用餐前 2 小時內無法取消」的錯誤回應。
發現二：看不到的技術問題 → 技術項。
應修正的擁有者：ui-ux-plan，在 UI 契約補上定位 waitlist-cancel。
```

## Rule 4 -- 寫明交辦方式

**強度：MUST**

每個應修正的擁有者都要附上交辦方式。擁有者就是呼叫者時，寫明由呼叫者在這次執行中修正。技術項的擁有者是 clarify-over-specs、spec-by-example、technical-research、system-analysis、Planner、dsl-refine 或 task 而不是呼叫者時，寫明「修正：」已讓這一行成為它的輸入，由它在 plan-package 列出它待補跑時修正，呼叫者不必另外交辦。直接修而擁有者不是呼叫者時，已依發現分類規範 Rule 1 記成技術項，比照技術項處理。其餘情況（新增 AC，以及擁有者是 dev-finding 的技術項）寫明「請交給 <擁有者>」；新增的 AC 依發現分類規範 Rule 1 是提議改變已核准的需求、與它們矛盾時，另寫明 PM 決定前 dsl-refine 不會衍生它、結果維持不能改，建議先執行 dev-finding 的 review 請 PM 決定，不必等到 task 前。呼叫者是相依表中的擁有者、這次的產出又依據這份出錯的資料時，另寫明它這次的結果是「不能改」，不得記錄，維持待補跑到該擁有者改正。以下 Example 皆對照此發現：

```text
呼叫者：dsl-refine（依 AC-03 衍生 `specs/truth/features/backend/取消預約.feature` 時交來四個發現）
發現一：`specs/truth/features/backend/dsl.md` 的「預約 {預約} 的狀態為 {狀態}」與「預約 {預約} 目前是 {狀態}」意思相同 → 技術項；應修正的擁有者：dsl-refine
發現二：`specs/truth/data/預約.dbml` 宣告了外鍵 `fk_bookings_slot_id`，`backend/migrations/0003_bookings.sql` 沒有建立 → 技術項；應修正的擁有者：task
發現三：`contracts/paths/預約/api_bookings_{bookingId}_cancel.yaml` 寫取消後刪除預約，與 AC-03「預約仍列在清單中並標為已取消」不符 → 直接修（違反 AC-03）；應修正的擁有者：api-plan
發現四：dsl-refine 認為用餐前 24 小時以上取消的客人不需要取消通知，提議 FR-004「取消預約時必須寄送取消通知」只在 24 小時內適用 → PM 看得到，新增 AC-09，依據寫明與 FR-004 矛盾；應修正的擁有者：dsl-refine
```

### Good Example

這個範例為四種情況各寫出交辦方式，提醒 dsl-refine 這次因發現三而不能記錄，並為與 FR-004 矛盾的 AC-09 建議先執行 review。

```text
發現一：擁有者就是 dsl-refine，請在這次執行中合併這兩個句型。
發現二：「修正：task」已讓這一行成為 task 的輸入，由 task 在 plan-package 列出它待補跑時排任務，dsl-refine 不必另外交辦。
發現三：直接修，已記成技術項「修正：api-plan」，api-plan 因此成為待補跑，改正時把契約改為取消後保留預約並標為已取消。dsl-refine 這次依 AC-03 衍生的 Rule 依據這份契約，結果是「不能改」，不得記錄，維持待補跑；api-plan 改正後再依差異補跑。
發現四：已新增 AC-09，請交給 dsl-refine。AC-09 與 FR-004 矛盾，PM 決定前 dsl-refine 不會衍生它、結果維持不能改；建議先執行 /dev-finding review 請 PM 決定，不必等到 task 前。
```

### Bad Example

這個範例只寫出擁有者，發現三也沒有記成技術項；dsl-refine 照 AC-03 衍生完就記錄「改了」，api-plan 的輸入沒有變、不會成為待補跑，對話中斷後沒有人交給 api-plan，錯的契約隨交付留在 truth。

```text
發現一：應修正的擁有者 dsl-refine。
發現二：應修正的擁有者 task。
發現三：應修正的擁有者 api-plan。
```
