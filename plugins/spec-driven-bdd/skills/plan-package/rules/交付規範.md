# 交付規範

## Rule 1 -- 五個條件全部成立才可詢問

**強度：MUST**

交付條件有五個：tasks.md 的任務全部勾選、全端點驗證的結果是最新的且沒有失敗、所有 truth owner 的異動紀錄核對通過、沒有待補跑的擁有者、交付階段的交叉檢查通過。交付前的 dev-finding review 改動了 AC 或技術項時，這些條件要在 review 之後重新判定。任一不成立時不得詢問是否交付，也不得以只差一項或與這次無關為由略過。以下 Example 皆對照此檢查結果：

```text
任務：T012、T013 未勾選
全端點驗證：結果是最新的，沒有失敗
truth 異動紀錄：全部 owner 核對通過
待補跑：無
交叉檢查（deliver）：通過
```

### Good Example

這個範例有一個條件不成立，沒有詢問是否交付。

```text
還不能交付：T012、T013 尚未勾選。
```

### Bad Example

這個範例以只剩兩個任務為由照樣詢問，使用者同意後交付的 commit 就不包含這兩個任務的成果，plan 卻被標為已交付。

```text
只剩 T012、T013 兩個任務未勾選，其餘條件都成立。是否交付 004-ranking？
```

## Rule 2 -- 不成立的條件必須逐條列出明細

**強度：MUST**

每個不成立的條件都要列出明細與補齊它的下一步：未勾選任務的編號與標題、失敗的 Example、改了沒記或記了沒改的檔案與所屬 owner、待補跑的擁有者與它變了的輸入、交叉檢查的每個問題與它的交辦對象。成立的條件也要列出。不得自行補做，包括勾選任務、補記異動、替擁有者記錄或修改其他擁有者的產物。以下 Example 皆對照此檢查結果：

```text
任務：T012「更新 README 的啟動說明」、T013「移除連猜三次的前端元件」未勾選
全端點驗證：結果是最新的，沒有失敗
truth 異動紀錄：data-plan 改了沒記 data/房間.dbml
待補跑：data-plan（契約 RoomState.yaml 變了，本 plan 沒有紀錄）
交叉檢查（deliver）：技術項「資料模型宣告了外鍵 fk_x，實際的資料庫沒有建立」的任務 T014 尚未勾選（交給 implement）
```

### Good Example

這個範例逐條列出四個不成立的條件、明細與下一步，也列出已成立的條件。

```text
還不能交付，缺 4 項：
1. 任務未全部勾選：T012「更新 README 的啟動說明」、T013「移除連猜三次的前端元件」。下一步：以 /implement 完成。
2. truth 異動紀錄不一致：data/房間.dbml 改了沒記（data-plan）。下一步：由 data-plan 補記。
3. 有待補跑的擁有者：data-plan（契約 RoomState.yaml 變了，本 plan 沒有紀錄）。下一步：以 /system-analysis 的依差異入口只重跑資料庫端，或直接執行 /data-plan。
4. 交叉檢查未通過：技術項「資料模型宣告了外鍵 fk_x，實際的資料庫沒有建立」的任務 T014 尚未勾選。下一步：以 /implement 完成 T014。
已成立：全端點驗證的結果是最新的且沒有失敗。
```

### Bad Example

這個範例沒有列出明細，還自行補記異動紀錄並替 data-plan 記錄，使用者不知道缺什麼，沒有人判斷過的原因也被寫進紀錄。

```text
還有條件沒完成。我已經把 data/房間.dbml 補記到 truth-changes.md，也替 data-plan 記錄了不用改，請完成剩下的任務後再交付。
```

## Rule 3 -- 詢問必須列出全部檔案與完整訊息

**強度：MUST**

詢問時完整列出將被 commit 的每一個檔案與完整的 commit 訊息，並寫明只會建立一個 commit、不會推送。不得只給檔案數量或摘要，也不得略去看起來與這個 plan 無關的檔案。

### Good Example

這個範例列出每一個檔案、完整的訊息與交付的範圍後才詢問。

```text
五個交付條件都成立。將建立一個 commit（不會推送），包含 5 個檔案：
- ADD specs/plans/004-ranking/spec.md
- ADD specs/plans/004-ranking/truth-changes.md
- ADD specs/truth/contracts/paths/排行/api_rankings.yaml
- MOD backend/app/services/rooms.py
- MOD notes/todo.txt

commit 訊息：
deliver(004-ranking): 排行榜

需求
- 使用者故事 1 查看排行榜（FR-001、NFR-001）

開發發現
- 無

技術修正
- 無

是否以這個 commit 交付 004-ranking？
```

### Bad Example

這個範例只給檔案數量，使用者看不到與這個 plan 無關的 `notes/todo.txt` 也會被 commit，同意後才發現私人筆記進了交付紀錄。

```text
五個交付條件都成立。共 5 個檔案將被 commit，訊息為「deliver(004-ranking): 排行榜」。是否交付？
```

## Rule 4 -- 只有明確同意才可交付

**強度：MUST**

只有使用者明確表示同意交付時才執行交付。提問、附帶條件、要求修改或沒有回覆都不是同意，此時不建立 commit，plan 維持進行中；使用者要求修改時，修改後重新列出並再次詢問。以下 Example 皆對照此回覆：

```text
詢問是否交付後，使用者回覆：標題改成「排行榜與移除連猜三次」
```

### Good Example

這個範例把回覆視為修改要求，修改後重新詢問，沒有交付。

```text
已把標題改為「排行榜與移除連猜三次」。（重新列出檔案與完整訊息）
是否以這個 commit 交付 004-ranking？
```

### Bad Example

這個範例把修改要求當成同意，改完就直接交付，使用者沒有機會確認修改後的訊息與檔案。

```text
已把標題改為「排行榜與移除連猜三次」並完成交付，commit 4d9505a。
```

## Rule 5 -- 只建立一個 commit 且不推送

**強度：MUST**

使用者同意的範圍是建立一個本機的 commit。交付只能透過交付腳本進行，不得另外執行 git commit、把變更拆成多個 commit、修改既有的 commit 或推送到遠端。commit 失敗時回報原因並維持進行中，不得略過 commit hook 重試。

### Good Example

這個範例只執行交付腳本，回報結果並說明沒有推送。

```text
已交付 004-ranking：commit 4d9505a，工作區乾淨，沒有推送。
```

### Bad Example

這個範例在交付後自行推送，使用者同意的只是本機的 commit，推送會把內容發布給其他人，無法收回。

```text
已交付 004-ranking：commit 4d9505a，並已執行 git push origin main。
```
