# 串接規範

## Rule 1 -- 只在改了或不用改時記錄

**強度：MUST**

擁有者每次跑完只有三種結果：改了、不用改、不能改。只有「改了」與「不用改」以 record 記錄；「不能改」不得記錄，也不得改記成「不用改」，讓該擁有者維持待補跑，直到上游擁有者改正，或使用者、PM 的決定改變了它的輸入。以下 Example 皆對照此情境：

```text
dsl-refine 依 AC 衍生規範 Rule 5 先依 AC-03 衍生 Rule，但契約的改答案操作寫「回合轉移給對手」，與 AC-03「甲送出新答案後仍輪到甲」衝突，api-plan 還沒改正
```

### Good Example

這個範例判定為不能改，沒有記錄，dsl-refine 留在待補跑，交付前一定會再被發現。

```text
結果：不能改（上游 api-plan 的契約與 AC-03 衝突，還沒改正）
不執行 record。dsl-refine 維持待補跑。
```

### Bad Example

這個範例因為 feature 已經依 AC 寫完就記成不用改，dsl-refine 不再是待補跑，api-plan 的輸入也沒有變，沒有任何擁有者會再發現契約是錯的，交付時契約與測試互相矛盾。

```bash
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-ranking --owner dsl-refine --result 不用改
```

## Rule 2 -- 記錄必須在產出全部完成之後

**強度：MUST**

record 必須是擁有者這次執行的最後一步：產出、檢查腳本、憲法核對、truth-changes 的 record 都完成之後才記錄。記錄之後同一次執行又改了任何輸入或產出時，改完要重新記錄。

### Good Example

這個範例先完成 truth-changes 的紀錄與核對，最後才記錄這次的結果。

```text
1. 增修 specs/truth/contracts/ 並通過 check_openapi.py
2. truth-changes record 核對通過
3. plan_trace.py record specs/plans/004-ranking --owner api-plan --result 改了
```

### Bad Example

這個範例先記錄再修正檢查發現的問題，紀錄的輸入摘要不是最後的狀態，修正中動到的 ui-contract.md 段落不會讓 api-plan 再被判為待補跑，也看不出記錄後還有修改。

```text
1. 增修 specs/truth/contracts/
2. plan_trace.py record specs/plans/004-ranking --owner api-plan --result 改了
3. 修正 check_openapi.py 回報的問題，並改了 ui/ui-contract.md 的 UI-02 讀到的欄位名稱
```

## Rule 3 -- 不能改必須寫出擋住的對象與交辦對象

**強度：MUST**

結果是不能改時，回報必須寫出三件事後停止：擋住的是哪條規則或憲法條款，或哪個上游事實錯了或缺了（寫出位置）；應交給誰（上游擁有者，或需要決定的使用者、PM）；這次沒有記錄、本 skill 仍是待補跑（check 已記下開始時間，沒有 record 時 plan-package 會一直列出它）。缺的事實屬於 check 的 `upstream_pending` 中還沒補跑的擁有者時，不是上游錯了，寫「不能改：上游待補跑」並交給該擁有者先補跑，不必經 dev-finding 記錄。不得只寫「有衝突」，也不得自行修改其他擁有者的產物來讓自己可以記錄。

### Good Example

這個範例寫出擋住的條款與位置、交給誰，以及沒有記錄。

```text
不能改：AC-12「聊天室一次列出全部訊息」與憲法 C-API-03「列表 API 必須分頁」衝突，api-plan 無法在不違反 AC-12 的前提下化解。
交給：PM 決定修改 AC-12（以 clarify-over-specs 修改需求後，由 spec-by-example 依差異改寫 AC-12），或由使用者修訂 C-API-03。
這次沒有記錄，api-plan 仍是待補跑。
```

### Bad Example

這個範例只說有衝突，自己改了 acceptance 的 AC-12 讓契約可以分頁，PM 沒有機會決定，AC 的擁有者也不知道它的 AC 被改了。

```text
AC-12 與憲法有衝突，已把 AC-12 改成分頁顯示，契約照分頁設計，已記錄改了。
```

## Rule 4 -- 有紀錄時只依差異逐項判斷

**強度：MUST**

check 回報本 skill 有紀錄且是待補跑時，這次的範圍只有 `self.changes` 列出的輸入單位：每個單位都要判斷「連帶異動」（寫出要改自己的哪個產出）、「不受影響」（寫出理由），或「上游衝突」（這個輸入與 AC、FR 或其他上游事實矛盾，寫出位置與應修正的擁有者，這次的結果是不能改），依據是 truth-changes 異動盤點規範 Rule 1、3；只改判為連帶異動的部分，其餘產出不重寫。check 回報 `recorded` 為 false（本 plan 第一次跑、Planner 新排進 Wave，或上次執行沒有完成）時照完整流程執行。被交辦修正時（dev-finding 的回覆、技術項.md 點名本 skill 的行、Planner 回報的上游問題、implement 的交辦、交叉檢查列出交給本 skill 的問題、使用者或 PM 的需求變更），不論本 plan 有沒有紀錄，交辦內容都列入這次的範圍；`self.changes` 另外還有交辦以外的差異時，也必須一併逐項判斷，因為 record 會記下目前全部的輸入，只處理交辦就記錄會把其他差異吞掉。沒有被交辦、本 plan 也沒有紀錄時，照完整流程執行。以下 Example 皆對照此 check 結果：

```json
{"self": {"owner": "data-plan", "recorded": true, "pending": true, "changes": [
  {"status": "MOD", "unit": "truth:contracts/components/schemas/RoomState.yaml"},
  {"status": "MOD", "unit": "plan:truth-changes.md＞api-plan"}]}}
```

### Good Example

這個範例逐項判斷兩個差異，只改受影響的資料表，其他模組檔不重寫。

```markdown
| 差異 | 判斷 | 說明 |
|---|---|---|
| MOD `contracts/components/schemas/RoomState.yaml` | 連帶異動 | 新增的 `rank` 要持久化，`data/房間.dbml` 的 Table `rooms` 加欄位 `rank` |
| MOD `truth-changes.md` ＞ api-plan | 連帶異動 | 同上一列（api-plan 記錄的就是 `rank`） |
```

### Bad Example

這個範例無視差異清單，重新盤點並重寫所有模組檔，工作量與實際影響不成比例，也可能順手改到這次沒有原因的內容。

```text
data-plan 待補跑，重新執行完整流程：重新分析全部介面列並重寫 data/ 底下的 5 個模組檔。
```

## Rule 5 -- 待補跑必須轉述並依序補跑

**強度：MUST**

check 列出待補跑時，必須依 `pending` 的順序轉述每個擁有者、變了的輸入摘要與執行方式（`via`），再繼續呼叫者自己的工作，不得略過或只轉述與自己有關的。呼叫者的 `upstream_pending` 不是空的時，要提醒上游的輸入可能還會變，建議先補跑上游。plan-package 只列出，不替使用者委派其他 skill。

### Good Example

這個範例依序轉述兩個待補跑，提醒上游還沒補跑，然後繼續 dsl-refine 自己的工作。

```text
待補跑（依序）：
1. data-plan：契約 RoomState.yaml 與 api-plan 的異動紀錄變了（本 plan 沒有紀錄，與基準 commit 比較）。執行方式：/system-analysis 的依差異入口只重跑資料庫端，或直接執行 /data-plan。
2. dsl-refine：同上，另有 truth-changes ＞ data-plan。
提醒：上游的 data-plan 還沒補跑，它改了資料模型後 dsl-refine 會再成為待補跑，建議先補跑 data-plan。
（繼續 dsl-refine 的 Phase 1 Step 2）
```

### Bad Example

這個範例只說「有待補跑」就繼續，使用者不知道是 data-plan 還沒判斷契約的異動，對話中斷後也沒有人接手。

```text
plan-package：有待補跑的擁有者。繼續執行 dsl-refine。
```

## Rule 6 -- 交叉檢查的問題交給事實的家

**強度：MUST**

交叉檢查的每個問題都要轉述它的 `home` 與 `next`：問題屬於哪個擁有者的事實，就交給那個擁有者修正；寫「A 或 B」時先判斷錯在哪一邊。不得由發現問題的 skill 直接改其他擁有者的產物，屬於規格沒寫或兩份文件矛盾的，經 dev-finding 記錄後交辦。

### Good Example

這個範例依問題寫明的家交辦，先判斷 testid 錯在哪一邊。

```text
交叉檢查：features/frontend/dsl.md 用到 `ranking-open-button`，UI 契約沒有這個定位。
判斷：dsl-refine 擬定了 UI 契約沒有的 testid，testid 的家是 UI 契約。
交給：ui-ux-plan 在本 plan 的 ui/ui-contract.md 補上（經 dev-finding 記錄，應修正的擁有者 ui-ux-plan）。
```

### Bad Example

這個範例由 task 直接在 UI 契約加上 testid，ui-ux-plan 不知道它的契約被改了，原型與狀態入口也沒有跟著更新。

```text
交叉檢查說 UI 契約沒有 ranking-open-button，我直接把它加進 ui/ui-contract.md 的定位清單。
```

## Rule 7 -- 不得手動改寫串接紀錄

**強度：MUST**

`.plan-trace.json` 只能由 `plan_trace.py record` 寫入。不得手動編輯或刪除它、不得替其他擁有者記錄，也不得為了讓交付條件成立而記錄沒有實際跑過的擁有者。

### Good Example

這個範例在 data-plan 待補跑時交由它判斷，判斷完才由它自己記錄。

```text
交付條件不成立：data-plan 待補跑。下一步：以 /system-analysis 的依差異入口只重跑資料庫端，data-plan 判斷後自己記錄。
```

### Bad Example

這個範例為了讓交付條件成立，替沒有跑過的 data-plan 記錄不用改，契約新增的 `rank` 沒有人判斷要不要持久化，資料模型與契約不一致就被交付。

```bash
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-ranking --owner data-plan --result 不用改
```

## Rule 8 -- 多人共寫的產物只改自己的節

**強度：MUST**

多個 skill 共寫的產物以節定義擁有者，每個 skill 只能新增、修改自己的節，需要改其他節時交給該節的擁有者：

| 產物 | 節 | 擁有者 |
|---|---|---|
| spec.md | 使用者故事、FR、NFR、SC、邊界情況、關鍵實體、假設、受影響的既有功能 | specify 建立；plan 進行中由 clarify-over-specs（需求變更、保留並取代）與 spec-by-example（驗收澄清的答案）修改 |
| spec.md | 釐清紀錄的每個場次 | 舉辦該場次的 skill，只新增自己的場次，歷史場次不改 |
| acceptance | 未標 `@開發發現` 的 AC、Rule 標頭與 Background | spec-by-example |
| acceptance | 標 `@開發發現` 的 AC | dev-finding |
| tasks.md | Phase 與任務 | task |
| tasks.md | 任務的勾選 | implement |
| truth-changes.md | 每個 truth owner 的一節 | 節名稱的 owner |

### Good Example

這個範例中 spec-by-example 只改自己的 AC，發現 @開發發現 的 AC-09 與 AC-08 矛盾時交給 dev-finding 的 review 由 PM 決定。

```text
AC-08 依澄清答案改寫完成。AC-09（@開發發現）與新的 AC-08 矛盾，交給 dev-finding 的 review 請 PM 決定保留或刪除。
```

### Bad Example

這個範例中 spec-by-example 順手刪掉 @開發發現 的 AC-09，PM 從沒審過這個刪除，dev-finding 的 review 也找不到它曾經存在。

```text
AC-08 改寫完成，並刪除與它矛盾的 AC-09（@開發發現）。
```

## Rule 9 -- 刪除的編號不得重用

**強度：MUST**

FR、NFR、SC、使用者故事、AC、研究決策（R-xx）、介面 ID 與憲法條款 ID 被刪除後，新的項目一律取既有最大編號加一，不得重用被刪除的編號。依據：編號是其他文件引用這個事實的識別碼（上下游一致原則第 1 條），已交付的 plan 不能修改，重用會讓既有的引用（含已交付 plan 中的引用）指到不同的事實。

### Good Example

這個範例的 FR-004 已被刪除，新的需求取最大編號加一。

```markdown
- **FR-016**：結果畫面必須顯示這場對局的總回合數。
```

### Bad Example

這個範例重用被刪除的 FR-004，truth-changes.md 中原因寫 FR-004 的列、已交付 plan 引用的 FR-004，都會被讀成「顯示總回合數」，追溯到錯的需求。

```markdown
- **FR-004**：結果畫面必須顯示這場對局的總回合數。
```

## Rule 10 -- 先前 plan 留下的問題只提醒

**強度：MUST**

交叉檢查的 `warnings` 是基準時就存在、本 plan 也沒有改到它所在那一列的問題，不擋傳遞與交付。check 與 deliver 時必須逐一轉述每個提醒，並建議交付後另開技術修正 plan，以技術項交給問題的家修正；不得要求本 plan 的擁有者在這次修正，也不得略過不說。以下 Example 皆對照此交叉檢查結果：

```json
{"ok": true, "problems": [], "warnings": [
  {"check": "techstack 與 research", "detail": "techstack.md 第 42 行：「聊天頻率限制」的技術欄重述了以下內容：原始碼檔案或目錄 `backend/app/limits.py`。…", "home": "technical-research",
   "next": "先前 plan 留下、本 plan 沒有改到的問題，不擋本 plan 的傳遞與交付；交付後另開技術修正 plan，以技術項交給 technical-research 修正"}]}
```

### Good Example

這個範例在交叉檢查通過時仍轉述提醒，寫明不擋交付與之後的處理方式。

```text
交叉檢查通過。
提醒（先前 plan 留下，不擋交付）：techstack.md 第 42 行「聊天頻率限制」重述了原始碼檔案 `backend/app/limits.py`。建議這個 plan 交付後另開技術修正 plan，以技術項交給 technical-research 修正。
```

### Bad Example

這個範例把提醒當成本 plan 的問題，要 technical-research 這次就修正；與本 plan 需求無關的 truth 被一起改動，techstack.md 的差異也讓讀它的下游擁有者全部成為待補跑。

```text
交叉檢查有提醒：techstack.md 第 42 行重述了原始碼檔案。請先以 /technical-research 修正後再繼續。
```
