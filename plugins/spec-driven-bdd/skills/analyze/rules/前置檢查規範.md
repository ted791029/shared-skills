# 前置檢查規範

## Rule 1 -- 只有產物缺漏才停止分析

**強度：MUST**

只有 collect_artifacts.py 輸出的 `missing` 不為空（plan 與 `specs/truth/` 的必要產物、truth 用語表登記的端點資料夾、Planner、truth-changes.md 中該 Planner 的紀錄或介面文檔缺漏）時才停止分析並詢問使用者。check_plan.py、check_tasks.py 或 plan-package 的交叉檢查回報問題、plan-package check 回報待補跑，或 collect_artifacts.py 回報 `endpoints_without_cases` 時都不得停止，必須繼續分析，並把它們列為發現事項。

### Good Example

這個範例在產物齊全、只有 check_tasks.py 回報問題時繼續分析，把腳本回報的問題帶入發現事項。

```text
collect_artifacts.py：missing 為空
check_tasks.py：1 個問題（L124 T022 寫 5 條 Rule、8 個 Example，specs/truth/features/backend/平鋪預覽.feature 實際 6 條 Rule、9 個 Example）
→ 繼續建立追溯模型，T022 的數量問題列入發現事項。
```

### Bad Example

這個範例因為 check_tasks.py 回報一個數量問題就停止分析，使用者只拿到一個問題，其他跨產物的覆蓋缺口與不一致都沒有被找出，修完再跑才又發現下一批。

```text
check_tasks.py：1 個問題（L124 T022 寫 5 條 Rule、8 個 Example，specs/truth/features/backend/平鋪預覽.feature 實際 6 條 Rule、9 個 Example）
→ 停止分析，請先修正 tasks.md 後再執行 /analyze。
```

## Rule 2 -- 缺漏必須對應上游 skill

**強度：MUST**

列出缺漏時，每項缺漏必須寫出產出它的上游 skill，並只建議先執行最上游的那一個。對應如下，上游順序由上而下：

| 缺漏 | 上游 skill |
|---|---|
| spec.md、truth-changes.md | specify |
| `features/acceptance/` | spec-by-example |
| research.md、`specs/truth/techstack.md` | technical-research |
| plan.md、缺少的 Planner、介面文檔（plan 的 `ui/`、truth-changes.md 中該 Planner 的紀錄與它列出的檔案） | system-analysis |
| `features/涵蓋表.md`、`specs/truth/features/用語表.md`、用語表登記的端點資料夾（含 dsl.md 與 feature） | dsl-refine |
| tasks.md | task |

### Good Example

這個範例為每項缺漏寫出上游 skill，並只建議先執行最上游的 spec-by-example。

```text
specs/plans/001-photo-album-organizer 缺少以下產物，無法分析：
- specs/plans/001-photo-album-organizer/features/acceptance/（spec-by-example）
- specs/plans/001-photo-album-organizer/features/涵蓋表.md、specs/truth/features/frontend/、specs/truth/features/backend/（dsl-refine）
- specs/plans/001-photo-album-organizer/tasks.md（task）

請先執行 /spec-by-example，再依序產出後續產物。
```

### Bad Example

這個範例只列出缺漏檔名，並建議直接執行 /dsl-refine，使用者照做後 dsl-refine 會因缺少驗收 feature 而再次停下。

```text
缺少 features/acceptance/、features/涵蓋表.md、tasks.md，請先執行 /dsl-refine。
```

## Rule 3 -- 待補跑的擁有者各列一項並排在下一步最前面

**強度：MUST**

Phase 1 的 plan-package check 回報的 `pending` 不為空時，表示有擁有者讀到的輸入在它上次跑完之後又變了（或本 plan 還沒有它的紀錄），它的產出與下游的 tasks.md 可能已經過時。每個待補跑的擁有者必須列為一個不一致：位置以「vs」列出該擁有者的產出與 `changes` 中變了的輸入單位，摘要寫出變了什麼，建議寫出 `via` 的執行方式；待補跑的是 Planner、而 collect_artifacts.py 的 `wave_report` 中它的狀態是「不能改」時，它是被規則、條款或上游事實擋住，建議改寫 `wave_report.blocked` 列出的擋住對象與應交給的使用者或 PM，不得建議直接補跑。下一步依 check 列出的順序（上游到下游）寫在最前面，並寫明補跑完重新執行 `/analyze`。有待補跑時 check 不執行交叉檢查，前置檢查的交叉檢查寫「—」並說明有待補跑、check 未執行；`pending` 為空時引用 `cross_check` 的結果，不自行重做交叉檢查。

### Good Example

這個範例把兩個待補跑的擁有者各列一項：wave-report 寫不能改的 api-plan 交給 PM 決定，不建議直接補跑；task 依 check 的順序排在後面，交叉檢查寫明未執行。

```text
plan-package check：pending 依序為 api-plan（MOD features/acceptance/房間聊天.feature ＞ AC-01）、task（MOD specs/truth/features/backend/房間聊天.feature ＞ Rule「聊天訊息必須依送出順序出現在房內雙方的聊天紀錄」）
wave_report：後端 api-plan 不能改；blocked：C-API-03「列表 API 必須分頁」與 AC-01「一次列出全部訊息」衝突，應交給 PM
I1 | 不一致 | CRITICAL | specs/truth/contracts/（api-plan）vs features/acceptance/房間聊天.feature ＞ AC-01（MOD） | api-plan 回報不能改：C-API-03 要求列表 API 分頁，AC-01 要求一次列出全部訊息 | 交給 PM 決定修改 AC-01，或由使用者以 /constitution 修訂 C-API-03，決定後再補跑 /api-plan
I2 | 不一致 | CRITICAL | tasks.md vs specs/truth/features/backend/房間聊天.feature ＞ Rule「聊天訊息必須依送出順序出現在房內雙方的聊天紀錄」（MOD） | 這條 Rule 在 task 上次拆解之後改了，tasks.md 沒有它的任務 | I1 解決後以 /task 的增量入口追加任務
前置檢查：交叉檢查 — 有待補跑，check 未執行
下一步：先由 PM 決定 I1 的衝突，再依序執行 /api-plan、/task，完成後重新執行 /analyze
```

### Bad Example

這個範例只檢查目前的 tasks.md 與 feature，沒有列出待補跑，data-plan 還沒判斷契約新增的欄位，實作照著缺欄位的資料模型做，到交付前才被 plan-package 擋下，已完成的任務要重做。

```text
plan-package check：pending 依序為 data-plan、task
需求覆蓋全部 ✅，結論：可以進入 `/implement`。
```

## Rule 4 -- 這次沒有案例的畫面或 API 端點只列一項

**強度：MUST**

collect_artifacts.py 的 `endpoints_without_cases` 列出這次有新增或修改介面、plan 的涵蓋表卻沒有任何一列落在其端點資料夾的端點，代表 dsl-refine 沒有為它產出這次的案例（例如只完成部分端點）。`behavior` 為 true 的畫面或 API 端點，每個端點只列一個覆蓋缺口：位置以「vs」列出 plan.md 介面盤點中這些介面的列與涵蓋表，建議先以 `/dsl-refine` 補齊該端點、再以 `/task` 更新 tasks.md；該端點的介面與只能由它驗證的需求在覆蓋表照常判定，備註寫這個發現事項的 ID，不另列發現事項。`behavior` 為 false 的儲存端點沒有儲存結構或約束的案例時，dsl-refine 本來就不產生它的資料夾，只在前置檢查的端點資料夾說明寫出，它的介面照常依介面文檔覆蓋判定。

### Good Example

這個範例把前端沒有案例列為一項，UI 介面與只能由前端驗證的需求在覆蓋表照常判 ❌，備註指回 C1。

```text
endpoints_without_cases：UI（frontend）UI-01～UI-03，behavior true，涵蓋表沒有任何一列的端點是 frontend
C1 | 覆蓋缺口 | CRITICAL | plan.md:L69-71（UI-01～UI-03）vs features/涵蓋表.md | 前端這次有 3 個介面異動，dsl-refine 沒有為 frontend 產出任何案例，tasks.md 也沒有前端的 Feature Phase | 先執行 /dsl-refine 補齊 frontend 的案例，再以 /task 更新 tasks.md
介面文檔覆蓋：UI-01、UI-02、UI-03 ❌（C1）；需求覆蓋：FR-009、NFR-009、NFR-010 ❌（C1）
```

### Bad Example

這個範例把同一個原因拆成十多個覆蓋缺口，使用者看不出是 dsl-refine 漏了整個前端，可能逐項手動補任務，各項的嚴重度也依個別需求判得高低不一。

```text
C1 | 覆蓋缺口 | MEDIUM | ui/ui-contract.md › UI-01 | 沒有 Rule 操作
C2 | 覆蓋缺口 | MEDIUM | ui/ui-contract.md › UI-02 | 沒有 Rule 操作
C3 | 覆蓋缺口 | HIGH | spec.md:L83（FR-009） | 沒有落點
（共 14 項）
```
