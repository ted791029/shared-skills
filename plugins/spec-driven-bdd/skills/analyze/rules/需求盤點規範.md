# 需求盤點規範

## Rule 1 -- SC 依量測對象判定是否需要建置

**強度：MUST**

每個 SC 必須先找出它量測的對象（要算的時間、比率、次數或檢測結果），再依下列方式判定：

- 量測對象只由系統的輸出決定（回應與送達時間、容量、資料與畫面的正確性、存取控制、無障礙檢測結果），判為需要建置並列入覆蓋；寫成「次數為 0」「100% 的玩家」等上線後的統計說法也一樣，因為上線前就能以 Rule、量測工具或檢測工具驗證。
- 量測對象取決於真實使用者的行為、理解或感受，或營運結果（首次使用成功率、在時限內完成的使用者比例、滿意度、留存、客服工單數），判為上線後才能量測，不列入覆蓋，並在報告的「不列入覆蓋的成功標準」寫出理由。
- 同一個 SC 兩者都有時拆開判定：系統的部分列入覆蓋，使用者的部分寫進「不列入覆蓋的成功標準」。

列入覆蓋的 SC 依量測對象寫出落點類型：行為保證由驗證該行為的 Rule 承接；時間、容量等量化門檻另需建立量測工具的任務；無障礙等規範檢測另需執行檢測工具的任務。

### Good Example

這個範例先找出每個 SC 的量測對象再判定：寫成次數的 SC-003 只由存取控制決定，列入覆蓋；取決於使用者學習的 SC-005 排除並附理由；SC-007 拆成鍵盤操作與無障礙檢測兩種落點。

```text
SC-001「玩家送出有效聊天訊息後，95% 的情況在 1 秒內雙方都看到該訊息」→ 需要建置：送達時間由系統決定（量化門檻，需要量測工具的任務）
SC-003「新加入者或其他房間的玩家取得前一段同房期間聊天訊息的次數為 0」→ 需要建置：只由存取控制決定（行為保證，由驗證存取控制的 Rule 承接）
SC-005「首次使用的玩家在沒有說明的情況下，90% 能在進房後 30 秒內送出第一則聊天訊息」→ 不列入覆蓋：取決於玩家能否自己找到並學會聊天，上線後才能量測
SC-007「聊天功能的所有操作皆可僅以鍵盤完成，且 WCAG 2.1 AA 無障礙檢測零嚴重違規」→ 需要建置：鍵盤操作為行為保證，WCAG 檢測需要執行檢測工具的任務
```

### Bad Example

這個範例看到「次數」「90%」就依字面判定：只由系統決定的 SC-003、SC-006 被排除，存取控制與「聊天不影響對局」的保證不再檢查覆蓋，少了 Rule 也不會被發現；取決於玩家學習的 SC-005 反而列入覆蓋，永遠找不到能實作它的任務，被誤報為覆蓋缺口。

```text
SC-003、SC-006「…的次數為 0」→ 不列入覆蓋：要上線後統計次數
SC-005「…90% 能在進房後 30 秒內送出第一則聊天訊息」→ 需要建置：送出訊息的時間由系統決定 → ❌ 沒有任務
```

## Rule 2 -- 沒有新增行為的需求以既有驗證判定

**強度：MUST**

需求只要求驗證方式（如自動化驗收、量測、壓測），或只要求先前 plan 留下的規則維持有效時，沒有新增的系統行為，覆蓋必須以驗證證據判定，不得因為沒有對應介面或 Feature Phase 而列為覆蓋缺口：

- 只要求驗證方式：它點名的行為都有 feature Rule 驗證，且 tasks.md 有 Verify 任務，判 ✅；要求量測的門檻（如 p95、容量）另需有建立量測工具的任務，沒有時判 ⚠️ 部分。
- 先前 plan 留下的規則維持有效：必須在 `specs/truth/features/` 中找到驗證該規則的 Rule（涵蓋表以「無」登記的列即是，見追溯 JSON 的 `existing_rules`），並在備註寫出端點、feature 與 Rule 名稱及「由既有 Rule 與 Verify 驗證」，才判 ✅；需求列出的規則有任何一條找不到對應 Rule 時判 ⚠️ 部分，建議由 dsl-refine 補案例。

### Good Example

這個範例把只要求驗證的 NFR-023 以 feature、Verify 與量測任務判定，把沿用 001 規則的 FR-035 逐條找出 truth 中的既有 Rule，找不到的部分判為部分覆蓋。

```text
NFR-023「驗收情境與效能、容量 NFR 都必須能自動化驗證」
→ 驗收情境：各 feature 的 Rule 與 T051（Verify）；效能：T046 的 perf.js 量測 p95 → ✅

FR-035「001 規格的規則必須維持有效，包含房主先手、每回合 60 秒倒數與回合逾時、離線判定與不限猜測次數」
→ 回合逾時：specs/truth/features/backend/回合逾時.feature › 回合逾時必須判輪到的玩家落敗（涵蓋表「無」）
→ 離線判定：specs/truth/features/backend/離開與斷線.feature › 遊戲中離開或斷線的玩家必須判負（涵蓋表「無」）
→ 不限猜測次數：truth 的 feature 沒有對應 Rule
→ ⚠️ 部分：由既有 Rule 與 Verify 驗證，不限猜測次數建議由 dsl-refine 補案例
```

### Bad Example

這個範例把只要求驗證的 NFR-023 判為範圍外，又只因 truth 的 feature 檔案存在就把 FR-035 判為完整覆蓋，不限猜測次數沒有任何測試保護，被新功能改壞時 Verify 也不會失敗。

```text
NFR-023 → ➖ 範圍外：tasks.md 不含測試
FR-035 → ✅ specs/truth/features/backend/ 仍有回合逾時.feature
```

## Rule 3 -- 跨領域需求不要求對應介面

**強度：MUST**

不屬於特定畫面、API、資料表或儲存區的需求（如安全、相容性、可維護性、設定管理），必須判定為跨領域需求。跨領域需求沒有出現在 plan.md 介面盤點時，不得只因此列為發現事項，覆蓋改由下列落點判定：Setup、Foundational、Polish 任務，Phase 標頭或任務的 NFR 約束，NFR 重構任務，以及 NFR 重構 Phase「不另列任務」中附理由的條目。需求明確指向特定操作時（如某操作的回應時間），不屬於跨領域。

### Good Example

這個範例把設定管理的 NFR-018 判為跨領域，由 Foundational 任務的 NFR 約束與「不另列任務」判定落點；指向特定操作的 NFR-014 不屬於跨領域，依前端 Phase 的 NFR 約束判定。

```text
NFR-018「照片庫只能由使用者本人存取」→ 跨領域：T005 的 NFR 約束；「不另列任務」（tasks.md:L255）寫明後端只監聽 127.0.0.1
NFR-014「所有點擊、按鍵、拖放 200ms 內要有可見回饋」→ 指向 UI 操作：Phase 6、8、11、14 的 NFR 約束
```

### Bad Example

這個範例只看 Setup、Foundational、Polish 任務，NFR-018 與 NFR-019 的 NFR 約束與「不另列任務」都被略過而誤報為覆蓋缺口，使用者會為已落實的需求再加任務。

```text
NFR-018、NFR-019 → plan.md 介面盤點沒有對應介面，Setup、Foundational、Polish 也沒有任務，列為覆蓋缺口
```
