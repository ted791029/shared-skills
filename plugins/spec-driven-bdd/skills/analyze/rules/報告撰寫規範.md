# 報告撰寫規範

## Rule 1 -- 狀態欄只用固定的用詞

**強度：MUST**

報告各表的狀態欄只能使用下表的用詞，不得寫「正常」「已檢查」「OK」等自訂用語。

| 欄位 | 用詞 |
|---|---|
| 分析範圍的狀態 | 沒有發現事項的位置在這份產物時寫「✅」；有時寫「⚠️」加上這些發現事項的 ID，依發現事項表的順序排列，例如「⚠️ U1、C1、I1」 |
| 前置檢查的結果 | 通過寫「✅」；有問題寫「❌」，說明寫出問題或併入的發現事項 ID；不擋分析、但要讓使用者知道的情況（例如儲存端點沒有這次的案例）寫「⚠️」；沒有可檢查的對象寫「—」，說明寫出原因 |
| 需求覆蓋、受影響的既有功能與介面文檔覆蓋的狀態 | 覆蓋判定的「✅」「⚠️ 部分」「❌」；介面異動為「無」時寫「—（不檢查）」，DEL 寫「—（由移除任務處理）」 |

### Good Example

這個範例的分析範圍以 ⚠️ 加上指向該產物的發現事項 ID 標示，前置檢查沒有可檢查的對象時寫「—」並說明原因。

```markdown
| `spec.md` | specify、clarify-over-specs | — | ⚠️ C1、A1、I4、I5、D1、U2 |
| `research.md` | technical-research | — | ⚠️ I6 |
| `specs/truth/techstack.md` | technical-research | — | ✅ |

| 交叉檢查（plan-package） | — | 有待補跑，check 未執行 |
```

### Bad Example

這個範例用自訂的用語，使用者看不出「有問題」與「已檢查」差在哪裡，也找不到指向這份產物的發現事項，要回頭逐列翻找發現事項的位置欄。

```markdown
| `spec.md` | specify、clarify-over-specs | — | 有問題 |
| `research.md` | technical-research | — | 已檢查 |
| `specs/truth/techstack.md` | technical-research | — | OK |
```

## Rule 2 -- 憲法的載入結果寫在前置檢查的憲法列

**強度：MUST**

前置檢查的「憲法」列必須寫出這次分析的憲法來源，不得省略這一列，也不得只在發現事項或結論中帶過：`.claude/constitution/CONSTITUTION.md` 存在時，說明寫憲法版本與這次載入的條款編號，結果依有沒有憲法違反寫「✅」或「❌」（列出 V 開頭的發現事項 ID）；`CONSTITUTION.md` 不存在時，結果寫「—」，說明寫專案沒有憲法、沿用各 skill 的內建規範、不偵測憲法違反；目錄沒有這次產物的條款時，結果寫「—」並寫明原因。產物引用了專案中不存在的憲法（例如 research.md 引用的憲法原則）時，仍另列為不一致。

### Good Example

這個範例在專案沒有憲法時寫「—」並說明沒有偵測憲法違反；有憲法時寫出版本、載入的條款與違反的發現事項。

```markdown
| 憲法 | — | 專案沒有 `.claude/constitution/CONSTITUTION.md`，沿用各 skill 的內建規範，不偵測憲法違反 |

| 憲法 | ❌ | CONSTITUTION.md v1.2.0，載入 C-API-01～C-API-03、C-DATA-01；V1 |
```

### Bad Example

這個範例在專案沒有憲法時仍寫「✅ 沒有違反」，讀者以為產物已通過憲法核對，之後訂了憲法也不知道這次其實沒有核對過。

```markdown
| 憲法 | ✅ | 沒有違反 |
```
