# 覆蓋判定規範

## Rule 1 -- 覆蓋狀態依落點判定

**強度：MUST**

每個需求與介面的覆蓋狀態必須依下表判定，不得自訂其他狀態。落點包括：經 Rule 2 確認的 Feature Phase 綠燈、Phase 標頭或任務的 NFR 約束、NFR 重構任務、其他 Phase 中實作它的任務，以及經 Rule 2 確認、這次不改的既有 Rule（涵蓋表中異動為「無」的列，即追溯 JSON `requirement_trace` 的 `existing_rules`，以及依 Rule 2 在 `specs/truth/features/` 中找到、沒有登記在涵蓋表的 Rule；由 Verify 驗證，不需要任務，任務欄寫「既有 Rule＋Verify」）。NFR 只出現在「不另列任務」時，追溯 JSON `nfr_landing` 的 `phase_checks` 與理由相符（理由說已是某 Phase 的 NFR 約束，該 Phase 確實有），或理由說明已由 Rule、既有設定滿足且可查證時才算落點；不相符時不算落點，發現事項依 Rule 6 列出。

| 狀態 | 判定 |
|---|---|
| ✅ | 需求的每個操作、條件與門檻都有落點 |
| ⚠️ 部分 | 有落點，但部分操作、條件或門檻沒有落點，或需要建置的量測工具沒有任務 |
| ❌ | 沒有任何落點 |

### Good Example

這個範例中 NFR-013 要求匯入、開啟相簿、拖放排序都符合回應時間，但只有相簿頁與排序的 Phase 帶 NFR 約束，判為部分覆蓋並寫出缺少的部分。

```text
NFR-013「匯入、開啟相簿、拖放排序的回應時間必須符合 SC-001、SC-003、SC-004」
→ Phase 7（T023）、Phase 10（T032）的 NFR 約束；T046 的列表彙總查詢與 p95 量測
狀態：⚠️ 部分 — Phase 5 backend/匯入與分組 的標頭沒有 NFR-013，匯入的回應時間沒有落點
```

### Bad Example

這個範例只要有一個任務就判為完整覆蓋，匯入的回應時間缺口被隱藏，實作完成後才在驗收時被發現。

```text
NFR-013 → T046
狀態：✅
```

## Rule 2 -- 候選任務必須依 Rule 確認

**強度：MUST**

追溯 JSON `requirement_trace` 的 `via_ac`、`via_supplement`、`via_interface`、`existing_rules` 都只是候選：同一個 AC 涵蓋的需求不一定由每個端點的 feature 驗證；經介面連到的任務（`via_interface`）只是操作到該介面段落的任務，不一定驗證這個需求，`unmapped_interfaces` 列出的介面沒有以介面 ID 開頭的段落，要先依 Rule 3 把 operation、Table 對應到介面，再以那些段落的 `tasks` 作為候選；AC 的「無」列也不一定驗證那個 AC 涵蓋的每個需求。必須讀候選任務範疇內這次新增與修改的 Rule（任務的 `scoped_rules`、`scope_features[].rules` 與 feature 原文）或「無」列的 Rule，確認有 Rule 驗證該需求，才把該 Phase 的綠燈或「既有 Rule＋Verify」填入覆蓋表的任務欄；`direct` 也要確認不是只順帶提到需求編號。需求或需求的某一部分在所有候選中都沒有驗證它的 Rule 時（如 SC，以及 Rule 登記在其他需求編號下的需求），必須以 Rule 名稱與內容在 `specs/truth/features/` 中尋找驗證它的 Rule；找到的既有 Rule 算落點，沒有登記在涵蓋表時只在備註寫明，不列為發現事項。`acceptance_without_coverage` 列出的 AC 在涵蓋表沒有任何一列，表示它沒有衍生到任何端點，它涵蓋的需求不得以這個 AC 判定覆蓋，必須列為覆蓋缺口並建議由 dsl-refine 衍生。

### Good Example

這個範例從 3 個 Phase 的候選中，只保留範疇 feature 確實有 Rule 驗證相簿名稱的 Phase。

```text
FR-006「相簿名稱以拍攝日期顯示」
via_ac：AC-01 → Phase 3、5、6（T010～T012、T016～T021）
讀 Rule：database/匯入與分組 只驗唯一索引與外鍵；backend/匯入與分組 有「相簿必須以拍攝日期命名」；frontend/匯入與分組 有「相簿卡片必須顯示拍攝日期名稱」
確認後：T017、T020
```

### Bad Example

這個範例把候選任務全部填入，FR-006 看起來被 9 個任務覆蓋，資料庫端根本沒有驗證相簿名稱，真正缺漏的需求混在大量無關任務裡，覆蓋表失去判讀價值。

```text
FR-006 → T010、T011、T012、T016、T017、T018、T019、T020、T021
```

## Rule 3 -- 介面文檔覆蓋看主要段落的涵蓋

**強度：MUST**

只檢查這次異動為 ADD 或 MOD 的介面（`interface_trace` 的 `checked`）與這次異動的段落（`doc_sections` 的 `changed`）：異動為「無」的介面不檢查，DEL 的介面與 `deleted_docs` 由 check_tasks.py 檢查移除任務，先前 plan 留下、這次沒有異動的段落不列為問題。介面的主要段落包括 Markdown 以介面 ID 開頭的段落、OpenAPI 路徑檔的 operation、DBML 模組檔的 Table、儲存契約的儲存區段落，以及其他格式介面文檔的頂層定義（追溯 JSON 中 kind 為 `definition` 的段落，如 GraphQL 的 `type`、protobuf 的 `service`）；`unindexed_docs` 列出的文檔必須讀原文找出主要段落。主要段落有 Rule 操作或查證它（`rule_count` 大於 0：Rule 的步驟、表格，或步驟對到的 dsl.md 句型提到它的定位值），或被任何必讀指向（`anchored_by`，Phase 標頭的必讀算該 Phase 的每個任務）時才算涵蓋；`rule_count` 是字面比對的候選，只出現在測試資料清理等非驗證用途時不算。異動為 MOD 的段落含有沿用的元素，必須有這次的 Rule（`scoped_rules`）操作或查證這次新增或改變的部分才算涵蓋；operation 的 `change` 為空表示與基準 commit 相同，這次沒有改變，不檢查。只有 schema 被引用而 operation 沒有時，該 operation 不算涵蓋。介面的負責任務是它的主要段落的 `tasks`（範疇含操作或查證該段落的這次 Rule 的任務，加上必讀指向它的任務），不得以介面 ID 前綴把同端點的任務都算進來：以介面 ID 開頭的段落由 `interface_trace` 的 `tasks` 直接給出（`mapped` 為 true；多個介面共用同一個定位值時，同一個任務會對到它們，要讀 Rule 確認），operation、Table 與頂層定義依其描述與欄位對應到介面盤點的介面後，合併這些段落的 `tasks`。Feature Phase 依設計不列範疇所屬端點自己的介面文檔，不得因此判未覆蓋。介面的每個主要段落都涵蓋、有負責任務，且 operation 的回應依 Rule 7 都涵蓋時才判 ✅。

### Good Example

這個範例以每個 operation 的 `rule_count` 與 `tasks` 判定，getAlbum 沒有任何 Rule 操作、也沒有必讀指向，判為未涵蓋，API-02 為部分覆蓋；負責任務只合併三個 operation 的 `tasks`，Phase 7 標頭沒有列 contracts/ 的路徑檔不影響判定。

```text
API-02：listAlbums（rule_count 4，tasks T016～T018）、moveAlbum（rule_count 3，tasks T031～T033；anchored_by：T034～T036）、getAlbum（rule_count 0，tasks 無）
負責任務：T016～T018、T031～T036
狀態：⚠️ 部分 — getAlbum 沒有任何 Rule 操作，綠燈不會實作它
```

### Bad Example

這個範例以介面 ID 前綴把 backend 的每個 Feature Phase 都算成 API-02 的負責任務，沒有任何 Rule 操作的 getAlbum 被藏住；又因為 Phase 標頭的必讀沒有列契約就把 API-03 判為未覆蓋，使用者會把 bdd 本來就會整份讀的介面文檔塞回必讀。

```text
API-02：負責任務 T016～T018、T022～T024、T031～T033、T040～T042（backend 的每個 Feature Phase）→ ✅
API-03：Phase 7、13 的必讀沒有 contracts/ 的路徑檔 → ❌
```

## Rule 4 -- 支撐任務不列為反向覆蓋問題

**強度：MUST**

追溯 JSON 的 `tasks_without_requirement` 已排除 Setup、Foundational、移除、技術項、Polish、Verify 的支撐任務與只重新執行範疇的 [重跑] 任務（移除與技術項是否涵蓋每一列 DEL 與每一行技術項由 check_tasks.py 檢查），支撐任務只在報告中彙總說明，不列為發現事項；清單中的任務必須逐一判斷。Feature Phase 的任務出現在清單中，代表範疇內沒有這次新增或修改、並以 ADD 或 MOD 登記在涵蓋表的 Rule（例如範疇 feature 這次沒有異動），必須列為覆蓋缺口，並建議由 task 移除該 Phase，或由 dsl-refine 補登涵蓋表；check_tasks.py 已回報同一個 Phase 時，與它合併為一個發現事項。

### Good Example

這個範例把 Setup、Foundational、Polish 與 Verify 的任務彙總說明，不列為發現事項。

```text
未對應需求的任務：無。T001～T004、T006、T008、T009 是 Setup 與 Foundational 基礎建設，T049、T050 是 Polish 收尾，T051 是 Verify，屬於合理的支撐任務；這個 plan 沒有移除與技術項的任務。
```

### Bad Example

這個範例把支撐任務逐一列為「未對應需求」的發現事項，真正有問題的任務被淹沒，使用者也可能誤刪必要的基礎建設與驗證任務。

```text
C4：T001 沒有對應需求
C5：T002 沒有對應需求
C6：T051 沒有對應需求
```

## Rule 5 -- 受影響的既有功能必須有對應的異動

**強度：MUST**

spec.md「受影響的既有功能」的每一項，必須在追溯 JSON `affected_functions` 的 `changes`（truth-changes.md 中該功能的 feature、`contracts/paths/<模組>/`、`data/<模組>.dbml` 的列，以及涵蓋表中該功能的 feature 以 ADD 或 MOD 登記的列）找到與這一項影響相符的修改或刪除，影響的每一部分都要有對應才判 ✅。只對應到一部分時判 ⚠️ 部分，完全沒有對應時判 ❌，兩者都列為覆蓋缺口，並建議由負責那類 truth 的 owner（dsl-refine、api-plan、data-plan）補改；`module_found` 為 false 時，列為不一致（名稱不在 truth 用語表的「模組」表）。只是 `changes` 不為空不算對應，必須讀列的改動摘要確認內容相符。以下 Example 皆對照此 spec.md 與追溯 JSON：

```text
spec.md 受影響的既有功能：房間：入口畫面多了開啟排行榜的入口；玩法說明不再介紹連猜三次。
affected_functions 的 changes：
- 涵蓋表：frontend/進入房間.feature › 入口畫面必須有開啟排行榜的按鈕（ADD）
```

### Good Example

這個範例逐一比對影響的兩部分，玩法說明沒有任何對應的修改，判為部分覆蓋並指出缺口。

```text
房間：開啟排行榜的入口 → frontend/進入房間.feature 新增 Rule；玩法說明 → 沒有對應
狀態：⚠️ 部分 — frontend/玩法說明.feature 的「入口畫面的玩法說明必須介紹改答案與連猜三次」沒有修改，建議由 /dsl-refine 修改
```

### Bad Example

這個範例只因 `changes` 不為空就判為完整覆蓋，玩法說明仍會介紹已移除的連猜三次，Verify 也不會失敗。

```text
房間：changes 1 筆 → ✅
```

## Rule 6 -- 不相符的「不另列任務」與它造成的缺口只列一項

**強度：MUST**

NFR 只寫在「不另列任務」、理由又與 tasks.md 或 Rule 的實際內容不相符時（例如理由說已是某 Phase 的 NFR 約束，`nfr_landing` 的 `phase_checks` 卻是 false），那一行不算落點。這個 NFR 因此判 ⚠️ 部分或 ❌ 時，只列一個覆蓋缺口：位置欄以「vs」列出 spec.md 的 NFR 與「不另列任務」那一行，摘要寫出理由的說法與實際的差異，嚴重度依覆蓋狀態判定，不得另列一個不一致。NFR 另有其他落點而判 ✅ 時，那一行只是說法有誤，才單獨列為不一致。

### Good Example

這個範例的 NFR-011 沒有任何 Rule、NFR 約束或重構任務，只靠理由不相符的「不另列任務」，只列一個覆蓋缺口，位置與摘要同時寫出那一行與實際的差異。

```text
nfr_landing：NFR-011 verified_by_rule false，constraint_tasks、refactor_tasks 都是空的
no_task_entry：tasks.md:L146「NFR-011：已是 Phase 5、7、9 的 NFR 約束」，phase_checks 的 Phase 5、7、9 都是 false
C3 | 覆蓋缺口 | HIGH | spec.md:L170（NFR-011）vs tasks.md:L146（不另列任務） | 不另列任務寫 NFR-011 已是 Phase 5、7、9 的 NFR 約束，三個 Phase 的標頭都沒有 NFR-011，相容性要求沒有任何落點 | 用 /task 在這三個 Phase 的 NFR 約束補上 NFR-011，或改排 NFR 重構任務
```

### Bad Example

這個範例把同一個原因拆成不一致與覆蓋缺口兩項，使用者照 I4 只改寫理由就以為處理完，NFR-011 的落點仍然沒有補上，發現事項的數量也被灌水。

```text
I4 | 不一致 | MEDIUM | tasks.md:L146（不另列任務）vs tasks.md:L120（Phase 5 標頭） | 不另列任務說 NFR-011 已是 Phase 5、7、9 的 NFR 約束，標頭沒有
C3 | 覆蓋缺口 | HIGH | spec.md:L170（NFR-011） | NFR-011 沒有任何落點
```

## Rule 7 -- operation 的每個回應各自判定涵蓋

**強度：MUST**

OpenAPI 的 operation 以回應為涵蓋的最小單位：追溯 JSON 中 operation 段落的 `responses` 列出每個狀態碼、它的錯誤碼（`codes`）與它和基準 commit 相比的異動（`change`）。這次新增的 operation（`change` 為 ADD）的每個回應，以及修改的 operation 中 `change` 為 ADD 或 MOD 的回應，都必須有 Rule 驗證才算涵蓋：有錯誤碼的回應逐個錯誤碼看 `rule_count`，MOD 的回應看 `scoped_rule_count`（要由這次的 Rule 驗證改變的部分），沒有錯誤碼的 2xx 回應在 operation 被 Rule 操作時即算涵蓋；`change` 為空的回應是先前 plan 留下、這次沒有改變的，不檢查。`shared_codes` 列出的錯誤碼中，說明相同、代表同一件事的共用錯誤碼（如權杖無效、房間不存在）只判定一次：本端點任一 Rule 驗證過（`rule_count` 大於 0）即算涵蓋，都沒有時只列一個發現事項並列出用到它的 operation；說明不同的同名錯誤碼（如各 operation 的 `state_conflict` 代表不同的狀態不符）仍逐個 operation 判定。有任何回應或錯誤碼沒有 Rule 驗證時，該介面判 ⚠️ 部分，備註寫出 operation、狀態碼與錯誤碼。`rule_count` 是字面比對的候選，判定前讀 Rule 確認它驗證的是這個回應。

### Good Example

這個範例逐個回應與錯誤碼判定：新增的 operation 中只有 422 的 `chat_after_seq_invalid` 沒有 Rule，修改的 kickGuest 只檢查這次改了說明的 409，沒改的回應不檢查，共用的 `player_token_invalid` 只列一項。

```text
API-01 sendChatMessage（ADD）：201、409（chat_no_opponent、chat_opponent_left）、422（chat_empty、chat_too_long）、429（chat_too_frequent）都有 Rule
API-01 listChatMessages（ADD）：422 chat_after_seq_invalid 的 rule_count 為 0
API-02 kickGuest（MOD）：409 state_conflict 的 change 為 MOD（說明補上聊天紀錄不變），scoped_rule_count 為 0；其他回應 change 為空，不檢查
shared_codes：player_token_invalid（14 個 operation，說明相同，rule_count 0）→ 只列 C4
狀態：API-01 ⚠️ 部分 — listChatMessages 的 422 chat_after_seq_invalid 沒有 Rule；API-02 ⚠️ 部分 — kickGuest 的 409 state_conflict 沒有這次的 Rule 驗證聊天紀錄不變
```

### Bad Example

這個範例只看 operation 有沒有被 Rule 操作就判完整覆蓋，listChatMessages 的 422 與 kickGuest 這次改了的 409 都沒有 Rule，綠燈不會實作這些錯誤處理，前端依錯誤碼顯示的訊息也從未被驗證。

```text
API-01：sendChatMessage、listChatMessages 都有 backend 的 Rule 操作 → ✅
API-02：kickGuest 有 backend 的 Rule 操作 → ✅
```
