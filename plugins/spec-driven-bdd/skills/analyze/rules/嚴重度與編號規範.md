# 嚴重度與編號規範

## Rule 1 -- CRITICAL 只限六種情況

**強度：MUST**

只有下列情況可以判為 CRITICAL：必要產物或介面文檔缺漏（含畫面或 API 端點這次有異動的介面、plan 的涵蓋表卻沒有該端點的案例）、plan-package check 回報待補跑的擁有者、check_plan.py、check_tasks.py 或 plan-package 的交叉檢查回報問題（照腳本修正會違反已載入的憲法條款者除外，改在位置欄註明條款編號並判為 LOW）、依 Rule 2 屬於 P1 的需求覆蓋狀態為 ❌、跨產物的技術選型互相衝突、違反 MUST 強度的憲法條款。有任何 CRITICAL 時，結論必須寫明不建議進入 `/implement`；沒有 CRITICAL 時，結論寫明可以進入，並點出需要先處理的 HIGH。

### Good Example

這個範例把 techstack 與 tasks 的框架衝突判為 CRITICAL，並在結論寫明不建議進入實作。

```text
I1 | 不一致 | CRITICAL | specs/truth/techstack.md:L32 vs tasks.md:L60（T007） | techstack 採用 Express 4，T007 以 Fastify 建立伺服器 | 讓 T007 改用 Express，或回到 /technical-research 改選 Fastify
結論：不建議進入 `/implement`。共 1 個 CRITICAL，請先處理 I1。
```

### Bad Example

這個範例把 P4 故事的部分覆蓋判為 CRITICAL，結論擋下了整個實作，但 P1～P3 的故事本來可以先開始做。

```text
C2 | 覆蓋缺口 | CRITICAL | spec.md:L193（NFR-014） | 刪除操作沒有即時回饋任務 | 補上任務
結論：不建議進入 `/implement`。
```

## Rule 2 -- 需求的優先順序依所屬故事判定

**強度：MUST**

需求是否屬於 P1 必須依追溯 JSON `requirement_trace` 的 `stories` 與 `priority` 判定：需求定義在使用者故事底下，或被某個故事的 AC 的涵蓋註解列出時，屬於那些故事，取其中最高的優先順序；`priority` 為 P1 才是 P1 的需求。SC 與全域需求這類定義在故事以外、也沒有被任何 AC 的涵蓋註解列出的需求（`priority` 為 null）不屬於任何故事，不算 P1，覆蓋 ❌ 時判 HIGH；不得因為 SC 描述的是整體成果、或全域需求適用於所有故事，就把它當成 P1。CRITICAL 只保護 P1 故事能先實作與 Demo，不屬於任何故事的需求不在 P1 的旅程上，它的缺口不會擋住 P1 的實作。

### Good Example

這個範例依 `stories` 與 `priority` 判定：被三個故事的 AC 涵蓋的 FR-004 取最高的 P1，沒有任何故事的 NFR-007 與 SC-003 不算 P1。

```text
FR-004：stories US1、US2、US3，priority P1 → 覆蓋 ❌ 時判 CRITICAL
NFR-007（全域需求，沒有 AC 的涵蓋註解列出）：stories 無，priority null → 覆蓋 ❌ 時判 HIGH
SC-003（成功標準）：stories 無，priority null → 覆蓋 ❌ 時判 HIGH
```

### Bad Example

這個範例把不屬於任何故事的 SC 當成 P1，一個只缺驗證的成功標準就擋下整個實作，P1 故事本來可以先開始做；同一份 spec 換一次分析也可能判成 HIGH，結論前後不一。

```text
SC-003「新加入者或其他房間的玩家取得前一段同房期間聊天訊息的次數為 0」→ 適用於所有故事，視為 P1 → ❌ → CRITICAL
結論：不建議進入 `/implement`。
```

## Rule 3 -- 其他嚴重度依實作影響判定

**強度：MUST**

不屬於 CRITICAL 的發現事項必須依下表判定。

| 嚴重度 | 判定 |
|---|---|
| HIGH | 照現況實作會產生錯誤行為，或需求覆蓋 ❌（依 Rule 2 不屬於 P1 的需求，含 SC 與不屬於任何故事的全域需求） |
| MEDIUM | 需求或介面部分覆蓋、跨產物不一致需要更新上游產物、模糊但已有可補回的門檻、違反 SHOULD 強度的憲法條款且未寫出偏離理由 |
| LOW | 措辭、重複、文件狀態，以及不影響實作結果的描述差異 |

### Good Example

這個範例把會直接產生錯誤路徑的 U1 判為 HIGH，把只需更新 plan 描述的 I3 判為 LOW。

```text
U1 | 規格不足 | HIGH | STORAGE_DIR 相對路徑會解析成 backend/backend/storage
I3 | 不一致 | LOW | plan 介面盤點的 API-02 描述沒提到單本查詢，openapi 與 tasks 已有
```

### Bad Example

這個範例把措辭問題判為 HIGH，會造成錯誤的 U1 反而判為 LOW，使用者依嚴重度排序處理時，會先改文字而漏掉真正會出錯的問題。

```text
U2 | 規格不足 | HIGH | spec 狀態仍是「草稿」
U1 | 規格不足 | LOW | STORAGE_DIR 相對路徑會解析成 backend/backend/storage
```

## Rule 4 -- 條件重疊時取最高的嚴重度

**強度：MUST**

一個發現事項同時符合 Rule 1 與 Rule 3 表中兩個以上的條件時（包括把同一原因的多個問題併成一項的發現事項），必須取其中最高的嚴重度，不得依類別或先比對到的條件判較低的嚴重度。唯一的例外是 Rule 1 中照腳本修正會違反已載入憲法條款的腳本問題，固定判 LOW。

### Good Example

這個範例的不一致同時符合「跨產物不一致需要更新上游產物」（MEDIUM）與「照現況實作會產生錯誤行為」（HIGH），取 HIGH。

```text
I2 | 不一致 | HIGH | specs/truth/features/backend/dsl.md:L119 vs specs/truth/contracts/paths/聊天/api_rooms_{roomId}_messages.yaml:L54（422） | dsl.md 斷言空白訊息回 400，契約寫 422 chat_empty；綠燈依 dsl.md 回 400，前端依契約找不到 chat_empty 的提示 | 由 dev-finding 記錄後交 dsl-refine 改為 422 chat_empty
```

### Bad Example

這個範例依類別先比對到 MEDIUM 就停下，會讓前端顯示錯誤提示的問題排在措辭問題附近，使用者依嚴重度處理時延後修正，實作後才發現畫面錯誤。

```text
I2 | 不一致 | MEDIUM | specs/truth/features/backend/dsl.md:L119 vs specs/truth/contracts/paths/聊天/api_rooms_{roomId}_messages.yaml:L54（422） | 屬於跨產物不一致，dsl.md 斷言 400，契約寫 422 chat_empty | 更新 dsl.md
```

## Rule 5 -- ID 由類別字首加流水號組成

**強度：MUST**

ID 字首依類別固定：C 覆蓋缺口、I 不一致、A 模糊、D 重複、U 規格不足、V 憲法違反。首次分析時，同一類別內依嚴重度由高到低從 1 起編流水號，嚴重度較低的問題不得排在較高的問題之前。

### Good Example

這個範例的不一致類別先編 MEDIUM 再編 LOW，字首與類別一致。

```text
I1 | 不一致 | MEDIUM | tasks.md:L23
I2 | 不一致 | MEDIUM | plan.md:L11-18
I3 | 不一致 | LOW | plan.md:L120
```

### Bad Example

這個範例把不一致的問題以 D 開頭，D 與重複類別的字首相撞，使用者看到 D1 會以為是重複問題而跳過；LOW 的問題又編在 MEDIUM 之前，依編號處理時會先改次要問題。

```text
D1 | 不一致 | LOW | plan.md:L120
D2 | 不一致 | MEDIUM | tasks.md:L23
```

## Rule 6 -- 重跑時同一問題沿用前次 ID

**強度：MUST**

同一對話中已有前次分析時，類別相同且指向同一個需求、任務或文檔段落的問題，視為同一問題，必須沿用前次 ID，即使行號或措辭改變。前次有、本次沒有的 ID 列為已解決，不得再分配給新問題；新問題從該類別前次最大編號的下一號開始編。

### Good Example

這個範例在 T005 行號改變後仍沿用 U1，已解決的 I9 不再使用，新的不一致問題從 I10 開始。

```text
前次：U1（tasks.md:L34，T005）、I9（T002 exifr 版本）
本次：U1（tasks.md:L36，T005）仍存在；I9 已解決；新問題 → I10
```

### Bad Example

這個範例依本次結果重新編號，已解決的 I9 被分配給新問題，使用者比對兩份報告時會誤以為 I9 沒有修好。

```text
前次：I9（T002 exifr 版本）
本次：I9（UI-04 依據需求缺 FR-011）
```
