# 問題偵測判準

## Rule 1 -- 模糊依訊號詞判定

**強度：MUST**

需求、驗收情境或任務描述含下列訊號，且同一句沒有可量測的門檻時，必須列為模糊：

| 類型 | 訊號 |
|---|---|
| 主觀形容詞 | 快速、迅速、即時、流暢、順暢、明顯、卡頓、延遲、友善、直覺、簡單、清楚、適當、合理、穩定、大量、良好、盡量 |
| 未定佔位 | TODO、TBD、待定、待補、待確認、???、`{{ }}`、`<placeholder>` |

訊號以詞為單位判定，不得只因字串出現就列入：把訊號和前後的字一起讀，它和前後的字組成另一個詞（如「等待補猜」是「等待」加「補猜」，「待補」只是跨在兩個詞之間）、屬於固定的技術用語（如「穩定排序」「延遲載入」），或位於引號中的畫面文案、程式碼片段與識別碼時，不算訊號。同一句已有數值門檻（如「200ms 內」「CLS ≤ 0.1」）時不算模糊。門檻只寫在 research.md、沒有寫在 spec.md 時，仍列為模糊，並在建議中指出門檻所在位置。

### Good Example

這個範例對有訊號詞且沒有門檻的句子列為模糊，並指出門檻只在 research.md；已有門檻的句子不列；「等待補猜」中的「待補」不是未定佔位，也不列。

```text
SC-003「捲動時無明顯卡頓」→ 模糊：門檻 p95 200ms 只寫在 research.md R-14
NFR-014「200ms 內要有可見回饋」→ 不列（已有門檻）
tasks.md:L72（T009）「實作技能列…連猜進度與等待補猜提示」→ 不列（「待補」是「等待補猜」的一部分，不是訊號）
```

### Bad Example

這個範例只要字串出現就列入，把「等待補猜」誤報為未定佔位，又憑感覺把已有門檻的 NFR-014 列為模糊，SC-003 的「無明顯卡頓」反而沒列，有問題的句子沒找出，沒問題的句子又被誤報。

```text
tasks.md:L72（T009）→ 模糊：含未定佔位「待補」
NFR-014「200ms 內要有可見回饋」→ 模糊：「可見回饋」不夠具體
SC-003 → 不列
```

## Rule 2 -- 不重複偵測腳本負責的項目

**強度：MUST**

check_plan.py 已檢查的項目（介面 ID、介面盤點的異動欄、需求引用、Wave 分配、委派、統計數字、殘留佔位符）、check_tasks.py 已檢查的項目（任務編號、Phase 結構與順序（含移除與技術項 Phase）、每個 Feature Phase 恰好三個任務、範疇與這次新增修改的 Rule 一致（含行號）、紅燈的 Rule 數與 Example 數、驗收 AC、NFR 約束的必讀、Feature Phase 必讀不得列的檔案、非 Feature 任務的必讀、每一列 DEL 與每一行技術項的涵蓋、未驗證 NFR 的分割、NFR 重構每個端點資料夾至多一個 [重構] 任務、NFR 重構任務必讀的 NFR 須為描述項首、依賴與舊標記、Verify 的位置、殘留佔位符，以及它轉述的 feature_summary.py 問題：涵蓋表與基準以來的實際異動不符），與 plan-package check 的交叉檢查（`cross_check`）已檢查的項目（dsl.md 用到的識別碼存在於契約、UI 契約與資料模型、每個 AC 都有測試、tasks.md 的範疇與基準以來的實際異動一致、每一行技術項都有任務或寫在「不另列任務」、techstack.md 與 research.md 一致），不得再自行偵測，腳本回報的問題直接依回報內容列為發現事項；交叉檢查與 check_tasks.py 回報同一個任務、Rule 或涵蓋表列時，合併為一個發現事項。介面盤點的依據需求引用本 plan 標 `@開發發現` 的 AC（追溯 JSON 介面的 `finding_acs`），或只在最後寫「技術：<原因>」（`technical`，PM 看不到差異的技術原因）都是合法寫法，由 check_plan.py 檢查，不得列為缺少依據需求或引用不存在。追溯 JSON 不比對 Phase 標頭與 feature 的事實，驗收 AC、範疇與 Rule、Example 數以 check_tasks.py 的回報為準；腳本無法執行時，必須依 `scope_features` 自行比對並列為不一致。

### Good Example

這個範例直接採用 check_tasks.py 與交叉檢查的回報，同一條 Rule 的兩個回報合併為一項，不再檢查必讀、驗收 AC、紅燈數量與 dsl.md 的識別碼，只做腳本不涵蓋的語意比對。

```text
check_tasks.py：2 個問題（L111 Phase 7 驗收 AC 缺 AC-10；backend/刪除照片.feature 這次有修改的 Rule，卻沒有 Feature Phase）→ 直接列為發現事項
cross_check：tasks.md 範疇 1 個問題（backend/刪除照片.feature 的 Rule「刪除照片必須一併刪除縮圖」改了但沒有任務涵蓋）→ 與 check_tasks.py 的第二個問題合併為一項
→ 不再逐一開啟必讀錨點、不再重算 Rule 數、不再自行比對 dsl.md 的識別碼與契約
→ 檢查 Phase 5 預計修改的 `backend/src/lib/sniff.js` 是否出現在 plan.md 原始碼結構（腳本不涵蓋）
```

### Bad Example

這個範例重新逐一比對每個必讀錨點與紅燈的 Rule 數，結果與腳本相同卻多花大量 context，若比對方式和腳本不同，還會產生與腳本矛盾的結論。

```text
check_tasks.py：0 個問題
→ 逐一開啟 52 個任務的所有必讀錨點，確認檔案與片段存在
→ 逐份重算 12 份 feature 的 Rule 數
```

## Rule 3 -- 不一致必須列出雙方位置

**強度：MUST**

術語漂移、技術選型衝突、同一介面在 plan、介面文檔、feature、tasks 之間描述不符，都屬於不一致。每個不一致的位置欄必須以「vs」列出衝突雙方的檔案與行號，摘要必須寫出雙方各自的說法。

### Good Example

這個範例以 vs 列出衝突雙方，摘要寫出雙方各自的驗收 AC。

```text
I1 | 不一致 | MEDIUM | tasks.md:L111（Phase 7 驗收 AC）vs features/涵蓋表.md:L88（AC 涵蓋表） |
Phase 7 標頭寫 AC-03、AC-04，AC 涵蓋表中 backend/平鋪預覽.feature 另有 AC-10
```

### Bad Example

這個範例只列出一方的位置，也沒寫出另一方的說法，使用者無法判斷該改 tasks.md 還是重新產生 feature。

```text
I1 | 不一致 | MEDIUM | tasks.md:L111 | Phase 7 的驗收 AC 不正確
```

## Rule 4 -- 內容一致的重述才算重複

**強度：MUST**

同一條規則在多處重述且內容完全一致時，才列為重複。重述的內容有出入時（如範圍、數值、用詞指向不同概念），必須列為不一致，不得列為重複。

### Good Example

這個範例把內容一致的重述列為重複，把用詞指向不同範圍的重述列為不一致。

```text
FR-018、邊界情況 L174、US4 情境 3 都寫「刪除最後一張照片時一併移除相簿」→ 重複
相簿定義「同一日期區間」vs FR-003「以天為單位」→ 不一致
```

### Bad Example

這個範例把範圍不同的兩句話列為重複並建議保留，「日期區間」與「以天為單位」的衝突沒有被修正，實作者可能依日期區間分組。

```text
D2 | 重複 | LOW | spec.md:L233、FR-003 | 相簿分組規則重述 | 可保留
```

## Rule 5 -- 照字面實作會出錯才算規格不足

**強度：MUST**

實作者照產物的字面實作會產生錯誤，或必須自行決定產物沒寫的關鍵資訊（如路徑基準、錯誤回應、狀態轉換）時，才列為規格不足。只是寫得不夠詳細、但不影響實作結果時，不列為規格不足。

### Good Example

這個範例指出照字面實作會解析出錯誤的路徑。

```text
U1：STORAGE_DIR 預設值 backend/storage 是相對路徑，start script 以 backend/ 為工作目錄執行，會解析成 backend/backend/storage
```

### Bad Example

這個範例把不影響實作結果的描述長短列為規格不足，真正會出錯的問題被淹沒在大量低價值的發現事項中。

```text
U3：T032 的卡片樣式描述只有一行，建議補充更多細節
```

## Rule 6 -- 憲法違反必須指出條款

**強度：MUST**

產物在所屬憲法條款的作用位置不符合條款要求時，列為憲法違反；SHOULD 條款已在產物寫出偏離理由時不列入。位置欄必須寫出產物的檔案與行號，並以「vs」接上條款編號；摘要必須寫出條款的要求與產物的實際內容。

### Good Example

這個範例寫出違反的條款編號，摘要對照條款要求與實際內容，使用者知道該回到 data-plan 補欄位。

```text
V1 | 憲法違反 | CRITICAL | specs/truth/data/房間.dbml:L18-30（rooms）vs C-DATA-01 | 條款要求每張表有 created_at 與 updated_at，rooms 只有 created_at
```

### Bad Example

這個範例只寫「不符憲法」，沒有條款編號與實際內容，使用者無法判斷違反哪一條，也無從確認修正後是否符合。

```text
V1 | 憲法違反 | CRITICAL | specs/truth/data/房間.dbml | 資料表不符憲法規定
```

## Rule 7 -- 只偵測這次範圍內的問題

**強度：MUST**

模糊、重複、不一致、規格不足與憲法違反，只在這次的範圍內偵測：追溯 JSON 標為這次異動的內容，加上 spec.md「受影響的既有功能」涉及的內容。先前 plan 留下、這次沒有異動也不在受影響範圍的 truth 內容，不列為發現事項。plan-package 交叉檢查的 `warnings`（先前 plan 留下、本 plan 沒改到的問題）在報告中只轉述為提醒，不分級、不擋 `/implement`，並建議交付後另開技術修正 plan 處理。以下 Example 皆對照此情境：

```text
這次異動：features/backend/排行榜.feature（ADD）、contracts/paths/排行/api_rankings.yaml（ADD）
先前 plan 留下：features/frontend/dsl.md 的「系統處於 {前置狀態}」說明重述技能次數（這次沒有異動，也不在受影響的既有功能）
交叉檢查 warnings：techstack.md 第 42 行重述了原始碼檔案（先前 plan 留下）
```

### Good Example

這個範例只就排行榜的異動偵測，先前留下的重述不列為發現；交叉檢查的提醒單獨轉述，不分級。

```text
D1 | 重複 | MEDIUM | features/backend/排行榜.feature:12 vs contracts/paths/排行/api_rankings.yaml | 名次的計算規則在兩處各寫一次
提醒（不分級、不擋 /implement）：techstack.md 第 42 行重述了原始碼檔案，為先前 plan 留下的問題，建議交付後另開技術修正 plan 處理
```

### Bad Example

這個範例把先前 plan 留下的重述與交叉檢查的提醒都列為發現並分級，報告被與這次需求無關的項目占滿，CRITICAL 還讓使用者以為不能開始 /implement。

```text
D1 | 重複 | MEDIUM | features/frontend/dsl.md:9 | 起點句型說明重述技能次數
D2 | 重複 | CRITICAL | techstack.md:42 | 重述了原始碼檔案
```
