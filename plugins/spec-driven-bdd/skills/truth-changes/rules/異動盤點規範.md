# 異動盤點規範

## Rule 1 -- 需求必須對照既有 truth 判定異動

**強度：MUST**

該 owner 負責的每一項需求（FR、NFR 與開發發現的 AC）都必須先在既有 truth 中找出描述同一個對象的內容，再判定異動：找得到且內容要變就是修改，找不到才是新增。不得在既有內容旁邊另外新增一份描述同一個對象的內容。以下 Example 皆對照此需求與既有 truth：

```text
FR-003：房間人數上限由 2 人改為 4 人
既有 truth：features/backend/房間.feature 有 Rule「房間滿員時必須拒絕再加入的玩家」，Example 驗證第三位玩家加入被拒絕
```

### Good Example

這個範例找到既有的 Rule 描述的是同一個對象（房間滿員），判定為修改。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `features/backend/房間.feature` ＞ Rule「房間滿員時必須拒絕再加入的玩家」 | Example 由第三位改為第五位玩家加入才被拒絕 | FR-003 |
```

### Bad Example

這個範例沒有對照既有 truth 就新增一條 Rule，truth 會同時存在「第三位被拒絕」與「第五位才被拒絕」兩條互相矛盾的 Rule，下游無法判斷哪一條才是現況。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `features/backend/房間.feature` ＞ Rule「四人房滿員時必須拒絕第五位玩家」 | 新增一條 Rule | FR-003 |
```

## Rule 2 -- 被移除的行為必須連帶列出刪除

**強度：MUST**

需求移除或取代既有行為時，該 owner 路徑下只為這個行為存在的內容必須全部列為刪除。仍被其他行為使用的內容不得刪除，改列修改，並在改動摘要寫出它還被誰使用。以下 Example 皆對照此需求與既有 truth：

```text
FR-002：移除「連猜三次」技能
既有 truth（contracts/）：
- paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml：連猜三次的操作
- components/schemas/TripleGuessRequest.yaml：只被連猜三次的操作使用
- components/schemas/SkillCounts.yaml：欄位 tripleGuess 與 changeAnswer，後者被「改答案」使用
```

### Good Example

這個範例列出只為連猜三次存在的操作與 schema，仍被改答案使用的 SkillCounts 改列修改並寫出保留的理由。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| DEL | `contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` | 刪除連猜三次的操作 | FR-002 |
| DEL | `contracts/components/schemas/TripleGuessRequest.yaml` | 只被連猜三次的操作使用，一併刪除 | FR-002 |
| MOD | `contracts/components/schemas/SkillCounts.yaml` | 刪除欄位 `tripleGuess`；`changeAnswer` 仍被改答案使用，保留 | FR-002 |
```

### Bad Example

這個範例只刪除操作，沒有列出只為它存在的 TripleGuessRequest 與 SkillCounts 的 `tripleGuess` 欄位，truth 會留下沒有人使用的內容，下游會把它當成現況繼續實作。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| DEL | `contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` | 刪除連猜三次的操作 | FR-002 |
```

## Rule 3 -- 已知的影響來源必須逐項處置

**強度：MUST**

上游各 owner 表格中的每一列修改與刪除、spec.md「受影響的既有功能」的每一項、技術項.md 中「修正：」點名該 owner 的每一行，以及呼叫者依 plan-package check 帶入的每個輸入差異，都必須各有一個處置：「連帶異動」並寫出要改該 owner 的哪個對象，或「不受影響」並寫出理由。不得只列出有影響的項目。呼叫者依差異執行時，只需處置帶入的輸入差異與它們涉及的上游列，先前已處置、這次沒有變的來源不必重列。以下 Example 皆對照此影響來源，盤點的 owner 為 data-plan：

```text
上游 api-plan 的表格：
| DEL | `contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` | 刪除連猜三次的操作 | FR-002 |
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank` | FR-001 |

spec.md「受影響的既有功能」：
- 房間：房間畫面新增排行榜入口
```

### Good Example

這個範例為兩列上游異動與一項既有功能各寫一個處置，不受影響的項目也寫出理由。

```markdown
| 來源 | 處置 | 說明 |
|---|---|---|
| api-plan DEL `contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` | 連帶異動 | 刪除 `data/技能.dbml` 的 Table `triple_guess_uses` |
| api-plan MOD `contracts/components/schemas/RoomState.yaml` | 不受影響 | `rank` 由既有的勝場數即時計算，不需要新的欄位 |
| 既有功能「房間」 | 不受影響 | 排行榜入口只改畫面，不改房間的資料 |
```

### Bad Example

這個範例只列出有影響的一項，其餘兩項沒有處置，下游無從得知它們是判斷過不受影響，還是被漏看。

```markdown
| 來源 | 處置 | 說明 |
|---|---|---|
| api-plan DEL `contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` | 連帶異動 | 刪除 `data/技能.dbml` 的 Table `triple_guess_uses` |
```

## Rule 4 -- 沒有原因的改動不得列入

**強度：MUST**

每項異動都必須能對應到本 plan 的 FR、NFR 或開發發現的 AC，或有技術上的必要（不改就無法完成這次的需求、技術項.md 點名這個 owner 修正的問題，或依憲法套用規範整份核對時必須改正的違憲內容）。對應不到的改動不得列入，包括順手改寫既有 truth 的說明文字、命名與排版。

### Good Example

這個範例的兩項異動一項對應需求，一項是檔案搬移後不改就會失效的引用。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank` | FR-001 |
| MOD | `contracts/openapi.yaml` | 新增排行榜操作的 `$ref` | 技術：新增的操作必須掛進入口檔才會被打包 |
```

### Bad Example

這個範例把與需求無關的文字潤飾列為異動，truth 被改動卻追溯不到任何需求，審閱者必須逐字比對才能確認行為沒有變。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/GuessEntry.yaml` | 把說明文字改得更通順 | 技術：順手整理 |
```

## Rule 5 -- 需求以外的問題不得自行決定

**強度：MUST**

盤點時發現既有 truth 沒寫清楚、互相矛盾或與程式不符，而本 plan 的 FR、NFR 與開發發現的 AC 都沒有涵蓋時，不得把它列為異動並自行填寫原因。必須列在盤點清單的「待分類的發現」，由呼叫者交給 dev-finding 記錄，取得分類結果後才列為異動。

### Good Example

這個範例把契約與程式不符的現象列為待分類的發現，沒有自行決定要不要修改。

```markdown
## 待分類的發現

- `contracts/paths/房間/api_rooms_{roomId}_leave.yaml`：對局中離開房間時程式會拒絕，契約沒有寫這個回應。
```

### Bad Example

這個範例把使用者看得到的行為差異當成技術理由直接列為修改，PM 沒有機會決定對局中能不能離開房間，這個行為就以未經審核的狀態進入 truth。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/paths/房間/api_rooms_{roomId}_leave.yaml` | 補上對局中離開房間被拒絕的回應 | 技術：契約與程式不一致 |
```
