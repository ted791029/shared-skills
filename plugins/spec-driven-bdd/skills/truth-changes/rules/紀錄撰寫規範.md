# 紀錄撰寫規範

## Rule 1 -- 只整張改寫呼叫者的表格

**強度：MUST**

每次記錄都以基準以來的全部異動重寫該 owner 的整張表格，不得在既有的列之後追加。其他 owner 的表格不得更動。以下 Example 皆對照此既有表格與這次的異動：

```markdown
## api-plan（contracts/）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank` | FR-001 |
```

```text
api-plan 重跑：把欄位 rank 改名為 ranking，並新增排行榜的操作
```

### Good Example

這個範例以目前的全部異動重寫整張表格，RoomState 只有一列，內容是最新的結果。

```markdown
## api-plan（contracts/）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `contracts/paths/排行/api_rankings.yaml` | 新增查詢排行榜的操作 | FR-001 |
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `ranking` | FR-001 |
```

### Bad Example

這個範例在既有的列之後追加，RoomState 出現兩列，其中 `rank` 已不存在於 truth，下游讀到會以為有兩個欄位。

```markdown
## api-plan（contracts/）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank` | FR-001 |
| ADD | `contracts/paths/排行/api_rankings.yaml` | 新增查詢排行榜的操作 | FR-001 |
| MOD | `contracts/components/schemas/RoomState.yaml` | 欄位 `rank` 改名為 `ranking` | FR-001 |
```

## Rule 2 -- 沒有自己的一節時必須新增

**強度：MUST**

檔案中還沒有呼叫者的一節時，必須在最後新增一節，不得把列寫進其他 owner 的表格。節名括號內是它寫入的 truth 路徑，相對於 truth 資料夾，目錄以「/」結尾，多個路徑以「、」分隔。以下 Example 皆對照此情境：

```text
新補建的 Planner「event-plan」把事件定義寫進 truth 的 events/，truth-changes.md 目前沒有它的一節
```

### Good Example

這個範例為 event-plan 新增自己的一節，標題寫出 skill 名稱與它寫入的路徑。

```markdown
## event-plan（events/）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `events/排行榜更新.yaml` | 新增排行榜更新的事件 | FR-001 |
```

### Bad Example

這個範例把 event-plan 的異動寫進 api-plan 的表格，核對時這一列不在 `contracts/` 之下而無法比對，`events/` 的異動也會被判為沒有 owner。

```markdown
## api-plan（contracts/）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `events/排行榜更新.yaml` | 新增排行榜更新的事件 | FR-001 |
```

## Rule 3 -- 對象必須是下游會引用的具名單位

**強度：MUST**

一列只記一個對象的一種異動，異動欄描述的是對象欄所寫的那個對象。對象是 truth 中有名稱、下游會引用的單位，例如一條 Rule、一個操作、一個 schema、一張資料表、一項技術；比它更小的變動（欄位、步驟、說明文字）記為該單位的修改。整個檔案都是新增或刪除時，以檔案為對象記一列，並在改動摘要寫出它包含的單位數量（新增的檔案中有 Rule 改名時，依 Rule 11 另為它記一列）。

### Good Example

這個範例的新檔案以檔案為對象記一列，既有檔案中的修改與刪除各以一條 Rule 為對象。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `features/backend/排行榜.feature` | 整份 feature，2 條 Rule | FR-001 |
| MOD | `features/backend/房間.feature` ＞ Rule「房間滿員時必須拒絕再加入的玩家」 | 提示文字由「房間已滿」改為「房間已滿，請換一個暗號」 | AC-08 |
| DEL | `features/backend/房間.feature` ＞ Rule「連猜三次必須一次送出三組數字」 | 刪除整條 Rule | FR-002 |
```

### Bad Example

這個範例把同一個檔案中的修改與刪除合成一列，對象只寫到檔案，下游無法得知哪一條 Rule 被刪除、哪一條要重新驗證，也分不出哪個改動對應哪個原因。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| ADD | `features/backend/排行榜.feature` | 整份 feature，2 條 Rule | FR-001 |
| MOD | `features/backend/房間.feature` | 改了一條 Rule 的提示文字，刪了一條 Rule | AC-08、FR-002 |
```

## Rule 4 -- 對象必須以反引號標出 truth 路徑

**強度：MUST**

對象欄必須以反引號寫出檔案相對於 truth 資料夾的路徑，且位於該 owner 的路徑之下；檔案內的單位接在「＞」之後。核對以這個路徑比對 git 的實際異動。

### Good Example

這個範例以反引號寫出相對於 truth 資料夾的完整路徑，單位接在「＞」之後。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 新增欄位 `wins` | FR-001 |
```

### Bad Example

這個範例只寫資料表名稱，沒有檔案路徑，核對時這一列對不到任何檔案，實際異動的 `data/房間.dbml` 會被判為改了沒記。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | Table `rooms` | 新增欄位 `wins` | FR-001 |
```

## Rule 5 -- 合併列只限同一種改動

**強度：MUST**

多個檔案的異動類型、改動內容與原因都相同時，可以合併為一列：對象寫它們共同的目錄（以「/」結尾）並註明數量，或逐一列出路徑。改動內容或原因不同的檔案不得合併。

### Good Example

這個範例合併的 6 個操作做的是同一種改動，原因也相同。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/paths/房間/`（6 個操作） | 每個操作新增「尚未登入」的回應 | NFR-002 |
```

### Bad Example

這個範例把內容與原因都不同的改動合成一列，摘要只能寫成「調整」，下游看不出哪個檔案改了什麼。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/`（9 個檔案） | 配合排行榜與登入檢查調整 | FR-001、NFR-002 |
```

## Rule 6 -- 改動摘要必須寫出改了什麼

**強度：MUST**

改動摘要以一句話寫出新增或刪除了什麼；修改時寫出改之前與改之後。契約新增或修改回應欄位時，另寫出它的資料來源（要保存在資料庫，或由既有資料即時計算），讓 data-plan 依它判斷要不要連帶異動。不得只寫「調整」「更新」「配合需求修改」這類看不出內容的字眼。

### Good Example

這個範例寫出修改前後的值，不需打開檔案就知道改了什麼。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 人數上限的檢查約束由 2 改為 4 | FR-003 |
```

### Bad Example

這個範例的摘要只重複原因，沒有寫出內容，下游必須自己比對差異才知道約束改成什麼。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 配合 FR-003 調整 | FR-003 |
```

## Rule 7 -- 原因只能是需求編號或技術理由

**強度：MUST**

原因欄只能填本 plan 的 spec.md 中的 FR、NFR 編號、本 plan 的 acceptance 中標 `@開發發現` 的 AC 編號（多個以「、」分隔），或「技術：」加一句說明。不得填其他文字、留空或使用不存在的編號。

### Good Example

這個範例的原因一列是需求編號，一列是技術理由。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 新增欄位 `wins` | FR-001 |
| MOD | `data/對戰.dbml` ＞ Table `guesses` | 補上外鍵 `fk_guesses_room_id` | 技術：資料模型宣告的外鍵沒有建立 |
```

### Bad Example

這個範例的原因是一句隨意的說明，既不是需求編號也不是「技術：」開頭，核對會判為格式錯誤，審閱者也無法追溯這個改動該由誰驗收。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/對戰.dbml` ＞ Table `guesses` | 補上外鍵 `fk_guesses_room_id` | 之前漏掉了 |
```

## Rule 8 -- 沒有異動時寫一列無異動

**強度：MUST**

該 owner 在基準以來（整個 plan，不是只看這一次執行）沒有修改任何 truth 時，表格只寫一列：異動欄為「無異動」，對象與改動摘要為「—」，原因欄寫出為什麼這次不需要改。不得讓表格留空，也不得與其他列並存。

### Good Example

這個範例只有一列「無異動」，並寫出不需要改的理由。

```markdown
## technical-research（techstack.md）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| 無異動 | — | — | 排行榜沿用既有的後端與資料庫技術，不需要新的技術 |
```

### Bad Example

這個範例讓表格留空，下游與核對無法分辨這個 owner 是判斷過不需要改，還是還沒執行。

```markdown
## technical-research（techstack.md）

| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
```

## Rule 9 -- 不是自己改的異動也必須記錄

**強度：MUST**

表格必須涵蓋基準以來該 owner 路徑下的全部實際異動，包含先前執行留下的與使用者手動修改的。不是自己造成的異動，先讀差異內容判定對象與原因再記錄；找不到原因時不得編造，在回覆中列出這些異動交由呼叫者處理。已經還原的異動不得留在表格。以下 Example 皆對照此情境：

```text
核對結果：改了沒記 data/房間.dbml
差異內容：使用者手動把 rooms.code 的長度由 4 改為 6
spec.md：FR-005 暗號長度由 4 碼改為 6 碼
```

### Good Example

這個範例讀了差異內容，判定對象與對應的需求後補上一列。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 欄位 `code` 的長度由 4 改為 6 | FR-005 |
```

### Bad Example

這個範例以不是自己修改為由略過，交付時核對仍然不通過，下游也不知道資料模型已經改了。

```markdown
核對列出 `data/房間.dbml` 改了沒記，但這不是本次執行修改的檔案，略過不記。
```

## Rule 10 -- 原因必須追溯到最初的來源

**強度：MUST**

原因欄寫的是造成這項異動的最初來源，不是轉手的 owner：連帶異動沿用造成它的上游列的原因（上游列寫 FR-001，連帶的列也寫 FR-001）；依憲法改正既有內容寫「技術：依憲法 <條款 ID> 改正」；技術項.md 的問題造成的寫「技術：」加該技術項的問題；技術修正 plan 沒有 spec.md，原因只能是技術項的問題。同一個對象同時有需求原因與技術原因時，原因欄寫需求編號，改動摘要寫出技術原因的部分（例如「；依憲法 C-API-01 補上分頁參數」）；同時有兩個技術原因時，以「；」並列各自的「技術：…」。以下 Example 皆對照此情境：

```text
api-plan 的表格：| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank` | FR-001 |
data-plan 因此在 rooms 加欄位 rank，並依憲法 C-DATA-02 把同一個檔案中沒有註解的欄位補上註解
```

### Good Example

這個範例的連帶異動沿用上游的 FR-001，依憲法改正的列寫出條款編號。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 新增欄位 `rank`（勝場排名，整數） | FR-001 |
| MOD | `data/房間.dbml` ＞ Table `room_events` | 為 3 個沒有註解的欄位補上 note | 技術：依憲法 C-DATA-02 改正 |
```

### Bad Example

這個範例把連帶異動的原因寫成轉手的 owner，下游以 FR-001 查詢時找不到資料模型的異動，憲法改正也看不出依據哪一條條款。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/房間.dbml` ＞ Table `rooms` | 新增欄位 `rank`（勝場排名，整數） | 技術：配合 api-plan 的契約 |
| MOD | `data/房間.dbml` ＞ Table `room_events` | 為 3 個沒有註解的欄位補上 note | 技術：順便整理 |
```

## Rule 11 -- Rule 改名時對象寫新名稱並寫出原名

**強度：MUST**

修改 feature 中 Rule 的名稱時，對象寫改名後的 `Rule「<新名稱>」`，改動摘要寫出「改名：原為「<舊名稱>」」：基準 commit 已有的 Rule 記一列 MOD，摘要以這段開頭，再寫這條 Rule 其他的改動（只改名稱時寫「其餘不變」）；本 plan 先前的執行才新增的 Rule 照常記 ADD，這段接在新增說明之後；整份 feature 是本 plan 新增、只記了檔案一列時，另為改名的 Rule 記一列 ADD，摘要只寫這段。同一條 Rule 在本 plan 再次改名時沿用同一列，對象改為最新的名稱，「原為」之後依序列出這個 plan 用過的每個舊名稱，以「、」分隔。不得把改名記成舊名稱的 DEL 加新名稱的 ADD，也不得漏寫原名：task 依這段把新舊名稱視為同一條 Rule，已實作的程式才不會被當成撤回而排出移除任務。以下 Example 皆對照此兩個改名：

```text
plan 005（需求 plan）：
1. features/backend/房間.feature 是基準已有的檔案：Rule「房間滿員時必須顯示「房間已滿」」改名為「房間滿員時再加入的玩家必須看到已滿的提示」，提示由「房間已滿」改為「房間已滿，請換一個暗號」（FR-003）
2. features/backend/排行榜.feature 是本 plan 新增的檔案（FR-001），已有勾選的紅燈與綠燈：Rule「排行榜必須顯示「勝場數」欄」改名為「排行榜必須列出每位玩家的勝場數」，Example 不變
```

### Good Example

這個範例為基準已有的 Rule 記 MOD、摘要開頭寫出原名稱；本 plan 新增的檔案除了檔案一列，另為改名的 Rule 記一列 ADD 寫出原名稱。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `features/backend/房間.feature` ＞ Rule「房間滿員時再加入的玩家必須看到已滿的提示」 | 改名：原為「房間滿員時必須顯示「房間已滿」」；提示由「房間已滿」改為「房間已滿，請換一個暗號」 | FR-003 |
| ADD | `features/backend/排行榜.feature` | 整份 feature，2 條 Rule | FR-001 |
| ADD | `features/backend/排行榜.feature` ＞ Rule「排行榜必須列出每位玩家的勝場數」 | 改名：原為「排行榜必須顯示「勝場數」欄」 | FR-001 |
```

### Bad Example

這個範例把基準已有的 Rule 改名記成刪除加新增，新增的排行榜檔案也沒有寫出改名；task 把兩個舊名稱都當成撤回的 Rule，為已實作的程式排出移除任務，移除任務排在修正 Phase 之後，會刪掉新名稱剛驗證過的程式。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| DEL | `features/backend/房間.feature` ＞ Rule「房間滿員時必須顯示「房間已滿」」 | 刪除整條 Rule | FR-003 |
| ADD | `features/backend/房間.feature` ＞ Rule「房間滿員時再加入的玩家必須看到已滿的提示」 | 新增一條 Rule，1 個 Example | FR-003 |
| ADD | `features/backend/排行榜.feature` | 整份 feature，2 條 Rule | FR-001 |
```
