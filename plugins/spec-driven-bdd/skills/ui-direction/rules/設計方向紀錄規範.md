# 設計方向紀錄規範

## Rule 1 -- 只在本 plan 決定方向時撰寫

**強度：MUST**

`ui/設計方向.md` 只在這次判為建立或取代設計方向時撰寫；這個 plan 已有 `ui/設計方向.md` 時，方向是本 plan 決定的，重跑改變了方向就直接改寫這份紀錄，不因 DESIGN.md 已存在而停止更新。判為延伸、只更新產品背景或不用改，且這個 plan 沒有 `ui/設計方向.md` 時，不得產出這份紀錄，回報寫出沿用的既有方向。

### Good Example

這個範例判為延伸，這個 plan 也沒有設計方向紀錄，因此不產出。

```text
判斷：延伸，沿用「社區診所的櫃台」，新增 --color-warning。
ui/設計方向.md：本 plan 沒有 → 不產出（延伸不重新決定方向）。
```

### Bad Example

這個範例在延伸時也產出設計方向紀錄，把沿用的方向寫成這次的決策，審閱者誤以為這個 plan 重新評估過設計方向。

```text
判斷：延伸 → 撰寫 ui/設計方向.md，選定方向：社區診所的櫃台（沿用）。
```

## Rule 2 -- 候選與理由只取自 ui-design 的回報

**強度：MUST**

產品與受眾、候選、參考資料候選、選定方向與各自採用或排除的理由，只能取自 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）這次決定設計方向的回報，不得補上回報中沒有的候選、屬性或理由。回報沒有比較候選時，照實寫出回報的原因（例如使用者指定了美學），不得自行補編，也不得為了取得候選再委派一次。

### Good Example

這個範例的每個候選與理由都對應到 ui-design 的回報；另一個 plan 的回報沒有候選，照實寫出原因。

```text
ui-design 回報：候選 社區診所的櫃台（採用）、藥袋與處方箋（排除：資訊太密）、診間的衛教海報（排除：說教感太重）
設計方向紀錄：候選表三列，屬性與理由與回報相同。

ui-design 回報：使用者指定「仿 1970 年代的鐵道時刻表」，依視覺方向規範直接採用，沒有比較候選
設計方向紀錄：候選段寫「沒有比較候選：使用者指定美學」。
```

### Bad Example

這個範例在回報之外自行加上一個「極簡白」候選並寫出排除理由，紀錄看起來比較完整，卻記下一個從沒被比較過的方向，之後取代時會以為它已被否決。

```text
ui-design 回報：候選 社區診所的櫃台（採用）、藥袋與處方箋（排除）
設計方向紀錄：候選表另加「極簡白（排除：太冷淡）」。
```

## Rule 3 -- 取代時寫出被取代的方向與來源

**強度：MUST**

判為取代時，必須寫出被取代的既有方向（取自 `specs/truth/ui/DESIGN.md` 的「整體方向」）、決定它的 plan（以「整體方向」中的方向名稱搜尋已交付 plan 的 `ui/設計方向.md`，取編號最大的一份；找不到時寫「未記錄」）與取代的原因。建立時不寫這一段。

### Good Example

這個範例寫出被取代的方向、它來自哪個 plan 與取代的原因，之後的 plan 能回頭查當初的候選。

```text
被取代的方向：「社區診所的櫃台」（001-booking）
取代原因：FR-010 品牌改版，診所連鎖化後要呈現專業醫療集團的形象。
```

### Bad Example

這個範例取代時只寫新方向，看不出原本的方向是什麼、在哪裡決定，之後有人提議回到舊方向時無從判斷它當初為什麼被放棄。

```text
選定方向：「醫學期刊的版面」
```

## Rule 4 -- 對應需求只能使用已定義的識別

**強度：MUST**

「對應需求」與「取代原因」引用的需求只能填寫 spec.md 已定義的 FR、NFR、SC 編號、使用者故事（`US<n>`），或本 plan `技術項.md` 中的技術項（`技術項「<技術項的問題>」`），多項以頓號分隔。技術修正 plan 沒有 spec.md，只能填技術項。

### Good Example

這個範例引用 spec.md 中存在的使用者故事與非功能性需求。

```text
- **對應需求**：US1、NFR-002
```

### Bad Example

這個範例以描述代替編號，下游無法追溯這個方向服務哪條需求，需求改寫時也無法判斷方向要不要重新評估。

```text
- **對應需求**：長輩友善、掛號流程
```
