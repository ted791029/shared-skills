# 設計方向紀錄規範

## Rule 1 -- 只在本 plan 決定方向時撰寫

**強度：MUST**

`ui/設計方向.md` 只在 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）回報這次判定為建立或取代設計方向時撰寫；本 skill 帶入建立，ui-design 讀程式碼後改判延伸或品牌不完整時，以回報的判定為準；這個 plan 已有 `ui/設計方向.md` 時，方向是本 plan 決定的，重跑改變了方向就直接改寫這份紀錄，不因 DESIGN.md 已存在而停止更新。判為延伸、只更新產品背景或不用改，且這個 plan 沒有 `ui/設計方向.md` 時，不得產出這份紀錄，回報寫出沿用的既有方向。

### Good Example

這個範例判為延伸，這個 plan 也沒有設計方向紀錄，因此不產出。

```text
判斷：延伸，沿用「社區診所的櫃台」，新增 --color-warning。
ui/設計方向.md：本 plan 沒有 → 不產出（延伸不重新決定方向）。
```

### Bad Example

這個範例在延伸時也產出設計方向紀錄，把沿用的方向寫成這次的決策，審閱者誤以為這個 plan 重新評估過設計方向。

```text
判斷：延伸 → 撰寫 ui/設計方向.md，選定方向：社區診所的櫃台（沿用）。
```

## Rule 2 -- 候選與理由只取自 ui-design 的回報

**強度：MUST**

產品與受眾（產品的運作方式與受眾情境）、候選與其來源類別、熟悉度、撐得住運作方式的理由、長相與結果、每一輪擲骰、使用者選定的卡片與附帶的調整、參考資料候選，以及各自採用或排除的理由，只能取自 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）這次決定設計方向的回報，不得補上回報中沒有的候選、屬性、輪次或理由。候選的結果只能是使用者選定、擲中、推薦、挑戰者、標準做法或未展示；展示過但沒被選定的候選（含標準做法），理由欄寫回報中的原因，回報沒有原因時寫「使用者選了其他卡片」；未展示的候選寫「沒有展示」。回報沒有擲骰時，照實寫出回報的原因（例如使用者指定了美學），不得自行補編，也不得為了取得候選再委派一次。

### Good Example

這個範例的每個候選、輪次與理由都對應到 ui-design 的回報；另一個 plan 的回報沒有擲骰，照實寫出原因。

```text
ui-design 回報：七個候選；第 1 輪一般模式擲中藥袋與處方箋；第 2 輪保守一點擲中社區診所的櫃台；使用者選定第 2 輪第 1 張，附帶「字再大一點」
設計方向紀錄：候選表七列（社區診所的櫃台｜使用者選定，藥袋與處方箋｜擲中｜使用者選了其他卡片…），擲骰紀錄兩列，選定寫「第 2 輪擲中的卡片，附帶調整：字再大一點」。

ui-design 回報：使用者指定「仿 1970 年代的鐵道時刻表」，依視覺方向規範直接採用，沒有擲骰
設計方向紀錄：候選段寫「沒有比較候選：使用者指定美學」，不寫擲骰紀錄。
```

### Bad Example

這個範例在回報之外自行加上一個「極簡白」候選，又把使用者選了其他卡片的候選寫成「太冷淡」，紀錄看起來比較完整，卻記下一個從沒被比較過的方向與一個沒人說過的理由，之後取代時會以為它們已被否決。

```text
ui-design 回報：七個候選，使用者選定社區診所的櫃台
設計方向紀錄：候選表另加「極簡白（排除：太冷淡）」，藥袋與處方箋的理由寫「太冷淡」。
```

## Rule 3 -- 取代時寫出被取代的方向與來源

**強度：MUST**

判為取代時，必須寫出被取代的既有方向（取自 `specs/truth/ui/DESIGN.md` 的「整體方向」）、決定它的 plan（以「整體方向」中的方向名稱搜尋已交付 plan 的 `ui/設計方向.md`，取編號最大的一份；找不到時寫「未記錄」）與取代的原因。建立時不寫這一段。

### Good Example

這個範例寫出被取代的方向、它來自哪個 plan 與取代的原因，之後的 plan 能回頭查當初的候選。

```text
被取代的方向：「社區診所的櫃台」（001-booking）
取代原因：FR-010 品牌改版，診所連鎖化後要呈現專業醫療集團的形象。
```

### Bad Example

這個範例取代時只寫新方向，看不出原本的方向是什麼、在哪裡決定，之後有人提議回到舊方向時無從判斷它當初為什麼被放棄。

```text
選定方向：「醫學期刊的版面」
```

## Rule 4 -- 對應需求只能使用已定義的識別

**強度：MUST**

「對應需求」與「取代原因」引用的需求只能填寫 spec.md 已定義的 FR、NFR、SC 編號、使用者故事（`US<n>`），或本 plan `技術項.md` 中的技術項（`技術項「<技術項的問題>」`），多項以頓號分隔。技術修正 plan 沒有 spec.md，只能填技術項。

### Good Example

這個範例引用 spec.md 中存在的使用者故事與非功能性需求。

```text
- **對應需求**：US1、NFR-002
```

### Bad Example

這個範例以描述代替編號，下游無法追溯這個方向服務哪條需求，需求改寫時也無法判斷方向要不要重新評估。

```text
- **對應需求**：長輩友善、掛號流程
```
