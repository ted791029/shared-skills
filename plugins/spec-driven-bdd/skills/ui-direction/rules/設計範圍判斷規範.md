# 設計範圍判斷規範

## Rule 1 -- 沒有畫面時不建立設計

**強度：MUST**

這次範圍內的使用者故事與 FR 沒有任何使用者看得到的畫面或畫面變更時，不得委派 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）、不得產出或修改 `specs/truth/ui/PRODUCT.md` 與 `specs/truth/ui/DESIGN.md`，這次的結果是「不用改」，回報寫出沒有畫面的依據。

### Good Example

這個範例的需求只改後端的排程與資料表，判斷沒有畫面後直接記錄不用改。

```text
範圍：FR-001 每晚 2 點清除 30 天前的暫存檔、FR-002 清除紀錄寫入稽核表。
判斷：兩條需求都沒有使用者看得到的畫面 → 不用改。
依據：spec.md 的使用者故事只有「系統管理員不需操作，暫存檔自動清除」。
```

### Bad Example

這個範例在沒有畫面的需求上仍委派 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾），產生的產品背景與設計方向沒有任何畫面會用到，DESIGN.md 的異動還讓 ui-ux-plan 被列為待補跑。

```text
範圍：FR-001 每晚 2 點清除 30 天前的暫存檔。
判斷：先建立設計方向以備日後使用 → 委派 ui-design 產出 PRODUCT.md 與 DESIGN.md。
```

## Rule 2 -- 依既有設計系統決定範圍

**強度：MUST**

有畫面時，必須依 `specs/truth/ui/DESIGN.md` 與需求判斷設計方向的範圍，判斷結果與依據寫進回報：

| 情況 | 範圍 |
|---|---|
| DESIGN.md 不存在 | 建立：決定新的設計方向並建立 DESIGN.md |
| DESIGN.md 存在，需求在既有視覺世界中新增或修改畫面 | 延伸：沿用既有方向，只補這次新增的值或元件；既有值足夠時 DESIGN.md 不用改 |
| spec.md 的需求或使用者明確要求換掉現有外觀 | 取代：重新決定設計方向，舊外觀只當作要避開的參考 |

不得因為新增畫面或沒有讀到喜好就判為取代。

### Good Example

這個範例的 DESIGN.md 已存在，需求只新增一個匯出頁，判為延伸，既有值足以呈現時 DESIGN.md 不用改。

```text
DESIGN.md：存在，有品牌藍、中性色、按鈕與表格元件。
需求：FR-004 新增報表匯出頁，使用既有的表格與按鈕。
判斷：延伸。既有色彩與元件足以呈現匯出頁，DESIGN.md 不用改。
```

### Bad Example

這個範例的需求同樣只新增匯出頁，卻判為取代並重新決定方向，既有頁面與新頁面的外觀從此不一致，使用者也沒有要求換掉現有外觀。

```text
DESIGN.md：存在，有品牌藍、中性色、按鈕與表格元件。
需求：FR-004 新增報表匯出頁。
判斷：取代。為匯出頁重新決定一套更現代的設計方向。
```

## Rule 3 -- 有畫面時產品背景必須與本 plan 的 spec.md 比對

**強度：MUST**

這次範圍內有畫面時，`specs/truth/ui/PRODUCT.md` 不存在就必須建立；已存在時，必須逐一比對這次範圍內 spec.md 的使用者故事、使用情境與限制：PRODUCT.md 沒有涵蓋的產品層級事實列為新增，spec.md 明確改變或移除的列為修改或刪除，只更新受影響的節，都已涵蓋時產品背景不用改。PRODUCT.md 沒有記錄品牌個性、必須保留的品牌元素或設計禁區時，把缺少的節列為「由 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）詢問」的異動。不得因為 DESIGN.md 不用改就略過比對，不得因為這次的 spec.md 沒有提到就刪除既有的內容，也不得重寫已涵蓋的節或重問 PRODUCT.md 已記錄的品牌個性、品牌元素與設計禁區。

### Good Example

這個範例的 DESIGN.md 不用改，仍逐一比對 spec.md 與既有產品背景，只把新出現的族群與其主要工作列為異動；PRODUCT.md 已記錄設計禁區，不重問。

```text
判斷：延伸，DESIGN.md 不用改。
PRODUCT.md「使用者」：門市店長（月底對帳）；「設計禁區」：不要像銀行網銀那樣冷冰冰（已記錄）。
spec.md：US1 門市店長匯出當月銷售（已涵蓋）、US2 總部會計每季下載各門市彙總（未涵蓋）。
產品背景異動：「使用者」「使用情境」「使用者要完成的任務」新增總部會計；門市店長保留；品牌個性與設計禁區已記錄，不重問。
```

### Bad Example

這個範例以 DESIGN.md 不用改為由略過比對，spec.md 新出現的總部會計沒有進入產品背景，撰寫原型時只能沿用門市店長的假設，彙總頁被做成店長用的樣子。

```text
判斷：延伸，DESIGN.md 不用改 → 產品背景也不用改，不比對 spec.md。
```

## Rule 4 -- 產品背景只收產品層級的事實

**強度：MUST**

列為產品背景異動的只能是產品層級的事實：使用者族群、他們的使用情境與主要工作、產品用途、新的主要功能區（例如給新族群使用的後台）、產品刻意不做或還做不到的能力，以及改變整個產品能力邊界的限制（平台、帳號、資料保存與同步、法規、無障礙）。單一畫面或既有功能區內的操作、欄位、數值與流程不得寫入，這些以 spec.md 與 `specs/truth/features/` 為準。

### Good Example

這個範例只把改變整個產品能力邊界的限制列為異動，匯出頁的欄位留在 spec.md。

```text
spec.md：FR-001 匯出 CSV 含日期、品項、金額三欄；FR-002 匯出前需登入，資料改存雲端。
產品背景異動：「功能與限制」把「資料只存在瀏覽器，沒有帳號」改為「需登入，資料存在雲端」（FR-002）。
不列入：CSV 的三個欄位（單一畫面的內容，FR-001）。
```

### Bad Example

這個範例把每個 plan 的畫面功能都寫進產品背景，PRODUCT.md 每次都有異動，ui-ux-plan 在每個 plan 都被列為待補跑，產品背景也和 spec.md 重複描述同一份需求。

```text
產品背景異動：「功能與限制」新增「已有功能：報表匯出（CSV，含日期、品項、金額）」。
```

## Rule 5 -- 需求缺口不得在產品背景補完

**強度：MUST**

spec.md 缺少會改變設計的使用者、使用情境或功能時，必須經 dev-finding 記錄，不得自行推測後寫進 `specs/truth/ui/PRODUCT.md`，也不得從 PRODUCT.md 已有的族群中自行挑一個當作這次功能的使用者；只有品牌個性、想給人的感覺、必須保留的品牌元素、設計禁區這類不屬於需求的事實，才由 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）詢問使用者後寫入產品背景或設計系統。

### Good Example

這個範例把「誰會使用」這個需求缺口交給 dev-finding，只把 PRODUCT.md 還沒記錄的品牌感覺留給 ui-design skill（可由 ui-studio plugin 提供，或為與本 skill 資料夾同層的 `ui-design` 資料夾）詢問。

```text
spec.md 沒寫報表匯出頁由誰使用，PRODUCT.md 有門市店長與總部會計，兩者的資訊密度不同 → 以 dev-finding record 記錄。
品牌想給人的感覺 spec.md 沒有、也不屬於需求，PRODUCT.md 也還沒記錄 → 由 ui-design 詢問使用者後寫入 PRODUCT.md。
```

### Bad Example

這個範例從產品背景既有的族群中推測這次的使用者，spec.md 與原型對使用者的認定不同，之後依 spec.md 撰寫的驗收與依原型實作的畫面互相矛盾。

```text
spec.md 沒寫報表匯出頁由誰使用 → PRODUCT.md 有總部會計，推測是總部會計，原型照總部會計的資訊密度設計。
```

## Rule 6 -- 設計系統不存在時不得判為不用改

**強度：MUST**

這個 plan 的 plan.md 已排出前端介面列時，`specs/truth/ui/DESIGN.md` 不存在就必須判為建立，只缺 `specs/truth/ui/tokens.css` 或 `tokens.json` 時必須沿用 DESIGN.md、以撰寫設計系統轉出 tokens；即使本 skill 在這個 plan 已有紀錄、check 沒有列出輸入差異，也不得依差異判為不用改。

### Good Example

這個範例先前判為沒有畫面而記錄了不用改，之後 plan.md 排出前端介面列，再次執行時依設計系統不存在判為建立。

```text
本 skill 紀錄：不用改（先前 spec.md 判斷沒有畫面）；check 沒有輸入差異
plan.md：UI-01 ADD；specs/truth/ui/DESIGN.md 不存在
判斷：建立。委派 ui-design 決定設計方向，盤點後撰寫 DESIGN.md 並轉出 tokens。
```

### Bad Example

這個範例因為已有紀錄又沒有差異就判為不用改，system-analysis 下次執行時仍因 DESIGN.md 不存在而停止，兩個 skill 互相等待，流程卡住。

```text
本 skill 紀錄：不用改；check 沒有輸入差異
plan.md：UI-01 ADD；specs/truth/ui/DESIGN.md 不存在
判斷：輸入沒有變，不用改。
```
