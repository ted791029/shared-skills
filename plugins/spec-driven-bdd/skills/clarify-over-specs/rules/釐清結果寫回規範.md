# 釐清結果寫回規範

## Rule 1 -- 問答必須寫入本次執行的場次

**強度：MUST**

本次執行的每個問答在「## 釐清紀錄」下寫成一行 `- [<覆蓋分類>] 問：<總結之提問> → 答：<使用者選擇與補充的合併結論>`，覆蓋分類為該題面向所屬的需求覆蓋分類名稱。使用者或 PM 直接提出、沒有經過提問的需求變更也各寫一行，問的部分寫成「（使用者提出）<變更的摘要>」；PM 保留了與需求矛盾的 AC 而交辦的改寫（dev-finding review 的保留並取代，或 spec-by-example 回報的矛盾），問的部分寫成「（PM 保留 <AC 編號>）<變更的摘要>」。每次執行第一次寫回時，在既有場次之後新增 `### 場次 YYYY-MM-DD`，當天已有場次時在日期後加上「（第 N 場）」，N 為這是當天的第幾場；同一次執行再問一輪時接在本次新增的場次最後，即使日期相同也不得接進先前執行的場次。spec.md 沒有「## 釐清紀錄」時，在「**建立日期**」行之後、「**輸入**」行之前新增。以下 Example 皆對照此既有內容與本次執行：

```markdown
**建立日期**：2026-10-25

## 釐清紀錄

### 場次 2026-10-25

- 問：第一版要涵蓋哪些假別？ → 答：特休與病假。

### 場次 2026-11-02

- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核；未指定代理人時改由上一層主管審核。

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

```text
本次執行：2026-11-02 下午，處理 dev-finding review 的交辦（PM 保留 AC-12「員工按『撤回』已核准的申請時看到『已核准的申請不能撤回』」，請依它改寫 FR-004「員工必須能撤回自己的請假申請」）；PM 另提出病假申請要能附上證明文件，並回答了一題追問
```

### Good Example

這個範例在同一天新增「第 2 場」，沒有接進上午那次執行的場次；每行標出所屬覆蓋分類，答案寫成合併後的結論，交辦的改寫與使用者直接提出的變更也各寫一行並標明來源。

```markdown
### 場次 2026-11-02

- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核；未指定代理人時改由上一層主管審核。

### 場次 2026-11-02（第 2 場）

- [功能範圍與行為] 問：（PM 保留 AC-12）已核准的請假申請不能撤回 → 答：員工只能撤回尚未核准的請假申請；按「撤回」已核准的申請時顯示「已核准的申請不能撤回」。
- [功能範圍與行為] 問：（使用者提出）病假申請要能附上證明文件 → 答：病假申請可以附上一份證明文件，特休申請不需要。
- [邊界與失敗處理] 問：病假證明文件超過大小上限時要怎麼處理？ → 答：不送出申請，提示「證明文件不可超過 5 MB」，已填的內容保留。

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

### Bad Example

這個範例把下午這次執行的問答接進上午的場次，沒有標出覆蓋分類與來源，答案也只記「照 AC-12」與選項編號，使用者提出的變更沒有寫；日後看不出哪幾題是哪一次執行問的、FR-004 為什麼改，也看不出答案內容。

```markdown
### 場次 2026-11-02

- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核；未指定代理人時改由上一層主管審核。
- 問：已核准的請假申請能不能撤回？ → 答：照 AC-12。
- 問：病假證明文件超過大小上限時要怎麼處理？ → 答：選項 2

**輸入**：使用者描述：「幫我做一個請假申請功能」
```

## Rule 2 -- 答案必須落入對應章節

**強度：MUST**

每個答案除了寫入釐清紀錄，還必須依下表改寫 spec.md 的對應章節；只寫入釐清紀錄而正文未改，視為未寫回。

| 答案性質 | 寫入章節 |
|---|---|
| 新增或縮減範圍、新角色 | 使用者故事（含驗收情境；開新故事或併入既有故事依 Rule 8） |
| 系統行為 | 所屬故事或全域的功能需求 |
| 品質要求 | 對應類別的非功能性需求，並把形容詞改為可量測條件 |
| 資料定義 | 關鍵實體 |
| 例外或失敗處理 | 邊界情況，必要時補驗收情境 |
| 完成指標 | 成功標準 |
| 限制、取捨或不做的範圍 | 假設 |
| 新增、拿掉或改變既有功能的行為 | 對應的故事或需求，並在「受影響的既有功能」補上或改寫該功能的一行（名稱以 `specs/truth/features/用語表.md` 的「模組」表為準） |
| 用語統一 | 全文（依 Rule 4） |

### Good Example

這個範例把代理審核的答案同時寫進故事的驗收情境與功能需求。

```markdown
3. **假設** 主管已指定代理人且主管請假中，**當** 員工送出特休申請，**那麼** 申請送交代理人審核。

- **FR-009**：主管請假期間，系統**必須**將其待審申請改送主管指定的代理人；未指定代理人時改送上一層主管。
```

### Bad Example

這個範例只在釐清紀錄記下答案，功能需求與驗收情境沒有改，下游的 technical-research 與 task 讀正文時看不到代理審核。

```markdown
- [功能範圍與行為] 問：主管請假時，請假申請要由誰審核？ → 答：由主管事先指定的代理人審核。
```

## Rule 3 -- 被推翻的內容必須直接替換

**強度：MUST**

答案或需求變更與 spec.md 中釐清紀錄以外的既有內容衝突或使其失效時，必須直接改寫或刪除原內容，不得保留舊說法再另加新說法；釐清紀錄依 Rule 6 不修改。以下 Example 皆對照此既有內容：

```markdown
- **FR-012**：主管 3 天內未審核的申請，系統**必須**自動核准。

## 假設
- 主管逾期未審核時預設自動核准。
```

### Good Example

這個範例依答案改寫 FR-012，並刪除被推翻的假設。

```markdown
- **FR-012**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管，不得自動核准。

## 假設
```

### Bad Example

這個範例保留舊需求並新增一條相反的需求，假設也未刪除，實作者面對兩條互相矛盾的 FR，無從判斷該做哪一個。

```markdown
- **FR-012**：主管 3 天內未審核的申請，系統**必須**自動核准。
- **FR-013**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管。

## 假設
- 主管逾期未審核時預設自動核准。
```

## Rule 4 -- 同一概念全文只用一個詞

**強度：MUST**

答案確定某個概念的標準用語時，必須把 spec.md 中釐清紀錄以外的同義詞全部改為該用語，並在第一次出現處加註一次 `（原稱「<舊詞>」）`；之後不再出現舊詞。釐清紀錄依 Rule 6 保留原本的用詞。

### Good Example

這個範例統一使用「代理人」，只在第一次出現時加註舊詞。

```markdown
- **FR-009**：主管請假期間，系統**必須**將其待審申請改送代理人（原稱「代簽人」）。
- **FR-010**：代理人**必須**能在待審清單中看到代理的申請。
```

### Bad Example

這個範例新需求用「代理人」，舊需求仍寫「代簽人」，下游會把兩者當成不同角色，各自設計權限與畫面。

```markdown
- **FR-009**：主管請假期間，系統**必須**將其待審申請改送代理人。
- **FR-010**：代簽人**必須**能在待審清單中看到代理的申請。
```

## Rule 5 -- 新增或刪除項目不得重新編號

**強度：MUST**

FR、NFR、SC 與使用者故事的編號是它的身分，plan 中的 acceptance、涵蓋表、truth-changes.md、plan.md 與 tasks.md 都以編號引用。新增項目時，編號取寫回前 check_spec.py 輸出的 `next_ids` 中同類的編號，寫在它所屬的故事或章節；`next_ids` 已排除 spec.md 現有的編號與 plan 中其他檔案引用過的編號，所以同一輪刪除的、以及刪除後仍被引用的編號都不會再給新的項目。刪除項目時整條刪除，並刪除或改寫 spec.md 中引用它的地方；其餘項目的編號一律不變。不得依出現順序重新編號，也不得以 `FR-009a` 插入編號。以下 Example 皆對照此既有內容、check_spec.py 的輸出與本輪答案：

```markdown
### 使用者故事 2 - 主管審核請假（優先順序：P1）

- **FR-009**：系統**必須**在申請核准後通知員工。

### 使用者故事 3 - HR 查詢假別餘額（優先順序：P2）

- **FR-010**：HR **必須**能查詢每位員工的假別餘額。
- **FR-012**：系統**必須**在每年 1 月 1 日重新計算特休天數。

check_spec.py 的 next_ids：FR-013
本輪答案：主管請假時改由代理人審核（新增）；特休不需要每年重新計算（刪除 FR-012）
```

### Good Example

這個範例把新的需求寫在它所屬的故事 2，編號取 next_ids 的 FR-013；FR-012 整條刪除，FR-009、FR-010 不變，plan 中引用它們的涵蓋表與 tasks.md 仍指向同一條需求。

```markdown
### 使用者故事 2 - 主管審核請假（優先順序：P1）

- **FR-009**：系統**必須**在申請核准後通知員工。
- **FR-013**：主管請假期間，系統**必須**將其待審申請改送代理人。

### 使用者故事 3 - HR 查詢假別餘額（優先順序：P2）

- **FR-010**：HR **必須**能查詢每位員工的假別餘額。
```

### Bad Example

這個範例依出現順序重新編號，原本的 FR-010 變成 FR-011；plan 的涵蓋表、truth-changes.md 與 tasks.md 仍寫 FR-010，現在指到代理人審核，下游會把查詢餘額的 Rule 當成代理審核的涵蓋。

```markdown
### 使用者故事 2 - 主管審核請假（優先順序：P1）

- **FR-009**：系統**必須**在申請核准後通知員工。
- **FR-010**：主管請假期間，系統**必須**將其待審申請改送代理人。

### 使用者故事 3 - HR 查詢假別餘額（優先順序：P2）

- **FR-011**：HR **必須**能查詢每位員工的假別餘額（原 FR-010）。
```

## Rule 6 -- 先前的釐清紀錄不得修改

**強度：MUST**

釐清紀錄是過程紀錄：先前場次與本次已寫入的問答一律不改寫、不刪除，即使答案已被推翻或用語已經統一；Rule 3、Rule 4 的改寫只針對釐清紀錄以外的章節。本次的答案推翻先前的答案時，在這一行的答案最後寫明「取代 <場次標題> 的『<被取代的答案摘要>』」，讓讀者知道哪一個答案有效。check_spec.py 回報釐清紀錄某一行引用的編號不存在時，若那是已刪除的需求，不修改那一行，也不為了消除回報而補回需求。以下 Example 皆對照此既有內容與本次的答案：

```markdown
### 場次 2026-10-25

- [邊界與失敗處理] 問：主管逾期未審核的申請要怎麼處理？ → 答：3 天後自動核准。
- [功能範圍與行為] 問：特休天數要不要每年重新計算？ → 答：要，每年 1 月 1 日重新計算（FR-010）。

- **FR-012**：主管 3 天內未審核的申請，系統**必須**自動核准。

本次執行（2026-10-27）的答案：主管 3 個工作天未審核時改送上一層主管，不得自動核准
check_spec.py 的回報：第 4 行引用的 FR-010 不存在（FR-010 已在先前的執行刪除）
```

### Good Example

這個範例保留 2026-10-25 的兩行問答原文，check_spec.py 回報的那一行也不改；在本次的場次新增一行並寫明取代的對象，FR-012 依 Rule 3 改寫。

```markdown
### 場次 2026-10-25

- [邊界與失敗處理] 問：主管逾期未審核的申請要怎麼處理？ → 答：3 天後自動核准。
- [功能範圍與行為] 問：特休天數要不要每年重新計算？ → 答：要，每年 1 月 1 日重新計算（FR-010）。

### 場次 2026-10-27

- [邊界與失敗處理] 問：主管逾期未審核的申請要怎麼處理？ → 答：3 個工作天未審核時改送上一層主管，不得自動核准；取代場次 2026-10-25 的『3 天後自動核准』。

- **FR-012**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管，不得自動核准。
```

### Bad Example

這個範例直接把 2026-10-25 的答案改成新的決定，又為了消除 check_spec.py 的回報刪掉那一行的 FR-010；看不出這兩個決定改過、何時改的，先前依「自動核准」寫成的驗收 feature 與研究紀錄，也查不到當時依據的是哪個答案。

```markdown
### 場次 2026-10-25

- [邊界與失敗處理] 問：主管逾期未審核的申請要怎麼處理？ → 答：3 個工作天未審核時改送上一層主管，不得自動核准。
- [功能範圍與行為] 問：特休天數要不要每年重新計算？ → 答：要，每年 1 月 1 日重新計算。

- **FR-012**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管，不得自動核准。
```

## Rule 7 -- 假設只列使用者還沒確認的預設值

**強度：MUST**

AI 為答案或需求變更沒有涵蓋的細節自選的預設值，寫進需求時必須同時列在「假設」，不得寫進釐清紀錄當成答案，也不得為了讓分類看起來已解決而不寫。這次的範圍內，「假設」中已由使用者在本輪或先前場次確認或推翻的 AI 預設值必須刪除（同一行還有其他預設值時只刪去這一部分），因為該決定已由釐清紀錄記載；記載限制、取捨或不做的範圍的項目不受影響。以下 Example 皆對照此既有內容與本輪的寫回：

```markdown
### 場次 2026-10-25

- [邊界與失敗處理] 問：主管 3 個工作天未審核的申請要怎麼處理？ → 答：改送上一層主管。

- **FR-012**：主管 3 個工作天內未審核的申請，系統**必須**改送上一層主管。

## 假設
- 主管 3 個工作天未審核時預設改送上一層主管（FR-012）。
- 工作天預設不含國定假日（FR-012）。
- 第一版不含排班與補卡。

本輪的寫回：主管請假期間改由指定的代理人審核，新增 FR-014；代理人也在請假時由誰審核沒有問到，AI 選定改送上一層主管
```

### Good Example

這個範例刪除場次 2026-10-25 已確認、卻還留在假設的逾期處理，保留還沒確認的國定假日預設值與不做的範圍，並把這次 AI 選定的代理人請假處理同時寫進 FR-014 與假設。

```markdown
- **FR-014**：主管請假期間，系統**必須**將其待審申請改送主管指定的代理人；代理人也在請假時改送上一層主管。

## 假設
- 工作天預設不含國定假日（FR-012）。
- 第一版不含排班與補卡。
- 代理人也在請假時預設改送上一層主管（FR-014）。
```

### Bad Example

這個範例留下已確認的逾期處理，又把 AI 選定的代理人請假處理只寫進 FR-014；使用者審閱假設時以為逾期處理還沒決定，代理人請假的處理卻看起來像確認過的決定，不會被拿出來推翻。

```markdown
- **FR-014**：主管請假期間，系統**必須**將其待審申請改送主管指定的代理人；代理人也在請假時改送上一層主管。

## 假設
- 主管 3 個工作天未審核時預設改送上一層主管（FR-012）。
- 工作天預設不含國定假日（FR-012）。
- 第一版不含排班與補卡。
```

## Rule 8 -- 新增的範圍依能否單獨交付決定故事

**強度：MUST**

答案或需求變更新增使用者行為時，必須先判斷它能否單獨交付：不經過本 plan 既有故事的流程，就能讓使用者完成一件有價值的事，並寫得出不依賴其他故事的獨立測試時，開新的使用者故事；它是本 plan 既有故事流程中的一個步驟、條件、分支或多出的結果時，併入該故事的驗收情境與功能需求。不得把既有流程的延伸開成新故事，也不得把能單獨交付的使用者目標併入不相關的故事。以下 Example 皆對照此既有內容、check_spec.py 的輸出與本輪的變更：

```markdown
### 使用者故事 1 - 送出請假申請（優先順序：P1）

### 使用者故事 2 - 主管審核請假申請（優先順序：P2）

check_spec.py 的 next_ids：FR-014、使用者故事 3
本輪的變更：病假申請要能附上證明文件；員工要能查看自己過去一年的請假紀錄
```

### Good Example

這個範例把附證明文件併入故事 1，它只是送出申請時多出的一個欄位；查看請假紀錄不必經過送出或審核的流程，寫得出獨立測試，開成新的故事 3。

```markdown
### 使用者故事 1 - 送出請假申請（優先順序：P1）

3. **假設** 員工選擇病假，**當** 附上一份證明文件後送出，**那麼** 申請狀態為「待審核」，申請明細顯示該證明文件。

- **FR-014**：病假申請**必須**能附上一份證明文件；特休申請不提供附件。

### 使用者故事 2 - 主管審核請假申請（優先順序：P2）

### 使用者故事 3 - 查看自己的請假紀錄（優先順序：P3）

**為何此優先順序**：紀錄的內容來自故事 1 送出的申請與故事 2 的審核結果，沒有它們時紀錄是空的。

**獨立測試**：以一位已有 3 筆請假紀錄的員工登入，確認「我的請假紀錄」依日期列出這 3 筆與各自的狀態。

- **FR-015**：員工**必須**能查看自己過去一年的請假紀錄與每筆的狀態。
```

### Bad Example

這個範例把附證明文件開成新的故事 3，它離開送出申請的流程就無法操作，獨立測試仍要先走完故事 1 的送出；同一個送出流程被拆到兩個故事，下游會為它各做一次驗收與任務。

```markdown
### 使用者故事 3 - 上傳病假證明文件（優先順序：P3）

**獨立測試**：員工送出病假申請時附上證明文件，確認申請明細顯示該文件。

- **FR-014**：病假申請**必須**能附上一份證明文件；特休申請不提供附件。
```
