# 缺口影響力判準

## Rule 1 -- 只挑選會改變規格結果的缺口

**強度：MUST**

只有答案會改變使用者故事範圍、需求內容、資料定義、使用者可見行為或驗收結果的缺口，才能列為提問面向。答案不論為何都不影響上述任一項的缺口，不列入提問，在覆蓋總表標為 Outstanding。

### Good Example

這個範例挑選的缺口會改變需求與驗收結果，命名細節則不列入提問。

```markdown
提問面向：
- 主管請假時的代理審核：決定是否新增代理人角色與對應的驗收情境
不列入（Outstanding）：
- 審核按鈕文字用「核准」或「同意」：不影響需求與驗收
```

### Bad Example

這個範例把按鈕文字列為提問面向，占用一題卻不改變任何需求，真正影響驗收的缺口可能因此排到下一輪。

```markdown
提問面向：
- 審核按鈕文字用「核准」或「同意」
- 主管請假時的代理審核
```

## Rule 2 -- 不得挑選技術與實作缺口

**強度：MUST**

缺口屬於技術選型、實作方式、資料儲存結構或任務拆解時，不得列為提問面向，在覆蓋總表標為 Deferred，並註明交由 technical-research、system-analysis 或 task 處理。只有缺少它時連使用者可見的行為都無法定義，才可改寫成使用者可見行為的問題後列入。

### Good Example

這個範例把資料庫選型標為 Deferred，並把「離線時能否送出」改寫成使用者可見行為的問題。

```markdown
提問面向：
- 網路中斷時員工能否先送出請假申請，恢復連線後再補送
Deferred：
- 請假資料要存在 PostgreSQL 或 MongoDB → 交由 technical-research
```

### Bad Example

這個範例把資料庫選型列為提問面向，使用者在規格階段被迫做技術決策，也搶走了 technical-research 的職責。

```markdown
提問面向：
- 請假資料要存在 PostgreSQL 或 MongoDB
```

## Rule 3 -- 依影響乘以不確定性排序

**強度：MUST**

提問面向依「影響 × 不確定性」由高到低排序：影響看答案會改變的範圍大小（故事範圍 > 需求內容 > 單一驗收情境），不確定性看 spec.md 中可合理推得的解讀數量。同一分類有多個面向時，先排影響最大者；不得在高影響分類仍有缺口時，先排兩個以上低影響面向。

### Good Example

這個範例把影響整個故事範圍的代理審核排在第一，只影響單一情境的通知文案排在最後。

```markdown
1. 主管請假時的代理審核（影響故事範圍，可能解讀 3 種）
2. 特休餘額不足時能否預支（影響需求內容，可能解讀 2 種）
3. 審核結果通知的時間上限（影響單一驗收情境，可能解讀 2 種）
```

### Bad Example

這個範例依分類在表格中的順序排列，影響最大的代理審核排到最後，若使用者在第一輪後停止，最關鍵的缺口不會被問到。

```markdown
1. 審核結果通知的時間上限
2. 特休餘額不足時能否預支
3. 主管請假時的代理審核
```

## Rule 4 -- 推薦再問一輪必須有高影響缺口

**強度：MUST**

每輪結束後，只有剩餘缺口中仍有符合 Rule 1 且影響達「需求內容」以上的面向時，才可推薦再問一輪；否則推薦結束並進入下一步。推薦時必須列出這些面向與各自的影響，不得只寫「建議繼續」。

### Good Example

這個範例列出剩餘的高影響面向，讓使用者依具體內容決定是否繼續。

```markdown
剩餘高影響缺口：
- 特休餘額不足時能否預支（影響需求內容）
- 同一天重複送出請假時的處理（影響需求內容）
推薦：再問一輪，上述兩項會改變 FR 與驗收情境。
```

### Bad Example

這個範例剩下的都是低影響缺口卻仍推薦繼續，也沒有列出理由，使用者被拖進一輪不會改變規格的訪談。

```markdown
推薦：建議再問一輪，讓規格更完整。
```

## Rule 5 -- 下一步建議依 plan-package 列出的待補跑

**強度：MUST**

覆蓋總表的下一步建議必須寫出這次新增、修改、刪除的需求編號（含使用者提出與交辦的變更），接著要執行哪些 skill、依什麼順序，一律依 plan-package 在記錄這次結果後列出的待補跑；不得依 plan 資料夾已有哪些產物自行推測要重跑或接著執行的 skill。這次沒有修改任何需求時寫明沒有需求異動；結果是不能改時寫明要先等使用者或 PM 決定擋住的衝突。以下 Example 皆對照此 plan 資料夾與這次的寫回：

```text
specs/plans/004-ranking/：spec.md、features/acceptance/、research.md、plan.md、features/涵蓋表.md、tasks.md（實作進行中）
這次寫回：新增 FR-016，修改 FR-009，刪除 NFR-003
```

### Good Example

這個範例寫出這次異動的需求，要接著執行的 skill 交由 plan-package 依相依表與輸入摘要列出。

```markdown
本次新增 FR-016、修改 FR-009、刪除 NFR-003。接下來請依 plan-package 記錄後列出的待補跑依序執行。
```

### Bad Example

這個範例依 plan 資料夾已有的產物推測要重跑的 skill，漏掉已經跑過的 dsl-refine 與 task；使用者照著做完 `/system-analysis` 就以為完成，FR-016 沒有 Rule 也沒有任務，要到交付時才被待補跑擋下。

```markdown
本次新增 FR-016、修改 FR-009、刪除 NFR-003。依序重跑 `/spec-by-example` 與 `/technical-research`，再執行 `/system-analysis`。
```

## Rule 6 -- 覆蓋總表的狀態依剩下的缺口判定

**強度：MUST**

覆蓋總表中每個分類的狀態，依這次的範圍內、寫回後剩下的缺口判定：

| 狀態 | 標準 |
|---|---|
| Clear | 這次的掃描與重新判定都沒有發現缺口 |
| Resolved | 這次發現的缺口都已由問答或需求變更寫回解決 |
| Open | 剩下的缺口中有符合 Rule 1、但這次沒有問到或沒有得到答案的面向，包括只有 AI 自選的預設值寫在「假設」的子項 |
| Deferred | 剩下的缺口屬於 Rule 2 的技術與實作缺口 |
| Outstanding | 剩下的缺口答案不論為何都不影響 Rule 1 的任一項 |

同一分類剩下不只一種缺口時，依 Open、Deferred、Outstanding 的順序取最前面的狀態；只解決一部分的分類不得標為 Resolved，說明必須分別寫出這次已解決的部分與每個剩下的缺口。以下 Example 皆對照此兩個分類這次的缺口與處理結果：

```text
功能範圍與行為：
- 主管請假時由誰審核（影響故事範圍）→ 已問，答「代理人審核」，寫入 FR-014
- 主管能否審核自己的請假（影響需求內容）→ 使用者在第一輪後選擇結束，沒有問到
邊界與失敗處理：
- 主管逾期未審核時的處理 → 已問，寫入 FR-012
- 上一層主管也逾期時的處理（影響單一驗收情境）→ 沒有問到，以 AI 預設值「再改送 HR」寫入 FR-012 並列於假設
- 退回通知中備註的長度上限（答案不影響需求與驗收）→ 不列入提問
```

### Good Example

這個範例兩個分類都只解決一部分，依剩下的缺口標為 Open；邊界與失敗處理另有不影響規格的缺口，依順序仍取 Open。說明分別寫出已解決的部分與每個剩下的缺口，AI 預設值也寫明列於假設、使用者可推翻。

```markdown
| 功能範圍與行為 | Open | 已解決：主管請假時改由代理人審核（FR-014）。仍缺：主管能否審核自己的請假，影響需求內容，這次沒有問到。 |
| 邊界與失敗處理 | Open | 已解決：主管逾期未審核時改送上一層主管（FR-012）。仍缺：上一層主管也逾期時暫以 AI 預設值「再改送 HR」寫入 FR-012，列於假設，使用者可推翻；退回通知的備註長度上限不影響需求與驗收（Outstanding）。 |
```

### Bad Example

這個範例因為問過的題目都有答案就標為 Resolved，沒有問到的審核自己請假與 AI 自選的預設值從總表上消失；使用者以為這兩個分類都已經確定，下游會照沒有人決定過的行為設計與實作。

```markdown
| 功能範圍與行為 | Resolved | 主管請假時改由代理人審核（FR-014）。 |
| 邊界與失敗處理 | Resolved | 主管逾期未審核時改送上一層主管（FR-012）。 |
```
