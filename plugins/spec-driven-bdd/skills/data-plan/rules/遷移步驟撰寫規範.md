# 遷移步驟撰寫規範

## Rule 1 -- 每一項結構異動都必須有遷移步驟

**強度：MUST**

對照 plan 的 `truth-changes.md` 中 data-plan 一節：資料表、欄位、索引、關聯與約束的每一項新增、修改與刪除，都必須對應到至少一個遷移步驟。步驟依執行順序編號，寫出異動的資料表與具體的結構（欄位型別、預設值、鍵與約束的名稱）。這次只改 note 或交易邊界表、沒有結構異動時，不產生 `data-migration.md`。以下 Example 皆對照此紀錄：

```text
truth-changes.md 的 data-plan 一節：
| ADD | `data/標籤.dbml` | 整份檔案，1 張資料表 `photo_tags`、1 個 Ref | FR-021 |
| MOD | `data/照片.dbml` ＞ Table `photos` | 新增欄位 `tag_count` | FR-021 |
```

### Good Example

這個範例的兩個步驟各對應一列異動，並寫出型別、預設值與鍵的名稱。

```markdown
1. photos：新增欄位 tag_count（INT NOT NULL DEFAULT 0）。
2. 建立 photo_tags：欄位 photo_id（CHAR(36) NOT NULL）、tag（VARCHAR(32) NOT NULL），主鍵 (photo_id, tag)，外鍵 fk_photo_tags_photo_id 參照 photos.id（ON DELETE CASCADE）。
```

### Bad Example

這個範例只寫建立新表，漏掉 photos 新增的欄位，步驟也沒有寫出結構；實作遷移時要回頭比對資料模型的差異才知道要做什麼。

```markdown
1. 建立標籤相關的資料表。
```

## Rule 2 -- 必須寫明既有資料的處理

**強度：MUST**

會影響既有資料列的每個步驟（新增不可為空的欄位、改變型別或約束、刪除欄位或資料表）都必須在「既有資料的處理」寫出既有的列如何處理：由預設值填入、依什麼規則回填，或哪些資料會被刪除。沒有任何既有資料受影響時，寫一行說明原因。

### Good Example

這個範例寫出既有照片的 tag_count 由預設值填入，新表沒有既有資料。

```markdown
- photos 既有的列由預設值填入 tag_count = 0，不需要回填。
- photo_tags 是新的資料表，沒有既有資料。
```

### Bad Example

這個範例沒有交代既有的列，新增的欄位不可為空又沒有說明預設值是否足夠，執行遷移的人無法判斷既有的照片會不會讓遷移失敗。

```markdown
- 無。
```
