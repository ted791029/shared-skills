# 依差異判斷規範

## Rule 1 -- 沒有排進 Wave 時只判斷前置端點寫進 truth 的異動

**強度：MUST**

plan.md 沒有 DB 前綴的介面列（本 skill 沒有排進 Wave，呼叫參數的 Wave 為「無」）而 check 回報本 skill 待補跑時，不照串接規範「本 plan 沒有紀錄時照完整流程」的做法：只逐項判斷 check 列出的契約檔案（本 plan 沒有紀錄時是 `changed_artifacts` 列出的檔案；改了什麼以 `truth-changes.md` 中 api-plan 一節對應的列為準）、`技術項.md` 中「修正：data-plan」的行與 `truth-changes.md` 本節引用的開發發現 AC，資料模型要不要跟著改。需要改時，本端點沒有可以承接的介面列，不修改 `specs/truth/data/`、不撰寫 `data-migration.md`，依資料模型分析規範回報 system-analysis，這次的結果是「不能改」；全部不受影響時依 Rule 3 記錄「不用改」。以下 Example 皆對照此情境：

```text
plan.md：只有 UI、API 前綴的介面列，Wave 中沒有資料庫端
check：data-plan 待補跑、本 plan 沒有紀錄，變了的產物為 truth:contracts/components/schemas/ChatMessage.yaml、truth:contracts/components/schemas/Error.yaml
truth-changes.md 的 api-plan 一節：
| MOD | `contracts/components/schemas/ChatMessage.yaml` | 新增要持久化的必填欄位 `pinned`（訊息是否被釘選） | FR-002 |
| MOD | `contracts/components/schemas/Error.yaml` | `code` 的範例新增 `chat_pin_limit` | FR-003 |
```

### Good Example

這個範例只判斷兩個變了的契約檔案；`pinned` 要保存，但本端點沒有介面列，回報 system-analysis 而不自行修改資料模型。

```markdown
| 差異 | 判斷 | 說明 |
|---|---|---|
| MOD `contracts/components/schemas/ChatMessage.yaml` | 連帶異動 | 重新整理後仍要看到釘選，`pinned` 必須保存：`data/聊天.dbml` 的 Table `chat_messages` 要新增欄位 |
| MOD `contracts/components/schemas/Error.yaml` | 不受影響 | 錯誤碼的範例只出現在回應，不需要保存 |
```

```text
不能改：plan.md 的介面盤點沒有資料庫端，`chat_messages` 要新增欄位 `pinned`（FR-002）。
交給：system-analysis 新增資料庫端「聊天訊息資料表（釘選）」的 MOD 列（FR-002）並排入 Wave。
這次沒有修改 specs/truth/data/、沒有記錄，data-plan 仍是待補跑。
```

### Bad Example

這個範例以沒有排進 Wave 為由，當成與資料庫無關並記錄了不用改；`pinned` 沒有欄位可以保存，重新整理後釘選就消失，data-plan 也不再是待補跑，資料模型與契約不一致直到交付都沒有人發現。

```text
data-plan 沒有排進 Wave，這次的需求只動到畫面與 API → 不用改
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-chat-pin --owner data-plan --result 不用改
```

## Rule 2 -- 技術修正 plan 以技術項指出的對象為範圍

**強度：MUST**

目標是技術修正 plan 時沒有 spec.md 與 plan.md，不讀取它們，也不以缺少介面列為由回報 system-analysis：這次的範圍是 `技術項.md` 中「修正：data-plan」的每一行指出的資料模型對象，以及 check 列出的其他差異（例如 api-plan 這次修改的契約，依 Rule 1 判斷），只增修修正它們所需的對象，`truth-changes.md` 的原因寫「技術：」加該行的問題，結構有異動時照常撰寫 `data-migration.md`，憲法照常核對本 plan 動到的檔案整份。修正需要改變 PM 看得到的行為（例如收緊使用者會碰到的長度或數量限制）時不得修改，這一行的結果是「不能改」，回報需在有需求的 plan 處理。以下 Example 皆對照此技術修正 plan 的技術項：

```text
plan：005-data-fix（技術修正 plan）
- `data/聊天.dbml` 的 `fk_chat_messages_room_id` 宣告為 restrict，表 Note 卻寫房間刪除時連帶刪除訊息（dsl-refine；`specs/truth/data/聊天.dbml`；修正：data-plan）
- `data/聊天.dbml` 的 `chat_messages.text` 宣告 varchar(1000) 太寬，可以改為 varchar(200)（使用者；`specs/truth/data/聊天.dbml`；修正：data-plan）
```

### Good Example

這個範例只改寫與外鍵矛盾的表 Note，以技術項的問題為原因；改窄 `text` 會讓使用者送出失敗，判定為不能改。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `data/聊天.dbml` ＞ Table `chat_messages` | 表 Note 的「房間刪除時連帶刪除訊息」改為「刪除房間前先刪除該房的訊息」，與 `fk_chat_messages_room_id` 的 restrict 一致 | 技術：`fk_chat_messages_room_id` 宣告為 restrict，表 Note 卻寫房間刪除時連帶刪除訊息 |
```

```text
第二行 → 不能改：100 字以內的訊息含組合 emoji 時可能超過 200 個字元，改窄後使用者會看到送出失敗，技術修正 plan 不得改變 PM 看得到的行為，需在有需求的 plan 處理。
這次只改了表 Note、沒有結構異動，不撰寫 data-migration.md。
```

### Bad Example

這個範例兩行都照改，把 `text` 改為 varchar(200) 並寫入遷移步驟；部分 100 字以內的訊息從此存不進去，使用者看得到送出失敗，卻在 PM 不會審核的技術修正 plan 中定案。

```text
修改 聊天.dbml：chat_messages 的表 Note 改寫；text 由 varchar(1000) 改為 varchar(200)
data-migration.md：1. chat_messages：欄位 text 改為 VARCHAR(200) NULL。
```

## Rule 3 -- 第一次判斷就不用改時仍寫一列無異動

**強度：MUST**

本 plan 還沒有本 skill 的紀錄（沒有排進 Wave，或技術修正 plan 第一次判斷），而每個差異都判斷為不受影響時，結果是「不用改」：`truth-changes.md` 的 data-plan 一節沒有任何列時，必須依 truth-changes 的 record 寫一列「無異動」並寫出理由，再以 plan-package 記錄「不用改」，讓 system-analysis 的產出確認與讀 truth-changes.md 的下游分得出本 skill 判斷過。以下 Example 皆對照此情境：

```text
plan.md：只有 UI、API 前綴的介面列，Wave 中沒有資料庫端
check：data-plan 待補跑、本 plan 沒有紀錄，變了的產物為 truth:contracts/components/schemas/Error.yaml
truth-changes.md 的 api-plan 一節：| MOD | `contracts/components/schemas/Error.yaml` | `code` 的範例新增 `chat_pin_limit` | FR-003 |
truth-changes.md 的 data-plan 一節：只有表頭
```

### Good Example

這個範例判斷契約的異動不需要保存任何資料，先為本節寫一列「無異動」，再記錄不用改。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| 無異動 | — | — | 契約只新增錯誤碼的範例，回應內容不需要保存，資料模型不需要修改 |
```

```bash
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-chat-pin --owner data-plan --result 不用改
```

### Bad Example

這個範例只記錄不用改，data-plan 一節維持只有表頭；經 system-analysis 重跑時，產出確認找不到 data-plan 的紀錄而停止，讀 truth-changes.md 的下游也分不出 data-plan 是判斷過不用改，還是根本沒有執行。

```text
契約只新增錯誤碼的範例 → 不用改
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-chat-pin --owner data-plan --result 不用改
truth-changes.md 的 data-plan 一節：只有表頭
```
