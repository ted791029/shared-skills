# 資料模型分析規範

## Rule 1 -- 每個需要持久化的欄位必須有存放位置

**強度：MUST**

前置產出 `x-inner-needs.data` 列出的每個資料名稱都必須對應到一張資料表；API request 與 response schema 中需要持久化的欄位，都必須對應到某張資料表的欄位，名稱不同時以欄位 note 說明對應關係。不得新增前置產出與介面列都沒有需要的資料表。

### Good Example

這個範例的 `has_thumbnail` 對應 API 回應中的同名欄位，並說明用途。

```dbml
  has_thumbnail tinyint [not null, default: 0, note: '1 表示已有縮圖檔']
```

### Bad Example

這個範例漏掉 API 回應中的 `has_thumbnail`，後端只能每次查檔案系統判斷縮圖是否存在。

```dbml
Table photos {
  id char(36) [pk]
  content_hash char(64) [not null]
}
```

## Rule 2 -- 每個索引必須對應實際查詢

**強度：MUST**

每個索引與唯一鍵必須能指出它支援的 API 查詢、排序、分頁或去重需求，非一目了然時以索引 note 寫出。不得建立沒有查詢使用的索引，也不得漏掉分頁與唯一性需要的索引。

### Good Example

這個範例的複合索引寫出它支援相簿內游標分頁。

```dbml
    (album_id, taken_at, id) [name: 'ix_photos_album_taken', note: '供相簿內游標分頁']
```

### Bad Example

這個範例為每個欄位各建一個索引，沒有一個能支援依相簿與拍攝時間的游標分頁，寫入成本增加卻沒有改善查詢。

```dbml
    album_id
    taken_at
    created_at
```

## Rule 3 -- 多筆寫入必須寫出交易邊界

**強度：MUST**

一個 API 操作會寫入多筆資料或多張資料表、或必須全有或全無時，必須在入口檔 Project Note 的交易邊界表寫出交易範圍與失敗處理；與檔案寫入有先後關係時，必須寫出檔案在交易前或交易後處理。

### Good Example

這個範例寫出刪除照片的交易範圍，並說明檔案只在交易成功後刪除。

```markdown
| 刪除照片 | 刪除 photos 列；若該相簿已無照片則刪除 albums 列 | 整筆回滾，檔案刪除只在交易成功後執行 |
```

### Bad Example

這個範例只寫「使用交易」，看不出範圍與失敗處理，實作時可能先刪檔案再回滾資料，留下指向不存在檔案的資料列。

```markdown
| 刪除照片 | 使用交易 | 回滾 |
```

## Rule 4 -- 其他模組的資料表以 use 引用

**強度：MUST**

`Ref` 的父表定義在其他模組檔時，必須在本檔開頭以 `use { table <資料表> } from './<模組>'` 引用，不得在本檔重抄該表的定義，也不得省略引用。同一張資料表只能在一個模組檔定義；plan.md 或其他輸入文件要求重複定義時，仍依本規則引用，並把該衝突列入回報。

### Good Example

這個範例的 photo_tags 參照照片模組的 photos，在檔案開頭以 use 引用，photos 的定義只存在於 `照片.dbml`。

```dbml
use {
  table photos
} from './照片'

Table photo_tags {
  photo_id char(36) [not null, note: '被標記的照片']
  tag varchar(32) [not null, note: '標籤文字']
}

Ref fk_photo_tags_photo_id: photo_tags.photo_id > photos.id [delete: cascade]
```

### Bad Example

這個範例在標籤模組重抄 photos 的定義，同一張資料表有兩份定義，解析整份資料模型時回報資料表已存在；之後修改 photos 時也只會改到其中一份。

```dbml
Table photos {
  id char(36) [pk, note: '照片識別']
  album_id char(36) [not null, note: '所屬相簿']
}

Table photo_tags {
  photo_id char(36) [not null, note: '被標記的照片']
  tag varchar(32) [not null, note: '標籤文字']
}

Ref fk_photo_tags_photo_id: photo_tags.photo_id > photos.id [delete: cascade]
```

## Rule 5 -- 交易邊界只寫範圍與失敗處理

**強度：MUST**

交易邊界表的「範圍」只寫動到哪些資料表、更新哪些欄位（可概括）、插入或刪除什麼；「失敗處理」只寫回滾範圍、擋下重複寫入的約束，以及檔案在交易前或交易後處理。不得寫驗證條件與其先後順序、寫入演算法、鎖、推播或計時。

### Good Example

這個範例的範圍只寫更新的表與欄位，失敗處理只寫回滾與擋下重複的約束。

```markdown
| 移動相簿順序 | 更新 albums（position、order_mode） | 整筆回滾；uk_albums_position 擋下並發移動造成的重複位置 |
```

### Bad Example

這個範例把驗證順序、重新編號的演算法與推播都寫進交易邊界表，與 API 契約和程式碼重複，表格每列長到無法掃讀，演算法一改就與程式碼不一致。

```markdown
| 移動相簿順序 | 在交易內重新讀取 albums 並驗證相簿與 beforeAlbumId 存在（否則 404、422）；以 beforeAlbumId 的 position 減 0.5 暫存，再依 position 由小到大重新編號為 1 到 N，order_mode 改為 custom；commit 後推播 album_order 給所有連線 | 整筆回滾；uk_albums_position 擋下並發移動造成的重複位置 |
```

## Rule 6 -- note 只寫意義與結構表達不出的約束

**強度：MUST**

欄位與索引的 note 以一句寫出意義，Enum 型別或欄位名稱已能說明時可省略；表 Note 只寫這張表存什麼、DBML 結構表達不出的約束（如 CHECK），以及宣告與實際資料庫不一致之處。不得寫 FR、NFR、R 等追溯編號，不得寫業務規則或程式如何使用這個欄位。需求決定的界限只以型別、`default` 與表 Note 的 CHECK 表達，note 不再以文字重述數值；資料模型對應哪些需求記在 truth-changes.md 的原因欄與 plan.md 的介面列，不在資料模型中以編號引用。

### Good Example

這個範例的欄位 note 各一句，表 Note 只寫存什麼與 DBML 表達不出的 CHECK 約束。

```dbml
Table photos {
  id char(36) [pk, note: '照片識別']
  content_hash char(64) [not null, note: '檔案內容 SHA-256，用於去重']
  has_thumbnail tinyint [not null, default: 0, note: '1 表示已有縮圖檔']

  indexes {
    content_hash [unique, name: 'uk_photos_content_hash']
  }

  Note: '''
    每一張已匯入照片的中繼資料；檔案本體不存放於此。
    CHECK ck_photos_has_thumbnail：has_thumbnail 只能為 0 或 1。
  '''
}
```

### Bad Example

這個範例在欄位 note 寫進追溯編號、背景任務流程與前端行為，讀者找不到欄位本身的意義，流程一改也不會有人記得回來改這裡。

```dbml
  has_thumbnail tinyint [not null, default: 0, note: '1 表示已有縮圖檔（FR-006）；匯入 API 收到縮圖時設為 1，縮圖產生失敗則維持 0 並由背景任務每 10 分鐘重試，重試三次仍失敗時前端顯示預設圖（FR-011、R-04）']
```

## Rule 7 -- 上游問題只回報不自行修改

**強度：MUST**

分析或判斷差異時發現上游問題，必須只回報，不得自行修改上游的產物，也不得為受影響的資料表增修資料模型與遷移步驟；不受影響的資料表照常完成，這次的結果是「不能改」。上游問題與交給的對象如下：

| 上游問題 | 交給 |
|---|---|
| 要新增、修改或移除的資料表在 plan.md 的介面盤點沒有 ADD、MOD、DEL 的列（包括標「無」的介面），或介面列的依據需求缺了驅動它的需求 | system-analysis：回報要新增或修改的介面列（介面、異動，以及依據需求或「技術：」開頭的原因） |
| 前置端點的產出錯了或缺了（例如需要刪除的資料，契約卻沒有刪除操作） | 經 dev-finding 記錄，交給回覆寫明的應修正的擁有者 |

技術項或交辦要改的資料表在本 plan 已是 ADD 或 MOD 時，技術項就是依據，不算依據需求缺漏。技術修正 plan 沒有 plan.md，介面盤點的問題不適用本條。以下 Example 皆對照此介面列與前置產出：

```text
本 plan 的介面列：| DB-01 | 聊天訊息資料表（釘選、清除紀錄） | 資料庫端 | MOD | FR-002、FR-004 |
truth-changes.md 的 api-plan 一節：
| MOD | `contracts/components/schemas/ChatMessage.yaml` | 新增必填欄位 `pinned`（訊息是否被釘選） | FR-002 |
| MOD | `contracts/components/schemas/RoomState.yaml` | 新增欄位 `rank`（要保存的勝場排名） | FR-001 |
契約：沒有清除聊天紀錄的操作（FR-004 要求房主可以清除聊天紀錄）
```

### Good Example

這個範例照常完成不受影響的釘選；契約缺少清除紀錄的操作經 dev-finding 交給契約的擁有者，`rank` 沒有可以承接的介面列則回報 system-analysis，兩者都不自行補上，沒有記錄。

```text
DB-01 釘選 → `chat_messages` 新增欄位 `pinned`，資料模型完成並通過解析與核對。
DB-01 清除紀錄 → 不能改：FR-004 要清除聊天紀錄，契約卻沒有這個操作，交易邊界無從設計；經 dev-finding 記錄，應修正的擁有者 api-plan，補上操作後再判斷。
rank → 不能改：`rank` 要保存在 `rooms`，但介面盤點沒有資料庫端 `rooms` 資料表的列；交給 system-analysis 新增資料庫端「房間資料表（勝場排名）」的 MOD 列（FR-001）並排入 Wave。
這次沒有修改 `rooms`、沒有記錄，data-plan 仍是待補跑。
```

### Bad Example

這個範例直接在 `rooms` 加上欄位並寫入遷移步驟；介面盤點與 truth 的異動對不上，data-plan 的輸入也只含 DB-01 引用的 FR-002，之後 FR-001 改了排名的保存方式而契約不變時，data-plan 不會被列為待補跑，`rooms` 的設計就與需求脫節。

```text
介面盤點沒有 rooms，但契約已經有 rank → 在 data/房間.dbml 的 rooms 加上 rank，data-migration.md 補一個步驟；記錄改了。
```
