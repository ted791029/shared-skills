# 契約拆檔規範

## Rule 1 -- 一個路徑一個檔，位置由路徑與模組決定

**強度：MUST**

每個 API 路徑必須各自寫成一個路徑檔，同一路徑的所有方法寫在同一個檔案，最上層的鍵是 HTTP 方法。檔名是路徑去掉開頭的「/」、把其餘的「/」換成「_」再加上 `.yaml`；檔案放在 `paths/<模組>/`，模組是該路徑各操作的第一個 tag，沿用 truth 既有的模組名稱，既有模組都不適用時才新增。不得把多個路徑寫在同一個檔案，也不得依方法拆成多個檔案。

### Good Example

這個範例的路徑 `/api/albums/{albumId}/photos` 屬於「照片」模組，檔案是 `paths/照片/api_albums_{albumId}_photos.yaml`，兩個方法寫在同一個檔案。

```yaml
get:
  tags:
    - 照片
  summary: 列出相簿內照片
post:
  tags:
    - 照片
  summary: 把照片加入相簿
```

### Bad Example

這個範例把同一路徑的兩個方法拆成 `paths/照片/list_photos.yaml` 與 `paths/照片/add_photo.yaml`，檔名看不出路徑，入口檔的一個路徑也無法同時掛上兩個檔案。

```yaml
get:
  tags:
    - 照片
  summary: 列出相簿內照片
```

## Rule 2 -- 入口檔只掛載，不寫內容

**強度：MUST**

入口檔 `openapi.yaml` 只放 `openapi`、`info`、`servers`、`tags`、`paths` 與 `components`。`paths` 的每個路徑、`components` 底下的每個 schema 與參數，都只有一行 `$ref` 指向它的檔案，`components` 的鍵與檔名相同；不得在入口檔寫操作或結構的內容。新增路徑檔、schema 檔或參數檔時必須在入口檔加上對應的一項，模組是新的時在 `tags` 補上；刪除檔案時必須移除那一項，模組已沒有任何路徑時一併移除它的 tag。

### Good Example

這個範例新增「標籤」模組的路徑檔與 TagList，入口檔補上 tag、路徑與 schema 各一項。

```yaml
tags:
  - name: 相簿
  - name: 照片
  - name: 標籤
paths:
  /api/albums:
    $ref: paths/相簿/api_albums.yaml
  /api/photos/{photoId}/tags:
    $ref: paths/標籤/api_photos_{photoId}_tags.yaml
components:
  parameters:
    photoId:
      $ref: components/parameters/photoId.yaml
  schemas:
    Error:
      $ref: components/schemas/Error.yaml
    TagList:
      $ref: components/schemas/TagList.yaml
```

### Bad Example

這個範例把新操作直接寫進入口檔，新的 TagList 也沒有掛進 `components`；入口檔會隨每次迭代變長，不再是整份契約的目錄，下游也無法從 truth 異動紀錄的檔案路徑看出哪個操作被改過。

```yaml
paths:
  /api/albums:
    $ref: paths/相簿/api_albums.yaml
  /api/photos/{photoId}/tags:
    post:
      tags:
        - 標籤
      summary: 為照片加上標籤
components:
  schemas:
    Error:
      $ref: components/schemas/Error.yaml
```

## Rule 3 -- 共用的結構各自一個檔，以相對路徑引用

**強度：MUST**

有名稱的請求與回應結構各自寫成 `components/schemas/<名稱>.yaml`，多個操作共用的參數各自寫成 `components/parameters/<名稱>.yaml`，檔名與名稱相同。路徑檔以 `../../components/…` 引用，schema 之間以 `./<名稱>.yaml` 引用，不得使用 `#/components/…`。只有一個操作使用、沒有其他地方引用的簡單結構可以直接寫在路徑檔。新檔案的 YAML 寫法比照既有的檔案。

### Good Example

這個範例的共用參數 `components/parameters/albumId.yaml` 自成一個檔，路徑檔以相對路徑引用它與共用的 Error。

```yaml
name: albumId
in: path
required: true
description: 相簿識別
schema:
  type: string
```

```yaml
get:
  parameters:
    - $ref: ../../components/parameters/albumId.yaml
  responses:
    '404':
      description: 相簿不存在
      content:
        application/json:
          schema:
            $ref: ../../components/schemas/Error.yaml
```

### Bad Example

這個範例沿用單一檔案的寫法引用 `#/components/…`，路徑檔裡沒有 components，引用指不到任何內容。

```yaml
get:
  parameters:
    - $ref: '#/components/parameters/albumId'
  responses:
    '404':
      description: 相簿不存在
      content:
        application/json:
          schema:
            $ref: '#/components/schemas/Error'
```

## Rule 4 -- 只增修盤點列出的檔案

**強度：MUST**

只能新增、修改、刪除盤點結果列出的對象。修改既有的操作或 schema 時在原檔修改那個對象，同一個檔案的其他內容與沒有列出的檔案一字不改，不得重排順序、改寫說明或調整格式。刪除操作時刪除它的路徑檔（該路徑還有其他方法時只刪除那個方法）與入口檔的那一項；只被它使用的 schema 與參數檔連同入口檔的那一項一併刪除，仍被其他操作引用的保留。以下 Example 皆對照此盤點結果與既有契約：

```text
盤點結果：
| DEL | `contracts/paths/照片/api_photos_{photoId}_neighbors.yaml` | 刪除取得前後張的操作 | FR-022 |
| DEL | `contracts/components/schemas/PhotoNeighbors.yaml` | 只被取得前後張的操作使用，一併刪除 | FR-022 |
既有契約：Photo.yaml 被列出照片與取得前後張兩個操作引用
```

### Good Example

這個範例刪除路徑檔、只被它使用的 PhotoNeighbors 與入口檔的兩項，仍被列出照片引用的 Photo.yaml 與其他檔案都沒有異動。

```text
刪除 paths/照片/api_photos_{photoId}_neighbors.yaml
刪除 components/schemas/PhotoNeighbors.yaml
修改 openapi.yaml：移除 paths 的 /api/photos/{photoId}/neighbors 與 components 的 PhotoNeighbors
```

### Bad Example

這個範例只刪除路徑檔，入口檔仍掛著不存在的檔案，PhotoNeighbors 也成為沒有操作引用的檔案；又順手改寫了盤點沒有列出的 Photo.yaml 的說明，truth 異動紀錄多出一筆沒有原因的修改。

```text
刪除 paths/照片/api_photos_{photoId}_neighbors.yaml
修改 components/schemas/Photo.yaml：把各欄位的說明改得更完整
```
