# 依差異判斷規範

## Rule 1 -- 沒有排進 Wave 時只判斷技術項與開發發現

**強度：MUST**

plan.md 沒有 API 前綴的介面列（本 skill 沒有排進 Wave，呼叫參數的 Wave 為「無」）而 check 回報本 skill 待補跑時，不照串接規範「本 plan 沒有紀錄時照完整流程」的做法：前端的產出寫在 plan 資料夾，不算前置端點寫進 truth 的異動，只逐項判斷 `技術項.md` 中「修正：api-plan」的行與 `truth-changes.md` 本節引用的開發發現 AC（本 plan 沒有紀錄時，check 只以 `changed_artifacts` 列出變了的產物）。需要修改任何 API 時，本端點沒有可以承接的介面列，依 API 分析規範回報 system-analysis，這次的結果是「不能改」；全部不受影響時依 Rule 3 記錄「不用改」。以下 Example 皆對照此情境：

```text
plan.md：只有 UI 前綴的介面列，Wave 中沒有後端
check：api-plan 待補跑、本 plan 沒有紀錄，變了的產物為 plan:技術項.md
技術項.md：
- 契約中送出聊天訊息的 429 回應少了 `Retry-After` 標頭，程式有回傳（implement；`backend/app/routes/api.py:212`；修正：api-plan）
```

### Good Example

這個範例只判斷點名本 skill 的一行，標頭要補進契約，但本 plan 沒有後端的介面列，回報 system-analysis 而不自行修改契約。

```text
技術項 → 連帶異動：`contracts/paths/聊天/api_rooms_{roomId}_messages.yaml` 的 POST 429 回應補上 `Retry-After` 標頭。
不能改：本 plan 的介面盤點沒有後端，契約的修改沒有可以承接的介面列。
交給：system-analysis 新增後端「聊天訊息 API」的 MOD 列（技術：契約的 429 回應少了 Retry-After 標頭）並排入 Wave。
這次沒有修改 contracts/、沒有記錄，api-plan 仍是待補跑。
```

### Bad Example

這個範例因為本 plan 沒有紀錄就照完整流程，依 `ui/ui-contract.md` 重新推導全部操作並改寫多個路徑檔；本 plan 沒有任何後端介面列作為依據，truth-changes.md 卻多出一串異動，以契約為輸入的 data-plan、dsl-refine 與 task 都被列為待補跑。

```text
api-plan 本 plan 沒有紀錄 → 完整流程：依 UI-01、UI-02 需要內層提供的資料重新推導聊天與房間的 API，改寫 5 個路徑檔與 3 個 schema。
```

## Rule 2 -- 技術修正 plan 以技術項指出的對象為範圍

**強度：MUST**

目標是技術修正 plan 時沒有 spec.md 與 plan.md，不讀取它們，也不以缺少介面列為由回報 system-analysis：這次的範圍只有 `技術項.md` 中「修正：api-plan」的每一行指出的契約對象，只增修修正它所需的對象，`truth-changes.md` 的原因寫「技術：」加該行的問題，憲法照常核對本 plan 動到的契約檔案整份。修正需要改變 PM 看得到的行為（例如會顯示在畫面上的錯誤訊息）時不得修改，這一行的結果是「不能改」，回報需在有需求的 plan 處理。以下 Example 皆對照此技術修正 plan 的技術項：

```text
plan：005-contract-fix（技術修正 plan）
- 契約把 `SkillCounts` 的 `change_answer_left` 寫成字串，程式回傳整數（implement；`backend/app/services/snapshot.py:57`；修正：api-plan）
- 契約 Error 的 `chat_too_frequent` 訊息範例與其他聊天錯誤的語氣不一致（使用者；`specs/truth/contracts/components/schemas/Error.yaml`；修正：api-plan）
```

### Good Example

這個範例只修正型別並以技術項的問題為原因；錯誤訊息會顯示在畫面上，判定為不能改。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/SkillCounts.yaml` | `change_answer_left` 的型別由 string 改為 integer | 技術：契約把 `SkillCounts` 的 `change_answer_left` 寫成字串，程式回傳整數 |
```

```text
第二行 → 不能改：`chat_too_frequent` 的訊息會顯示在聊天輸入下方，改寫它就改變使用者看到的文字，技術修正 plan 不得改變 PM 看得到的行為，需在有需求的 plan 處理。
```

### Bad Example

這個範例順手改寫同一份 schema 其他欄位的說明，又改了錯誤訊息的措辭；說明的改寫沒有技術項作為原因，錯誤訊息則是使用者看得到的文字，卻在 PM 不會審核的技術修正 plan 中定案。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/components/schemas/SkillCounts.yaml` | `change_answer_left` 改為 integer，並改寫 `triple_guess_left` 的說明 | 技術：契約把 `SkillCounts` 的 `change_answer_left` 寫成字串，程式回傳整數 |
| MOD | `contracts/components/schemas/Error.yaml` | `chat_too_frequent` 的訊息範例改為「傳太快了，等一下再送」 | 技術：訊息範例與其他聊天錯誤的語氣不一致 |
```

## Rule 3 -- 第一次判斷就不用改時仍寫一列無異動

**強度：MUST**

本 plan 還沒有本 skill 的紀錄（沒有排進 Wave，或技術修正 plan 第一次判斷），而每個差異都判斷為不受影響時，結果是「不用改」：`truth-changes.md` 的 api-plan 一節沒有任何列時，必須依 truth-changes 的 record 寫一列「無異動」並寫出理由，再以 plan-package 記錄「不用改」，讓 system-analysis 的產出確認與讀 truth-changes.md 的下游分得出本 skill 判斷過。以下 Example 皆對照此情境：

```text
plan.md：只有 UI 前綴的介面列，Wave 中沒有後端
check：api-plan 待補跑、本 plan 沒有紀錄，變了的產物為 plan:技術項.md
技術項.md：- 契約中聊天訊息的 `created_at` 沒有寫時區（dsl-refine；`specs/truth/contracts/components/schemas/ChatMessage.yaml`；修正：api-plan）
truth-changes.md 的 api-plan 一節：只有表頭
`contracts/components/schemas/ChatMessage.yaml`：`created_at` 的說明已寫「發送時間，UTC ISO 8601，含毫秒」
```

### Good Example

這個範例判斷技術項指出的問題在契約中已不存在，先為本節寫一列「無異動」，再記錄不用改。

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| 無異動 | — | — | 技術項指出的時區已寫在 ChatMessage.yaml 的 created_at，契約不需要修改 |
```

```bash
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-chat-pin --owner api-plan --result 不用改
```

### Bad Example

這個範例只記錄不用改，api-plan 一節維持只有表頭；經 system-analysis 重跑時，產出確認找不到 api-plan 的紀錄而停止，讀 truth-changes.md 的下游也分不出 api-plan 是判斷過不用改，還是根本沒有執行。

```text
技術項指出的時區已寫在契約 → 不用改
uv run "D:/plugins/spec-driven-bdd/skills/plan-package/scripts/plan_trace.py" record specs/plans/004-chat-pin --owner api-plan --result 不用改
truth-changes.md 的 api-plan 一節：只有表頭
```
