# 錨點對照規範

## Rule 1 -- 需讀原因不得當作內容來源

**強度：MUST**

需讀原因只說明該位置是哪些決定的依據，實作需要的欄位、值、文案與行為必須取自錨點原文。不得只讀需讀原因就推測原文內容，也不得以記憶中的同類規格取代原文。

### Good Example

這個範例依需讀原因知道要找兩個設定的預設值，實際值取自 research.md 原文。

```text
必讀：research.md › R-13 — 新增設定的名稱與預設值以此為準
原文：DISCONNECT_GRACE_SECONDS（預設 10，見 R-08）、EFFECT_SECONDS（預設 3，見 R-07）
實作：backend/app/config.py 依原文設定兩個預設值
```

### Bad Example

這個範例只看需讀原因，依 001 斷線重連的印象把寬限設為 60 秒，對手斷線後要等一分鐘才判定離線，與 spec US2 情境 15 的 10 秒不符。

```text
需讀原因提到斷線寬限 → 沿用 001 的 RECONNECT_GRACE_SECONDS 預設 60，DISCONNECT_GRACE_SECONDS = 60
```

## Rule 2 -- 錨點必須定位到原文中的同名位置

**強度：MUST**

錨點依 ` › ` 逐層定位到檔案中的段落標題、operationId、Table、頂層定義（如 `type Room`、`service RoomService`）、需求編號（如 `NFR-010`）、研究編號（如 `R-08`）、識別碼或 `data-testid`；同一層以「、」並列多個目標時，每個目標都要各自在該層找到。任一層或任一並列目標在原文找不到同名位置時視為錨點找不到，不得改用名稱相近的段落或整份檔案替代。

### Good Example

這個範例逐一定位並列的兩個 Table，`Table room_events` 找不到時判定錨點找不到。

```text
錨點：data-model.dbml › Table rooms、Table room_events
data-model.dbml 有 Table rooms，沒有 Table room_events → 錨點找不到，T017 開始前停止
```

### Bad Example

這個範例只找到並列的第一個目標就視為定位成功，`room_events` 的欄位與唯一索引沒有原文依據，只能由 bdd 綠燈時自行推測。

```text
錨點：data-model.dbml › Table rooms、Table room_events
找到 Table rooms → 定位成功，委派 /bdd red
```

## Rule 3 -- 任務描述與原文不一致時不得自行擇一

**強度：MUST**

任務描述中的具體值、名稱、狀態碼、路徑或行為，與錨點原文矛盾時，或同一任務的兩個錨點原文彼此矛盾時，視為錨點衝突。任務描述寫了原文未提及的細節不算衝突，依任務描述實作。

### Good Example

這個範例區分衝突與補充：預設值矛盾判定衝突，原文未提的設定讀取方式依任務描述實作。

```text
任務：EFFECT_SECONDS 預設 2，以 float() 轉型
research.md › R-13：EFFECT_SECONDS（預設 3，見 R-07），未提轉型方式
→ 預設值衝突，停止 T003
```

### Bad Example

這個範例遇到矛盾時選擇「看起來比較新」的錨點原文，任務描述與實作從此不一致，下一個依賴回合順延秒數的任務又依任務描述的 2 秒設計。

```text
任務寫 2，R-13 寫 3 → research 比較權威，改用 3 並繼續
```
