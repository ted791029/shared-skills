# 輸入完整性規範

## Rule 1 -- 腳本回報任一缺漏即停止

**強度：MUST**

tasks.md 不存在、腳本回報沒有任何任務、`missing_anchors` 不為空，或 `scope_problems` 中有範圍內的任務時，必須停止，不得開始任何任務。不得自行補拆任務、改寫範疇、刪除行號或指向缺漏檔案的必讀；任務格式不符或範疇有問題（含行號不是 Rule 的標題行、Rule 名稱在 feature 中找不到、與 Phase 標題不一致）時請使用者以 task 修正 tasks.md，範疇或必讀指向的 feature、plan 的檔案或 truth 的檔案不存在時請使用者執行產出該檔案的上游 skill（feature 與 dsl.md 為 dsl-refine，介面文檔為 system-analysis）。

### Good Example

這個範例在範疇的行號不是 Rule 的標題行時停止，指出由 task 修正。

```text
無法開始實作：階段任務的範疇有問題。
- T008 範疇 `specs/truth/features/backend/改答案.feature:8`：範疇的行號 8 不是 Rule 的標題行
請以 task 重新產出 tasks.md，再重新執行 /implement。
```

### Bad Example

這個範例自行刪掉行號繼續執行，tasks.md 與實際執行的範疇不一致，之後 T009 綠燈也用這個範疇呼叫 bdd，使用者無法從 tasks.md 看出實際執行了什麼。

```text
T008 範疇的 :8 不是 Rule → 改用 specs/truth/features/backend/改答案.feature，開始執行 T008
```

## Rule 2 -- 範圍篩選必須對應到具體任務編號

**強度：MUST**

使用者的範圍篩選必須換算成任務編號清單再執行：指定 Phase 時取該 Phase 的所有任務，指定「從 Phase N 開始」時取 Phase N 到最後一個 Phase，指定功能名稱（如「改答案」）時取 Phase 標題中檔名為該名稱的所有 Feature Phase，指定任務編號時取所列任務；沒有篩選時取所有未完成任務。已勾 `[X]` 的任務不重做。篩選無法對應到唯一的任務集合時，必須詢問使用者。

### Good Example

這個範例把「只做改答案」換算成三個同名 Feature Phase 的任務。

```text
範圍：只做改答案 → Phase 3 database/改答案.feature、Phase 4 backend/改答案.feature、Phase 5 frontend/改答案.feature 的 T005～T013（共 9 個任務）
```

### Bad Example

這個範例把「只做改答案」解讀成「做到改答案為止」，連同 Setup 與 Foundational 一起執行，超出使用者指定的範圍。

```text
範圍：只做改答案 → T001～T013
```

## Rule 3 -- 範圍內任務之前有未完成任務時不得自動補做

**強度：MUST**

tasks.md 順序中排在範圍內任務之前、且不在範圍內的任務，有任何一個未完成時，必須停止並列出這些任務（腳本的 `scope_blocked` 中的 `unfinished_earlier_tasks`），由使用者決定是否擴大範圍。不得自動把它們加入範圍執行，也不得略過順序直接執行範圍內任務；同一個 Phase 內較前的任務也算。

### Good Example

這個範例只指定 T009 綠燈，同一個 Phase 的 T008 紅燈未完成，停止請使用者決定。

```text
無法開始 T009：以下排在前面的任務未完成且不在範圍內。
- Phase 4 backend/改答案.feature：T008 [紅燈]
請執行 /implement T008、T009，或指定範圍「從 Phase 4 開始」。
```

### Bad Example

這個範例只檢查較早的 Phase，T008 與 T009 同在 Phase 4 就直接執行 T009，bdd green 因範疇沒有紅燈（step 未定義）而停下，使用者被打斷處理一個順序就能避免的停下。

```text
Phase 1～3 已完成 → 執行 T009 → /bdd green specs/truth/features/backend/改答案.feature
```
