# 實作範圍規範

## Rule 1 -- 階段任務連同 Phase 標頭委派 bdd

**強度：MUST**

任務標 `[紅燈]`、`[綠燈]`、`[重構]`、`[重跑]` 時，必須依下表呼叫 bdd：範疇照 `next_task` 的 `scope` 原樣傳入（含 `<feature 路徑> ＞ Rule「…」` 的 Rule 名稱寫法），不得改寫路徑、把 Rule 名稱換成行號、加上行號或合併其他任務的範疇；同時把 `next_task.phase_header` 的 NFR 約束、預計修改與 📎 必讀（錨點與需讀原因）原文附給 bdd。NFR 重構 Phase 與「重跑」Phase 的任務沒有 Phase 標頭，改附任務描述與逐任務的 📎 必讀（`[重跑]` 的描述寫出只改說明的句型或參數，必讀指向 `truth-changes.md` 中標明改動的列，bdd 依此比對既有 step）。階段任務由 bdd 撰寫 step definitions、Driver 與產品程式（`[重跑]` 不修改任何程式）並在結尾自行完成任務驗證；implement 不得在同一任務內自行撰寫測試或產品程式、另外執行測試指令或 `/bdd verify`，也不得對它執行 Phase 4 的靜態檢查。bdd 回報該階段完成才算任務完成。

| 標記 | 呼叫 |
|---|---|
| `[紅燈]` | `/bdd red <範疇>`＋Phase 標頭 |
| `[綠燈]` | `/bdd green <範疇>`＋Phase 標頭 |
| `[重構]` | `/bdd refactor <範疇>`＋Phase 標頭（NFR 重構任務為任務描述與逐任務必讀） |
| `[重跑]` | `/bdd rerun <範疇>`＋任務描述與逐任務必讀 |

### Good Example

這個範例把範疇原樣傳入，並附上 Phase 4 標頭的 NFR 約束、預計修改與必讀。

```text
T009 [綠燈] 範疇：`specs/truth/features/backend/改答案.feature`
→ /bdd green specs/truth/features/backend/改答案.feature
  NFR 約束：NFR-010、NFR-011
  預計修改：`backend/app/routes.py`、`service.py`、`snapshot.py`、`errors.py`、`models.py`，`backend/alembic/versions/0002_battle_skills.py` 的 `step2_guesses`（`seq` 更名）與 `step3_room_events`
  📎 必讀：
  - `data-model.dbml › Project pvp_1a2b_online › 遷移順序` — `step2_guesses` 的更名與 `step3_room_events` 的建立以此為準
  - `data-model.dbml › Table room_events` — 技能紀錄的欄位與唯一索引以此為準
  - `spec.md › NFR-010、NFR-011` — NFR 約束的原文以此為準
  - `plan.md › 原始碼（repo 根目錄）` — 路由、服務與快照模組的位置以此為準
bdd：green 完成 → T009 勾為 [X]
```

這個範例把修正 Phase 以 Rule 名稱寫的範疇原樣傳入，`[重跑]` 任務附上任務描述與逐任務必讀，由 bdd 知道要比對的句型。

```text
T028 [紅燈] 範疇：`specs/truth/features/backend/改答案.feature ＞ Rule「確認改答案後，新答案必須生效」`
→ /bdd red specs/truth/features/backend/改答案.feature ＞ Rule「確認改答案後，新答案必須生效」（附 Phase 12 標頭，不換成行號）
T031 [重跑] 範疇：`specs/truth/features/frontend/改答案.feature`：句型「系統處於 {前置狀態}」只改說明，確認既有 step 不用改後重新執行
  - 📎 必讀：`truth-changes.md › features/frontend/dsl.md ＞ 句型「系統處於 {前置狀態}」` — 這次改了什麼以此為準
→ /bdd rerun specs/truth/features/frontend/改答案.feature（附任務描述與必讀）→ rerun 完成，未修改任何程式 → T031 勾為 [X]
```

### Bad Example

這個範例只傳範疇，bdd 讀不到 data-model 的 room_events 定義與 NFR-011 原文，建表時漏掉唯一索引，雙方畫面一致的要求也沒有被遵守，直到 [驗證] 或驗收才被發現。

```text
T009 [綠燈] → /bdd green specs/truth/features/backend/改答案.feature
```

## Rule 2 -- 修改範圍以任務需要為準

**強度：MUST**

沒有標記的任務，任務描述寫出的檔案是預計範圍；完成任務需要修改其他檔案時直接修改，不停下詢問，並在完成報告列為任務外修改。不得修改和任務無關的程式。描述以短檔名指稱時，依 plan.md 的原始碼結構與先前任務建立的檔案解析為完整路徑。

### Good Example

這個範例的 T003 新增兩個設定，`backend/.env.example` 也要同步才能啟動，直接修改並列為任務外修改，沒有順手改其他程式。

```text
T003 在 `backend/app/config.py` 新增 disconnect_grace_seconds、effect_seconds
需要同步範本 → 修改 backend/.env.example
完成報告 › 任務外修改：T003 backend/.env.example，補上兩個新設定的預設值
```

### Bad Example

這個範例順手整理和 T003 無關的 `backend/app/routes.py`，任務不需要這個改動，也沒有任何階段任務驗證它，既有房間端點的行為可能被改變卻沒有人發現。

```text
T003 修改檔案：backend/app/config.py、backend/app/routes.py（順手整理路由命名）
```

## Rule 3 -- 套件只能使用 techstack.md 列出的版本

**強度：MUST**

依賴宣告檔（如 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml`）只能加入 techstack.md 套件安裝清單中對應 workspace 列出的套件，版本範圍照列。程式碼只能 import 已宣告的套件與執行環境內建模組，不得為了方便加入工具函式庫、polyfill 或型別套件。

### Good Example

這個範例的 backend 只用 techstack.md 列出的套件，設定值以 `python-dotenv` 載入後自行轉型。

```text
dependencies：fastapi>=0.115.0、sqlalchemy[asyncio]>=2.0.0、aiomysql>=0.2.0、alembic>=1.13.0、pydantic>=2.0.0、python-dotenv>=1.0.0、uvicorn[standard]>=0.30.0
設定轉型：float(env.get("EFFECT_SECONDS", 3))（沿用 config.py 既有寫法）
```

### Bad Example

這個範例為了讀設定加入 `pydantic-settings`，techstack.md 的 backend 清單沒有它，與 R-13 決定以 `python-dotenv` 載入不一致，也多了一個未經評估的依賴。

```text
dependencies：fastapi>=0.115.0、pydantic>=2.0.0、python-dotenv>=1.0.0、pydantic-settings>=2.0.0
```

## Rule 4 -- 契約原文必須逐字照用

**強度：MUST**

UI 文案、錯誤碼、`data-testid`、API 路徑、JSON 欄位名稱、狀態列舉值與資料表欄位名稱，必須與必讀原文逐字相同，不得改寫、翻譯、改變大小寫或加上標點。

### Good Example

這個範例的設定名稱與預設值和 research.md 原文完全相同。

```python
disconnect_grace_seconds = float(env.get("DISCONNECT_GRACE_SECONDS", 10))
effect_seconds = float(env.get("EFFECT_SECONDS", 3))
```

### Bad Example

這個範例把環境變數改名為 `GRACE_SECONDS`，`backend/.env.example` 與部署設定依原文設定 `DISCONNECT_GRACE_SECONDS` 時讀不到，寬限永遠是預設值。

```python
disconnect_grace_seconds = float(env.get("GRACE_SECONDS", 10))
```

## Rule 5 -- 不實作任務以外的功能

**強度：MUST**

只實作任務描述與其必讀要求的行為，不得提前實作後續任務的功能或加入未要求的錯誤處理分支與設定項。任務要求的行為必須完整實作，不得留下 `TODO` 或空函式後視為完成；任務描述明寫留空的骨架（如由後續綠燈填入的空函式）除外。

### Good Example

這個範例的 T004 只建立遷移骨架與描述要求的空函式，欄位與約束留給後續的綠燈任務。

```text
T004 建立 backend/alembic/versions/0002_battle_skills.py：revision、down_revision、_has_column、_has_table、_has_constraint，以及依序呼叫的 step1_rooms、step2_guesses、step3_room_events 空函式
rooms、guesses、room_events 的欄位：未建立（由 T006、T009、T015 綠燈填入）
```

### Bad Example

這個範例在 T004 一併寫完 `step1_rooms` 的欄位與 CHECK 約束，T005 紅燈的範疇第一次執行就通過，bdd 只能破壞產品程式重建紅燈，這段沒有經過紅燈驅動的程式也沒有讀過 Phase 3 的必讀。

```text
T004 建立 0002_battle_skills.py，並順手在 step1_rooms 加入技能欄位與 CHECK 約束
```

## Rule 6 -- tasks.md 只能改勾選狀態

**強度：MUST**

執行期間對 tasks.md 的修改只能把完成任務的 `- [ ]` 改為 `- [X]`。不得改寫任務描述、範疇、Phase 標頭、必讀或新增刪除任務；任務內容有誤時停止回報，由使用者以 task 修正。

### Good Example

這個範例只改勾選狀態。

```markdown
- [X] T008 [紅燈] 範疇：`specs/truth/features/backend/改答案.feature`：撰寫 16 條 Rule、26 個 Example 的 step definitions 與 Driver，確認因 change-secret 回 404 而失敗
```

### Bad Example

這個範例在 bdd 停下後把 Phase 標頭的預計修改補上 `domain/battle.py`，tasks.md 不再反映 task 的拆解結果，之後 [驗證] 判定回歸是否由已完成任務造成時，依據也跟著被改掉。

```markdown
**預計修改**：`backend/app/routes.py`、`service.py`、`domain/battle.py`、`snapshot.py`
```

## Rule 7 -- 不動測試程式與規格

**強度：MUST**

沒有標記的任務不得修改 step definitions、Driver、測試支援程式與測試設定的斷言或收集範圍，也不得修改 `specs/truth/features/` 底下的 feature、dsl.md 與用語表；這些只由 bdd 在階段任務中修改，或由 dsl-refine 產生。`specs/truth/` 的契約、資料模型、技術堆疊，以及 plan 資料夾的 spec.md、acceptance、plan.md 與 UI 契約同樣不得修改；認為它們應該改時，經 dev-finding 的 record 交給它們的擁有者。任務本身要求的格式化或依賴宣告不算動測試。

### Good Example

這個範例的 T025 依任務要求執行 lint 修正，只改產品程式，測試程式與 feature 都沒有變動。

```text
T025 `npm run lint`（frontend/）→ 修正 frontend/src/components/SkillPanel.jsx 未使用的變數
frontend/tests/e2e/steps/、specs/truth/features/frontend/：未修改
```

### Bad Example

這個範例為了讓 T025 的 lint 通過刪除 step 裡未使用的斷言變數，step 不再驗證剩餘次數，產品程式扣錯次數也會通過。

```text
T025 lint 回報 frontend/tests/e2e/steps/modules/技能/改答案.js 的 left 未使用 → 刪除 expect(left).toBe(0) 與 left 變數
```

## Rule 8 -- 直接實作的任務列出原始碼段以外的產品檔

**強度：MUST**

沒有標記的任務完成並通過靜態檢查後，必須對照進行中 plan 的 plan.md「原始碼（repo 根目錄）」目錄樹，列出這個任務新增、改名或修改的產品檔中，既不是目錄樹列出的檔案、也不在目錄樹中沒有列出子項目的目錄底下的檔案，沒有時寫「原始碼段以外的產品檔：無」；有時依 bdd 停下處理規範 Rule 6 先交 system-analysis、再交 task，兩者都完成才勾選這個任務。不得留到收尾才回報，也不得以檔案寫在任務描述中為由略過對照。技術修正 plan 沒有 plan.md，不適用本條。以下 Example 皆對照此任務與原始碼段：

```text
T004（Foundational）建立聊天訊息的共用寫入函式；完成後新增 backend/app/services/chat_helpers.py，修改 backend/app/services/rooms.py
plan.md 原始碼段：backend/app/services/ 只列 rooms.py、snapshot.py
```

### Good Example

這個範例在 T004 完成後就對照原始碼段，列出不在其中的 chat_helpers.py，先交 system-analysis 補上，再交 task 修正未勾選的任務，兩者完成才勾選。

```text
T004 完成，靜態檢查通過。
原始碼段以外的產品檔：backend/app/services/chat_helpers.py（plan.md 原始碼的 services/ 只列 rooms.py、snapshot.py）
→ /system-analysis 以原始碼段入口：backend/app/services/chat_helpers.py（聊天訊息的共用寫入函式）→ 原始碼段補上 chat_helpers.py，check_plan.py 通過
→ /task 以增量入口修正未勾選的任務 → Phase 5 的預計修改補上 backend/app/services/chat_helpers.py
→ T004 勾為 [X]
```

### Bad Example

這個範例直接勾選 T004，到收尾才回報 chat_helpers.py 不在原始碼段；Phase 5 的綠燈照原始碼段把聊天訊息的寫入另寫進 rooms.py，同一段邏輯分散兩處，交付的 plan.md 也與程式不符。

```text
T004 完成，靜態檢查通過 → T004 勾為 [X]，繼續 T005
（收尾驗證才回報：專案結構不符合，backend/app/services/chat_helpers.py 不在 plan.md 原始碼段）
```
