# 收尾驗證規範

## Rule 1 -- 依固定項目對照規格與技術計畫

**強度：MUST**

收尾必須逐項對照下表，每項寫出符合或不符合與依據；不得只寫「實作符合規格」的整體結論。

| 項目 | 對照 |
|---|---|
| 任務完成 | 範圍內任務在 tasks.md 皆為 `[X]` |
| 依賴 | 各 workspace 的依賴宣告檔（如 `package.json`、`pyproject.toml`、`go.mod`、`pom.xml`、`Cargo.toml`）中的依賴、相依類型與版本範圍等於 techstack.md 套件安裝清單 |
| 專案結構 | 實際建立或修改的產品檔位於 plan.md 原始碼段列出的位置（目錄樹列出的檔案，或目錄樹中沒有列子項目的目錄底下）；只是不在 tasks.md Phase 標頭「預計修改」的檔案列為任務外修改，不算不符合 |
| 環境變數 | 程式讀取的環境變數名稱皆列於 plan.md 專案結構與專案的環境變數範本（如 `.env.example`） |
| 需求覆蓋 | 範圍內 Feature Phase 標頭的驗收 AC 與 NFR 約束、NFR 重構 Phase 的任務與「不另列任務」合起來涵蓋 spec.md 的每個 NFR，其所屬任務皆已完成 |
| 檢查狀態 | 收尾靜態檢查的語法檢查與 lint 皆通過，腳本列入 `unchecked` 的檔案皆已寫入完成報告 |
| 驗證 | `[驗證]` 任務的 `/bdd verify`（依驗證任務規範引用；範圍不含 `[驗證]` 任務時為不符合，寫明未執行）沒有回歸、`not_run` 與 `unmapped` 皆為 0，且這個 plan 的 `features/涵蓋表.md`「AC 涵蓋表」與「補充案例」列出的 Rule 底下的 Example 全數通過；仍失敗的 Example 與原因、verify 停下時的停下說明皆已寫入完成報告 |
| 驗收標準 | 範圍內每個故事依 Rule 3 判定的完成判準皆為已達成 |

### Good Example

這個範例逐項寫出結果與依據，依賴項目指出具體差異，驗證項目寫出仍失敗的 Example 與原因。

```text
依賴：不符合，frontend/package.json 的 playwright-bdd 為 "latest"，techstack.md › 套件安裝清單 › frontend 為 ^9.2.1；@axe-core/playwright@^4.14.0 未宣告
專案結構：不符合，T026（Polish，直接實作）新增的 frontend/src/lib/focus.js 不在 plan.md 原始碼段（frontend/src/ 只列 api/、hooks/、pages/、components/、domain/）
環境變數：符合，backend/app/config.py 讀取 DATABASE_URL、DISCONNECT_GRACE_SECONDS、EFFECT_SECONDS，皆列於 backend/.env.example
驗證：不符合，regressions 0、not_run 0、unmapped 0；涵蓋表列出的 Rule 中 specs/truth/features/frontend/改答案.feature:10 失敗（乙的畫面 2 秒內沒有出現特效）
```

### Bad Example

這個範例只寫整體結論，`latest` 的浮動版本與漏宣告的無障礙掃描套件都沒有被發現。

```text
實作符合 spec.md 與 plan.md，verify 通過。
```

## Rule 2 -- 不符合項目只回報不修改

**強度：MUST**

收尾發現的不符合項目，包含 `/bdd verify` 停下回報的回歸與環境問題，必須寫入完成報告，不得在此階段修改程式碼、測試程式、feature、dsl.md、plan.md 或 tasks.md，也不得再委派 bdd 的 red、green 或 refactor 修正。專案結構不符合時，建議以 system-analysis 的原始碼段入口修正 plan.md 的原始碼段（附上不在其中的產品檔），不是回到 task 補搬動檔案的任務；其他修正需要新的任務時，由使用者決定是否回到 task 補任務，或依 verify 的建議下一步處理。

### Good Example

這個範例把 verify 回報的失敗、依賴差異與專案結構不符列入報告，專案結構交給 system-analysis 的原始碼段入口，由使用者決定。

```text
完成報告 › 收尾驗證：驗證不符合，frontend/改答案.feature:10 失敗；依賴不符合，建議以 task 新增任務把 playwright-bdd 固定為 ^9.2.1；專案結構不符合，建議以 system-analysis 的原始碼段入口補上 frontend/src/lib/focus.js
```

### Bad Example

這個範例在收尾時直接呼叫 `/bdd green` 修正失敗的 Example，這次修改沒有任務、沒有讀過必讀錨點，tasks.md 也看不出 SkillEffectOverlay.jsx 為什麼被改過。

```text
verify：frontend/改答案.feature:10 失敗 → /bdd green specs/truth/features/frontend/改答案.feature:10 → 修改 frontend/src/components/SkillEffectOverlay.jsx
```

## Rule 3 -- 驗收標準依涵蓋表對回 Example

**強度：MUST**

每個故事的完成判準必須逐個 AC 判定：故事的 AC 是 `features/acceptance/` 中 `# 涵蓋：` 列出該故事編號（如 `US1`）的 Rule 底下的 Example 標題所寫的 AC 編號；每個 AC 依這個 plan 的 `features/涵蓋表.md`「AC 涵蓋表」找出它在各端點的 feature 與 Rule，該 Rule 底下每個 Example 在這次 verify 結果都通過，該 AC 才算通過；故事的所有 AC 都通過才標已達成。標 `@開發發現` 的 AC 不屬於任何故事，另列一組「開發發現」，以同樣的方式逐個判定。AC 涵蓋表沒有列出某個 AC、列出的 Rule 在 feature 中找不到，或範圍不含 `[驗證]` 任務而沒有 verify 結果時，該 AC 標為無法判定並寫出原因。不得以任務全部完成、單一端點通過或補充案例的結果代替 AC 的判定。

### Good Example

這個範例依 acceptance 的涵蓋註解找出 US1 的 AC，再依 AC 涵蓋表逐端點對回 Rule 下的 Example，frontend 的一個 Example 失敗使 AC-01 未通過。

```text
US1 的 AC（acceptance/改答案.feature 的 # 涵蓋：US1）：AC-01、AC-02、AC-03
AC-01 → backend 改答案.feature「改答案必須取代祕密答案且不轉移回合」:10、:17、:27、:35、:45 通過；database 同名 Rule :10、:18、:27、:37、:50 通過；frontend 同名 Rule :10 失敗、:21、:29、:37、:48 通過 → 未通過
AC-02 → frontend「取消改答案不得留下任何痕跡」:63、:68、:76 通過；backend :59、database :64 通過 → 通過
AC-03 → 三個端點「新答案與舊答案相同時結果畫面仍必須標示原答案」全部通過 → 通過
US1：未達成（AC-01 未通過）
```

### Bad Example

這個範例以 US1 的任務全部勾選、backend 全數通過就判定已達成，frontend 改答案特效的 Example 失敗，PM 驗收 AC-01 時乙的畫面看不到特效。

```text
US1：T010～T030 皆為 [X]，backend 15/15 通過 → 已達成
```

## Rule 4 -- 任務全部勾選才委派交付

**強度：MUST**

只有 tasks.md 的任務全部勾選時才委派 plan-package 的 deliver；交付條件是否成立、要不要 commit 由 plan-package 檢查與詢問，implement 不自行判斷也不自行 commit。這次只執行部分範圍、還有未勾選的任務時，不委派 deliver，在完成報告的「交付」寫明還不能交付與剩下的任務。以下 Example 皆對照此狀態：

```text
執行範圍：Phase 1～6（T001～T020），皆已完成
tasks.md：T021～T027 尚未勾選
```

### Good Example

這個範例還有未勾選的任務，沒有委派 deliver，並寫出剩下的任務。

```text
完成報告 › 交付：還不能交付，T021～T027 尚未勾選。完成後執行 /implement 從 T021 開始。
```

### Bad Example

這個範例在還有未勾選任務時就委派 deliver，使用者被問到一個必定不成立的交付，還要讀完整份缺項清單才知道只是任務沒做完。

```text
範圍內任務皆已完成 → 委派 plan-package deliver
```
