# 案例任務規範

## Rule 1 -- 紅燈寫出 Rule 數、Example 數與是否新建 Driver

**強度：MUST**

紅燈描述的 Rule 數與 Example 數取 feature_summary.py 對該 Phase 輸出的 `rule_count`、`example_count`（只計範疇內的 Rule，場景大綱以標題計一個），不得估算或沿用範例的數字。只有本 feature 需要前面紅燈尚未建立的 Driver（新的頁面、資料表或儲存區操作物件）時才寫「與 Driver」。以下 Example 皆對照此輸出：

```json
{"phase": "backend/改答案.feature", "rule_count": 16, "example_count": 26}
{"phase": "backend/連猜三次.feature", "rule_count": 19, "example_count": 32}
```

### Good Example

這個範例的數字取自輸出；第一份 backend feature 建立 Driver，第二份沿用，所以不寫「與 Driver」。

```markdown
- [ ] T008 [紅燈] 範疇：`specs/truth/features/backend/改答案.feature`：撰寫 16 條 Rule、26 個 Example 的 step definitions 與 Driver，確認因 change-secret 回 404 而失敗
- [ ] T017 [紅燈] 範疇：`specs/truth/features/backend/連猜三次.feature`：撰寫 19 條 Rule、32 個 Example 的 step definitions，確認因 burst 回 404 而失敗
```

### Bad Example

這個範例憑印象寫出 Rule 與 Example 數，bdd red 完成後回報的數量對不上，implement 無法判斷是 feature 改過還是紅燈漏寫。

```markdown
- [ ] T008 [紅燈] 範疇：`specs/truth/features/backend/改答案.feature`：撰寫 10 條 Rule、20 個 Example 的 step definitions 與 Driver，確認因 change-secret 回 404 而失敗
```

## Rule 2 -- 紅燈的失敗原因必須屬於本層

**強度：MUST**

紅燈的失敗原因必須是本端點自己的產品入口或結構尚未存在，或修改前的行為仍在，依下表撰寫並寫出具體名稱；不得寫其他端點尚未實作，也不得只寫「測試失敗」。範疇可能在前面的 Phase 完成後就已經通過（例如同一個行為改變也由前面的 Rule 驗證），仍寫修改前的本層原因，第一次就通過的情況由 bdd red 處理。

| 端點 | 本層原因 |
|---|---|
| 資料庫端、檔案系統端等儲存端點 | 結構或約束尚未建立：資料表、欄位、約束或儲存函式（如 `fileStore.createUpload`）尚未存在 |
| 後端（新增 API） | 該 API 回 404 |
| 後端（擴充既有 API） | 本層的新入口或新回應尚未存在：既有 API 的回應缺少新欄位或新狀態 |
| 任何端點（修改既有行為） | 修改前的行為仍在：回應、資料或畫面仍是修改前的樣子，寫出仍存在的欄位、狀態或文案 |
| 前端 | 畫面元素不存在：頁面、按鈕或區塊找不到 |

### Good Example

這個範例三層各寫出自己的原因與具體名稱。

```markdown
- [ ] T010 [紅燈] 範疇：`specs/truth/features/database/匯入與分組.feature`：撰寫 3 條 Rule、3 個 Example 的 step definitions 與資料表 Driver，確認因 `albums` 資料表尚未建立而失敗
- [ ] T016 [紅燈] 範疇：`specs/truth/features/backend/匯入與分組.feature`：撰寫 9 條 Rule、14 個 Example 的 step definitions 與 Driver，確認因 `POST /api/photos` 回 404 而失敗
- [ ] T019 [紅燈] 範疇：`specs/truth/features/frontend/匯入與分組.feature`：撰寫 10 條 Rule、15 個 Example 的 step definitions 與頁面 Driver，確認因主頁沒有匯入按鈕而失敗
```

### Bad Example

這個範例的前端紅燈寫成後端尚未實作，表示 Phase 排序把前端放在後端之前，bdd red 無法分辨這是預期的紅燈還是 step 寫錯。

```markdown
- [ ] T019 [紅燈] 範疇：`specs/truth/features/frontend/匯入與分組.feature`：撰寫 10 條 Rule、15 個 Example 的 step definitions 與頁面 Driver，確認因後端匯入 API 尚未實作而失敗
```

## Rule 3 -- 綠燈寫出本 feature 要實作的入口與行為

**強度：MUST**

綠燈描述以一句話寫出讓範疇內全部 Example 通過要新增或修改的入口（路由、函式、畫面、資料表）與行為；整份 feature 為範疇時以「，讓 feature 通過」結尾，以 Rule 名稱列出範疇時以「，讓這些 Rule 通過」結尾。內容取自本 feature 的 Rule 與 dsl.md 技術對應，不得寫入其他 feature 才需要的行為，也不得只寫「實作功能」等無法對照的描述。

### Good Example

這個範例寫出要新增的路由與服務行為，範圍只到平鋪預覽 feature 需要的內容。

```markdown
- [ ] T023 [綠燈] 範疇：`specs/truth/features/backend/平鋪預覽.feature`：新增相簿內照片列表、原始檔與縮圖取得的路由與照片服務，讓 feature 通過
```

### Bad Example

這個範例一次實作整個照片服務，刪除照片是後面 feature 的行為，後面那份 feature 的紅燈第一次執行就通過，bdd red 只能破壞產品程式重建紅燈。

```markdown
- [ ] T023 [綠燈] 範疇：`specs/truth/features/backend/平鋪預覽.feature`：實作照片服務的列表、取得與刪除，讓 feature 通過
```

## Rule 4 -- 重構寫出整理範圍

**強度：MUST**

重構描述寫成「整理 <範圍>，不改變行為」，範圍是本 feature 綠燈修改的產品模組，以及本 feature 的 step definitions 或 Driver；不得把其他 feature 的程式或跨 feature 的 NFR 調整寫進來，跨 feature 的調整屬於 NFR 重構 Phase。

### Good Example

這個範例只整理本 feature 綠燈改到的服務與 step。

```markdown
- [ ] T024 [重構] 範疇：`specs/truth/features/backend/平鋪預覽.feature`：整理照片服務的分頁查詢與 step，不改變行為
```

### Bad Example

這個範例把全站錯誤訊息集中寫進單一 feature 的重構，修改範圍超出範疇，其他 feature 的行為改變也不會在這次 bdd refactor 的範疇內被驗證。

```markdown
- [ ] T024 [重構] 範疇：`specs/truth/features/backend/平鋪預覽.feature`：把所有路由的錯誤訊息集中到共用模組，不改變行為
```

## Rule 5 -- 預計修改寫出完整路徑

**強度：MUST**

Phase 標頭的「預計修改」列出本 feature 綠燈要修改、且出現在 plan.md「原始碼（repo 根目錄）」的檔案。每組的第一個檔案寫 repo 根目錄起的完整路徑，同目錄的後續檔名以「、」接在後面，換目錄時以「，」開新組並再寫完整路徑；不得讓檔名接在另一個目錄的組後面。

### Good Example

這個範例每換一個目錄就以「，」開新組並寫完整路徑。

```markdown
**預計修改**：`frontend/src/components/SkillPanel.jsx`、`ChangeSecretDialog.jsx`，`frontend/src/pages/GameBoard.jsx`，`frontend/src/api/client.js`，`frontend/src/messages.js`
```

### Bad Example

這個範例把位於 `frontend/src/` 的 `messages.js` 接在 `frontend/src/api/` 的組後面，執行的 AI 會在 `frontend/src/api/messages.js` 建立新檔，原本的文案檔沒有被修改。

```markdown
**預計修改**：`frontend/src/components/SkillPanel.jsx`，`frontend/src/api/client.js`、`messages.js`
```

## Rule 6 -- 範疇逐字取自 feature_summary.py 的輸出

**強度：MUST**

紅燈、綠燈、重構三個任務的範疇必須逐字取 feature_summary.py 對該 Phase 輸出的 `scope`：涵蓋 feature 的全部 Rule 時是 `specs/truth/features/<端點資料夾>/<檔名>.feature`；只涵蓋部分 Rule 時是同一個路徑接「 ＞ 」，再依 feature 中的順序以「、」接續每條 Rule 的 `Rule「<Rule 名稱>」`，三個任務只處理這些 Rule。只改了註解、只刪除了 Example、只改了 Rule 名稱（truth-changes.md 以「改名：原為「舊名稱」」記錄），或只受只改說明的改動影響的 Rule 不在範疇內，改排 [重跑]。不得把部分 Rule 寫成整份 feature，不得改用會隨 feature 修改而失效的行號，也不得自行增減 Rule；feature 在拆解後又被修改時，重新執行腳本。以下 Example 皆對照此輸出：

```json
{"phase": "backend/排行榜.feature", "status": "ADD", "scope": "specs/truth/features/backend/排行榜.feature", "rule_count": 7, "example_count": 9}
{"phase": "backend/互猜對戰.feature", "status": "MOD", "scope": "specs/truth/features/backend/互猜對戰.feature ＞ Rule「技能剩餘次數只剩改答案」、Rule「猜中時必須結束對局」", "rule_count": 2, "example_count": 3}
```

### Good Example

這個範例的新 feature 以整份為範疇，修改的 feature 以兩條 Rule 的名稱為範疇，Rule 數與 Example 數只算這兩條。

```markdown
- [ ] T008 [紅燈] 範疇：`specs/truth/features/backend/排行榜.feature`：撰寫 7 條 Rule、9 個 Example 的 step definitions 與 Driver，確認因 `GET /api/leaderboard` 回 404 而失敗
- [ ] T011 [紅燈] 範疇：`specs/truth/features/backend/互猜對戰.feature ＞ Rule「技能剩餘次數只剩改答案」、Rule「猜中時必須結束對局」`：撰寫 2 條 Rule、3 個 Example 的 step definitions，確認因房間狀態的技能剩餘次數仍有連猜三次而失敗
- [ ] T012 [綠燈] 範疇：`specs/truth/features/backend/互猜對戰.feature ＞ Rule「技能剩餘次數只剩改答案」、Rule「猜中時必須結束對局」`：從房間狀態與猜測流程移除連猜三次的次數與回合跳過，讓這些 Rule 通過
```

### Bad Example

這個範例為修改的 feature 寫整份範疇，紅燈要為 31 條先前就通過的 Rule 重寫 step，bdd red 發現它們第一次就通過，只能逐一破壞產品程式重建紅燈。

```markdown
- [ ] T011 [紅燈] 範疇：`specs/truth/features/backend/互猜對戰.feature`：撰寫 33 條 Rule、52 個 Example 的 step definitions，確認因房間狀態的技能剩餘次數仍有連猜三次而失敗
```

## Rule 7 -- 修正 Phase 沿用 Feature Phase 的寫法

**強度：MUST**

修正 Phase 的標頭與三個任務依 Feature Phase 的規則撰寫，驗收 AC、NFR 約束、範疇、Rule 數與 Example 數都取 feature_summary.py 對該項的輸出（驗收 AC 只計範疇內的 Rule 在涵蓋表的 AC），只有三處不同：預計修改只列這次修正要改的產品檔，綠燈不必改產品程式（例如只因句型改了測試寫法而重寫 step）時寫「無」；只因句型、Background、預設值或用語表改了測試寫法而重做、行為沒有改變時，紅燈的失敗原因寫出尚未改寫的句型；📎 必讀可以加上造成這次修正的 `truth-changes.md › <對象>` 或 `技術項.md › <問題原文>`。不得省略驗收 AC 或必讀，也不得把預計修改寫成整個目錄。以下 Example 皆對照此輸出：

```json
{"phase": "修正 frontend/互猜對戰.feature", "scope": "specs/truth/features/frontend/互猜對戰.feature ＞ Rule「每輪雙方各猜一次後，必須進入下一輪並輪到房主」", "rule_count": 1, "example_count": 1, "acceptance": [], "nfr_constraints": [],
 "rules": [{"name": "每輪雙方各猜一次後，必須進入下一輪並輪到房主", "change": "受影響", "reasons": ["句型「進入第 {數字} 輪，輪到玩家 {玩家} 猜測」已刪除", "句型「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」改了測試寫法"]}]}
```

### Good Example

這個範例的修正只是把兩個重複句型合併後重寫 step，產品程式不用改，預計修改寫「無」，紅燈寫出尚未改寫的句型，必讀指向合併句型的異動列。

```markdown
## Phase 5：修正 frontend/互猜對戰.feature

**驗收 AC**：無

**預計修改**：無

**📎 必讀**：

- `truth-changes.md › features/frontend/dsl.md ＞ 句型「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」` — 合併後的測試寫法以此為準

- [ ] T007 [紅燈] 範疇：`specs/truth/features/frontend/互猜對戰.feature ＞ Rule「每輪雙方各猜一次後，必須進入下一輪並輪到房主」`：撰寫 1 條 Rule、1 個 Example 的 step definitions，確認因句型「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」的 step 尚未改寫而失敗
- [ ] T008 [綠燈] 範疇：`specs/truth/features/frontend/互猜對戰.feature ＞ Rule「每輪雙方各猜一次後，必須進入下一輪並輪到房主」`：確認合併後的 step 通過、不新增產品程式，讓這些 Rule 通過
- [ ] T009 [重構] 範疇：`specs/truth/features/frontend/互猜對戰.feature ＞ Rule「每輪雙方各猜一次後，必須進入下一輪並輪到房主」`：整理合併後的 step，不改變行為
```

### Bad Example

這個範例的修正 Phase 沒有驗收 AC 與必讀，又把預計修改寫成整個前端目錄；bdd 不知道是哪一列異動造成重做，綠燈也可能改到範疇以外的產品檔，check_tasks.py 會回報缺少驗收 AC 與必讀。

```markdown
## Phase 5：修正 frontend/互猜對戰.feature

**預計修改**：`frontend/src/`

- [ ] T007 [紅燈] 範疇：`specs/truth/features/frontend/互猜對戰.feature ＞ Rule「每輪雙方各猜一次後，必須進入下一輪並輪到房主」`：撰寫 1 條 Rule、1 個 Example 的 step definitions，確認因句型「進入第 {輪次} 輪，輪到玩家 {玩家} 猜測」的 step 尚未改寫而失敗
```

## Rule 8 -- 只改說明的改動排 [重跑]

**強度：MUST**

feature_summary.py 輸出的 `reruns` 每一項排一個 [重跑] 任務，全部放在「## Phase N：重跑」：範疇逐字取該項的 `scope`，描述寫成「<`changes` 的每一項以「；」接續>，確認既有 step 不用改後重新執行」，`rows` 的每一列各寫一條「  - 📎 必讀：`truth-changes.md › <對象>` — <需讀原因>」。這些 Rule 只受 dsl-refine 以「只改說明：」標明的句型、Background、預設值或用語表參數值的改動影響（包括合併重複句型：被併入的句型記 DEL、摘要寫「併入「X」」，保留的 X 記 MOD「只改說明：」，用到被刪句型的 Rule 也排 [重跑]，描述寫保留的句型），或只改了註解、只刪除了 Example、只改了 Rule 名稱，bdd rerun 只比對既有 step 與新的說明並重新執行範疇，不破壞產品程式。不得為它們排紅燈、綠燈、重構，不得合併或拆開 `reruns` 的項目，沒有 `reruns` 時不寫重跑 Phase。以下 Example 皆對照此輸出：

```json
{"scope": "specs/truth/features/frontend/互猜對戰.feature", "rule_count": 17, "example_count": 18, "changes": ["句型「系統處於 {前置狀態}」只改說明"], "rows": ["features/frontend/dsl.md ＞ 句型「系統處於 {前置狀態}」"]}
{"scope": "specs/truth/features/backend/賽後聊天.feature ＞ Rule「對手離開結果畫面後，聊天必須停用並保留紀錄」", "rule_count": 1, "example_count": 1, "changes": ["只刪除了 Example「乙離開結果畫面後甲送出 \"下次再戰\"」"], "rows": ["features/backend/賽後聊天.feature ＞ Rule「對手離開結果畫面後，聊天必須停用並保留紀錄」"]}
```

### Good Example

這個範例為兩項 `reruns` 各排一個 [重跑]，描述照抄改動，必讀指向標明改動的列。

```markdown
## Phase 6：重跑

- [ ] T010 [重跑] 範疇：`specs/truth/features/backend/賽後聊天.feature ＞ Rule「對手離開結果畫面後，聊天必須停用並保留紀錄」`：只刪除了 Example「乙離開結果畫面後甲送出 "下次再戰"」，確認既有 step 不用改後重新執行
  - 📎 必讀：`truth-changes.md › features/backend/賽後聊天.feature ＞ Rule「對手離開結果畫面後，聊天必須停用並保留紀錄」` — 這次刪除了哪個 Example 以此為準
- [ ] T011 [重跑] 範疇：`specs/truth/features/frontend/互猜對戰.feature`：句型「系統處於 {前置狀態}」只改說明，確認既有 step 不用改後重新執行
  - 📎 必讀：`truth-changes.md › features/frontend/dsl.md ＞ 句型「系統處於 {前置狀態}」` — 句型的說明改了什麼以此為準
```

### Bad Example

這個範例為只改說明的句型排紅燈，用到它的 18 個 Example 都已通過，bdd red 只能逐一破壞產品程式再由綠燈還原，工作量和只刪掉一句說明的改動不成比例。

```markdown
- [ ] T011 [紅燈] 範疇：`specs/truth/features/frontend/互猜對戰.feature`：撰寫 17 條 Rule、18 個 Example 的 step definitions，確認因起點句型的說明改了而失敗
```
