# 需求對應規範

## Rule 1 -- 驗收 AC 取同端點、同 feature 的 AC

**強度：MUST**

Feature Phase 與修正 Phase 的「驗收 AC」列出 feature_summary.py 對該 Phase 輸出的 `acceptance`，也就是 plan 的涵蓋表「AC 涵蓋表」中端點與 feature 都相同、異動為 ADD 或 MOD、Rule 在範疇內的列的 AC，依編號排列；沒有任何 AC 時寫「無」。不得依使用者故事歸屬增減，也不得列入 Rule 名稱、FR 或 NFR 編號。以下 Example 皆對照此輸出：

```json
{"phase": "database/匯入與分組.feature", "acceptance": []}
{"phase": "backend/匯入與分組.feature", "acceptance": ["AC-01", "AC-02"]}
```

### Good Example

這個範例的 database feature 沒有 AC 列而寫「無」，backend feature 照輸出列出 AC-01、AC-02。

```markdown
## Phase 3：database/匯入與分組.feature

**驗收 AC**：無

## Phase 5：backend/匯入與分組.feature

**驗收 AC**：AC-01、AC-02
```

### Bad Example

這個範例因為同組的 backend 有 AC，就把 AC-01、AC-02 也列給 database，完成報告會以為資料表的 Phase 驗收了匯入流程，實際上 database feature 沒有驗證任何 AC 步驟。

```markdown
## Phase 3：database/匯入與分組.feature

**驗收 AC**：AC-01、AC-02
```

## Rule 2 -- NFR 約束取走到的介面中未驗證的 NFR

**強度：MUST**

Feature Phase 的「NFR 約束」由兩步決定：先依範疇內的 Example 用到的 dsl.md 句型，找出技術對應走到的本端點介面（API、資料表、畫面所在的介面文檔段落對應的介面 ID）；只走到該端點部分介面時，以 `--interfaces <端點資料夾>/<檔名>.feature=<介面ID>,…` 傳給 feature_summary.py，走到全部介面時不必傳。再照抄輸出的 `nfr_constraints`，也就是這些介面在 plan.md 介面盤點「依據需求」欄中的 NFR，扣掉依 Rule 6 確認已被 Rule 完整驗證、以 `--verified-nfr` 帶入的 NFR（`verified_nfrs`）；結果為空時省略整段。不得自行增刪，不得列入其他端點介面的 NFR，也不得列入已被 Rule 完整驗證的 NFR。以下 Example 皆對照此介面盤點與輸出：

```text
plan.md 介面盤點「依據需求」中的 NFR：
  API-01 技能 API：NFR-003、NFR-009、NFR-010、NFR-012、NFR-013
  API-02 猜測與勝負 API：NFR-003、NFR-010、NFR-012、NFR-013、NFR-019
  API-03 房間狀態快照與推播 API：NFR-001、NFR-002、NFR-005、NFR-007、NFR-010、NFR-011
backend/dsl.md：送出新答案 → POST change-secret（API-01）；猜 → POST guesses（API-02）；讀房間狀態 → GET /api/me/room（API-03）
feature_summary.py：以 --verified-nfr 帶入的 verified_nfrs 為 NFR-001、NFR-002、NFR-003、NFR-004、NFR-005、NFR-012、NFR-013、NFR-017；backend/改答案.feature 的 nfr_constraints 為 NFR-007、NFR-009、NFR-010、NFR-011、NFR-019
```

### Good Example

這個範例的 feature 走到 backend 全部三個介面，不必傳 `--interfaces`，照抄輸出的 `nfr_constraints`，已由連猜三次或 database 的 Rule 驗證的 NFR-002、NFR-003、NFR-013 不會出現。

```markdown
**NFR 約束**：NFR-007、NFR-009、NFR-010、NFR-011、NFR-019
```

### Bad Example

這個範例只扣本 feature 自己的 Rule，把其他 feature 已驗證的 NFR-002、NFR-003、NFR-013 也列為約束，又憑感覺刪掉 NFR-019；約束清單混入已有 Rule 把關的要求，也和 NFR 重構 Phase 只處理未驗證 NFR 的範圍對不上，check_tasks.py 會回報與 `nfr_constraints` 不符。

```markdown
**NFR 約束**：NFR-002、NFR-003、NFR-007、NFR-009、NFR-010、NFR-011、NFR-013
```

## Rule 3 -- 未驗證的 NFR 必須落在任務或不另列任務其一

**強度：MUST**

feature_summary.py 輸出的 `unverified_nfrs`（spec.md 的 NFR 扣掉依 Rule 6 確認已被 Rule 完整驗證的 NFR）每一個都必須出現在 NFR 重構 Phase，而且只能落在其中一種位置：任務的 `spec.md › NFR-xxx` 必讀（同一個 NFR 同時需要量測與重構時，量測任務與 [重構] 任務可各自列出），或「不另列任務」的一行並寫出不需要另列任務的理由。不得漏列，不得同時出現在任務必讀與「不另列任務」，也不得把 Rule 已驗證的 NFR 列進 NFR 重構 Phase。以下 Example 皆對照此輸出：

```json
"unverified_nfrs": ["NFR-006", "NFR-007", "NFR-009", "NFR-011", "NFR-016"]
```

### Good Example

這個範例的五個 NFR 各落在一種位置：三個列在不另列任務並寫理由，兩個由任務的必讀承接。

```markdown
**不另列任務**：

- NFR-006、NFR-007：只涉及特效元件，已是 Phase 5、Phase 8 的 NFR 約束
- NFR-009：已是各前端 Phase 的 NFR 約束，送出包裝由各畫面的綠燈完成

- [ ] T023 [重構] 範疇：`specs/truth/features/backend/`：NFR-011：讓 GET 快照與 WebSocket 推播共用 `backend/app/snapshot.py` 的組合函式，移除 `backend/app/service.py` 中各技能自行拼接的推播內容
  - 📎 必讀：`spec.md › NFR-011` — 雙方畫面狀態一致的要求以此為準
- [ ] T024 [重構] 範疇：`specs/truth/features/frontend/`：NFR-016：把 `frontend/src/components/ChangeSecretDialog.jsx` 與 `frontend/src/components/BurstConfirmDialog.jsx` 的焦點處理抽成 `frontend/src/hooks/useDialogFocus.js`
  - 📎 必讀：`spec.md › NFR-016` — 鍵盤操作與 WCAG 2.1 AA 的要求以此為準
```

### Bad Example

這個範例漏掉 NFR-016，又把 NFR-011 同時寫在不另列任務與任務必讀，鍵盤操作要求沒有任何地方承接，NFR-011 也看不出到底要不要做。

```markdown
**不另列任務**：

- NFR-006、NFR-007、NFR-009、NFR-011：已是各 Phase 的 NFR 約束

- [ ] T023 [重構] 範疇：`specs/truth/features/backend/`：NFR-011：讓 GET 快照與 WebSocket 推播共用組合函式
  - 📎 必讀：`spec.md › NFR-011` — 雙方畫面狀態一致的要求以此為準
```

## Rule 4 -- 重構標記只用於不改行為的結構調整

**強度：MUST**

NFR 重構 Phase 的任務只在「調整既有程式結構、不改變任何 Example 行為」時標 [重構]，範疇為端點資料夾 `specs/truth/features/<端點資料夾>/`，描述寫出要重構的檔案與做法。NFR 需要、但不是重構的工作（建立量測腳本、量測並對照門檻、產生報告）必須寫成不標階段的任務，由 implement 直接實作，描述寫出要建立的檔案、量測的對象與對照的門檻。

### Good Example

這個範例把量測寫成無標記任務，把消除 N+1 寫成 [重構]，bdd refactor 只負責保證列表行為不變。

```markdown
- [ ] T046 建立 `backend/scripts/seed-large.js` 與 `backend/scripts/perf.js`，以 10,000 張照片量測相簿列表與開啟相簿的 p95，對照 SC-003 的門檻
  - 📎 必讀：`spec.md › NFR-013、NFR-015` — 回應時間與照片庫容量的要求以此為準
- [ ] T047 [重構] 範疇：`specs/truth/features/backend/`：NFR-013：把 `backend/src/services/albumService.js` 的相簿列表改為一次取回照片數與封面的彙總查詢，消除每本相簿各查一次的 N+1
  - 📎 必讀：`spec.md › NFR-013` — 相簿列表回應時間的要求以此為準
  - 📎 必讀：`research.md › R-14` — 彙總查詢的效能策略以此為準
```

### Bad Example

這個範例把建立量測腳本與量測寫成 [重構]，bdd refactor 只確認測試仍通過，不會建立腳本也不會量測 p95，效能門檻從未被對照。

```markdown
- [ ] T046 [重構] 範疇：`specs/truth/features/backend/`：NFR-013：建立 `backend/scripts/perf.js` 並量測 p95，消除相簿列表的 N+1
  - 📎 必讀：`spec.md › NFR-013` — 相簿列表回應時間的要求以此為準
```

## Rule 5 -- 同一端點資料夾的 NFR 重構併為一個任務

**強度：MUST**

同一個端點資料夾需要重構的 NFR 必須全部併入一個 [重構] 任務，每個端點資料夾至多一個；不標階段的量測任務不併入，也不計入。描述寫在任務那一行，每個 NFR 一項、以「；」分隔，每項寫成「NFR-xxx：<要重構的檔案完整路徑與做法>」，多個 NFR 共用同一做法時項首以「、」並列；任務的 📎 必讀列出每一項 NFR 的 `spec.md › NFR-xxx` 原文與該項需要的介面文檔。bdd refactor 每次都對整個端點資料夾跑基準、修正與驗證，拆成多個任務會讓同一資料夾的測試時間成倍增加；implement 只把任務那一行當描述交給 bdd refactor，寫在子行的項目到不了 bdd。以下 Example 皆對照此情境：

```text
frontend 需要重構的未驗證 NFR：NFR-006（佔位框）、NFR-019 與 NFR-020（狀態訊息）、NFR-021（焦點樣式）
backend 另有量測任務 T046 與 [重構] 任務 T047
```

### Good Example

這個範例把 frontend 的四個 NFR 併成一個 [重構] 任務，三項各以 NFR 編號開頭、共用做法的 NFR-019 與 NFR-020 並列，必讀列出每項的原文與介面文檔。

```markdown
- [ ] T048 [重構] 範疇：`specs/truth/features/frontend/`：NFR-006：把縮圖格線與相簿卡片的佔位框統一為固定長寬比，集中到 `frontend/src/styles/components.css`；NFR-019、NFR-020：把各頁的錯誤、空狀態與載入訊息集中到共用的狀態呈現與 `frontend/src/components/toast.js`；NFR-021：把焦點指示與文字對比集中到 `frontend/src/styles/tokens.css` 的代幣
  - 📎 必讀：`spec.md › NFR-006` — 載入過程不得跳動的要求以此為準
  - 📎 必讀：`spec.md › NFR-019、NFR-020` — 訊息一致與四種狀態呈現的要求以此為準
  - 📎 必讀：`contracts/ui-contract.md › 共用約定` — 共用文案與狀態呈現以此為準
  - 📎 必讀：`spec.md › NFR-021` — WCAG 2.1 AA 的要求以此為準
```

### Bad Example

這個範例把 frontend 拆成三個 [重構] 任務，bdd refactor 要對整個前端資料夾跑三次基準、修正與驗證，測試時間變成三倍；T049 又把描述寫在子行，implement 只轉交任務那一行，bdd 拿不到要重構的內容。

```markdown
- [ ] T048 [重構] 範疇：`specs/truth/features/frontend/`：NFR-006：把縮圖格線與相簿卡片的佔位框統一為固定長寬比，集中到 `frontend/src/styles/components.css`
  - 📎 必讀：`spec.md › NFR-006` — 載入過程不得跳動的要求以此為準
- [ ] T049 [重構] 範疇：`specs/truth/features/frontend/`：
  - NFR-019、NFR-020：把各頁的狀態訊息集中到 `frontend/src/components/toast.js`
  - 📎 必讀：`spec.md › NFR-019、NFR-020` — 訊息一致與四種狀態呈現的要求以此為準
- [ ] T050 [重構] 範疇：`specs/truth/features/frontend/`：NFR-021：把焦點指示集中到 `frontend/src/styles/tokens.css` 的代幣
  - 📎 必讀：`spec.md › NFR-021` — WCAG 2.1 AA 的要求以此為準
```

## Rule 6 -- 只有每個條件都被 Rule 驗證的 NFR 才算已驗證

**強度：MUST**

涵蓋表與 acceptance 的涵蓋註解列出的 NFR 只是候選（feature_summary.py 的 `nfr_candidates`）：驗收旅程只要有 Then 以它為驗證對象就會列入，可能只驗到一部分條件。必須讀候選列出的每條 Rule 的 Example，只有 NFR 的每個條件（每個畫面或操作、門檻與狀態）都有 Example 的 Then 驗證時，才在執行 feature_summary.py 與 check_tasks.py 時以 `--verified-nfr` 帶入；只驗到一部分的 NFR 不帶入，它會留在 NFR 約束與 NFR 重構 Phase。不得只因 NFR 出現在涵蓋註解或補充案例就帶入。以下 Example 皆對照此需求與候選：

```text
NFR-013：相簿列表、開啟相簿與拖放排序都必須在 1 秒內回應
  nfr_candidates：backend/平鋪預覽.feature Rule「開啟相簿必須在 1 秒內回應」（AC-03）
NFR-021：每個畫面的焦點指示與文字對比都必須符合 WCAG 2.1 AA
  nfr_candidates：frontend/整體品質要求.feature Rule「每個畫面都不得有嚴重的無障礙違規」（補充案例），Example 逐一掃描主頁、相簿頁與燈箱
```

### Good Example

這個範例讀過 Rule 後判定：NFR-013 只驗到開啟相簿，相簿列表與拖放排序沒有驗證，不帶入；NFR-021 的掃描涵蓋每個畫面，帶入。

```bash
uv run "D:/plugins/spec-driven-bdd/skills/task/scripts/feature_summary.py" specs/plans/004-ranking --verified-nfr NFR-021
```

### Bad Example

這個範例因為兩個 NFR 都出現在涵蓋表就全部帶入，NFR-013 不會出現在任何 Phase 的 NFR 約束，也不在 NFR 重構 Phase，相簿列表與拖放排序的回應時間沒有任何任務承接。

```bash
uv run "D:/plugins/spec-driven-bdd/skills/task/scripts/feature_summary.py" specs/plans/004-ranking --verified-nfr NFR-013,NFR-021
```
