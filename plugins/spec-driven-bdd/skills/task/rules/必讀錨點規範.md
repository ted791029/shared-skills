# 必讀錨點規範

## Rule 1 -- Feature Phase 必讀只列 bdd 不會自己讀的位置

**強度：MUST**

Feature Phase 與修正 Phase 標頭的「📎 必讀」只能列下列位置：其他端點的介面文檔段落（範疇端點呼叫或被呼叫的 API、資料表、儲存區）、research.md 的 `R-` 編號、每個 NFR 約束的 `spec.md › NFR-xxx`、`plan.md › 原始碼（repo 根目錄）`，以及修正 Phase 造成這次修正的 `truth-changes.md` 列或 `技術項.md` 行。不得列 `specs/truth/features/` 底下的任何檔案（範疇的 feature、該端點 dsl.md、用語表），也不得列範疇端點自己的介面文檔，也就是該端點的介面前綴依輸入完整性規範 Rule 1 找到的 Planner 所產出的文檔；這些 bdd 每個階段都會整份讀取。以下 Example 皆對照此 Phase 與 Planner 產出：

```text
Phase：database/改答案.feature（介面前綴 DB → data-plan → specs/truth/data/）
其他端點：API → api-plan → specs/truth/contracts/；UI → ui-ux-plan → plan 的 ui/ui-contract.md
```

### Good Example

這個範例只列遷移檔位置；資料表定義在 database 自己的 `data/`，由 bdd 讀取，不列入。

```markdown
**📎 必讀**：

- `plan.md › 原始碼（repo 根目錄）` — 遷移檔與模型的位置以此為準
```

### Bad Example

這個範例列出 database 自己的資料模型與 dsl.md，bdd 已整份讀取，重複列出讓同一種資訊有時列、有時不列，implement 轉交的必讀也變長。

```markdown
**📎 必讀**：

- `data/技能.dbml › Table rooms` — 欄位型別與預設值以此為準
- `features/database/dsl.md › Then 句型` — 資料表斷言以此為準
- `plan.md › 原始碼（repo 根目錄）` — 遷移檔與模型的位置以此為準
```

## Rule 2 -- 錨點必須定位到段落或識別碼

**強度：MUST**

錨點固定寫成 `檔案 › 段落 › 識別碼`，之後每段以 ` › ` 往下定位，同一層的多個對象以「、」並列，一條必讀只寫一個檔案。檔案路徑依檔案所在的位置寫：plan 資料夾的檔案寫相對於 plan 資料夾的路徑（`spec.md`、`ui/ui-contract.md`），`specs/truth/` 的檔案寫相對於 `specs/truth/` 的路徑（`techstack.md`、`data/相簿.dbml`），其他檔案寫相對於專案根目錄的路徑。錨點必須至少定位到下表的層級，不得只寫檔名。

| 文件 | 定位方式 |
|---|---|
| `contracts/paths/<模組>/<檔名>.yaml` | `operationId` 或 HTTP 方法，可再接 `parameters`、`requestBody`、`responses` 與狀態碼 |
| `contracts/components/schemas/<名稱>.yaml` | 屬性名稱 |
| `data/<模組>.dbml` | `Table <名稱>`，可再接欄位、索引名稱或 `Note`；外鍵寫 `Ref <名稱>` |
| `data/data-model.dbml` | `Project <名稱> › <段落>` |
| Markdown 契約（如 `ui/ui-contract.md`）、`techstack.md`、`data-migration.md` | 標題文字，可再接表格的列名 |
| `spec.md` | `FR-`、`NFR-`、`SC-` 編號 |
| `research.md` | `R-` 編號 |
| `plan.md` | 標題文字，例如 `原始碼（repo 根目錄）` |
| `truth-changes.md` | 該列「對象」欄的原文，去掉反引號 |
| `技術項.md` | 該行問題部分（括號之前）開頭至少 6 個字的連續原文，去掉反引號 |
| `tasks.md` | 已勾選任務的編號，例如 `T032`（只用於撤回的 Rule 的移除任務） |
| `ui/prototype/*.html` | `data-testid` |
| 其他格式的介面文檔 | 該格式的頂層定義，寫成「關鍵字 名稱」（如 GraphQL 的 `type Room`、protobuf 的 `service RoomService`），可再接欄位或成員；沒有頂層定義的格式寫原文中的鍵路徑或識別碼 |

### Good Example

這個範例分別定位到路徑檔的 operationId 與模組檔的資料表，執行的 AI 不需要讀整個資料夾。

```markdown
- `contracts/paths/照片/api_photos.yaml › importPhoto` — 畫面呼叫的 API、回應與錯誤代碼以此為準
- `data/相簿.dbml › Table albums、Table photos` — 欄位與唯一索引以此為準
```

### Bad Example

這個範例只寫檔名，又把另一個資料夾的檔案接在同一條必讀；執行的 AI 不知道要讀哪個操作，檢查也只會去找第一個檔案。

```markdown
- `contracts/paths/照片/api_photos.yaml、contracts/paths/相簿/api_albums.yaml` — API 以此為準
```

## Rule 3 -- Setup 任務必須綁 techstack.md 的具體列

**強度：MUST**

Setup Phase 的每個任務都必須至少有一條指向 techstack.md 具體段落或表格列的必讀，例如 `techstack.md › 套件安裝清單 › backend`、`techstack.md › 開發工具`。

### Good Example

這個範例把 backend 設定檔任務綁到套件安裝清單中 backend 的列。

```markdown
- [ ] T002 建立 `backend/package.json`（dependencies `mysql2@^3.11.0`、`busboy@^1.6.0`、`exifr@^7.1.3`；scripts `start`、`test`）
  - 📎 必讀：`techstack.md › 套件安裝清單 › backend` — backend 的 dependencies 與版本以此為準，不得增列清單以外的套件
```

### Bad Example

這個範例的 Setup 任務沒有綁 techstack.md，執行的 AI 依記憶填入版本，與研究決定的版本不一致。

```markdown
- [ ] T002 建立 `backend/package.json`（dependencies `mysql2`、`busboy`、`exifr`；scripts `start`、`test`）
  - 📎 必讀：`plan.md › 原始碼（repo 根目錄）` — 目錄結構以此為準
```

## Rule 4 -- 需讀原因寫出以此為準的對象

**強度：MUST**

每條必讀在錨點後以「 — 」接一句需讀原因，寫出這個位置是哪些決定或內容的依據，或讀它要確認什麼，通常以「…以此為準」作結。不得轉述該位置的內容本身，例如列出欄位值、狀態碼意義、斷言或文案原文。

### Good Example

這個範例只說明以此為準的對象，欄位的實際值仍要讀原文。

```markdown
- `data/技能.dbml › Table room_events` — 技能紀錄的欄位與唯一索引以此為準
```

### Bad Example

這個範例在原因中轉述欄位內容，資料模型之後修改時這段轉述不會同步，執行的 AI 會照過時的轉述實作。

```markdown
- `data/技能.dbml › Table room_events` — room_id bigint、kind enum('skill','skip')、uk_room_events_room_seq (room_id, seq)
```

## Rule 5 -- 非 Feature 任務的必讀逐任務自給自足

**強度：MUST**

Setup、Foundational、重跑、技術項、移除與 NFR 重構 Phase 的每個任務（Polish 與 Verify 除外）都由 implement 直接實作或連同任務描述交給 bdd，完成時需要對照的所有位置都必須列在該任務自己的「  - 📎 必讀」中。不得以 Phase 開頭的共用參考、「同上」或「見前一任務」省略；多個任務需要同一位置時各自列出。Foundational 任務列出的每個 NFR 約束都必須有對應的 `spec.md › NFR-xxx` 必讀。

### Good Example

這個範例的兩個 Foundational 任務各自列出需要的位置，T005 的 NFR 約束也有對應原文。

```markdown
- [ ] T005 實作 `backend/src/config.js`：讀取環境變數 `HOST`（預設 `127.0.0.1`）、`PORT`（預設 `3000`），匯出凍結物件
  - NFR 約束：NFR-018
  - 📎 必讀：`research.md › R-16、R-18` — 環境變數載入方式與只監聽本機的決定以此為準
  - 📎 必讀：`spec.md › NFR-018` — 照片庫只能由使用者本人存取的要求以此為準
- [ ] T006 實作 `backend/src/db/pool.js` 與 `backend/src/db/migrate.js`：依檔名順序執行 `backend/src/db/migrations/*.sql`
  - 📎 必讀：`research.md › R-16` — 遷移機制的做法以此為準
```

### Bad Example

這個範例的 T006 以「同上」省略，又沒有列 NFR-018 的原文；implement 單獨執行 T006 時讀不到遷移機制的研究決定，T005 也只能憑約束編號猜測要求。

```markdown
- [ ] T005 實作 `backend/src/config.js`：讀取環境變數 `HOST`、`PORT`，匯出凍結物件
  - NFR 約束：NFR-018
  - 📎 必讀：`research.md › R-16、R-18` — 環境變數載入方式以此為準
- [ ] T006 實作 `backend/src/db/pool.js` 與 `backend/src/db/migrate.js`
  - 📎 必讀：同上
```
