# 基礎任務規範

## Rule 1 -- Setup 只為這次新增或修改的套件建立任務

**強度：MUST**

Setup Phase 放專案骨架、工具鏈與測試框架。專案的第一個 plan 為每個 workspace 的設定檔各排一個任務；之後的 plan 只為 feature_summary.py 輸出的 `techstack_changes`（`truth-changes.md` 中技術堆疊這次新增與修改的列）涉及的 workspace 排任務，沒有時只寫一句說明這個 plan 沒有新增或修改套件。套件名稱與版本必須與 `specs/truth/techstack.md`「套件安裝清單」完全相同，不得加入清單以外的套件，也不得放入任何商業邏輯。

### Good Example

這個範例的 frontend 設定檔任務列出清單中的建置與測試套件；另一個 plan 沒有新增或修改套件，只寫一句說明。

```markdown
- [ ] T003 建立 `frontend/package.json`（devDependencies `vite@^6.0.0`、`vitest@^3.0.0`、`jsdom@^25.0.0`；scripts `dev`、`build`、`test`）與 `frontend/vite.config.js`
```

```markdown
## Phase 1：Setup

這個 plan 沒有新增或修改套件，沿用既有的 `backend`、`frontend` 兩個 workspace。
```

### Bad Example

這個範例略過清單中的測試套件，第一個紅燈任務沒有測試框架可用。

```markdown
- [ ] T003 建立 `frontend/package.json`（devDependencies `vite@^6.0.0`；scripts `dev`、`build`）
```

## Rule 2 -- Foundational 只放 Rule 驅動不到的內容

**強度：MUST**

Foundational Phase 只能放這次多個 Phase 共同依賴、且沒有任何 Rule 能驅動的骨架，例如設定讀取機制、遷移機制（含這次新的遷移檔骨架）、連線池、應用程式進入點、設計代幣；沒有時只寫一句說明。feature 的 Example 經 dsl.md 技術對應走得到的內容（資料表、欄位、API、畫面元件，以及 Rule 會驗證到的設定值）必須由該 feature 的綠燈任務產生，不得提前放進 Foundational。

### Good Example

這個範例只在 Foundational 建立空的遷移骨架，技能欄位由 database feature 的綠燈填入 `step1_rooms`。

```markdown
## Phase 2：Foundational

- [ ] T004 建立 `backend/alembic/versions/0002_battle_skills.py` 的遷移骨架：`revision = "0002_battle_skills"`、`down_revision = "0001_initial"`，提供冪等輔助函式與依序呼叫的 `step1_rooms`、`step2_guesses`、`step3_room_events` 空函式
  - 📎 必讀：`data-migration.md › 遷移步驟` — 0002 遷移的步驟順序與冪等要求以此為準

## Phase 3：database/改答案.feature

- [ ] T006 [綠燈] 範疇：`specs/truth/features/database/改答案.feature`：依 data-model 實作 `step1_rooms` 的欄位、更名與 CHECK 約束並同步 models，讓 feature 通過
```

### Bad Example

這個範例把技能欄位全部放進 Foundational，database feature 的紅燈一寫完就通過，bdd red 只能破壞遷移檔重建紅燈，約束是否真的被驗證看不出來。

```markdown
## Phase 2：Foundational

- [ ] T004 撰寫 `backend/alembic/versions/0002_battle_skills.py`，建立全部技能欄位、room_events 與約束
```

## Rule 3 -- 測試基礎建設只放 bdd 的前置環境

**強度：MUST**

Foundational 的測試基礎建設只放 bdd 執行前必須就緒、而且 bdd 不會自行建立的內容：測試設定涵蓋 `specs/truth/features/<端點資料夾>/` 並載入 step 目錄（如 behave runner 的套件對照、`playwright.config.js` 的 features 與 steps）、測試資料庫的生命週期、前端測試啟動後端的方式。專案已有且已涵蓋這次的端點資料夾時不列任務。step definitions、Driver 與起點的建立由 bdd 紅燈撰寫，不得放在這裡。

### Good Example

這個範例只在測試設定未涵蓋新端點資料夾時補上設定，不撰寫任何 step。

```markdown
- [ ] T005 在 `backend/tests/behave_runner.py` 的 `SUITES` 加入 `"database": "database"`，讓 `specs/truth/features/database/` 由 `backend/tests/database/steps` 收集
```

### Bad Example

這個範例在 Foundational 預先寫好起點的 step 與 Driver，紅燈任務沒有 step 可寫，bdd red 也無法確認 step 與 dsl.md 的測試撰寫語意一致。

```markdown
- [ ] T005 建立 `backend/tests/api/steps/shared/起點.py`：實作「房主輪到且尚未改答案」等三個起點
```

## Rule 4 -- 任務描述必須寫出完整路徑與可驗收內容

**強度：MUST**

Setup、Foundational、技術項、移除與 NFR 重構 Phase 的每個任務由 implement 直接讀描述執行，描述中的每個檔案都必須寫出 plan.md「原始碼」中 repo 根目錄起的完整路徑（位於根目錄的檔案直接寫檔名），不得只寫檔名或接在前一個路徑後面，implement 不會推測目錄；並寫出可驗收的具體內容，例如設定值、匯出的函式或環境變數，不得只寫「建立後端骨架」等無法判斷是否完成的描述。

### Good Example

這個範例每個檔案都寫完整路徑，並寫出要建立的頁面掛載點與設計代幣，完成與否可以直接判斷。

```markdown
- [ ] T008 實作 `frontend/src/main.js`、`frontend/src/router.js`（hash 路由）與 `frontend/src/styles/tokens.css`、`frontend/src/styles/base.css`：建立頁面掛載點與設計代幣
```

### Bad Example

這個範例的 `base.css` 與 `ChangeSecretDialog.jsx` 只寫檔名，implement 不推測目錄，會在根目錄或錯誤的目錄建立新檔，原本的檔案沒有被修改。

```markdown
- [ ] T008 實作 `frontend/src/main.js` 與 `frontend/src/styles/tokens.css`、`base.css`：建立頁面掛載點與設計代幣
- [ ] T024 [重構] 範疇：`specs/truth/features/frontend/`：NFR-016：把對話框的焦點處理抽成 `frontend/src/hooks/useDialogFocus.js`，`ChangeSecretDialog.jsx` 改用它
```

## Rule 5 -- Polish 只放全專案的程式品質收尾

**強度：SHOULD**

Polish Phase 應只放全專案的程式品質收尾，也就是執行 techstack.md 列出的 lint、format 與 build 指令並修正問題；techstack.md 沒有列出的工具不另立任務。效能、無障礙等 NFR 由 feature 的 Rule 驗證，或列在 NFR 重構 Phase，不列入 Polish。

### Good Example

這個範例的 Polish 只執行 techstack.md 列出的 lint 與 build。

```markdown
## Phase 10：Polish

- [ ] T027 在 `frontend/` 執行 `npm run lint`（oxlint），修正前端程式碼問題
- [ ] T028 在 `frontend/` 執行 `npm run build`，修正建置錯誤並確認 `frontend/dist` 可由後端提供
```

### Bad Example

這個範例把無障礙掃描放進 Polish，NFR-016 沒有出現在 NFR 重構 Phase，掃描發現的問題也沒有任何任務承接。

```markdown
## Phase 10：Polish

- [ ] T029 撰寫 `frontend/tests/a11y.spec.js`：掃描對戰畫面的 WCAG 違規
```

## Rule 6 -- 每一列 DEL 與每條撤回的 Rule 都必須落在移除任務或不另列任務

**強度：MUST**

「移除」Phase 放在所有 Feature Phase、修正 Phase 與重跑之後，處理 feature_summary.py 輸出的兩份清單：`deletions` 是 `truth-changes.md` 中每個 owner 記錄的每一列 DEL，加上只刪除了 Example 的 Rule 的那一列 MOD（`examples` 列出被刪的 Example）；`withdrawn` 是已勾選的階段任務實作過、目前 truth 已沒有、也沒有 DEL 列的 Rule，例如本 plan 新增、實作後才被 PM 否決而刪除的開發發現 Rule，與基準相比沒有任何差異，只有已勾選任務的範疇看得出它曾被實作；truth-changes.md 以「改名：原為「舊名稱」」記錄改名的 Rule 仍然存在，不算撤回。每個移除任務不標階段，描述寫出要刪除的產品程式、step definitions 與 Driver 的完整路徑，以及刪除後不得殘留的入口；`deletions` 的每一列以 `truth-changes.md › <該列對象欄的原文>` 列為必讀，`withdrawn` 的每條 Rule 在描述寫出「Rule「<名稱>」」並以 `tasks.md › <實作它的已勾選任務編號>`（取 `tasks`）列為必讀，動到同一段程式的多項併成一個任務。被修改的對象中拿掉、而沒有任何 Feature Phase 的綠燈處理的部分（例如資料表中只為被移除的功能存在的欄位、約束與資料），也在這裡排任務，必讀指向 `data-migration.md` 的對應步驟。沒有程式要移除的項目（例如程式已由某個綠燈一併移除、該對象從未實作，或刪掉的 Example 只用到其他 Example 也在用的 step）寫在「不另列任務」並附理由，撤回的 Rule 寫成「- Rule「<名稱>」：理由」。不得把移除排在 Feature Phase 之前：驗證功能已經不存在的新 Rule（例如系統不再接受某個操作）會在紅燈第一次執行就通過，bdd red 只能破壞產品程式重建紅燈；被刪除的 step definitions 或 Driver 若仍被還沒改寫的 Example 使用，這些 Example 會出錯。兩份清單都沒有任何一項時只寫「這個 plan 沒有要移除的內容。」。以下 Example 皆對照此輸出：

```json
{"deletions": [
  {"owner": "api-plan", "type": "DEL", "target": "`contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml`"},
  {"owner": "api-plan", "type": "DEL", "target": "`contracts/components/schemas/TripleGuessRequest.yaml`"},
  {"owner": "data-plan", "type": "DEL", "target": "`data/技能.dbml` ＞ Table `rooms` ＞ 欄位 `triple_guess_left`"},
  {"owner": "dsl-refine", "type": "DEL", "target": "`features/backend/連猜三次.feature`"}],
 "withdrawn": [{"key": "frontend/改答案.feature", "rule": "技能特效播放時不能開啟改答案", "tasks": ["T031", "T032", "T033"]}]}
```

### Good Example

這個範例把動到同一段後端程式的三列併成一個任務，每一列都有一條必讀；欄位已由前面的綠燈移除，寫在不另列任務並說明原因；撤回的 Rule 另排一個任務，必讀指向實作它的綠燈。

```markdown
## Phase 12：移除

**不另列任務**：

- data/技能.dbml ＞ Table rooms ＞ 欄位 triple_guess_left：欄位已由 Phase 4 的綠燈在遷移中移除

- [ ] T036 刪除 `backend/app/routers/skills.py` 的連猜三次路由、`backend/app/schemas.py` 的 `TripleGuessRequest` 與 `backend/tests/api/steps/modules/技能/連猜三次.py`，刪除後 `POST /api/rooms/{room_id}/skills/triple-guess` 回 404
  - 📎 必讀：`truth-changes.md › contracts/paths/技能/api_rooms_{roomId}_skills_triple-guess.yaml` — 被移除的操作以此為準
  - 📎 必讀：`truth-changes.md › contracts/components/schemas/TripleGuessRequest.yaml` — 被移除的請求結構以此為準
  - 📎 必讀：`truth-changes.md › features/backend/連猜三次.feature` — 不再需要的 step 與 Driver 以此為準
- [ ] T037 刪除 `frontend/src/components/SkillPanel.jsx` 中為 Rule「技能特效播放時不能開啟改答案」加上的停用判斷與 `frontend/tests/steps/改答案/特效中.js`，刪除後特效播放時改答案按鈕回到加入這條 Rule 之前的狀態
  - 📎 必讀：`tasks.md › T032` — 撤回的 Rule 由這個已完成的綠燈實作，要移除的程式以它的範疇與描述為準
```

### Bad Example

這個範例只為 feature 的刪除排任務，契約與資料模型的 DEL 列沒有任何任務或理由，撤回的 Rule 也沒有任務；連猜三次的路由與 PM 否決的停用判斷都留在產品中，沒有任何 Rule 會發現它們。

```markdown
## Phase 12：移除

- [ ] T036 刪除 `backend/tests/api/steps/modules/技能/連猜三次.py`
  - 📎 必讀：`truth-changes.md › features/backend/連猜三次.feature` — 不再需要的 step 以此為準
```

## Rule 7 -- 技術項的每一行都必須落在任務或不另列任務

**強度：MUST**

「技術項」Phase 放在「移除」Phase 之後，處理 feature_summary.py 輸出的 `tech_items`，也就是 plan 的 `技術項.md` 的每一行「- 問題（發現的 skill；依據；修正：<擁有者>）」。需要修改程式的技術項各排一個不標階段的任務，描述依 Rule 4 寫出要修改的檔案與可驗收的內容，📎 必讀以 `技術項.md › <問題開頭的連續原文>` 指向那一行（取括號之前的問題部分，也就是輸出的 `problem`），並列出修改時要對照的介面文檔；修正的擁有者（`fix_owner`）是 task 的行只有程式要改，一定要排任務。修正的擁有者是其他 skill、它已經把文件修好、程式不需要修改的技術項（例如 api-plan 改正的契約型別，或 system-analysis 記下、交 technical-research 改正的條款衝突）寫在「不另列任務」並附理由，不得排沒有內容的任務。`技術項.md` 不存在或沒有任何一行時只寫「這個 plan 沒有技術項。」。技術項不得排在 Feature Phase 之前：技術項要修改的程式可能由這次的 Feature Phase 才建立（例如新的查詢），排在移除之後也不會改到即將刪除的程式。以下 Example 皆對照此技術項：

```text
- 資料模型宣告了外鍵 `fk_guesses_room_id`，實際的遷移沒有建立（data-plan；`specs/truth/data/對戰.dbml` 的 Table `guesses` 與 `backend/alembic/versions/0001_initial.py`；修正：task）
- 契約把勝場數的型別寫成字串，已改為整數，程式原本就回傳整數（api-plan；`specs/truth/contracts/components/schemas/RankingEntry.yaml`；修正：api-plan）
```

### Good Example

這個範例為修正擁有者是 task、要補上外鍵的技術項排一個任務，必讀指向那一行與資料模型；另一行由 api-plan 修好文件、程式不用改，寫在不另列任務。

```markdown
## Phase 10：技術項

**不另列任務**：

- 契約把勝場數的型別寫成字串：api-plan 已把契約改為整數，程式原本就回傳整數，沒有要修改的程式

- [ ] T021 在 `backend/alembic/versions/0004_ranking.py` 補上 `guesses.room_id` 到 `rooms.id` 的外鍵 `fk_guesses_room_id`，已存在時不重複建立
  - 📎 必讀：`技術項.md › 資料模型宣告了外鍵 fk_guesses_room_id` — 要補上的外鍵以此為準
  - 📎 必讀：`data/對戰.dbml › Table guesses、Ref fk_guesses_room_id` — 外鍵的欄位與刪除規則以此為準
```

### Bad Example

這個範例為程式不需要修改的技術項排了任務，implement 執行到它時找不到任何要改的檔案；修正擁有者是 task、要補上外鍵的那一行沒有任務也沒有理由，外鍵不會被補上。

```markdown
## Phase 10：技術項

- [ ] T021 確認勝場數的型別為整數
  - 📎 必讀：`技術項.md › 契約把勝場數的型別寫成字串` — 型別以此為準
```

## Rule 8 -- Verify 唯一且在最後

**強度：MUST**

整份 tasks.md 只能有一個 Verify Phase，放在最後一個 Phase，裡面只有一個 [驗證] 任務。tasks.md 已有勾選的任務、這次又在尚未開始的部分排了任務時，Verify Phase 必須移到新的最後一個 Phase，[驗證] 取消勾選、編號接在最後一個任務之後，讓全端點驗證在所有新任務之後重新執行；這次只補了「不另列任務」、沒有排任何新任務時保留原樣。不得在其他 Phase 另排 [驗證]，也不得讓已勾選的 [驗證] 留在新任務之前。以下 Example 皆對照此情境：

```text
原本：T001～T025 已勾選，Phase 11 的 T026 [驗證] 已勾選
這次：追加修正 Phase 的三個任務 T026～T028 與技術項任務 T029
```

### Good Example

這個範例把 Verify 移到最後並取消勾選，[驗證] 的編號接在新任務之後。

```markdown
## Phase 12：技術項

- [ ] T029 在 `backend/app/services/rooms.py` 的結果統計查詢加上 `status` 條件，讓查詢使用 `ix_rooms_status` 索引
  - 📎 必讀：`技術項.md › 結果統計的查詢沒有使用` — 要修正的查詢以此為準

## Phase 13：Verify

- [ ] T030 [驗證] 執行所有端點的完整測試並與上次結果比對
```

### Bad Example

這個範例把新的 Phase 接在已勾選的 Verify 之後，最後一次全端點驗證發生在新任務之前，修正 Phase 與技術項改動的程式沒有經過全端點驗證就進入交付。

```markdown
## Phase 11：Verify

- [X] T026 [驗證] 執行所有端點的完整測試並與上次結果比對

## Phase 12：修正 backend/結果統計.feature
```

## Rule 9 -- 技術修正 plan 只排修正、重跑、移除、技術項與驗證

**強度：MUST**

`.plan.json` 的種類是「技術修正」時（feature_summary.py 的 `kind`），tasks.md 只有修正 Phase（`phases` 在技術修正 plan 一律是修正 Phase）、重跑、移除、技術項與 Verify，不寫 Setup、Foundational、NFR 重構與 Polish：這種 plan 沒有 spec.md、plan.md 與 research.md，沒有可對照的套件清單、骨架與 NFR。技術項 Phase 處理 `技術項.md` 的每一行，點名其他擁有者、文件已改好的行寫在「不另列任務」；修正 Phase 的驗收 AC 寫「無」。以下 Example 皆對照此輸出：

```text
kind：技術修正；phases：無；reruns：frontend/互猜對戰.feature、frontend/改答案.feature（句型「系統處於 {前置狀態}」只改說明）；deletions：無
技術項.md：起點句型的說明重述了後端給定的技能剩餘次數（使用者；`specs/truth/features/frontend/dsl.md` 第 9 行；修正：dsl-refine）
```

### Good Example

這個範例只有重跑、移除、技術項與 Verify，技術項已由 dsl-refine 改好，寫在不另列任務。

```markdown
## Phase 1：重跑
```
