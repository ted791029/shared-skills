# 案例缺口規範

## Rule 1 -- 這次異動的 Rule 必須登記在涵蓋表

**強度：MUST**

feature_summary.py 列出的每條這次新增或修改的 Rule，都必須以相同的端點、feature 檔名與 Rule 名稱登記在 plan 的 `features/涵蓋表.md` 的「AC 涵蓋表」或「補充案例」，異動為 ADD 或 MOD；涵蓋表的每一列也必須在 `specs/truth/features/` 對應的 feature 找到同名 Rule，「異動」欄必須與基準以來的實際差異相符。名稱只差標點、括號說明或一兩個字也算不一致。內容沒有改變、只因用到改了的句型、Background、預設值或用語表參數值而重做或重跑的 Rule 不需要登記，登記為 MOD 也接受；技術修正 plan 沒有涵蓋表，不檢查本條。腳本回報的 `coverage` 問題即為案例缺口，不得自行判斷兩者是同一條 Rule。以下 Example 皆對照此 feature 與涵蓋表：

```text
backend/排行榜.feature:31  Rule: 勝場數相同時，較早達到的玩家必須排在前面（這次新增）
涵蓋表 補充案例：| FR-012 | backend | `排行榜.feature` | 勝場數相同時，較早達到的玩家排在前面 | ADD |
涵蓋表 補充案例：| FR-014 | backend | `排行榜.feature` | 排行榜的資料無法取得時，必須回覆暫時無法顯示 | ADD |
```

### Good Example

這個範例把名稱差「必須」兩個字也列為缺口，並列出涵蓋表有、feature 沒有的 FR-014。

```markdown
案例缺口（涵蓋表與 feature 不一致）：
- `backend/排行榜.feature:31` 的 Rule 沒有登記；涵蓋表補充案例 FR-012 的 Rule 名稱少了「必須」
- 涵蓋表補充案例 FR-014「排行榜的資料無法取得時…」在 `backend/排行榜.feature` 沒有同名 Rule
```

### Bad Example

這個範例自行把名稱相近的兩者視為同一條，FR-014 沒有 Rule 也被略過，資料無法取得時的回覆就沒有任何紅綠任務，tasks.md 看起來完整卻漏掉一條需求。

```markdown
FR-012 → backend/排行榜.feature:31（名稱相近，視為同一條）
FR-014 → 找不到 Rule，略過
```

## Rule 2 -- 實作內容必須能由 Rule 驅動

**強度：MUST**

必須逐一比對 plan.md「介面盤點」中異動為 ADD 或 MOD 的介面、`truth-changes.md` 中其他 owner 記錄的每一列新增與修改，以及 plan.md「原始碼」列出的這次要新增或修改的實作檔案：每個介面與每一列異動至少要有一條這次新增或修改的 Rule 的 dsl.md 技術對應（端點、資料表、畫面元素）落在它上面；每個實作檔案要屬於骨架或測試基礎建設，或是某條這次新增或修改的 Rule 的 Example 經 dsl.md 技術對應走得到的行為。都不符合時即為案例缺口。使用者看不到差異的技術問題不需要 Rule：已記在 `技術項.md` 的不算缺口，由技術項 Phase 排任務，依據需求寫「技術：…」的介面與原因寫「技術：…」的異動列對得到 `技術項.md` 的一行時也是如此；技術修正 plan 沒有 plan.md，只比對 `truth-changes.md` 的列。以下 Example 皆對照此 plan.md 與 dsl.md：

```text
plan.md 原始碼：backend/app/config.py、backend/app/domain/battle.py、frontend/src/components/SkillAnnouncer.jsx
backend/dsl.md：送出新答案 → POST /api/rooms/{room_id}/skills/change-secret；猜 → POST /api/rooms/{room_id}/guesses
frontend/dsl.md：沒有任何句型讀取螢幕閱讀器通知
```

### Good Example

這個範例判定 `battle.py` 由猜測的 Rule 走到，`config.py` 屬於骨架，`SkillAnnouncer.jsx` 兩者都不是，因此列為缺口。

```markdown
`backend/app/domain/battle.py` → backend/連猜三次.feature「補猜回合中連猜猜中必須判定平手」經 POST guesses 走得到
`backend/app/config.py` → 骨架
`frontend/src/components/SkillAnnouncer.jsx` → 沒有 Rule 走得到 → 案例缺口
```

### Bad Example

這個範例只比對介面是否有 Rule，UI-03 有特效的 Rule 就視為完整，`SkillAnnouncer.jsx` 的螢幕閱讀器通知沒有任何 Rule 驅動，功能會在實作時被漏掉。

```markdown
UI-03 有 Rule → 前端完整
```

## Rule 3 -- 有缺口時不得產出任務

**強度：MUST**

有案例缺口時必須停止，逐項寫出缺口的 Rule、涵蓋表列、truth 異動列、檔案或介面與缺少的行為，請使用者回到 dsl-refine 補齊 feature、dsl.md、用語表或涵蓋表；缺口源自 acceptance 沒有涵蓋時，請使用者先回到 spec-by-example。不得自行新增沒有 Rule 的任務、自行修改涵蓋表、用語表或 feature，也不得把缺口的實作塞進其他 Rule 的綠燈任務。

### Good Example

這個範例列出缺口後停止，讓 dsl-refine 補上 Rule 後再拆解。

```markdown
案例缺口：
- `frontend/src/components/SkillAnnouncer.jsx`：沒有 Rule 驗證技能使用後 2 秒內以螢幕閱讀器告知（NFR-017）

請先執行 /dsl-refine 補上對應的 Rule 與 dsl.md 句型，再重新拆解任務。
```

### Bad Example

這個範例把沒有 Rule 的 `SkillAnnouncer.jsx` 塞進 frontend feature 的預計修改與綠燈，這段程式碼沒有測試先行，bdd green 也會因為超出範疇需要的最小實作而無法判斷完成。

```markdown
**預計修改**：`frontend/src/components/SkillEffectOverlay.jsx`、`SkillAnnouncer.jsx`

- [ ] T021 [綠燈] 範疇：`specs/truth/features/frontend/連猜三次.feature`：實作特效與螢幕閱讀器告知，讓 feature 通過
```
