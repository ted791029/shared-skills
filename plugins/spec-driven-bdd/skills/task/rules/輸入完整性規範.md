# 輸入完整性規範

## Rule 1 -- 介面文檔依 Planner 的產出路徑判定

**強度：MUST**

每個端點應有的介面文檔，必須取該端點在 plan.md 介面盤點的介面 ID 前綴，依 [Planner 配對規範](../../planner-provisioning/rules/Planner配對規範.md) 找到對應的 Planner，再以該 Planner SKILL.md 中 `WRITE` 步驟寫明的檔案路徑判定：寫在 plan 資料夾的文檔必須存在，寫進 `specs/truth/` 的文檔以該資料夾存在、且 `truth-changes.md` 中該 Planner 的一節已有紀錄判定。不得依檔案內容是否出現介面 ID、或依檔名猜測判定。

### Good Example

這個範例依前綴找到 Planner，再依 Planner 寫明的產出路徑逐一確認檔案。

```markdown
| 端點 | 介面前綴 | Planner | 應有的介面文檔 | 狀態 |
|---|---|---|---|---|
| 前端 | `UI` | `ui-ux-plan` | plan 的 `ui/ui-contract.md`、`ui/prototype/` | 存在 |
| 後端 | `API` | `api-plan` | `specs/truth/contracts/`（truth-changes.md 有 api-plan 的紀錄） | 存在 |
| 資料庫端 | `DB` | `data-plan` | `specs/truth/data/`（truth-changes.md 有 data-plan 的紀錄） | 存在 |
| 檔案系統端 | `FS` | `storage-plan` | `specs/truth/storage/`（truth-changes.md 有 storage-plan 的紀錄） | 存在 |
```

### Bad Example

這個範例以檔案內容是否出現介面 ID 判定，`openapi.yaml` 只出現 `UI-01`～`UI-04` 而被當成前端文檔，`storage-contract.md` 沒有出現 `FS-01` 而被判為缺少，結果誤擋了完整的輸入。

```markdown
UI：ui-contract.md、openapi.yaml、states.html
API：（找不到含 API-01 的檔案）→ 缺少
FS：（找不到含 FS-01 的檔案）→ 缺少
```

## Rule 2 -- 缺少任一介面文檔即停止

**強度：MUST**

有任一端點缺少應有的介面文檔時，必須停止，不得只為文檔齊全的端點產出部分任務，也不得把必讀改指向 plan.md 或 spec.md 來替代。停止時必須逐列寫出端點、介面前綴、Planner 與缺少的路徑。

### Good Example

這個範例在檔案系統端缺少文檔時停止，並列出補齊所需的資訊。

```markdown
| 端點 | 介面前綴 | Planner | 缺少的介面文檔 |
|---|---|---|---|
| 檔案系統端 | `FS` | `storage-plan` | `specs/truth/storage/storage-contract.md` |

請先執行 system-analysis 的分析 Wave 補齊上述文檔，再重新拆解任務。
```

### Bad Example

這個範例在缺少儲存契約時仍產出任務，後端 Phase 呼叫儲存區的必讀改指 plan.md 介面盤點，執行時 AI 只能自行決定目錄結構與命名規則，與之後補上的契約互相衝突。

```markdown
## Phase 5：backend/匯入與分組.feature

**📎 必讀**：

- `plan.md › 介面盤點` — 呼叫 `fileStore` 的方式與儲存位置以此為準
```

## Rule 3 -- features 缺漏即停止

**強度：MUST**

`specs/truth/features/` 必須有 `用語表.md`，以及用語表「端點」表登記的每個端點資料夾，每個端點資料夾都有 `dsl.md` 與至少一份 feature；plan 資料夾必須有 `features/acceptance/` 與 `features/涵蓋表.md`。端點資料夾以用語表「端點」表為準：plan.md 介面盤點有某個前綴、但端點表沒有登記時（例如沒有儲存約束案例的資料庫端），不視為缺漏，該端點的介面文檔仍依 Rule 1、Rule 2 檢查。任一項缺少時必須停止，逐列寫出缺少的路徑與產出它的 skill：acceptance 缺漏交由 spec-by-example，其餘交由 dsl-refine。不得改由 plan.md 介面盤點或 spec.md 推導任務，也不得只為齊全的端點資料夾產出部分任務。以下 Example 皆對照此資料夾：

```text
specs/plans/002-battle-skills/
├── plan.md            介面盤點前綴：UI、API、DB
└── features/          acceptance/、涵蓋表.md
specs/truth/features/
├── 用語表.md          端點表：UI → frontend、API → backend、DB → database
├── frontend/          dsl.md、改答案.feature、連猜三次.feature
└── backend/           dsl.md、改答案.feature、連猜三次.feature
```

### Good Example

這個範例發現 DB 前綴登記的 `database` 資料夾不存在，停止並指出要由 dsl-refine 補齊。

```markdown
| 介面前綴 | 端點資料夾 | 缺少的路徑 | 產出的 skill |
|---|---|---|---|
| DB | `database` | `specs/truth/features/database/dsl.md`、`specs/truth/features/database/*.feature` | dsl-refine |

請先執行 /dsl-refine 補齊上述端點資料夾，再重新拆解任務。
```

### Bad Example

這個範例在缺少 database 資料夾時仍產出任務，把建立資料表塞進 Foundational，資料表約束沒有任何 feature 可當紅燈範疇，也沒有測試先行。

```markdown
## Phase 2：Foundational

- [ ] T004 在 `backend/alembic/versions/0002_battle_skills.py` 建立技能欄位、`room_events` 與約束
```

## Rule 4 -- 技術修正 plan 只要求異動紀錄、技術項與端點資料夾

**強度：MUST**

`.plan.json` 的種類是「技術修正」時，這個 plan 沒有 spec.md、plan.md、research.md、acceptance 與涵蓋表，Rule 1 至 Rule 3 對它們與 plan 中介面文檔的要求不適用；只必須確認 plan 資料夾有 `truth-changes.md` 與 `技術項.md`（plan-package 開立時建立），以及 `specs/truth/features/` 有用語表與「端點」表登記的每個端點資料夾，各有 `dsl.md` 與至少一份 feature。不得因為缺少 spec.md、plan.md 或 acceptance 而要求使用者回到 specify、system-analysis 或 spec-by-example，也不得為了符合需求 plan 的輸入而自行補寫它們。以下 Example 皆對照此資料夾：

```text
specs/plans/005-cleanup/
├── .plan.json         "kind": "技術修正"
├── truth-changes.md   dsl-refine 一節：MOD features/frontend/dsl.md ＞ 句型「系統處於 {前置狀態}」
└── 技術項.md           1 行，修正：dsl-refine
specs/truth/features/  用語表.md、frontend/、backend/、database/（各有 dsl.md 與 feature）
```

### Good Example

這個範例只確認技術修正 plan 需要的三項輸入齊全，就繼續拆解。

```markdown
| 輸入 | 狀態 |
|---|---|
| `truth-changes.md` | 存在 |
| `技術項.md` | 存在（1 行） |
| `specs/truth/features/` 的用語表與 frontend、backend、database | 存在 |
```

### Bad Example

這個範例照需求 plan 的清單判定，把不存在的 spec.md、plan.md 與 acceptance 列為缺漏並要求先執行 /specify，技術修正 plan 永遠拆不出任務，dsl.md 的修正也無法交付。

```markdown
| 缺少的輸入 | 產出的 skill |
|---|---|
| `spec.md` | specify |
| `plan.md` | system-analysis |
| `features/acceptance/` | spec-by-example |
```
