# 任務拆解規範

## Rule 1 -- 要重做紅燈的每份端點 feature 恰好一個 Phase

**強度：MUST**

feature_summary.py 輸出的 `phases` 每一項各成一個 Phase，標題逐字取該項的 `phase`（`<端點資料夾>/<檔名>.feature`；已有勾選階段任務的 feature 與技術修正 plan 是 `修正 <端點資料夾>/<檔名>.feature`），不得依使用者故事、Rule 或端點合併多份 feature，也不得把一份 feature 拆成多個 Phase。`phases` 收的是這次新增或修改的 Rule，以及用到改了測試寫法的句型、Background、預設值或用語表參數值的 Rule；不在 `phases` 的 feature 不列 Phase：先前的 plan 留下而這次沒有受影響的；只受 dsl-refine 標明只改說明的改動影響，或只改了註解、只刪除了 Example、只改了 Rule 名稱的（`reruns`，由「重跑」Phase 的 [重跑] 任務重新執行）；只刪除了 Rule 的（`skipped_features`，刪除的部分由「移除」Phase 處理）；以及被整份刪除的（`removed_features`，改由「移除」Phase 處理）。以下 Example 皆對照此輸出：

```text
phases：database/改答案.feature、backend/改答案.feature、frontend/改答案.feature、backend/互猜對戰.feature
reruns：frontend/賽後聊天.feature（句型「系統處於 {前置狀態}」只改說明）
skipped_features：backend/房間聊天.feature（只刪除了 Rule，沒有新增或修改的 Rule）
removed_features：backend/連猜三次.feature
```

### Good Example

這個範例只為 `phases` 的 4 份 feature 各開一個 Phase，Phase 名稱就是輸出的 `phase`；只改說明的 frontend/賽後聊天.feature 不開 Phase。

```markdown
## Phase 4：database/改答案.feature
## Phase 5：backend/改答案.feature
## Phase 6：frontend/改答案.feature
## Phase 7：backend/互猜對戰.feature
```

### Bad Example

這個範例依使用者故事把三個端點的 feature 併成一個 Phase，又為只改說明的 frontend/賽後聊天.feature 開了 Phase；implement 無法以單一 feature 為範疇交給 bdd，只需要重新執行的 Example 也會被 bdd red 逐一破壞再重做紅燈。

```markdown
## Phase 3：使用者故事 1 - 使用改答案技能換掉祕密答案（Priority: P1）
## Phase 4：frontend/賽後聊天.feature
```

## Rule 2 -- 同名 feature 成組並依故事優先排列

**強度：MUST**

各端點資料夾中檔名相同的 feature 為一組，組內的 Phase 連續排列。組的先後取 feature_summary.py 輸出的 `groups` 順序：組內 Rule 涵蓋的最高優先故事（AC 涵蓋註解的 US，加上補充案例來源需求在 spec.md 所屬的故事）在前，同優先時組內最小 AC 編號在前，再依檔名；沒有任何故事的組排在所有有故事的組之後。不得依實作難度、端點或 Rule 數量重排。以下 Example 皆對照此輸出：

```json
"groups": [
  {"file": "改答案.feature", "story": 1, "story_priority": 1, "min_ac": "AC-01", "endpoints": ["database", "backend", "frontend"]},
  {"file": "連猜三次.feature", "story": 2, "story_priority": 2, "min_ac": "AC-04", "endpoints": ["database", "backend", "frontend"]}
]
```

### Good Example

這個範例先排 P1 的改答案組，三份 feature 連續排列，再排 P2 的連猜三次組。

```markdown
## Phase 3：database/改答案.feature
## Phase 4：backend/改答案.feature
## Phase 5：frontend/改答案.feature
## Phase 6：database/連猜三次.feature
```

### Bad Example

這個範例把兩組的 database feature 先排在一起，同名功能被拆散，P1 的改答案要等連猜三次的資料表也完成才能往外推進，MVP 交付被延後。

```markdown
## Phase 3：database/改答案.feature
## Phase 4：database/連猜三次.feature
## Phase 5：backend/改答案.feature
```

## Rule 3 -- 組內由被呼叫的端點排到呼叫者

**強度：MUST**

同一組內，被其他端點呼叫的端點排在呼叫它的端點之前：資料庫端、檔案系統端等儲存端點與外部服務等其他內層端點 → backend → frontend。多個內層端點之間依用語表「端點」表的列出順序。每層的紅燈因此都是本層原因，不得把 frontend 排在 backend 之前。以下 Example 皆對照此組：

```text
匯入與分組.feature：database、filesystem、backend、frontend 各一份
用語表「端點」表順序：UI → frontend、API → backend、DB → database、FS → filesystem
```

### Good Example

這個範例先排兩個儲存端點（依端點表 database 在 filesystem 之前），再排 backend，最後 frontend。

```markdown
## Phase 3：database/匯入與分組.feature
## Phase 4：filesystem/匯入與分組.feature
## Phase 5：backend/匯入與分組.feature
## Phase 6：frontend/匯入與分組.feature
```

### Bad Example

這個範例把 frontend 排在 backend 之前，frontend 紅燈失敗的原因混入 `POST /api/photos` 回 404，綠燈時 bdd 會因後端尚未實作而停下。

```markdown
## Phase 3：frontend/匯入與分組.feature
## Phase 4：backend/匯入與分組.feature
```

## Rule 4 -- 跨組的內層相依要讓被用到的組提前

**強度：MUST**

某份 feature 的 Example 經 dsl.md 技術對應會用到另一組才提供的內層行為（API、資料表、儲存函式），而那一組依 Rule 2 排在後面時，必須把那一組整組提前到使用它的組之前，組內順序不變。沒有這種相依時維持 Rule 2 的順序。以下 Example 皆對照此情境：

```text
groups 順序：匯入與分組（US1）→ 平鋪預覽（US2）→ 自動封存（無故事，只有 backend）
frontend/平鋪預覽.feature 的 dsl.md：「相簿超過 30 天未開啟時顯示封存標記」→ 讀 GET /api/albums 的 archived 欄位，由 backend/自動封存.feature 的 Rule 產生
```

### Good Example

這個範例把只有 backend 的自動封存組提前到平鋪預覽組之前，frontend 綠燈執行時後端行為已經存在。

```markdown
## Phase 5：backend/匯入與分組.feature
## Phase 6：frontend/匯入與分組.feature
## Phase 7：backend/自動封存.feature
## Phase 8：backend/平鋪預覽.feature
## Phase 9：frontend/平鋪預覽.feature
```

### Bad Example

這個範例照 groups 順序把沒有故事的自動封存排在最後，Phase 9 的 frontend 綠燈需要的 `archived` 欄位還沒有實作，bdd green 判定為其他端點尚未實作而停下，implement 依 Phase 編號執行時卡住。

```markdown
## Phase 8：backend/平鋪預覽.feature
## Phase 9：frontend/平鋪預覽.feature
## Phase 10：backend/自動封存.feature
```

## Rule 5 -- 已有勾選的任務時只重新規劃尚未開始的部分

**強度：MUST**

tasks.md 已有勾選的任務時（feature_summary.py 的 `tasks_state.mode` 為「增量」），已勾選的任務是從 T001 起連續的一段，最後一個已勾選任務所在的 Phase 之前（含）是已開始的部分（`tasks_state.started_phases`）：必須原樣保留其中每個任務的內容、勾選、編號與位置，只有三種例外，一是進行中的 Phase（`tasks_state.in_progress`）未勾選的任務刪去 `missing_rules` 列出的 Rule（全部不存在時刪除該任務），並把 `renamed_rules` 列出的舊名稱改為改名後的名稱（不刪除任務），二是在已開始的同名 Phase 補上新的「不另列任務」，三是 plan.md 的原始碼段改變時（例如 implement 經 system-analysis 的原始碼段入口修正後交辦），進行中 Phase 的標頭與未勾選任務的預計修改、必讀改為指向修正後的位置。之後尚未開始的部分依目前的 `phases`、`reruns` 與各項清單重新規劃：仍然適用的任務沿用，要改的改寫，不再需要的刪除，新的 Phase 依 Setup → Foundational → Feature 與修正 → 重跑 → 移除 → 技術項 → NFR 重構 → Polish 的順序排入，從已開始部分的最後一個編號接著連續編號。種類排在已開始的固定 Phase 之前時（例如 Polish 已勾選後才出現的修正 Phase），從已開始的部分之後重新開始一輪，只放有新任務的 Phase；Verify 一律在最後。不得改寫、重排或重新編號已勾選的任務，也不得把新的任務插進已開始的 Phase。以下 Example 皆對照此情境：

```text
tasks.md：T001～T025 已勾選（Phase 1～10，Phase 10 是 Polish），Phase 11 的 T026 [驗證] 已勾選
feature_summary.py：phases 為「修正 backend/結果統計.feature」（1 條 Rule、1 個 Example）；技術項.md 新增一行修正擁有者為 task 的技術項
```

### Good Example

這個範例保留 Phase 1～10 與它們的編號，在 Polish 之後重新開始一輪，只放修正 Phase 與技術項 Phase，最後是 Verify。

```markdown
## Phase 10：Polish

- [X] T025 在 `frontend/` 執行 `npm run lint`（oxlint），修正前端程式碼問題

## Phase 11：修正 backend/結果統計.feature

**驗收 AC**：無

**預計修改**：`backend/app/services/rooms.py`

**📎 必讀**：

- `plan.md › 原始碼（repo 根目錄）` — 房間服務的位置以此為準

- [ ] T026 [紅燈] 範疇：`specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」`：撰寫 1 條 Rule、1 個 Example 的 step definitions，確認因認輸時的總回合數仍是修改前的值而失敗
- [ ] T027 [綠燈] 範疇：`specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」`：認輸結束對局時把總回合數記為已完成的輪次，讓這些 Rule 通過
- [ ] T028 [重構] 範疇：`specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」`：整理認輸結束對局的流程與 step，不改變行為

## Phase 12：技術項

- [ ] T029 在 `backend/app/services/rooms.py` 的結果統計查詢加上 `status` 條件，讓查詢使用 `ix_rooms_status` 索引
  - 📎 必讀：`技術項.md › 結果統計的查詢沒有使用` — 要修正的查詢以此為準

## Phase 13：Verify

- [ ] T030 [驗證] 執行所有端點的完整測試並與上次結果比對
```

### Bad Example

這個範例把修正 Phase 插在已勾選的 Phase 5 之後，並把之後已勾選的任務重新編號；已勾選的任務不再是從 T001 起連續的一段，implement 依勾選判斷的進度就錯了，check_tasks.py 也會回報已勾選任務的內容與上次拆解記下的不同。

```markdown
## Phase 5：backend/結果統計.feature

- [X] T009 [重構] 範疇：`specs/truth/features/backend/結果統計.feature`：整理結束對局的流程與 step，不改變行為

## Phase 6：修正 backend/結果統計.feature

- [ ] T010 [紅燈] 範疇：`specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」`：撰寫 1 條 Rule、1 個 Example 的 step definitions，確認因認輸時的總回合數仍是修改前的值而失敗

## Phase 7：重跑

- [X] T013 [重跑] 範疇：`specs/truth/features/frontend/互猜對戰.feature`：句型「系統處於 {前置狀態}」只改說明，確認既有 step 不用改後重新執行
```

## Rule 6 -- 已開始的 feature 只為之後變了的 Rule 排修正 Phase

**強度：MUST**

feature 已有勾選的階段任務時，feature_summary.py 以上次拆解記下的逐 Example 狀態（plan 資料夾的 `.task.json`）為參考點，只把之後新增、內容變了，或用到之後改了測試寫法的句型、Background、預設值、用語表參數值的 Rule，以及上次排了、還沒開始的任務涵蓋的 Rule，列為該 feature 的修正項；必須照這一項排一個「## Phase N：修正 <端點資料夾>/<檔名>.feature」，紅燈、綠燈、重構只涵蓋它的 `scope`。不得以整份 feature 重排紅燈、把已完成又沒有再變的 Rule 列進範疇，也不得改寫已開始的 Feature Phase 來涵蓋新的改動。以下 Example 皆對照此情境與輸出：

```text
backend/結果統計.feature：31 個 Example，Phase 5 的紅燈、綠燈、重構都已勾選；之後只改了 Rule「認輸結束時總回合數必須是當時的輪次」的一句提示
phases：{"phase": "修正 backend/結果統計.feature", "scope": "specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」", "rule_count": 1, "example_count": 2, "reference": "record"}
```

### Good Example

這個範例只為改了的那條 Rule 排修正 Phase，紅燈只寫 1 條 Rule、2 個 Example。

```markdown
- [ ] T026 [紅燈] 範疇：`specs/truth/features/backend/結果統計.feature ＞ Rule「認輸結束時總回合數必須是當時的輪次」`：撰寫 1 條 Rule、2 個 Example 的 step definitions，確認因認輸時的提示仍是修改前的文字而失敗
```

### Bad Example

這個範例因為 feature 改過就以整份 feature 重排紅燈，另外 29 個已綠的 Example 第一次就通過，bdd red 只能逐一破壞產品程式再還原，工作量和只改一句提示的改動不成比例。

```markdown
- [ ] T026 [紅燈] 範疇：`specs/truth/features/backend/結果統計.feature`：撰寫 4 條 Rule、31 個 Example 的 step definitions，確認因認輸時的提示仍是修改前的文字而失敗
```
