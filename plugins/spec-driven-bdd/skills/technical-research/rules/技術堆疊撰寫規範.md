# 技術堆疊撰寫規範

## Rule 1 -- 只增修這次決策與移除的行為涉及的列

**強度：MUST**

增修 techstack.md 時，新增或修改的每一列都必須是這次 research.md 某項決策「決策」欄中採用的技術；決策寫明不再使用的技術，必須連同套件安裝清單中的項目一併刪除。需求移除既有行為時（spec.md 的 FR 或「受影響的既有功能」寫明移除），不需要新的研究決策：只為該行為存在的列連同套件安裝清單中只有它使用的套件一併刪除，只有一部分為它存在的列只刪去那一部分。其餘既有列一字不改；不得收錄「考慮過的替代方案」中不採用的技術，也不得依這次的 research.md 重寫整份 techstack.md。以下 Example 皆對照此既有內容與這次的 plan：

```text
既有的 techstack.md（節錄）：
| HTTP 伺服器 | `node:http` ＋ 極簡路由器 | 自行實作 | — | 001/R-02 |
| EXIF 讀取 | `exifr` | 套件 | ^7.1.3 | 001/R-03、001/R-06 |
| 拖放排序 | Pointer Events | 自行實作 | — | 001/R-12 |
| 拖放位置與匯入完成的即時播報 | `aria-live` 區域 | 內建 | — | 001/R-10、001/R-12 |

這次（004）的 research.md：R-02 決定以 `sharp@^0.33.0` 在後端產生縮圖；沒有任何決策提到 HTTP 伺服器、EXIF 讀取與即時播報
這次的 spec.md：FR-003 移除相簿的拖放排序，「受影響的既有功能」列出相簿排序
```

### Good Example

這個範例新增 R-02 採用的 `sharp`；只為拖放存在的「拖放排序」整列刪除，即時播報只刪去拖放的部分，沒有為移除另立決策；決策與移除都沒有涉及的兩列維持原樣。

```markdown
| HTTP 伺服器 | `node:http` ＋ 極簡路由器 | 自行實作 | — | 001/R-02 |
| EXIF 讀取 | `exifr` | 套件 | ^7.1.3 | 001/R-03、001/R-06 |
| 匯入完成的即時播報 | `aria-live` 區域 | 內建 | — | 001/R-10、001/R-12 |
| 縮圖產生 | `sharp` | 套件 | ^0.33.0 | 004/R-02 |
```

### Bad Example

這個範例因為這次沒有決策提到拖放，就保留「拖放排序」一列與即時播報中拖放的部分；truth 仍描述已移除的功能，下游會以為拖放排序還在，保留它的程式與測試。

```markdown
| HTTP 伺服器 | `node:http` ＋ 極簡路由器 | 自行實作 | — | 001/R-02 |
| EXIF 讀取 | `exifr` | 套件 | ^7.1.3 | 001/R-03、001/R-06 |
| 拖放排序 | Pointer Events | 自行實作 | — | 001/R-12 |
| 拖放位置與匯入完成的即時播報 | `aria-live` 區域 | 內建 | — | 001/R-10、001/R-12 |
| 縮圖產生 | `sharp` | 套件 | ^0.33.0 | 004/R-02 |
```

## Rule 2 -- 每列必須附帶 plan 前綴的 R 編號

**強度：MUST**

每列的「研究紀錄」欄必須填寫選用該技術的決策，寫成 `<plan 編號>/R-<編號>`，plan 編號是 plan 資料夾名稱開頭的三位數；多項決策以頓號分隔，例如 `001/R-03、001/R-06`。編號必須存在於該 plan 的 research.md。這次的決策沿用、改變或取代既有的列時，在原有的編號之後加上這次的編號，不得刪除其他 plan 的編號；需求移除既有行為而只刪去列的一部分時，這次沒有決策可加，保留原有的編號。

### Good Example

這個範例的 `exifr` 由 001 的 R-03、R-06 選入，004 的 R-05 擴大它的用途；縮圖產生由 004 的 R-06 取代 001/R-07 的尺寸，001/R-07 其餘的決策仍成立；即時播報刪去了拖放的部分，這次沒有決策可加。三列的編號都帶 plan 前綴，原有的編號都保留。

```markdown
| EXIF 讀取 | `exifr` | 套件 | ^7.1.3 | 001/R-03、001/R-06、004/R-05 |
| 縮圖產生 | `createImageBitmap` ＋ `OffscreenCanvas` | 內建 | — | 001/R-07、004/R-06 |
| 匯入完成的即時播報 | `aria-live` 區域 | 內建 | — | 001/R-10、001/R-12 |
```

### Bad Example

這個範例的編號沒有 plan 前綴，還刪掉了原有的編號；讀者分不出 R-05 屬於哪個 plan，也找不到當初選用 `exifr` 的理由。

```markdown
| EXIF 讀取 | `exifr` | 套件 | ^7.1.3 | R-05 |
```

## Rule 3 -- 類型依取得方式判定

**強度：MUST**

需要透過套件管理工具安裝的技術填「套件」；執行環境或瀏覽器本身提供的模組與 API 填「內建」；專案程式碼中自行撰寫的模組填「自行實作」。由內建 API 組成、但需要專案撰寫邏輯的模組填「自行實作」。

### Good Example

這個範例把以 Pointer Events 撰寫的拖放模組判定為自行實作，下游會為它拆出實作任務。

```markdown
| 拖放排序 | Pointer Events | 自行實作 | — | 001/R-12 |
```

### Bad Example

這個範例因為 Pointer Events 是瀏覽器 API 就填「內建」，下游誤以為拖放不需撰寫程式，任務拆解漏掉約 150 行的拖放模組。

```markdown
| 拖放排序 | Pointer Events | 內建 | — | 001/R-12 |
```

## Rule 4 -- 套件一列一個且版本照抄 research.md

**強度：MUST**

類型為「套件」的列只能有一個套件，技術欄以反引號寫出套件名稱，版本欄必須與 research.md 中該套件 `套件名@版本範圍` 的版本範圍完全相同；多個 plan 的 research.md 都寫到這個套件時，以這一列引用的 plan 中編號最大者為準。

### Good Example

這個範例把驗收測試的兩個套件拆成兩列，版本與 research.md 的 `@cucumber/cucumber@^11.0.0`、`playwright@^1.49.0` 相同；Go 套件以完整 module 路徑寫出，版本照抄 research.md 的 `github.com/gorilla/websocket@v1.5.3`。

```markdown
| 驗收（BDD） | `@cucumber/cucumber` | 套件 | ^11.0.0 | 001/R-15 |
| 瀏覽器自動化 | `playwright` | 套件 | ^1.49.0 | 001/R-15 |
| 即時推播 | `github.com/gorilla/websocket` | 套件 | v1.5.3 | 001/R-04 |
```

### Bad Example

這個範例把兩個套件擠在同一列，並自行把版本改寫成 `latest`，下游無法對應版本到套件，安裝時也會拿到與研究時不同的主版號。

```markdown
| 驗收（BDD） | `@cucumber/cucumber` ＋ `playwright` | 套件 | latest | 001/R-15 |
```

## Rule 5 -- 相依類型依執行時是否載入判定

**強度：MUST**

「套件安裝清單」的相依類型必須使用該 workspace 套件管理工具的宣告名稱，並依正式環境執行時是否載入區分：會載入的放在執行期類型（如 npm 的 `dependencies`、Cargo 的 `dependencies`、Maven 的 `compile`），只在建置、測試、檢查時使用的放在開發期類型（如 npm 的 `devDependencies`、Cargo 的 `dev-dependencies`、Maven 的 `test`、Python 的 dependency group `dev`）。套件管理工具不區分相依類型時（如 Go modules 的 `require`），只使用該工具唯一的宣告名稱。每個套件只能出現在一個 workspace 的一種相依類型。

### Good Example

這個範例把後端執行時連線資料庫的 `mysql2` 放在 dependencies，把只在建置時使用的 `vite` 放在 devDependencies；Go 的 workspace 不區分相依類型，只用 `require`。

```markdown
| `backend` | dependencies | `mysql2@^3.11.0`、`busboy@^1.6.0`、`exifr@^7.1.3` |
| `frontend` | devDependencies | `vite@^6.0.0` |
| `e2e` | devDependencies | `@cucumber/cucumber@^11.0.0`、`playwright@^1.49.0` |
| `push-server` | require | `github.com/gorilla/websocket@v1.5.3` |
```

### Bad Example

這個範例把 `vite` 放進 frontend 的 dependencies，前端打包後的產物在正式環境不需要 Vite，卻讓部署時多安裝整套建置工具。

```markdown
| `frontend` | dependencies | `vite@^6.0.0` |
```

## Rule 6 -- 空值必須使用固定符號

**強度：MUST**

類型不是「套件」的列，版本欄固定填「—」；「套件安裝清單」中沒有任何套件的相依類型，套件與版本欄固定填「（無）」。不得留白，也不得填「N/A」、「無」、「-」等其他寫法。

### Good Example

這個範例的內建技術版本填「—」，沒有執行期相依的 frontend 填「（無）」。

```markdown
| 內容雜湊 | `node:crypto`（SHA-256） | 內建 | — | 001/R-08 |
| `frontend` | dependencies | （無） |
```

### Bad Example

這個範例的版本欄留白、相依欄填「N/A」，讀者無法分辨是刻意沒有版本還是漏填，下游也無法用固定符號判斷該列是否需要安裝套件。

```markdown
| 內容雜湊 | `node:crypto`（SHA-256） | 內建 |  | 001/R-08 |
| `frontend` | dependencies | N/A |
```

## Rule 7 -- 執行環境表只收錄基礎環境

**強度：MUST**

「執行環境」表只收錄執行環境、程式語言、資料庫與套件管理工具；框架、函式庫與工具必須放在所屬技術層級的表中。

### Good Example

這個範例的執行環境表只列出 Node.js、JavaScript、MySQL 與 npm workspaces。

```markdown
| 執行環境 | Node.js | 22 LTS | 001/R-01 |
| 程式語言 | JavaScript（ES Modules） | ES2022 | 001/R-01 |
| 資料庫 | MySQL | 8.0 以上 | 001/R-01 |
| 套件管理 | npm workspaces（`frontend`、`backend`、`e2e`） | 隨 Node 22 | 001/R-16 |
```

### Bad Example

這個範例把資料庫驅動 `mysql2` 放進執行環境表，該表沒有「類型」欄，下游無法判斷它是需要安裝的套件，也無法和後端層的其他套件一起拆任務。

```markdown
| 資料庫 | MySQL | 8.0 以上 | 001/R-01 |
| 資料庫驅動 | `mysql2` | ^3.11.0 | 001/R-03 |
```

## Rule 8 -- Workspace 以依賴宣告檔所在目錄判定

**強度：MUST**

「套件安裝清單」的 Workspace 欄必須填擁有獨立依賴宣告檔（如 `package.json`、`go.mod`、`pyproject.toml`、`pom.xml`、`Cargo.toml`）的目錄，以相對 repo 根目錄的路徑寫在反引號中；整個 repo 只有一份依賴宣告檔時填 `` `.` ``。不得以端點名稱、技術層級或套件管理工具的功能名稱代替目錄。

### Good Example

這個範例是單一 Go module 的專案，只有根目錄的 `go.mod`，Workspace 填 `.`。

```markdown
| `.` | require | `github.com/gorilla/websocket@v1.5.3`、`github.com/go-sql-driver/mysql@v1.8.1` |
```

### Bad Example

這個範例在同一個專案中以端點名稱當 Workspace，實際只有根目錄一份 `go.mod`，下游的 system-analysis 會依此建立 `後端/` 目錄，task 也會拆出兩個不存在的依賴宣告檔任務。

```markdown
| 後端 | require | `github.com/gorilla/websocket@v1.5.3` |
| 資料庫 | require | `github.com/go-sql-driver/mysql@v1.8.1` |
```

## Rule 9 -- 只寫技術與模組

**強度：MUST**

技術層級表格（「執行環境」與「套件安裝清單」以外的表格）的項目欄寫用途，技術欄只寫採用的技術：套件，執行環境、瀏覽器或套件提供的 API 與模組，以及演算法或做法的名稱。不得重述家在其他地方的內容：API 路徑與事件、資料表與欄位、畫面路由、testid 與文案（各端點的介面文檔），需求的數值與規則（spec.md），決策的參數與數值（research.md，讀者經研究紀錄欄的編號查閱），以及元件、hook、函式、類別、原始碼檔案與目錄、遷移版本與設定變數的名稱（程式）。這些內容的擁有者改了它們時不會經過本 skill，techstack.md 的副本會與現況不符。刪去這些內容後的技術欄依 Rule 10 改寫或刪除。以下 Example 皆對照此研究紀錄：

```text
001 的 research.md（節錄）：
- R-07：前端以 `createImageBitmap` 搭配 `OffscreenCanvas` 產生長邊 400px、品質 0.8 的 JPEG 縮圖
- R-13：hash 路由（`#/`、`#/albums/:id`），頁面元件 `HomePage`、`AlbumPage`；開發時 Vite 以 proxy 將 `/api` 轉發到後端
- R-16：遷移檔 `backend/src/db/migrations/*.sql` 依檔名順序執行，以 `schema_migrations` 表記錄已執行的版本；設計代幣定義在 `frontend/src/styles/tokens.css`
```

### Good Example

這個範例的項目欄寫用途、技術欄只寫技術與做法；縮圖的尺寸與品質留在研究紀錄，路由、API 路徑、檔案路徑與資料表以介面文檔與程式為準，頁面元件只有名稱、沒有技術，不另立一列。

```markdown
| 建置工具 | `vite`（開發時以 proxy 把 API 請求轉發至後端） | 套件 | ^6.0.0 | 001/R-13 |
| 路由 | hash 路由 | 自行實作 | — | 001/R-13 |
| 縮圖產生 | `createImageBitmap` ＋ `OffscreenCanvas` | 內建 | — | 001/R-07 |
| 設計代幣 | CSS 自訂屬性 | 內建 | — | 001/R-16 |
| 資料庫遷移 | 依檔名順序執行 SQL 遷移檔的自寫腳本 | 自行實作 | — | 001/R-16 |
```

### Bad Example

這個範例重抄縮圖參數、路由、API 路徑、元件名、檔案路徑與資料表；之後的 plan 由 api-plan 改了路徑、由程式改了元件名都不會經過 technical-research，techstack.md 留下錯的副本，下游照它找不到實際的端點與檔案。

```markdown
| 建置工具 | `vite`（開發時以 proxy 將 `/api` 轉發至後端） | 套件 | ^6.0.0 | 001/R-13 |
| 路由 | hash 路由（`#/`、`#/albums/:id`） | 自行實作 | — | 001/R-13 |
| 頁面 | `HomePage`、`AlbumPage` | 自行實作 | — | 001/R-13 |
| 縮圖產生 | `createImageBitmap` ＋ `OffscreenCanvas`（長邊 400px、品質 0.8） | 內建 | — | 001/R-07 |
| 設計代幣 | CSS 自訂屬性（`frontend/src/styles/tokens.css`） | 內建 | — | 001/R-16 |
| 資料庫遷移 | `backend/src/db/migrations/*.sql`，以 `schema_migrations` 表記錄版本 | 自行實作 | — | 001/R-16 |
```

## Rule 10 -- 自行實作的列以做法取代名稱

**強度：MUST**

類型為「自行實作」的列，技術欄寫專案自己實作的做法：用什麼機制、怎麼做到這一列的用途，而不是元件、hook、函式或檔案的名稱。依 Rule 9 刪去名稱後，必須依研究紀錄欄引用的決策把這一列改寫成做法，不得因技術欄只剩名稱就整列刪除；只有這一列只是在列舉名稱、引用的決策也沒有寫出做法時（例如列出全部頁面元件），才整列刪除。以下 Example 皆對照此既有內容與研究紀錄：

```text
既有的 techstack.md（節錄）：
| 匿名身份保存 | `sessionStorage` | 自行實作 | — | 001/R-04 |
| 連線、自動重連與房間狀態套用 | `useRoomSession`（比對 `state_version`） | 自行實作 | — | 001/R-11、001/R-16 |
| 頁面 | `EntryPage`、`RoomPage`、`GamePage`、`ResultPage` | 自行實作 | — | 001/R-16 |
| 認輸確認視窗 | 原生 `<dialog>` | 自行實作 | — | 001/R-17 |

001/R-11：前端收到狀態版本比目前小的快照時直接略過
001/R-16：以自寫的 hook 處理連線中斷後的自動重連，並套用快照、比對狀態版本；頁面元件依畫面切分
```

### Good Example

這個範例刪去 hook 與欄位的名稱後，依 R-11、R-16 把連線一列改寫成重連與套用快照的做法；頁面一列只列舉元件名稱，R-16 對頁面也只寫依畫面切分，整列刪除。

```markdown
| 匿名身份保存 | `sessionStorage` | 自行實作 | — | 001/R-04 |
| 連線、自動重連與房間狀態套用 | 連線中斷後自動重連、略過狀態版本較舊之快照的 React hook | 自行實作 | — | 001/R-11、001/R-16 |
| 認輸確認視窗 | 原生 `<dialog>` | 自行實作 | — | 001/R-17 |
```

### Bad Example

這個範例因為刪去 `useRoomSession` 後技術欄沒有剩下技術，就把連線一列也整列刪除；techstack.md 不再記得前端自己實作了重連與狀態版本比對，下一個 plan 的技術研究看不到這項既有的做法，可能另選一套重連機制，或重複研究同一個議題。

```markdown
| 匿名身份保存 | `sessionStorage` | 自行實作 | — | 001/R-04 |
| 認輸確認視窗 | 原生 `<dialog>` | 自行實作 | — | 001/R-17 |
```
