# 研究紀錄撰寫規範

## Rule 1 -- 技術方向只記錄使用者指定的內容

**強度：MUST**

開頭的「使用者於規劃階段指定的技術方向」只能記錄使用者在對話或 clarify 中明確指定的方向與限制，限制性的用語（如「不使用」）必須保留並加粗。不得把 AI 在研究中做出的決策寫進這一段。

### Good Example

這個範例只記錄使用者原本的要求，並保留「不使用」的限制。

```markdown
- 前端：Vite，搭配原生 HTML、CSS、JavaScript；**不使用** React 等框架，套件數量越少越好。
- 資料庫：MySQL。
```

### Bad Example

這個範例把 AI 選定的版本與套件寫進技術方向，讀者無法分辨哪些是使用者的硬性限制、哪些是可以重新評估的決策。

```markdown
- 後端：Node.js 22 LTS，使用 `node:http` 與 `busboy`。
- 資料庫：MySQL 8.0，透過 `mysql2` 連線。
```

## Rule 2 -- 對應需求只能使用已定義的識別

**強度：MUST**

「對應需求」只能填寫 spec.md 已定義的 FR、NFR、SC 編號、使用者故事（`US<n>`）、驗收情境（`US<n>-<m>`）、邊界情況（`邊界情況「<名稱>」`）或規格假設（`規格假設「<內容>」`），本 plan 的 acceptance 中標 `@開發發現` 的 AC 編號（`AC-<編號>`），或本 plan `技術項.md` 中的技術項（`技術項「<技術項的問題>」`），多項以頓號分隔。技術修正 plan 沒有 spec.md，只能填技術項。無直接對應時只寫「跨領域」，不得同時混寫編號與「跨領域」。

### Good Example

這個範例引用 spec.md 中存在的編號與邊界情況名稱，以及技術項.md 中的一行技術項，以頓號分隔。

```markdown
- **對應需求**：SC-001、邊界情況「大量匯入」、技術項「並行 8 個縮圖工作時測試機記憶體不足」
```

### Bad Example

這個範例引用 spec.md 不存在的編號，又混寫「跨領域」，下游無法追溯決策究竟服務哪條需求。

```markdown
- **對應需求**：FR-099、跨領域、效能需求
```

## Rule 3 -- 憲法只以條款編號引用

**強度：MUST**

研究紀錄提到憲法時，必須寫出 `.claude/constitution/` 中實際存在的條款編號（如 C-TR-01），不得寫「憲法原則」加羅馬數字或其他不存在的編號；決策不受任何條款約束時，不得提到憲法。

### Good Example

這個範例以實際存在的條款編號說明為何多列一個替代方案，讀者可以回到憲法檔查證。

```markdown
- **考慮過的替代方案**：Socket.IO 的自動重連與房間功能本專案用不到（依 C-TR-01 列出淘汰理由）。
```

### Bad Example

這個範例引用不存在的「憲法原則 IV」，讀者會去尋找不存在的條款，也無法判斷該決策受什麼約束。

```markdown
## R-14 效能策略（憲法原則 IV）
```

## Rule 4 -- 決策之間以 R 編號互相引用

**強度：SHOULD**

某項決策的內容已在其他決策中說明時，以「見 R-<編號>」引用，不得重複整段說明，避免同一決策在兩處寫成不同內容。引用其他 plan 的決策時寫成 `<plan 編號>/R-<編號>`；提到既有的技術堆疊時連到 `specs/truth/techstack.md`，不得連到其他 plan 的檔案。

### Good Example

這個範例引用同一份 research.md 的 R-07，並以帶 plan 前綴的編號引用 001 的決策，都沒有重複細節。

```markdown
因此改由前端產生縮圖（見 R-07），上傳仍使用既有的串流解析（見 001/R-04）。
```

### Bad Example

這個範例在兩項決策中各自寫了縮圖尺寸，且數值不一致，實作者無法判斷哪個才是決策。

```markdown
R-03：因此改由前端產生長邊 300px 的縮圖。
R-07：產生長邊 400px、品質 0.8 的 JPEG 縮圖。
```

## Rule 5 -- 沒有決策時寫明沿用既有技術

**強度：MUST**

需求 plan 盤點後沒有任何需要技術決策的議題時，research.md 只保留表頭與技術方向，並在分隔線之後寫一句「這次沒有需要技術決策的議題，沿用 [techstack.md](../../truth/techstack.md)。」不得省略 research.md，也不得為了有內容而立沿用的決策。技術修正 plan 沒有需要技術決策的議題時不寫 research.md，只增修 techstack.md。

### Good Example

這個範例沒有任何決策，只寫出沿用既有技術的一句話。

```markdown
使用者於規劃階段指定的技術方向：

- 沿用既有的技術堆疊，不新增套件。

---

這次沒有需要技術決策的議題，沿用 [techstack.md](../../truth/techstack.md)。
```

### Bad Example

這個範例為了讓 research.md 有內容而立一條沿用的決策，並重抄既有的套件；techstack.md 的同一批列會被加上這次的編號，下游以為這次重新決定過它們。

```markdown
---

## R-01 沿用既有的技術堆疊

- **對應需求**：FR-001
- **決策**：沿用 `mysql2@^3.11.0`、`busboy@^1.6.0`、`exifr@^7.1.3`，版本不變。
- **理由**：這次的需求不需要新的技術。
```

## Rule 6 -- 改變既有決策依所屬 plan 改寫或取代

**強度：MUST**

要改變的決策屬於這個 plan 時，直接改寫 research.md 中的那一項決策，不另立新的 R 編號；整項不再需要時刪除它，其餘決策的編號不變，之後新增的決策取既有最大編號加一。要改變的決策屬於已交付的 plan 時，不得修改該 plan 的 research.md，必須在這個 plan 新增一項決策，以「取代」欄寫出被取代的決策編號（`<plan 編號>/R-<編號>`）與被取代的部分；沒有寫進「取代」欄的部分仍依原決策。以下 Example 皆對照此情境：

```text
004 進行中，research.md 已有 R-01 至 R-05：
- 技術項.md 有一行「並行 8 個縮圖工作時測試機記憶體不足」（implement 發現，修正：technical-research），8 個是本 plan 的 R-02 決定的
- clarify-over-specs 刪除了 FR-005，本 plan 的 R-04 只為它而立
- 新增的 FR-004 要求高解析度螢幕上的縮圖清晰；001 已交付，它的 R-07 決定前端產生長邊 400px 的縮圖
```

### Good Example

這個範例直接改寫本 plan 的 R-02，不另立編號；只為 FR-005 而立的 R-04 整項刪除，其餘編號不變；001/R-07 屬於已交付的 plan，在本 plan 新增 R-06（既有最大編號加一，不重用 R-04），以「取代」欄寫出只取代尺寸，其餘仍依 001/R-07。

```markdown
## R-02 後端縮圖產生

- **對應需求**：FR-002、技術項「並行 8 個縮圖工作時測試機記憶體不足」
- **決策**：後端以 `sharp@^0.33.0` 產生縮圖，同時處理的縮圖工作上限為 2 個，其餘排入佇列。

## R-06 高解析度螢幕的縮圖尺寸

- **對應需求**：FR-004
- **取代**：001/R-07 的「長邊 400px」；001/R-07 的其餘決策不變。
- **決策**：前端產生的縮圖長邊改為 800px，產生方式與品質依 001/R-07。
```

### Bad Example

這個範例直接修改已交付的 001 的 research.md；001 交付時的決策從歷史紀錄消失，引用 001/R-07 的 techstack.md 列與 dsl.md 句型看不出決策已經改變，也查不到是哪個 plan 改的。

```markdown
（specs/plans/001-photo-album-organizer/research.md）

## R-07 縮圖產生方式

- **對應需求**：SC-003
- **決策**：由前端在上傳前用 `createImageBitmap` 搭配 `OffscreenCanvas`，產生長邊 800px、品質 0.8 的 JPEG 縮圖。
```
