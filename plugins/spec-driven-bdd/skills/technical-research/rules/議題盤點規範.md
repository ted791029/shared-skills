# 議題盤點規範

## Rule 1 -- 只為有多種實作方式的需求立議題

**強度：MUST**

逐條檢視 spec.md 的 FR、NFR、SC 與邊界情況，判斷實作時是否存在兩種以上合理的技術做法，或結果是否取決於技術選型。符合者必須納入某個議題；只描述業務規則、任何技術選型下做法都相同的需求不立議題。

### Good Example

這個範例為「重複照片偵測」立議題，因為雜湊比對、檔名比對、前端或後端判定都是可行做法；「相簿名稱顯示為日期」在任何技術下做法都相同，不立議題。

```markdown
- FR-008 檔案內容完全相同才算重複 → 立議題（偵測方式與判定位置有多種選擇）
- FR-006 相簿名稱預設為拍攝日期 → 不立議題（純業務規則）
```

### Bad Example

這個範例為純業務規則立議題，研究紀錄被灌入沒有取捨的決策，真正需要權衡的效能需求反而被遺漏。

```markdown
- FR-006 相簿名稱預設為拍攝日期 → R-05 相簿命名方式
- SC-003 200 張照片的相簿 1 秒內顯示第一屏 → 未立議題
```

## Rule 2 -- 議題以單一決策軸為粒度

**強度：MUST**

共用同一個技術選擇的多條需求必須合併為一個議題；彼此可以獨立選擇的技術問題必須拆成不同議題。判斷方式：改變其中一個選擇時，另一個選擇是否必須跟著改變，必須跟著改變就合併。

### Good Example

這個範例把預設排序、拖放排序、新相簿位置合併為「相簿排序模型」，因為三者都依賴同一個排序欄位設計；縮圖產生與檔案儲存位置可以各自選擇，拆成兩個議題。

```markdown
- R-11 相簿排序模型：FR-007、FR-013、FR-015、FR-016
- R-04 照片與縮圖的儲存位置
- R-07 縮圖產生方式
```

### Bad Example

這個範例把同一個排序模型拆成三個議題，三項決策可能各自選出互相矛盾的欄位設計，下游無法實作。

```markdown
- R-11 預設依日期排序：FR-007
- R-12 拖放後的排序儲存：FR-015
- R-13 新相簿的插入位置：FR-016
```

## Rule 3 -- 基礎議題只在尚未決定或需要改變時盤點

**強度：MUST**

除了由需求推得的議題，還必須盤點技術方向本身要拍板的基礎議題：執行環境與語言版本、主要框架或其替代、執行期相依套件、資料儲存位置、前端架構、測試策略，以及設定、遷移與程式碼品質工具。下列兩種項目不再立議題：技術方向已明確指定到版本與做法的項目；`specs/truth/techstack.md` 已有對應的列，而這次的需求與技術方向都沒有要改變它的項目。不得為了交代沿用而立「沿用既有技術」的議題；只有這次的需求讓既有技術不夠用，或技術方向要求更換時才立議題。

### Good Example

這個範例是專案的第一個 plan，techstack.md 還不存在，技術方向只說「後端 Node.js、資料庫 MySQL」，因此補上版本、HTTP 框架與測試策略等基礎議題。

```markdown
- R-01 執行環境與語言版本（Node 版本、ES 版本、MySQL 版本）
- R-02 後端 HTTP 框架
- R-15 測試策略
```

### Bad Example

這個範例的 techstack.md 已有執行環境、HTTP 框架與測試工具的列，這次的需求也沒有要改變它們，卻再立三個沿用的議題；research.md 多出與這次迭代無關的決策，同一項技術被兩個 plan 重複宣告。

```markdown
- R-01 執行環境與語言版本（沿用既有的版本）
- R-02 後端 HTTP 框架（沿用既有的框架）
- R-03 測試策略（沿用既有的測試工具）
```

## Rule 4 -- 規格與架構的解讀落差必須立議題

**強度：SHOULD**

spec.md 的需求或假設在技術方向的架構下有不同解讀時（例如規格寫「保留原始檔案」，而架構是上傳到後端），必須立議題記錄採用的解讀與理由，不得默默選一種解讀。

### Good Example

這個範例發現「原始檔案保留不動」在前後端架構下有兩種解讀，立議題寫明刪除只影響後端副本。

```markdown
- R-05 規格中「原始檔案保留不動」在前後端架構下的解讀：FR-017
```

### Bad Example

這個範例沒有記錄解讀，實作者可能以為要保留後端副本，刪除功能便無法真正刪除照片。

```markdown
- R-08 重複照片偵測：FR-008
（FR-017 未立議題）
```
