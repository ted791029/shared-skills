# 研究紀錄（Phase 0）：照片相簿整理器

**Plan**：`001-photo-album-organizer` | **日期**：2026-10-22 | **規格**：[spec.md](./spec.md)

使用者於規劃階段指定的技術方向：

- 前端：Vite，搭配原生 HTML、CSS、JavaScript；**不使用** React 等框架，套件數量越少越好。
- 後端：Node.js；照片上傳到後端保存，前端向後端查詢相簿、預覽照片。
- 資料庫：MySQL。
- **不使用**第三方服務或系統（例如雲端儲存、BaaS、第三方圖片服務）。

---

## R-01 執行環境與語言版本

- **對應需求**：跨領域
- **決策**：Node.js 22 LTS（前後端工具鏈都使用），JavaScript（ES2022、ES Modules），MySQL 8.0 以上。
- **理由**：Node 22 內建 `--env-file`、`fetch`、`crypto`，可以少裝好幾個套件。
  MySQL 8 支援視窗函式（`ROW_NUMBER`），可以用單一查詢取得相簿封面，避免 N+1。
- **考慮過的替代方案**：TypeScript 需要額外的編譯設定，與「簡單、原生」的方向不符，因此不採用。

## R-02 後端 HTTP 框架

- **對應需求**：跨領域
- **決策**：使用 Node 內建的 `node:http`，自行撰寫約 50 行的極簡路由器（方法 + 路徑樣式比對），不引入 Express／Fastify。
- **理由**：端點約 8 個，需求單純；內建模組就足以應付，符合「最少套件」。路由器是純函式，行為容易推斷。
- **考慮過的替代方案**：Express 生態成熟，但只為路由多引入一個相依套件，效益不高；Fastify 功能強大，但對本專案而言過度。

## R-03 後端執行期相依套件（共 3 個）

- **對應需求**：跨領域
- **決策**：後端執行期只引入下表 3 個套件，其餘一律使用 Node 內建模組。

| 套件 | 用途 | 為何無法用內建功能取代 |
|------|------|------------------------|
| `mysql2@^3.11.0` | MySQL 驅動程式（Promise API、預備陳述式） | Node 沒有內建 MySQL 用戶端 |
| `busboy@^1.6.0` | 以串流方式解析 `multipart/form-data` 上傳 | 內建模組沒有 multipart 解析器；自行實作容易出錯 |
| `exifr@^7.1.3` | 讀取 JPEG／HEIC／PNG 的 EXIF 拍攝日期 | EXIF／HEIC 容器格式複雜；`exifr` 為純 JS、零相依 |

- **理由**：每個套件都對應一項內建功能無法取代的需求（見上表最後一欄），符合「最少套件」。
- **考慮過的替代方案**：`sharp` 可以在伺服器端產生縮圖，但它含原生二進位檔，且預設建置不支援 HEVC 編碼的 HEIC 解碼，
  因此改由前端產生縮圖（見 R-07）。`multer` 依賴 `busboy` 並與 Express 綁定，所以直接使用 `busboy`。

## R-04 照片與縮圖的儲存位置

- **對應需求**：跨領域
- **決策**：照片原始檔與縮圖以檔案形式存放在後端的 `storage/` 目錄（路徑：`originals/<hash 前兩碼>/<sha256>.<副檔名>`、
  `thumbnails/<hash 前兩碼>/<sha256>.jpg`）。MySQL 只存放中繼資料。
- **理由**：MySQL 不適合存放大量 BLOB，會讓備份與查詢變慢；以內容雜湊命名檔案，天然避免重複，也方便設定長效快取。
- **考慮過的替代方案**：存成 MySQL `LONGBLOB` 會讓資料庫膨脹，查詢記憶體壓力也大，因此不採用；
  雲端物件儲存則違反「不要第三方系統」。

## R-05 規格中「原始檔案保留不動」在前後端架構下的解讀

- **對應需求**：FR-017、規格假設「原始檔案保留不動」
- **決策**：上傳時，瀏覽器只讀取使用者裝置上的檔案，並傳送一份副本到後端。刪除照片（FR-017）時，
  只會移除後端的資料列與後端保存的副本，**不會也無法**動到使用者裝置上的原始檔案。
- **理由**：瀏覽器沒有權限修改或刪除使用者的本機檔案，因此架構本身就能保證 FR-017 與規格假設。
- **考慮過的替代方案**：只記錄本機路徑、不上傳檔案，在 Web 架構下無法讀回檔案，也違背使用者「照片要上傳到後端」的要求。

## R-06 拍攝日期的取得與時區

- **對應需求**：FR-002、邊界情況「跨時區」
- **決策**：
  1. 後端以 `exifr` 讀取 `DateTimeOriginal`（找不到時依序改讀 `CreateDate`、`DateTimeDigitized`），並使用 `reviveValues: false` 取得原始字串
     `YYYY:MM:DD HH:MM:SS`，視為「拍攝當地時間」直接解析，不做時區換算。
  2. 若取不到 EXIF 日期，則使用前端上傳時一併送出的 `lastModifiedLocal` 欄位（由瀏覽器將 `File.lastModified`
     以使用者本地時區格式化成 `YYYY-MM-DDTHH:mm:ss`），並將 `date_estimated` 設為 `1`。
  3. 資料庫以 `DATETIME`（無時區）保存 `taken_at`，相簿日期 `album_date = DATE(taken_at)`。
- **理由**：規格要求「以照片記錄的當地拍攝日期為準」。EXIF 的 `DateTimeOriginal` 本身就是當地時間；若轉換成 UTC，
  反而會讓深夜拍的照片跑到隔天的相簿。
- **考慮過的替代方案**：儲存 UTC `TIMESTAMP` 再用 `OffsetTimeOriginal` 換回當地時間，但許多相機不寫入 offset 欄位，結果不可靠。
  另一個做法是由前端解析 EXIF，但會讓後端必須信任前端給的日期，並且需要在前端打包 `exifr`（增加 JS 體積），因此不採用。

## R-07 縮圖產生方式

- **對應需求**：SC-003
- **決策**：由**前端**在上傳前用 `createImageBitmap(file, { imageOrientation: 'from-image' })` 搭配 `OffscreenCanvas`，
  產生長邊 400px、品質 0.8 的 JPEG 縮圖，與原始檔一起放進同一個 multipart 請求上傳。若瀏覽器無法解碼該檔案
  （例如非 Safari 瀏覽器遇到 HEIC），就不附縮圖，後端記錄 `has_thumbnail = 0`。
- **理由**：前後端都不需要任何影像處理套件；縮圖約 30 KB，可以讓含 200 張照片的相簿在 1 秒內顯示第一屏（SC-003）。
- **已知限制**：HEIC 照片在不支援 HEIC 的瀏覽器上，無法產生縮圖，也無法放大檢視。介面會顯示「此瀏覽器無法預覽 HEIC 照片」，
  並提供下載原始檔的按鈕。照片仍會正確分組（EXIF 由後端讀取）。
- **考慮過的替代方案**：伺服器端使用 `sharp`，見 R-03；伺服器端呼叫 ImageMagick 則屬於外部系統相依，因此不採用。

## R-08 重複照片偵測

- **對應需求**：FR-008
- **決策**：後端在串流接收檔案時，同步以 `node:crypto` 計算 SHA-256。`photos.content_hash` 欄位設有 `UNIQUE` 索引；
  寫入時若遇到 `ER_DUP_ENTRY`，就判定為重複，刪除暫存檔並回應 `status: "duplicate"`。
- **理由**：「檔案內容完全相同才算重複，不論檔名或路徑」正好對應內容雜湊。由資料庫唯一索引擋下重複，
  並行上傳也不會有競態問題。
- **考慮過的替代方案**：前端先用 `crypto.subtle` 計算雜湊、詢問後端後再決定是否上傳，可以節省頻寬，
  但需要多一支 API 與一輪往返；在本機或區網的情境下效益不明顯（未經量測前不做預先優化）。
  若量測顯示 SC-001 無法達成，再列為優化選項。

## R-09 檔案格式判定

- **對應需求**：FR-009
- **決策**：前端先依 MIME／副檔名過濾，提供即時回饋；後端再讀取檔頭魔術位元組做最終判定：
  JPEG `FF D8 FF`、PNG `89 50 4E 47 0D 0A 1A 0A`、HEIC/HEIF（offset 4 為 `ftyp`，品牌為 `heic`/`heix`/`mif1`/`msf1`/`heif`）。
  不符合時回應 `415`，前端將檔名列入「不支援的檔案」清單。單檔上限 50 MB（超過時回應 `413`）。
- **理由**：前端的判斷可以被繞過，後端必須再驗證一次；判定邏輯約 20 行，不需要引入 `file-type` 套件。
- **考慮過的替代方案**：只相信 `Content-Type` 並不可靠，因此不採用。

## R-10 匯入流程與進度

- **對應需求**：SC-001、邊界情況「大量匯入」
- **決策**：前端維護一個模組層級的上傳佇列，**一個檔案一個請求**，並行數為 3。佇列在單頁應用程式中持續運作，
  使用者可以在匯入過程中切換頁面、瀏覽已完成的相簿。畫面上顯示「已完成 N／總數 M」的進度條（`role="progressbar"`），
  全部完成後顯示摘要：新增數、略過重複數、不支援的檔案清單。
- **理由**：每個檔案個別回應，結果分類單純，失敗也只影響單一檔案；並行數 3 能在吞吐量與伺服器負載之間取得平衡。
- **考慮過的替代方案**：單一請求一次上傳全部檔案，會讓進度與錯誤處理變複雜，失敗也必須整批重試；
  背景 Service Worker 則對本版本而言過度設計。

## R-11 相簿排序模型

- **對應需求**：FR-007、FR-013、FR-015、FR-016、NFR-010
- **決策**：
  - `app_settings` 表中的 `album_order_mode` 取值為 `date`（預設）或 `custom`。
  - `date` 模式：相簿依 `album_date DESC` 排序，`albums.position` 欄位不使用。
  - 第一次拖放時，在交易中依目前的日期順序把 `position` 實體化為 0..n-1，並將模式切換為 `custom`。
  - `custom` 模式：依 `position ASC` 排序；新建立的相簿的 `position = MIN(position) - 1`（放在最前面，符合 FR-016）。
  - 移動 API 語意為「把相簿 X 移到相簿 Y 之前」（Y 為 `null` 表示移到最後），後端以單一 `UPDATE` 位移區間內的
    `position`（±1），再設定 X 的新位置。整個操作包在交易中。
- **理由**：「移到某相簿之前」的語意與拖放、鍵盤操作完全對應；每次移動只需 O(區間) 一條 SQL，不用傳送整份順序清單，
  也能搭配分頁。使用者未自訂前，新相簿自然依日期插入正確位置。
- **考慮過的替代方案**：前端送出完整的 ID 清單，需要一次載入全部相簿，與分頁衝突，且並行匯入新增相簿時容易產生衝突；
  分數／字典序排序鍵（LexoRank）在幾百筆的規模下過度設計。

## R-12 拖放與鍵盤操作

- **對應需求**：FR-013、FR-014、FR-019、US3、SC-004、SC-006
- **決策**：以 **Pointer Events** 自行實作拖放（同時支援滑鼠與觸控），不使用 HTML5 原生 DnD API，也不使用 SortableJS。
  - 拖曳時顯示放置位置指示線；放到有效區域外或按下 `Esc` 時，相簿回到原位。
  - 放置判定只計算「插入點」（兩本相簿之間），不存在「放進相簿」的目標，因此結構上滿足 US3-5 與 FR-019。
  - 鍵盤操作：聚焦相簿卡片後按 `Space`／`Enter` 拿起，用方向鍵移動，再按 `Space`／`Enter` 放下，`Esc` 取消；
    透過 `aria-live="assertive"` 區域以繁體中文播報「已拿起…，目前位置第 N 本，共 M 本」等訊息。
  - 樂觀更新：放下後畫面立即重新排列（SC-004）；若 API 失敗，就還原順序並顯示錯誤提示。
- **理由**：HTML5 DnD 在行動裝置的觸控上支援不佳；Pointer Events 一套實作就能涵蓋兩種輸入方式，約 150 行，且邏輯可以拆成純函式來測試。
- **考慮過的替代方案**：SortableJS 雖然成熟，但違反「最少套件、不用第三方」的要求，無障礙鍵盤操作也需要另外補強。

## R-13 前端架構

- **對應需求**：跨領域
- **決策**：多頁式單一入口（`index.html`），搭配 hash 路由（`#/`、`#/albums/:id`）。各頁面以原生模組匯出 `render(container, params)`，
  元件以「回傳 DOM 元素的函式」實作。開發時，Vite（`vite@^6.0.0`）透過 proxy 將 `/api` 轉發到後端（`http://localhost:3000`）；
  正式環境由後端提供 `frontend/dist` 的靜態檔案。
- **理由**：頁面只有兩個（主頁、相簿頁）加上燈箱，不需要框架；hash 路由不需要伺服器端設定。
- **前端執行期相依**：**0 個**。
- **考慮過的替代方案**：History API 路由需要後端設定 fallback；React／Vue 已被使用者排除。

## R-14 效能策略

- **對應需求**：SC-003、SC-007、US2-3
- **決策**：
  - 相簿列表與相簿內照片的 API **一律分頁**：相簿列表用 `limit`／`offset`（預設 60，上限 200）；
    照片列表用游標（`taken_at`、`id`，預設 100，上限 200）。前端以 `IntersectionObserver` 無限捲動。
  - 縮圖使用 `<img loading="lazy" decoding="async">`，外層容器以 CSS `aspect-ratio: 1` 固定尺寸，搭配骨架佔位，
    避免 CLS（US2-3）。
  - 照片檔案回應帶 `ETag`（內容雜湊）與 `Cache-Control: public, max-age=31536000, immutable`。
  - 相簿列表以單一 SQL（`ROW_NUMBER()` 取封面 + `COUNT` 照片數）取得，避免 N+1；索引為 `photos(album_id, taken_at, id)`。
- **理由**：一萬張照片、數百本相簿的規模下，分頁搭配適當索引，即可讓 API p95 低於 200 ms；固定縮圖尺寸是 CLS ≤ 0.1 的關鍵。

## R-15 測試策略

- **對應需求**：跨領域
- **決策**：每個端點資料夾一層 BDD 測試，各層共用 `e2e` workspace 的 Cucumber 執行環境，並依下表分層。

| 層級 | 工具 | 範圍 |
|------|------|------|
| 後端 BDD 測試 | `@cucumber/cucumber@^11.0.0` ＋ 內建 `fetch`，對真實的本機 MySQL 測試資料庫（`photo_album_test`） | backend 端點的 feature；各端點的請求與回應須符合 [contracts/openapi.yaml](../../truth/contracts/openapi.yaml) |
| 前端 BDD 測試 | `@cucumber/cucumber@^11.0.0` ＋ `playwright@^1.49.0`，`.feature` 使用 `# language: zh-TW` 關鍵字（假設／當／那麼）；無障礙掃描 `@axe-core/playwright@^4.10.0` | frontend 端點的 feature；主頁、相簿頁、燈箱、匯入對話框零嚴重違規 |
| 效能量測 | 自寫的 Node 腳本（以 `fetch` 量測 p95／p99）；Playwright 以 `PerformanceObserver` 量測 LCP／CLS | 10,000 張照片的種子資料 |

- **理由**：後端與前端端點的 feature 都由 Cucumber 直接執行，讓規格與測試一一對應，也只需維護一套步驟執行環境。
- **確定性**：每個測試前都會清空資料表；測試用照片 fixture（含／不含 EXIF、重複檔、非圖片檔）存放在 repo 內；
  不依賴外部網路。
- **考慮過的替代方案**：後端單元測試（node:test）與前端單元測試（vitest、jsdom）不對應端點資料夾，下游不會為它們產生 feature 與任務，因此不規劃；
  Jest 與 ESM 的整合較麻煩；`playwright-bdd` 綁定特定的 Playwright Test 版本；
  以 SQLite 取代 MySQL 執行測試，會造成行為落差，請求與回應無法準確驗證。

## R-16 設定、遷移與程式碼品質工具

- **對應需求**：跨領域
- **決策**：
  - 環境變數使用 Node 內建的 `--env-file=.env`（不使用 `dotenv`）。
  - 資料庫遷移：`backend/src/db/migrations/*.sql`，依檔名順序執行，搭配約 30 行的自寫腳本，並以 `schema_migrations` 表記錄已執行的版本（不使用 ORM）。
  - Lint／格式化：`eslint@^9.0.0`（flat config）＋ `prettier@^3.4.0`，在 repo 根目錄共用。
  - 專案管理：npm workspaces（`frontend`、`backend`、`e2e`），由 npm 內建提供。
  - 設計規範：`frontend/src/styles/tokens.css` 以 CSS 自訂屬性定義顏色、間距與字級；元件樣式只能引用這些代幣。
- **理由**：能用 Node／npm 內建功能的部分一律不引入套件；ESLint 與 Prettier 是唯一的品質工具相依，在根目錄共用以避免各 workspace 設定不一致。

## R-17 匯入中斷時的資料一致性

- **對應需求**：NFR-002、NFR-003、SC-008
- **決策**：
  1. 後端以 `busboy` 串流接收時，先寫入 `storage/tmp/<隨機 UUID>.part`，同時計算 SHA-256（見 R-08）；
     接收完整後才以 `fs.rename` 搬到 `originals/` 的正式路徑（見 R-04）。
  2. 檔案就位後，在單一交易中建立相簿（不存在時）並寫入 `photos` 資料列；交易失敗時刪除剛搬移的檔案。
  3. 後端啟動時清除 `storage/tmp/` 內殘留的 `.part` 檔，以及 `originals/` 內沒有對應資料列的孤兒檔案。
  4. 每個檔案各自一個請求、一個交易（見 R-10），單一檔案失敗只回應該檔案的錯誤。
- **理由**：同一檔案系統內的 `rename` 是原子操作，正式路徑不會出現寫到一半的檔案；資料列在檔案就位後才寫入，
  相簿中不會出現殘缺照片（NFR-002）。重新匯入同一批照片時，已完成的照片會被內容雜湊的唯一索引擋下，不會產生重複（SC-008）；
  每個檔案獨立交易，單張照片損毀不影響同批其他照片（NFR-003）。
- **考慮過的替代方案**：先寫資料列再寫檔案，中斷時資料列會指向不存在的檔案，因此不採用；
  整批照片包在同一個交易中，中斷時已完成的照片也會一併回滾，違反「已完成匯入的照片必須完整保留」。

## R-18 存取範圍

- **對應需求**：NFR-017、NFR-018、SC-009
- **決策**：後端預設只監聽 `127.0.0.1`（由 `.env` 的 `HOST` 設定，預設值 `127.0.0.1`），不提供帳號與登入。
  後端不對外發出任何網路請求；前端不載入任何外部 CDN 資源，字型與腳本都隨 Vite 建置打包。
- **理由**：規格假設本版本為單一使用者、不含帳號；只監聽本機回送位址時，其他裝置無法連到 API，
  照片庫只能由使用者本人存取（NFR-018）。沒有任何對外請求與外部資源，照片與中繼資料不會送到第三方（NFR-017、SC-009）。
- **已知限制**：要在行動裝置上使用（NFR-022）時，使用者必須自行把 `HOST` 改成區網位址，此時同一區網的裝置都能存取照片庫。
- **考慮過的替代方案**：加入帳號密碼登入，與規格假設「不含帳號」衝突，因此不採用；
  只依賴作業系統防火牆阻擋外部連線，結果取決於使用者的環境設定，無法保證 NFR-018。
