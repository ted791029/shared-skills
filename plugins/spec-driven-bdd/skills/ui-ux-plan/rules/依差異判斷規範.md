# 依差異判斷規範

## Rule 1 -- 沒有排進 Wave 時只判斷技術項與開發發現

**強度：MUST**

plan.md 沒有 UI 前綴的介面列（本 skill 沒有排進 Wave，呼叫參數的 Wave 為「無」）而 check 回報本 skill 待補跑時，不照串接規範「本 plan 沒有紀錄時照完整流程」的做法：前端沒有前置端點，只逐項判斷 `技術項.md` 中「修正：ui-ux-plan」的行與本 skill 引用的開發發現 AC（本 plan 沒有紀錄時，check 只以 `changed_artifacts` 列出變了的產物）。需要修改任何畫面時，本端點沒有可以承接的介面列，依 UI 分析規範回報 system-analysis，這次的結果是「不能改」；全部不受影響時記錄「不用改」，不建立 `ui/` 的產出。以下 Example 皆對照此情境：

```text
plan.md：只有 API、DB 前綴的介面列，Wave 中沒有前端
check：ui-ux-plan 待補跑、本 plan 沒有紀錄，變了的產物為 plan:技術項.md
技術項.md：
- dsl.md 擬定了連猜確認視窗取消鈕的 testid `triple-guess-cancel`，UI 契約沒有（dsl-refine；`specs/truth/features/frontend/dsl.md:110`；修正：ui-ux-plan）
```

### Good Example

這個範例只判斷點名本 skill 的一行，定位要寫進 UI 契約，但本 plan 沒有前端的介面列，回報 system-analysis 而不自行建立 UI 契約。

```text
技術項 → 連帶異動：取消鈕的定位要寫進 UI 契約的對戰畫面技能介面。
不能改：本 plan 的介面盤點沒有前端，UI 契約沒有可以寫入的介面。
交給：system-analysis 新增前端「對戰畫面技能介面（連猜確認視窗）」的 MOD 列（技術：補上 dsl.md 擬定的定位 triple-guess-cancel）並排入 Wave。
這次沒有建立 ui/、沒有記錄，ui-ux-plan 仍是待補跑。
```

### Bad Example

這個範例因為本 plan 沒有紀錄就照完整流程，依 spec.md 的需求自行推導前端介面並寫出 `ui/ui-contract.md`；這份 UI 契約沒有任何介面列作為依據，dsl-refine 與 task 卻會把它當成這次的 UI 契約讀取。

```text
ui-ux-plan 本 plan 沒有紀錄 → 完整流程：依 FR-001～FR-004 推導 UI-01～UI-03，撰寫 ui/ui-contract.md 與 3 個原型頁面。
```

## Rule 2 -- 技術修正 plan 以技術項指出的介面為範圍

**強度：MUST**

目標是技術修正 plan 時沒有 spec.md 與 plan.md，不讀取它們，也不以缺少介面列為由回報 system-analysis：`技術項.md` 中「修正：ui-ux-plan」的每一行指出的介面，就是這次異動為 MOD 的介面，在該 plan 的 `ui/ui-contract.md` 依 MOD 的寫法只寫這一行要修正的部分，原型只改對應的頁面，憲法照常逐條核對。修正需要改變 PM 看得到的行為（可見的文字、版面、操作或狀態的呈現）時不得修改，這一行的結果是「不能改」，回報需在有需求的 plan 處理。以下 Example 皆對照此技術修正 plan 的技術項：

```text
plan：005-dsl-cleanup（技術修正 plan）
- dsl.md 擬定了連猜確認視窗取消鈕的 testid `triple-guess-cancel`，UI 契約沒有（dsl-refine；`specs/truth/features/frontend/dsl.md:110`；修正：ui-ux-plan）
- UI 契約沒有寫連猜確認視窗中按 Tab 時焦點的順序（使用者；`specs/plans/002-battle-skills/ui/ui-contract.md` 的 UI-01；修正：ui-ux-plan）
```

### Good Example

這個範例只為取消鈕補上定位；焦點順序會改變使用者操作時看到的結果，判定為不能改。

```text
第一行 → 在 005 的 ui/ui-contract.md 寫 UI-01（MOD）一節：「文案與無障礙」寫「| 連猜取消鈕 | 取消（定位 `[data-testid="triple-guess-cancel"]`） |」與「沿用」列，game.html 的取消鈕加上相同的 testid；憲法核對通過。
第二行 → 不能改：決定焦點順序會改變使用者按 Tab 時看到的結果，技術修正 plan 不得改變 PM 看得到的行為，需在有需求的 plan 處理。
```

### Bad Example

這個範例兩行都照寫，在技術修正 plan 中替取消鈕訂了焦點順序；這是使用者看得到的行為，卻在沒有需求、PM 不會審核的 plan 中定案，交付的 commit 訊息寫「無（技術修正）」，之後追溯不到誰核准過。

```text
005 的 ui/ui-contract.md UI-01（MOD）：補上取消鈕的定位 triple-guess-cancel；鍵盤操作改為「Tab 依序經過確認鈕、取消鈕」。
```
