# 使用者故事切分規範

## Rule 1 -- 每個故事必須可獨立交付

**強度：MUST**

每個使用者故事必須在只完成它本身與優先順序更高的故事時，就能讓使用者完成一件有價值的事，並能寫出一個不依賴後續故事的獨立測試。不得把同一個使用流程的前後半段切成兩個故事，也不得切出只有技術工作、沒有使用者可感知結果的故事。

### Good Example

這個範例的每個故事都能單獨完成一件使用者在意的事，各自寫得出獨立測試。

```markdown
### 使用者故事 1 - 送出請假申請（優先順序：P1）
**獨立測試**：員工送出一筆特休申請，確認申請出現在「我的申請」且狀態為「待審核」。

### 使用者故事 2 - 主管審核請假申請（優先順序：P2）
**獨立測試**：主管核准一筆待審核申請，確認員工端狀態變為「已核准」。
```

### Bad Example

這個範例把同一個流程切成「填寫表單」與「送出表單」，故事 1 單獨完成時使用者什麼事也做不成，也寫不出不依賴故事 2 的獨立測試。

```markdown
### 使用者故事 1 - 填寫請假表單（優先順序：P1）
### 使用者故事 2 - 送出請假表單（優先順序：P2）
### 使用者故事 3 - 建立請假資料表（優先順序：P3）
```

## Rule 2 -- 優先順序必須依價值依賴排序

**強度：MUST**

被其他故事依賴的故事必須排在前面，相互獨立的故事再依使用者最常做的事排序。「為何此優先順序」必須寫出依賴關係或使用頻率，不得只重述故事很重要。

### Good Example

這個範例的優先順序理由寫出依賴關係，讀者能看出為何審核排在申請之後。

```markdown
**為何此優先順序**：審核的對象是員工送出的申請；沒有故事 1 的申請，審核功能沒有內容可操作。
```

### Bad Example

這個範例只說故事很重要，看不出它和其他故事的先後依據，實作時可能先做到依賴尚未存在的功能。

```markdown
**為何此優先順序**：審核是非常重要的核心功能，因此優先處理。
```

## Rule 3 -- 釐清新增的範圍必須成為故事

**強度：MUST**

釐清紀錄中使用者確認納入、但原始描述沒有提到的使用者行為，必須成為獨立的使用者故事，或併入既有故事的驗收情境與功能需求；確認不納入的，必須寫入「假設」作為範圍外項目。不得只出現在釐清紀錄而沒有落入規格本文。

### Good Example

這個範例把釐清時新增的「刪除照片」寫成獨立故事，確認不做的「跨相簿移動」寫入假設。

```markdown
- 問：使用者能否在應用程式中刪除照片？ → 答：可刪除，僅從應用程式移除。
- 問：能否手動將照片移到其他相簿？ → 答：不行。

### 使用者故事 4 - 從應用程式刪除照片（優先順序：P4）

## 假設
- 跨相簿移動照片不在本版本範圍。
```

### Bad Example

這個範例的釐清答案確認要能刪除照片，規格本文卻沒有任何故事或需求提到刪除，後續規劃只讀本文時會漏掉這個功能。

```markdown
- 問：使用者能否在應用程式中刪除照片？ → 答：可刪除，僅從應用程式移除。

### 使用者故事 1 - 匯入照片並依日期自動分組成相簿（優先順序：P1）
### 使用者故事 2 - 在相簿中以平鋪方式預覽照片（優先順序：P2）
### 使用者故事 3 - 在主頁面以拖放重新排列相簿（優先順序：P3）
```
