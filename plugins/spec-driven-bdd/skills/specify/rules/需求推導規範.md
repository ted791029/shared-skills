# 需求推導規範

## Rule 1 -- 驗收結果必須有需求對應

**強度：MUST**

每個驗收情境「那麼」所描述的系統結果，都必須能從規格中的一條或多條需求推導出來。需求指 FR 或 NFR，可寫在任一使用者故事或全域需求；成功標準（SC）不算需求。只與結果主題相關、但推導不出該結果的需求不算涵蓋。不得有任何情境的結果找不到涵蓋它的需求。

### Good Example

這個範例的每個情境結果都能從需求推導出來：情境 1 由故事 1 的 FR-007 與本故事的 FR-017 組合涵蓋，情境 2 由 FR-017 涵蓋，情境 3 由 FR-018 涵蓋，情境 4 由全域的 NFR-016 涵蓋。

```markdown
### 使用者故事 1 - 匯入照片並依日期自動分組成相簿（優先順序：P1）

- **FR-007**：主頁面**必須**列出所有相簿，每本相簿顯示名稱、照片數量與封面縮圖。

### 使用者故事 4 - 從應用程式刪除照片（優先順序：P4）

**驗收情境**：

1. **假設** 相簿含 5 張照片，**當** 使用者刪除其中 1 張，**那麼** 相簿只剩 4 張照片，主頁面該相簿的照片數量同步顯示為 4。
2. **假設** 使用者已刪除一張照片，**當** 檢查裝置上該照片的原始檔案，**那麼** 原始檔案的位置、檔名與內容皆未改變。
3. **假設** 相簿只剩 1 張照片，**當** 使用者刪除該照片，**那麼** 該相簿自動從主頁面移除。
4. **假設** 使用者已刪除一張照片，**當** 關閉並重新開啟應用程式，**那麼** 該照片不再出現。

**功能需求**：

- **FR-017**：使用者**必須**能從應用程式刪除照片；刪除僅將照片自應用程式移除，**不得**刪除或修改裝置上的原始檔案。
- **FR-018**：相簿內的照片全部被刪除時，系統**必須**自動移除該相簿。

## 全域需求

#### 可靠性與資料完整性

- **NFR-016**：應用程式重新啟動後，照片刪除結果**必須**與關閉前一致；已刪除的照片**不得**重新出現。
```

### Bad Example

這個範例的情境 2 要求可返回平鋪檢視，FR-011 雖然同樣講放大檢視，卻推導不出「返回平鋪檢視」，把主題相關誤當成涵蓋，實作者照 FR 開發時會漏掉返回操作，驗收時才發現情境不通過。

```markdown
### 使用者故事 2 - 在相簿中以平鋪方式預覽照片（優先順序：P2）

**驗收情境**：

1. **假設** 相簿含 50 張照片，**當** 使用者開啟該相簿，**那麼** 照片以統一尺寸的縮圖平鋪排列。
2. **假設** 使用者正在相簿頁面，**當** 點選任一縮圖，**那麼** 顯示該照片的放大檢視，並可返回平鋪檢視。

**功能需求**：

- **FR-010**：相簿頁面**必須**以大小一致的平鋪縮圖呈現照片。
- **FR-011**：使用者**必須**能點選縮圖放大檢視，並可切換上一張／下一張。
```

## Rule 2 -- 需求類型必須符合結果性質

**強度：MUST**

撰寫涵蓋驗收結果的需求時，結果描述系統「做什麼」（提供的操作、行為或資料變化）就寫成 FR；結果描述系統「做得多好」（效能、可靠性、無障礙等品質要求）就寫成 NFR，並標示所屬類別。

### Good Example

這個範例把「點選後放大檢視」這項操作寫成 FR，把「載入時版面不跳動」這項品質要求寫成效能類 NFR。

```markdown
**驗收情境**：

1. **假設** 使用者正在相簿頁面，**當** 點選任一縮圖，**那麼** 顯示該照片的放大檢視。
2. **假設** 縮圖尚在載入中，**當** 使用者開啟相簿，**那麼** 每個縮圖位置先顯示佔位載入狀態，版面不會因載入完成而跳動。

**功能需求**：

- **FR-011**：使用者**必須**能點選縮圖放大檢視。

**非功能性需求**：

- **NFR-006**（效能）：頁面載入與縮圖陸續出現的過程中，既有內容**不得**發生明顯跳動或位移。
```

### Bad Example

這個範例把「載入時版面不跳動」這項品質要求寫成 FR，NFR 類別判斷時會漏看這條效能要求，後續規劃也不會把它當成需要量測的品質目標。

```markdown
**驗收情境**：

1. **假設** 使用者正在相簿頁面，**當** 點選任一縮圖，**那麼** 顯示該照片的放大檢視。
2. **假設** 縮圖尚在載入中，**當** 使用者開啟相簿，**那麼** 每個縮圖位置先顯示佔位載入狀態，版面不會因載入完成而跳動。

**功能需求**：

- **FR-011**：使用者**必須**能點選縮圖放大檢視。
- **FR-012**：縮圖載入過程中，系統**不得**讓既有內容發生明顯跳動或位移。
```

## Rule 3 -- NFR 類別必須逐一判斷適用性

**強度：MUST**

必須逐一判斷每個使用者故事與全域的 NFR 類別（效能、容量、可靠性與資料完整性、安全與隱私、易用性與一致性、無障礙、相容性、可維護性與可測試性）是否適用。判斷依據為功能描述、釐清結果、驗收情境或邊界情況中出現的品質要求。適用的類別至少寫出一條 NFR；不適用的類別在全域刪除該類別的子標題，在故事內則不寫該類別的 NFR。故事內沒有任何專屬 NFR 時，刪除整個「**非功能性需求**：」段落。不得為了填滿樣板而寫出沒有依據的 NFR。

### Good Example

這個範例的內部記帳工具沒有容量與相容性的需求依據，因此刪除這兩個子標題；有依據的類別各寫出 NFR。

```markdown
### 非功能性需求

#### 效能

- **NFR-005**：月報表**必須**在 3 秒內產生完成。

#### 安全與隱私

- **NFR-006**：只有財務部成員**可以**檢視他人的報帳明細。
```

### Bad Example

這個範例為了填滿樣板，在沒有任何依據的容量與相容性類別湊出空泛的 NFR，審閱者無法分辨哪些是真實需求，後續規劃還會為假需求投入成本。

```markdown
### 非功能性需求

#### 效能

- **NFR-005**：月報表**必須**在 3 秒內產生完成。

#### 容量

- **NFR-006**：系統**必須**支援足夠的資料量。

#### 安全與隱私

- **NFR-007**：只有財務部成員**可以**檢視他人的報帳明細。

#### 相容性

- **NFR-008**：系統**必須**相容於主流環境。
```

## Rule 4 -- 需求必須放在所屬範圍

**強度：MUST**

只影響單一使用者故事的 FR、NFR 寫在該故事內；影響兩個以上故事或整個系統的寫在「全域需求」。同一項需求不得在兩處重複，需要時以編號引用。

### Good Example

這個範例把適用全部畫面的語系需求放在全域，只屬於拖放的需求放在故事 3。

```markdown
### 使用者故事 3 - 在主頁面以拖放重新排列相簿（優先順序：P3）
- **FR-013**：使用者**必須**能在主頁面透過拖放重新排列相簿順序。

## 全域需求
- **FR-020**：所有錯誤、空狀態與載入狀態的訊息**必須**以繁體中文呈現。
```

### Bad Example

這個範例把同一條語系需求重複寫在兩個故事內，日後修改其中一條時另一條容易被遺漏，兩處說法開始不一致。

```markdown
### 使用者故事 1 - 匯入照片並依日期自動分組成相簿（優先順序：P1）
- **FR-009**：匯入的錯誤訊息**必須**以繁體中文呈現。

### 使用者故事 2 - 在相簿中以平鋪方式預覽照片（優先順序：P2）
- **FR-012**：相簿頁面的錯誤訊息**必須**以繁體中文呈現。
```
