# 增量範圍判斷規範

## Rule 1 -- 只為本次需求涉及的產出物寫條款

**強度：MUST**

本次增量只能新增或修改使用者這次需求直接約束的產出物條款。其他產出物即使看起來也適用同類約束，或憲法目錄中尚未有任何條款，都不得順手補寫；判斷其他產出物也需要時，只在回報中列為建議，由使用者決定是否在下一次增量處理。

### Good Example

這個範例的需求只約束 API 錯誤回應，只修改契約的條款檔，儲存契約的同類問題列為建議。

```markdown
需求：API 的錯誤回應要有業務錯誤代碼，前端才能分流。
涉及產出物：specs/truth/contracts/ → skills/api-plan/contracts.md
建議（未執行）：specs/truth/storage/storage-contract.md 的錯誤情境也可能需要代碼，待使用者決定。
```

### Bad Example

這個範例把需求擴大到每一份產出物，一次產出四份條款檔，使用者沒要求的約束被寫進憲法，下游 skill 開始受未經同意的條款約束。

```markdown
需求：API 的錯誤回應要有業務錯誤代碼，前端才能分流。
涉及產出物：specs/truth/contracts/、ui/ui-contract.md、specs/truth/storage/storage-contract.md、spec.md
```

## Rule 2 -- 需求必須落到具體作用位置

**強度：MUST**

只有能指出「哪一份產出物的哪一個區塊或欄位、要寫成什麼樣子」的需求才能寫成條款。需求只表達方向（如「寫清楚一點」、「品質要好」），或對應不到具體位置時，屬於待釐清的缺口，必須交給 clarify 訪談，不得自行推測位置與內容。

### Good Example

這個範例的需求只有方向，因此列為缺口交給 clarify，條款內容等使用者拍板後才寫。

```markdown
需求：規格書要寫清楚一點。
判斷：無法對應到 spec.md 的具體區塊 → 缺口，交 clarify 確認要約束的區塊與標準。
```

### Bad Example

這個範例自行把方向推測成三條具體要求，使用者真正在意的可能是驗收情境，寫出的條款卻約束了別的區塊。

```markdown
需求：規格書要寫清楚一點。
條款：C-SPEC-03 每條 FR 不超過 50 字；C-SPEC-04 必須附名詞表；C-SPEC-05 禁用「等」字。
```

## Rule 3 -- 重複或衝突時修改既有條款

**強度：MUST**

新需求與既有條款約束同一作用位置時，必須直接修改既有條款，或在需求已被完全涵蓋時告知使用者不需異動；不得另寫一條與既有條款重複，或寫明「優先於」既有條款的新條款。新需求與既有條款相牴觸時，必須先交給 clarify 確認要取代既有條款還是放棄新需求。

### Good Example

這個範例的新需求和 C-SPEC-02 作用在同一位置，因此改寫 C-SPEC-02，不新增條款。

```markdown
需求：回應時間要寫 P99，不是 P95。
既有：C-SPEC-02 要求寫 P95 或 P99
處理：修改 C-SPEC-02，限定只能寫 P99。
```

### Bad Example

這個範例另寫一條新條款覆蓋 C-SPEC-02，下游 skill 讀到兩條互相矛盾的要求，必須自行猜測哪一條優先。

```markdown
需求：回應時間要寫 P99，不是 P95。
新增：C-SPEC-03 回應時間只能寫 P99，優先於 C-SPEC-02。
```

## Rule 4 -- 流程需求不寫入憲法

**強度：MUST**

憲法只約束產出物的內容與格式。需求要求改變 skill 的步驟、執行順序、委派對象或互動方式（如「specify 前要先做競品分析」）時，不得寫成條款，必須告知使用者這屬於修改 skill 本身，建議使用者改用 skill-engineering skill（可由 skill-workshop plugin 提供，或為與本 skill 資料夾同層的 `skill-engineering` 資料夾）。

### Good Example

這個範例辨識出需求在改變流程，因此不寫條款，並指出負責的 skill。

```markdown
需求：technical-research 每次都要先問我預算。
判斷：改變 skill 的訪談流程，不是產出物內容 → 不寫入憲法，建議以 skill-engineering 修改 technical-research。
```

### Bad Example

這個範例把流程需求硬寫成 research.md 的條款，條款的作用位置對不到任何產出內容，下游 skill 無從核對，流程也沒有真的改變。

```markdown
## C-TR-03 -- 研究前必須詢問預算

**作用位置**：research.md 全文
```
