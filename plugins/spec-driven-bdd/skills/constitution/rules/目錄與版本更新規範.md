# 目錄與版本更新規範

## Rule 1 -- 版本號依異動類型升級

**強度：MUST**

版本號格式為 `主版號.次版號.修訂號`，首次建立憲法為 `1.0.0`。之後每次增量依本次最大的異動類型升級一次，升級後較低位數歸零：

| 異動類型 | 升級 |
|---|---|
| 刪除條款，或修改條款使原本符合的產出物變成違反 | 主版號 |
| 新增條款或共通條款引用 | 次版號 |
| 只修改措辭、Example 或連結，不改變條款要求 | 修訂號 |

### Good Example

這個範例同時新增 C-DATA-01 並修改 C-API-01 的措辭，依最大的異動類型只升一次次版號。

```markdown
**版本**：1.2.0 ｜ **最後修訂**：2026-10-25
```

### Bad Example

這個範例新增條款卻只升修訂號，讀者以為只是措辭調整，不會去檢查既有產出物是否需要補上新條款要求的內容。

```markdown
**版本**：1.1.1 ｜ **最後修訂**：2026-10-25
```

## Rule 2 -- 每次增量只新增一列修訂紀錄

**強度：MUST**

每次增量在修訂紀錄末尾新增一列，涵蓋本次所有異動，不得改寫既有列。「異動條款」以「新增」、「修改」、「刪除」開頭列出條款 ID；「起因需求」寫使用者這次遇到的問題，取自使用者的需求原文或訪談的回答，不得自行推測，也不得只重述條款標題。

### Good Example

這個範例的起因需求寫出使用者在訪談中說的問題，讀者日後能判斷這條條款是否仍有必要。

```markdown
| 1.2.0 | 2026-10-25 | 新增 C-DATA-01、C-DATA-02、C-SH-01；C-API 引用 C-SH-01 | API 欄位與資料表欄位各自取名，後端實作時要另外記對應關係。 |
```

### Bad Example

這個範例的起因需求只重述條款標題，看不出當初要解決什麼問題，條款是否還需要保留無從判斷。

```markdown
| 1.2.0 | 2026-10-25 | 新增 C-DATA-01、C-DATA-02、C-SH-01 | 每張表要有建立與更新時間、主鍵用 UUID、欄位命名風格。 |
```

## Rule 3 -- 目錄只列有條款檔的產出物

**強度：MUST**

目錄只列出已有條款檔的產出物，不得為尚未訂立條款的產出物預留空列。刪除某產出物的最後一條條款且沒有引用任何共通條款時，必須同時刪除該條款檔與目錄列；共通條款不再被任何產出物引用時，刪除該條款與共通條款表的對應列。

### Good Example

這個範例只訂過 spec.md 的條款，目錄只有一列。

```markdown
| 產出物 | 憲法檔 | 條款 | 引用共通條款 |
| --- | --- | --- | --- |
| spec.md | [skills/specify/spec.md](skills/specify/spec.md) | C-SPEC-01、C-SPEC-02 | — |
```

### Bad Example

這個範例為未訂條款的產出物預留空列，連結指向不存在的檔案，下游 skill 依目錄載入時會讀檔失敗。

```markdown
| 產出物 | 憲法檔 | 條款 | 引用共通條款 |
| --- | --- | --- | --- |
| spec.md | [skills/specify/spec.md](skills/specify/spec.md) | C-SPEC-01、C-SPEC-02 | — |
| plan.md | [skills/system-analysis/plan.md](skills/system-analysis/plan.md) | — | — |
```
