# 憲法套用規範

## Rule 1 -- 依目錄載入產出物的憲法檔

**強度：MUST**

撰寫、寫回或檢查產出物前，必須讀取 `.claude/constitution/CONSTITUTION.md`，在「目錄」表以「產出物」欄找出本次寫入的產出物（產出物以 `/` 結尾時是資料夾，寫入其中任何檔案都屬於該產出物），讀取該列「憲法檔」欄的檔案。只套用本次寫入的產出物所屬的憲法檔，不得套用其他產出物的條款；`CONSTITUTION.md` 不存在或目錄沒有該產出物時，沿用 skill 內建規範。不得依記憶或舊對話中的條款撰寫，每次都必須重新讀取。

### Good Example

這個範例在 clarify-over-specs 寫回 spec.md 時，依「產出物」欄找到 specify 的憲法檔，即使寫入的 skill 不是 specify 也照樣載入。

```markdown
寫入產出物：spec.md
目錄列：| spec.md | skills/specify/spec.md | C-SPEC-01、C-SPEC-02 | — |
載入：.claude/constitution/skills/specify/spec.md
```

### Bad Example

這個範例依寫入的 skill 名稱找 `skills/clarify-over-specs/`，找不到就沿用內建規範，寫回時刪除了無障礙一節，違反 C-SPEC-01 卻沒有被發現。

```markdown
寫入產出物：spec.md
尋找：.claude/constitution/skills/clarify-over-specs/ → 不存在
載入：無，沿用內建規範
```

## Rule 2 -- 共通條款只在被引用時生效

**強度：MUST**

除了產出物的憲法檔，必須再讀取該列「引用共通條款」欄列出的每個共通條款；欄位為「—」時不讀取 `shared/`。不得把未被引用的共通條款套用到產出物。

### Good Example

這個範例撰寫契約的路徑檔時，依所屬的資料夾找到目錄列，再依「引用共通條款」欄另外載入 C-SH-01。

```markdown
寫入：specs/truth/contracts/paths/相簿/api_albums.yaml
目錄列：| specs/truth/contracts/ | skills/api-plan/contracts.md | C-API-01、C-API-02 | C-SH-01 |
載入：skills/api-plan/contracts.md、shared/欄位命名風格.md
```

### Bad Example

這個範例撰寫儲存契約時也套用 C-SH-01，把命名規則表中的 `content_hash` 改成 `contentHash`，與資料模型的欄位對不上。

```markdown
寫入：specs/truth/storage/storage-contract.md
目錄列：| specs/truth/storage/storage-contract.md | skills/storage-plan/storage-contract.md | C-FS-01、C-FS-02 | — |
載入：skills/storage-plan/storage-contract.md、shared/欄位命名風格.md
```

## Rule 3 -- 憲法條款優先於內建規範

**強度：MUST**

條款與 skill 內建的 Rule、樣板或範例衝突時，以條款為準：條款的「覆寫對象」列出的 Rule 不再適用於條款涵蓋的範圍；「覆寫對象」為「無（增補）」時，條款要求的內容照樣寫入，樣板沒有的段落或列依條款補上，範例與條款不一致時不得照抄範例。條款強度依 MUST、SHOULD、MAY 的語意執行。

### Good Example

這個範例的 C-UI-01 為增補，樣板的狀態表只有四列，仍依條款加上「離線」列。

```markdown
### 狀態

| 狀態 | 呈現 |
|---|---|
| 成功 | 顯示房間成員與目前回合。 |
| 載入 | 顯示「正在載入房間…」。 |
| 空狀態 | 只有自己在房間時顯示「等待對手加入」。 |
| 錯誤 | 顯示錯誤訊息與「重新整理」按鈕。 |
| 離線 | 頂部顯示「連線中斷，正在重新連線…」；猜測按鈕停用。恢復連線後重新取得房間狀態並移除提示。 |
```

### Bad Example

這個範例因為樣板與範例都只有四種狀態就照抄，C-UI-01 要求的離線狀態沒有寫入，網路中斷時畫面的行為沒有定義。

```markdown
### 狀態

| 狀態 | 呈現 |
|---|---|
| 成功 | 顯示房間成員與目前回合。 |
| 載入 | 顯示「正在載入房間…」。 |
| 空狀態 | 只有自己在房間時顯示「等待對手加入」。 |
| 錯誤 | 顯示錯誤訊息與「重新整理」按鈕。 |
```

## Rule 4 -- 檢查腳本的錯誤不得推翻條款

**強度：MUST**

檢查腳本回報的問題，若照腳本修正會違反已載入的條款，必須保留符合條款的內容，並在回報中列出該問題、對應的條款編號與保留理由；其餘問題照常修正。

### Good Example

這個範例保留依 C-TR-02 收斂的版本，並在回報中說明腳本錯誤的來源。

```markdown
check_techstack.py 回報 `vite` 版本 ~8.0.0 與 research.md 的 ^8.0.0 不一致：
依 C-TR-02 保留 ~8.0.0，研究紀錄欄已加註「（版本依 C-TR-02 收斂）」。
```

### Bad Example

這個範例照腳本訊息把版本改回 `^8.0.0`，產出物重新違反 C-TR-02，各成員安裝時又可能拿到不同的次版號。

```markdown
check_techstack.py 回報 `vite` 版本 ~8.0.0 與 research.md 的 ^8.0.0 不一致：
已改為 ^8.0.0。
```

## Rule 5 -- 寫入後逐條核對整份產出物

**強度：MUST**

寫入產出物後，必須依已載入的每條條款逐一核對：先核對「作用位置」是否寫入條款要求的內容，再以條款描述中「不得」「一律」等禁止或限定的寫法掃描整份產出物，作用位置以外出現的違反同樣算違反。產出物是 truth 的資料夾時，只核對這個 plan 新增與修改的檔案，每份都整份核對，包括檔案中先前 plan 留下的內容；這個 plan 沒有動到的檔案不核對。違反 MUST 條款時直接修正，修正會違反 PM 核准的需求時依 Rule 7 處理；偏離 SHOULD 條款時，必須依該條款描述寫明的方式在產出物留下說明。不得只寫出整體結論而不逐條核對，也不得因違反出現在作用位置以外而判定通過。

### Good Example

這個範例只核對這個 plan 修改的兩份檔案，核對完作用位置後，再以 C-DATA-01「不得設計成物理刪除」掃描這兩份檔案的全文，抓到作用位置以外的 `Ref` 與表 Note。

```markdown
- 核對範圍：這個 plan 修改的 data-model.dbml 與 相簿.dbml；沒有動到的 標籤.dbml 不核對。
- C-DATA-01（`*.dbml › Table.*` 欄位）：albums、photos 皆含 created_at、updated_at、updated_by、soft_deleted_at。
- C-DATA-01（`data-model.dbml › ## 交易邊界`）：刪除照片改為更新 photos.soft_deleted_at。
- C-DATA-01 禁止事項「不得設計成物理刪除」掃描兩份檔案的全文：
  - `Ref fk_photos_album_id ... [delete: cascade]` 違反 → 移除 cascade，刪除相簿交易改為先軟刪除該相簿的 photos。
  - photos 的 Note「相簿刪除時連帶刪除」違反 → 改寫為軟刪除。
```

### Bad Example

這個範例只核對作用位置就判定通過，`Ref` 上的 cascade 與表 Note 的連帶刪除都不在作用位置內而被放過，實作後刪除相簿會物理刪除照片列，違反條款卻沒有被發現。

```markdown
- C-DATA-01（`*.dbml › Table.*` 欄位）：四個欄位齊全。
- C-DATA-01（`data-model.dbml › ## 交易邊界`）：刪除照片改為軟刪除。
→ 符合所有條款。
```

## Rule 6 -- 憲法條款優先於輸入文件

**強度：MUST**

條款與本次寫入產出物以外的輸入文件衝突時，以條款為準；輸入文件指本次讀取的上游產物，如 plan.md、`specs/truth/techstack.md`，本 plan 中 PM 核准的需求不屬於本條，與它衝突時依 Rule 7 處理。產出物必須照條款撰寫，不得以輸入文件的決策或「沿用既有」為由保留違反條款的內容：truth 的檔案在 Rule 5 的核對範圍內時，檔案中先前 plan 留下的內容違反條款，本次必須改成符合條款的內容。這項改正依 Rule 3 優先於產出 skill「只增修盤點列出的對象」一類的規範，並和其他異動一樣記入 truth-changes.md：對象這次沒有其他異動時，原因寫「技術：依憲法 <條款 ID> 改正」；已有其他異動時，在那一列的改動摘要寫出依憲法改正的部分。改正會改變 PM 看得到的行為時，不得以技術理由記錄，必須交給 dev-finding 以 record 記成開發發現的 AC，該列的原因寫上這個 AC 編號；dev-finding 回覆要改以有需求的 plan 處理時，這項改正不寫入，依 Rule 8 回報「不能改」後不記錄並停止。先前 plan 資料夾中的檔案是歷史紀錄，不得修改。

### Good Example

這個範例的 plan.md 寫「相簿列表不變」，這個 plan 在 `paths/相簿/api_albums.yaml` 新增建立相簿的操作，同一份檔案中 001 留下的列表操作沒有分頁參數，本次依 C-API-01 補上；相簿頁會因此改成分頁顯示，PM 看得到差異，所以交給 dev-finding 記成 AC-15，truth-changes.md 在這份檔案的一列寫出依憲法補上的部分，原因帶上 AC-15。

```yaml
get:
  summary: 列出相簿
  parameters:
    - $ref: ../../components/parameters/Page.yaml
    - $ref: ../../components/parameters/PageSize.yaml
post:
  summary: 建立相簿
```

```markdown
| 異動 | 對象 | 改動摘要 | 原因 |
|---|---|---|---|
| MOD | `contracts/paths/相簿/api_albums.yaml` | 新增建立相簿的操作；依憲法 C-API-01 為列表操作補上 Page、PageSize 參數 | FR-002、AC-15 |
```

### Bad Example

這個範例以 plan.md 的決策為由保留 001 留下的列表操作，列表沒有分頁參數，實作照此文件仍違反 C-API-01。

```yaml
get:
  summary: 列出相簿（依 plan.md 不變）
post:
  summary: 建立相簿
```

## Rule 7 -- 與 PM 核准的需求衝突時回報不能改

**強度：MUST**

PM 核准的需求指本 plan 的 acceptance 中的 AC 與 spec.md 中的 FR、NFR。條款與這些需求衝突時，必須先判斷兩者能否都符合：照條款撰寫後，需求要的行為完全不變（包括 PM 看得到的結果），就照條款撰寫，依 Rule 8 回報；照條款撰寫就會改變需求要的行為，或拿不準時，不得自行擇一，既不得照條款改掉需求要的行為，也不得照需求寫出違反條款的內容。此時衝突的部分不寫入產出物（既有的內容維持原狀），其餘部分照常撰寫，這次的結果是「不能改」：依 Rule 8 回報後不記錄並停止，交給 PM 決定修改需求，或由使用者修訂條款。不得把衝突記下後繼續，也不得自行修改需求來化解衝突。

### Good Example

這個範例逐條判斷需求能否與 C-DATA-01 都符合：FR-009 改成軟刪除後使用者看到的結果不變，照條款撰寫；FR-010 照條款就一定違反，於是不寫入衝突的交易，回報不能改並停止，交給 PM 或使用者決定。

```markdown
- FR-009「刪除相簿後，相簿從列表消失且無法復原」與 C-DATA-01「不得設計成物理刪除」：刪除改為更新 albums.soft_deleted_at，所有查詢排除已刪除的相簿，使用者看到的結果與 FR-009 相同 → 照條款撰寫
- FR-010「刪除帳號時永久清除該使用者的照片與個人資料」與 C-DATA-01：照條款只能軟刪除，資料仍留在資料庫，FR-010 一定被違反 → 「刪除帳號」交易不寫入，其餘照常撰寫
- 結果：不能改。不記錄並停止，交給 PM 決定修改 FR-010，或由使用者修訂 C-DATA-01
```

### Bad Example

這個範例自行照條款改掉 PM 核准的 FR-010，記下衝突就繼續並記錄改了，data-plan 不再是待補跑，PM 沒有機會決定要改需求還是修訂條款，交付後刪除帳號仍會留下個人資料。

```markdown
- FR-010「刪除帳號時永久清除該使用者的照片與個人資料」與 C-DATA-01 衝突 → 「刪除帳號」交易依條款改為軟刪除 → clarify-over-specs 修正 FR-010
- 繼續撰寫 data-migration.md。結果：改了
```

## Rule 8 -- 衝突必須逐項回報

**強度：MUST**

依 Rule 6、Rule 7 處理的每項衝突，都必須在回報中逐項列出：文件與位置、衝突內容、條款編號、產出物的處理與後續處理。後續處理對上游產物寫出應修正它的 skill，對先前 plan 留下的 truth 內容寫出本 plan 實作需調整的既有實作；結果是「不能改」的衝突，寫出交給 PM 修改的需求或由使用者修訂的條款，並寫明這次沒有記錄、本 skill 仍是待補跑。不得只寫「已依憲法修正」而不列出位置，也不得把不能改的衝突寫成已處理。

### Good Example

這個範例逐項列出衝突，讀者能直接知道要回頭修正哪個 skill、實作要動到哪些既有程式，以及哪一項要等 PM 或使用者決定。

```markdown
- research.md R-03：「刪除相簿以 FK CASCADE 連帶刪除照片」與 C-DATA-01 衝突 → photos 外鍵改 restrict，刪除相簿改為軟刪除 → technical-research 修正 R-03
- plan.md「結構決策」：「albums 表不變」與 C-DATA-01 衝突 → albums 補上四個生命週期欄位 → system-analysis 修正結構決策
- specs/truth/data/相簿.dbml 的 albums 表（001 留下）：缺 updated_by、soft_deleted_at，與 C-DATA-01 衝突 → 本次已在相簿.dbml 補齊 → 本 plan 實作需新增遷移補齊既有表
- spec.md FR-010：「刪除帳號時永久清除該使用者的照片與個人資料」與 C-DATA-01 衝突，照條款一定違反 → 「刪除帳號」交易未寫入 → 不能改：交給 PM 決定修改 FR-010，或由使用者修訂 C-DATA-01；這次沒有記錄，data-plan 仍是待補跑
```

### Bad Example

這個範例只寫結論，讀者不知道哪份上游文件與條款衝突，plan.md 與 research.md 維持錯誤寫法，後續任務拆解照舊漏掉遷移。

```markdown
- 已依 C-DATA-01 修正資料模型。
```

## Rule 9 -- 要上游修正的後續處理必須記成技術項

**強度：MUST**

後續處理要由其他擁有者修正上游產物時（例如 technical-research 修正 research.md、system-analysis 修正 plan.md），除了依 Rule 8 寫在回報中，還必須委派 dev-finding 以 record 記成技術項，並寫上「修正：<該擁有者>」，讓 plan-package 把該擁有者列為待補跑。不得只寫在回報或 wave-report.md 的後續處理中。上游產物的修正會改變 PM 看得到的行為時，依 Rule 6 記成開發發現的 AC。

### Good Example

這個範例把 research.md 要修正的部分記成技術項並點名 technical-research，對話中斷後它仍是待補跑，交付前一定會被處理。

```markdown
- research.md 的 R-03「刪除相簿以 FK CASCADE 連帶刪除照片」與 C-DATA-01 衝突，資料模型已改為軟刪除（data-plan；`research.md` 的 R-03 與 C-DATA-01；修正：technical-research）
```

### Bad Example

這個範例只把後續處理寫在 wave-report.md，對話中斷後沒有任何擁有者是待補跑，交付時 research.md 的 R-03 仍寫著 FK CASCADE，下一個 plan 讀到的是與資料模型矛盾的決策。

```markdown
| 資料庫端 | research.md R-03 | 刪除相簿以 FK CASCADE 連帶刪除照片 | C-DATA-01 | 資料模型改為軟刪除 | technical-research 修正 R-03 |
```
