# 條款撰寫規範

## Rule 1 -- 作用位置必須對到產出物樣板

**強度：MUST**

作用位置必須使用產出 skill 樣板中實際存在的標題、表格或欄位路徑：Markdown 產出物以 `›` 串接各層標題，結構化格式（YAML、DBML、HTML）以該格式的路徑或選擇器表示；產出物是資料夾時，先寫資料夾中的檔案（多個檔案以 `*` 表示），再以 `›` 接檔案內的位置。條款要求的內容分布在多個位置時，每個位置都依前述寫法寫出，以「、」串接在同一行，不得只寫其中一個；共通條款每個受約束的產出物一行，同一產出物的多個位置同樣以「、」串接。樣板中沒有的位置不得寫成作用位置；條款要求新增樣板沒有的段落或列時，作用位置寫其所屬的上層區塊。

### Good Example

這個範例的 spec.md 條款使用 specify 樣板中的兩層標題；契約的條款要求列表操作的回應與參數，兩個位置各自先寫路徑檔，再接 api-plan 路徑檔樣板中的欄位路徑，以「、」串接在同一行；共通條款每個受約束的產出物一行，契約的兩個位置同樣以「、」串接。下游 skill 都可以直接定位每個要核對的位置。

```markdown
**作用位置**：`## 成功標準 › ### 可量測成果`
```

```markdown
**作用位置**：`paths/*/*.yaml › *.responses.2XX.content.application/json.schema`、`paths/*/*.yaml › *.parameters`
```

```markdown
**作用位置**：
- `specs/truth/contracts/components/schemas/*.yaml › properties`、`specs/truth/contracts/paths/*/*.yaml › *.parameters[*].name`
- `specs/truth/data/*.dbml › Table.*` 的欄位名稱
```

### Bad Example

這個範例寫了樣板中不存在的「效能需求」標題，契約的位置寫成合併後文件的路徑，下游 skill 在 spec.md 與拆開的契約檔案中都找不到這些位置；要求列表操作回應與參數的條款只寫了回應的位置，下游 skill 只核對回應，列表操作少了分頁參數也不會被要求補上。

```markdown
**作用位置**：`## 效能需求`
```

```markdown
**作用位置**：`components.schemas.Error`
```

```markdown
**作用位置**：`paths/*/*.yaml › *.responses.2XX.content.application/json.schema`
```

## Rule 2 -- 覆寫對象依能否同時遵守判定

**強度：MUST**

撰寫前必須讀取產出 skill 中約束同一作用位置的 Rule，逐條判斷能否與條款同時遵守。在條款涵蓋的範圍內，只要有照條款撰寫就無法遵守某條 Rule 的情況，該 Rule 就是覆寫對象：「覆寫對象」寫成 `<產出 skill> 的「<RuleFile 標題>」Rule <編號>`，有多條時全部列出，以「、」串接；不得寫成連結，skill 可能由 plugin 安裝在專案外，從條款檔連不到 RuleFile。條款只增加內建 Rule 沒有的要求、只在內建 Rule 允許的寫法中限定一種，或只與樣板、範例不一致時，都能與內建 Rule 同時遵守，寫 `無（增補）`。不得把能同時遵守的 Rule 列為覆寫對象：列出的 Rule 在條款涵蓋的範圍內整條不再適用，它其餘的要求會跟著失效。

### Good Example

這個範例的 C-TR-02 禁止 `^` 範圍，技術堆疊撰寫規範 Rule 4 要求版本照抄 research.md，引用的 research.md 寫 `^8.0.0` 時兩者無法同時遵守，因此寫出產出 skill、RuleFile 標題與 Rule 編號；C-API-02 只要求 Error 另含 `code` 並列舉代碼，與 API 分析規範 Rule 3 對錯誤結構與訊息的要求能同時遵守，因此寫增補。

```markdown
**覆寫對象**：technical-research 的「技術堆疊撰寫規範」Rule 4
```

```markdown
**覆寫對象**：無（增補）
```

### Bad Example

這個範例的 C-TR-02 與 Rule 4 無法同時遵守卻寫增補，下游 skill 同時讀到兩個相反的要求，可能照內建 Rule 寫出違反憲法的版本範圍；C-API-02 能與 API 分析規範 Rule 3 同時遵守，卻把 Rule 3 列為覆寫對象，下游 skill 對 `components/schemas/Error.yaml` 不再套用 Rule 3，錯誤訊息的語言、寫法與以 `examples` 列出代表性訊息的要求跟著失效。

```markdown
**覆寫對象**：無（增補）
```

```markdown
**覆寫對象**：api-plan 的「API 分析規範」Rule 3
```

## Rule 3 -- 引用共通條款行依引用數量撰寫

**強度：MUST**

產出物條款檔沒有引用任何共通條款時，刪除整行「引用共通條款」，不得寫成「無」或「—」；引用多條時，各條連結以「、」串接在同一行。

### Good Example

這個範例引用兩條共通條款，以「、」串接兩個連結。

```markdown
**引用共通條款**：[C-SH-01 欄位命名風格](../../shared/欄位命名風格.md)、[C-SH-02 時間格式](../../shared/時間格式.md)
```

### Bad Example

這個範例沒有引用共通條款卻保留該行並寫「無」，檢查腳本會把「無」與目錄的「—」判為不一致，讀者也要多讀一行無效資訊。

```markdown
**引用共通條款**：無
```

## Rule 4 -- 強度依是否允許例外決定

**強度：MUST**

使用者要求的約束沒有例外時標 `MUST`；使用者同意在特定情況下可以偏離時標 `SHOULD`，並在條款描述寫出偏離時必須在產出物留下的說明。強度必須取自使用者的回答，使用者未表態時交給 clarify 確認，不得自行降為 `SHOULD`。

### Good Example

這個範例的使用者同意特殊頁面可以自訂斷點，因此標 SHOULD，並寫出偏離時要留下註解。

```markdown
**強度：SHOULD**

寬度類的 media query 只使用 `max-width: 600px` 與 `max-width: 1024px`；其他寬度需要特別處理時，在原型旁註解原因。
```

### Bad Example

這個範例標了 SHOULD 卻沒有寫偏離時要做什麼，下游 skill 可以任意改用其他斷點而不留痕跡，SHOULD 實際上變成 MAY。

```markdown
**強度：SHOULD**

寬度類的 media query 只使用 `max-width: 600px` 與 `max-width: 1024px`。
```

## Rule 5 -- 條款描述必須可在產出物中核對

**強度：MUST**

條款描述必須寫出可在產出物中逐項核對的要求，例如必填的名稱、數值門檻、格式或必須出現的列；不得只寫「清楚」、「友善」、「合理」等無法核對的形容詞。

### Good Example

這個範例寫出百分位數、門檻與單位三項可核對的要求，驗收時能直接比對。

```markdown
描述等待或回應時間的 SC，必須寫出百分位數（P95 或 P99）、門檻數值與單位，不得只寫平均值或「很快」。
```

### Bad Example

這個範例只寫形容詞，下游 skill 寫出「平均 1 秒」也能宣稱符合，條款無法被核對。

```markdown
成功標準中的回應時間必須合理且明確。
```

## Rule 6 -- Example 必須是產出物的片段

**強度：MUST**

Good Example 與 Bad Example 的 code block 必須是該產出物本身格式的片段，語言標示使用產出物的格式（如 `markdown`、`yaml`、`dbml`、`css`），內容取自本專案的實際情境。Bad Example 只能違反本條款，說明句必須寫出違反造成的後果。

### Good Example

這個範例以 `components/schemas/Error.yaml` 的 YAML 片段示範，下游 skill 可以直接比對自己的產出。

```yaml
type: object
required: [code, message]
```

### Bad Example

這個範例以文字敘述代替產出物片段，下游 skill 無法看出條款要求的實際寫法。

```text
Error schema 要有 code 和 message 兩個必填欄位。
```
