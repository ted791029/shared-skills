# 全端點驗證規範

## Rule 1 -- 端點清單取自用語表，完整指令依測試設定

**強度：MUST**

verify 的端點清單必須是 `specs/truth/features/用語表.md`「端點」表登記的端點資料夾，不得寫死端點名稱，也不得略過任何已登記的端點資料夾。每個端點資料夾的完整指令必須依「哪個專案測試設定涵蓋這個資料夾的 feature」決定，寫成該設定不帶範疇路徑、涵蓋整個端點資料夾的執行方式；不得依資料夾名稱或結構寫特例。多個端點資料夾由同一個測試設定涵蓋（完整指令相同）時只執行一次。沒有任何測試設定涵蓋某個端點資料夾的 feature 時，依範疇與執行規範的就緒標準視為測試設定未就緒。

### Good Example

這個範例從用語表的「端點」表得到五個端點資料夾，逐一找出涵蓋它的測試設定，歸併成四個完整指令。

```text
端點資料夾：frontend、frontend/e2e、frontend/component、backend、database
backend → behave_runner.py suite=api 收集 specs/truth/features/backend → cd backend && uv run --no-sync python -m behave -D suite=api
database → suite=database 收集 specs/truth/features/database → cd backend && uv run --no-sync python -m behave -D suite=database
frontend、frontend/e2e → playwright.config.js features 涵蓋兩者 → cd frontend && npm run test:e2e（執行一次）
frontend/component → vitest.config.js include tests/component/**/*.steps.js 讀取 specs/truth/features/frontend/component → cd frontend && npm run test:component
```

### Bad Example

這個範例依資料夾名稱寫特例，認定「名為 frontend 的資料夾一律用 Playwright」，把 `frontend/component` 也排進 Playwright 指令；Playwright 設定沒有收集它，元件測試從未執行，被改壞時 verify 仍回報沒有回歸。

```text
規則：資料夾以 frontend 開頭 → cd frontend && npm run test:e2e
frontend/component → npm run test:e2e
```

## Rule 2 -- 所有端點就緒才開始執行

**強度：MUST**

執行任何完整指令前，必須依範疇與執行規範的就緒標準確認每個端點的測試環境（套件已安裝、需要的服務可連線或可由測試設定啟動）與測試設定（有測試設定涵蓋該端點資料夾的 feature 且載入 step 目錄）都就緒。任一端點未就緒時必須停下，不得先執行已就緒的端點，也不得在未就緒的情況下照常執行。red、green、refactor 開始時同樣依本規則確認所有端點，因為階段開始可能要以完整指令建立基準（`specs/truth/features/.verify-result.json` 不存在時），任務驗證也會執行其中的 behave 端點。

### Good Example

這個範例在執行前逐一確認四個完整指令需要的套件、服務與測試設定，全部就緒才開始。

```text
behave：cd backend && uv run --no-sync python -m behave --version → 1.3.3；MySQL 127.0.0.1:3307 可連線；suite=api、suite=database 各自載入 tests/api/steps、tests/database/steps
playwright：cd frontend && npx --no-install playwright --version → 1.65.0；chromium 已安裝；後端由 tests/e2e/support/server.js 啟動，port 8000 未被占用；steps 載入 tests/e2e/steps/**/*.js
vitest：cd frontend && npx --no-install vitest --version → 5.1.0（jsdom，不需服務）；include 的 *.steps.js 讀取 specs/truth/features/frontend/component
→ 全部就緒，開始依序執行
```

### Bad Example

這個範例在 MySQL 沒有啟動時照常執行，backend 與 database 的 Example 全部因連線失敗而失敗，上次通過的 Example 都被列為回歸，使用者得逐一排除這些假回歸。

```text
MySQL 127.0.0.1:3307：Connection refused
處理：照常執行四個完整指令 → 回歸 87 個
```

## Rule 3 -- 只附加 JSON 報告選項且以絕對路徑輸出到專案外

**強度：MUST**

每個要執行的指令只能附加產生 JSON 報告的命令列選項，不得修改測試設定檔：behave 加 `-f json -o <暫存>/<端點>.json`；Playwright 以環境變數 `PLAYWRIGHT_JSON_OUTPUT_NAME=<暫存>/<名稱>.json` 指定輸出並加 `-- --reporter=json`（專案的 `test:e2e` 是 `bddgen && playwright test`，`--` 後的參數接在整串指令最後，只有 playwright 收到，bddgen 不受影響）；vitest 加 `-- --reporter=json --outputFile=<暫存>/<名稱>.json`。`<暫存>` 必須是專案外的暫存目錄，所有報告路徑必須是絕對路徑（Windows 下如 `C:/Users/.../bdd-verify/e2e.json`；相對路徑會相對於各指令的工作目錄，報告落在專案內或找不到）。以 run_suite.py 執行時，指令與 `--env` 值中的 `{out}` 會換成輸出目錄的絕對路徑。報告交給 verify_result.py 時，behave 報告附上執行 behave 的目錄，vitest 報告附上它執行的端點資料夾。有多份 vitest 報告（原報告與單一 Example 的重跑報告）時必須重複整個 `--vitest <json> <端點資料夾>`，每份報告各接自己的資料夾；寫成 `--vitest a.json b.json <dir>` 時，b.json 會被當成 feature 資料夾而報錯或找不到 Example。重跑報告因行號或名稱篩選而出現的 pending、skipped、todo、skipped 場景視為報告中不存在，不覆蓋原結果也不算失敗，只有真正執行且失敗才算。

### Good Example

這個範例在不改設定檔的前提下為每個完整指令附加 JSON 報告選項，以 `{out}` 讓所有報告都用專案外暫存目錄的絕對路徑；Playwright 的路徑以環境變數指定，`--reporter=json` 接在 `bddgen && playwright test` 之後。

```text
暫存：$TMP/bdd-verify
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/run_suite.py" --out $TMP/bdd-verify \
  --step backend backend 900 "uv run --no-sync python -m behave -D suite=api -f json -o {out}/backend.json" \
  --step database backend 300 "uv run --no-sync python -m behave -D suite=database -f json -o {out}/database.json" \
  --step component frontend 300 "npm run test:component -- --reporter=json --outputFile={out}/component.json" \
  --step e2e frontend 1800 "npm run test:e2e -- --reporter=json" --env e2e PLAYWRIGHT_JSON_OUTPUT_NAME={out}/e2e.json
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --behave $TMP/bdd-verify/backend.json backend --behave $TMP/bdd-verify/database.json backend --playwright $TMP/bdd-verify/e2e.json --vitest $TMP/bdd-verify/component.json specs/truth/features/frontend/component
```

### Good Example

這個範例以 `-t` 篩選重跑一個失敗的元件測試，重複 `--vitest` 把重跑報告接在原報告之後，各自附上端點資料夾；重跑報告中被篩掉的 pending 測項不覆蓋原結果。

```text
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --vitest $TMP/bdd-verify/component.json specs/truth/features/frontend/component --vitest $TMP/bdd-verify/component-rerun.json specs/truth/features/frontend/component --dry-run
```

### Bad Example

這個範例把重跑報告直接接在第一個 `--vitest` 後面，component-rerun.json 被當成 feature 資料夾，回報找不到資料夾（或重跑結果沒有覆蓋原報告）。

```text
verify_result.py --vitest component.json component-rerun.json specs/truth/features/frontend/component
```

### Bad Example

這個範例沒有指定 Playwright 的輸出檔，把 stdout 導向專案內的檔案，JSON 前面混入 npm 與 bddgen 的輸出，verify_result.py 無法解析，專案內還多出一個不屬於任何人的報告檔。

```text
cd frontend && npm run test:e2e -- --reporter=json > e2e.json
```

## Rule 4 -- 只執行與判定，不修改檔案

**強度：MUST**

Phase 5 的 Step 不得修改產品程式、step definitions、Driver、測試支援程式、測試設定、feature、dsl.md 或用語表，唯一寫入的檔案是 verify_result.py 存回的 `specs/truth/features/.verify-result.json`；`--out` 的完整結果與重跑報告寫在專案外的暫存目錄。測試工具依專案設定本來就會產生的報告與暫存（如 `backend/reports/`、`frontend/test-results/`、`frontend/.features-gen/`）照常產生，不另外清除或修改。單獨 `/bdd verify` 發現失敗時只回報，不修正；修正迴圈的修正由該階段的修正 Step 依 Rule 9 執行，不在 Phase 5 的 Step 內進行。

### Good Example

這個範例在單獨 verify 發現回歸後只停下回報，執行前後只有 `specs/truth/features/.verify-result.json` 由腳本更新。

```text
/bdd verify
verify_result.py：regressions 1（specs/truth/features/backend/改答案.feature:10）
處理：停下回報，建議執行 /bdd green specs/truth/features/backend/改答案.feature:10
修改的檔案：specs/truth/features/.verify-result.json（verify_result.py 寫入）
```

### Bad Example

這個範例在單獨 verify 發現回歸後直接修改產品程式，這次修改沒有經過 green 的最小實作與端點資料夾檢查，使用者也不知道 verify 改了程式。

```text
/bdd verify
verify_result.py：regressions 1（改答案.feature:10）
處理：修正 backend/app/skills.py 的 replace_answer，重新執行 backend → 通過
```

## Rule 5 -- 回歸只依 verify_result.py 的分類

**強度：MUST**

回歸只能是 verify_result.py 輸出的 `regressions`（上次 verify 通過或上次已是回歸，這次失敗，且不在 `--expected-fail` 內）。`in_progress`（上次就失敗、這次新出現的失敗，或列在 `--expected-fail` 的失敗）與 `no_baseline_failures`（沒有上次結果）是開發中，不得當成回歸停下。`carried`（傳 `--ran-scope` 時範疇外沒有報告而沿用上次結果的 Example）不是回歸，也不需要停下。`not_run` 或 `unmapped` 不為空時，代表完整指令組有 Example 沒有執行、範疇內的 Example 沒有報告（報告漏項、腳本崩潰或逾時），或報告對不回 feature，必須當成環境問題停下。不得依失敗訊息或印象自行改判哪些 Example 是回歸。

### Good Example

這個範例只把 `regressions` 的 1 個 Example 當成回歸，前端開發中的 27 個失敗不影響判定。

```text
verify_result.py：regressions 1、in_progress 27、not_run 0、unmapped 0
→ 回歸 1 個 → 停下回報這 1 個；開發中 27 個不列為回歸
```

### Bad Example

這個範例把上次就失敗的前端 Example 也當成回歸停下，開發中的功能每次 verify 都被當成壞掉，使用者無法分辨哪些是真的被改壞。

```text
verify_result.py：regressions 0、in_progress 27
→ 停下：27 個 Example 失敗，發現回歸
```

## Rule 6 -- 回歸停下時寫出位置、類別、AC 與下一步

**強度：MUST**

有回歸時，每個回歸的 Example 必須寫出：位置（`檔案:行號`）與所屬 Rule；依範疇與執行規範的失敗原因類別判定的類別，無法確定時先讀完整錯誤訊息；對應的 AC，以進行中 plan 的 `features/涵蓋表.md`「AC 涵蓋表」依端點、feature 與 Rule 對回，對不到時改查同一份檔案的「補充案例」寫出來源需求，兩者都沒有時寫「不在這個 plan 的涵蓋表中」；建議下一步，業務行為尚未實作寫 `/bdd green <位置>`，測試程式錯誤寫 `/bdd red <位置>`，其他端點尚未實作寫要先對哪個端點執行 `/bdd green`，feature、dsl.md 或用語表有問題交由 dsl-refine（dsl.md 與介面文檔矛盾時依範疇與執行規範 Rule 16 判斷，錯在介面文檔時寫「建議委派 dev-finding 的 record 記錄，由該文檔的 Planner 修正」），環境問題交由使用者。

### Good Example

這個範例為回歸的 Example 寫出位置、Rule、類別、從 AC 涵蓋表對回的 AC 與可直接執行的下一步。

```text
停下：verify 發現 1 個回歸（上次 verify 通過，這次失敗）
位置：specs/truth/features/backend/改答案.feature:10（Rule：改答案後，答案必須換成新答案）
失敗訊息：Then "甲" 的目前答案為 "4567"：AssertionError: my_secret 0123 != 4567
類別：業務行為尚未實作（Then 斷言失敗，答案沒有被取代）
AC：AC-01（涵蓋表：backend｜改答案.feature｜改答案後，答案必須換成新答案）
建議下一步：/bdd green specs/truth/features/backend/改答案.feature:10
```

### Bad Example

這個範例只寫出回歸數量，沒有位置、類別、AC 與下一步，使用者得自己翻報告找出是哪個 Example、影響哪個驗收標準、該交給哪個階段。

```text
停下：verify 發現 1 個回歸，請檢查 backend。
```

## Rule 7 -- 沒有回歸時簡短說明

**強度：MUST**

沒有回歸時只簡短說明：各端點資料夾的通過與失敗數、這次沿用上次結果的 Example 數與所屬端點資料夾（任務驗證範疇外沒有執行的 Example）、開發中 Example 的位置、這次轉為通過的 Example、重跑後通過的偶發 Example 位置；沒有上次結果時必須說明這次沒有基準、無法判定回歸，並列出全部失敗 Example 的位置。不使用完成報告樣板，不列出通過的 Example 清單。

### Good Example

這個範例在第一次執行時說明沒有基準，列出各端點數量與全部失敗的位置。

```text
verify 完成：這是第一次執行，沒有上次結果可比對，無法判定回歸；本次結果已存為下次的基準。
各端點：backend 42/57 通過；frontend/component 125/125 通過；frontend 0/27 通過
失敗（42）：specs/truth/features/backend/改答案.feature:10、:17、…；specs/truth/features/frontend/改答案.feature:9、…
```

### Bad Example

這個範例在第一次執行時只回報沒有回歸，使用者誤以為全部通過，42 個失敗的 Example 與「這次沒有基準」都被略過。

```text
verify 完成：沒有回歸。
```

## Rule 8 -- 階段呼叫依層級與時機決定指令組、執行範圍與預期失敗

**強度：MUST**

驗證分任務層與全端點層。任務層的任務驗證就是修正迴圈：每次執行都是任務指令組的 Step 4 至 Step 8（比對一律 `--dry-run`），迴圈沒有本階段可修正的項目時，以最後一次執行的報告、參數與執行紀錄執行 Step 9 至 Step 10 存回，不得為了「結尾驗證」再執行一次。指令組、執行的 Step、傳給 verify_result.py 的 `--ran-scope`（本次實際執行的範疇）與 `--expected-fail`、失敗時的處理必須依下表，與單獨 `/bdd verify` 區分；表中未列的做法兩者相同。完整指令組是 Rule 1 決定的所有端點完整指令（含 e2e）；任務指令組依 Rule 10。任務層只檢查範疇與快速端點資料夾，範疇外（其他端點、前端範疇以外的 Example）的回歸由全端點層的 verify 檢查，任務層不得為了補檢查而加跑。

| 層級 | 呼叫時機 | 指令組 | 執行的 Step | `--ran-scope` | `--expected-fail` | 有失敗或回歸時 |
|---|---|---|---|---|---|---|
| 任務層 | 階段開始（`specs/truth/features/.verify-result.json` 不存在） | 完整 | Step 4 至 Step 9 | 不傳 | 不傳 | 只存結果，不因失敗停下（沒有上次結果，不會有回歸） |
| 任務層 | green、refactor 確認現況（範疇與執行規範 Rule 6） | 任務 | Step 4 至 Step 8 | 傳 | 不傳 | 作為現況判定進入條件 |
| 任務層 | red 修正迴圈的每次執行 | 任務 | Step 4 至 Step 8 | 傳 | 第一次為整個範疇；之後為範疇內因業務行為尚未實作而失敗的 Example，加上這次破壞產品程式後失敗的 Example，與改寫既有 step 後因業務行為尚未實作而失敗的範疇外 Example（紅燈規範） | 依 Rule 9 |
| 任務層 | green、refactor 修正迴圈的每次執行 | 任務 | Step 4 至 Step 8 | 傳 | 不傳 | 依 Rule 9 |
| 任務層 | 迴圈結束（沒有本階段可修正的項目） | 不執行 | Step 9 至 Step 10 | 同最後一次執行 | 同最後一次執行 | 仍有不可修正的回歸、未執行或無法對應的 Example 時依 Step 10 停下 |
| 任務層 | rerun（範疇與執行規範 Rule 6 判定要執行時） | 任務 | Step 4 至 Step 10 | 傳 | 不傳 | rerun 不修改任何檔案，沒有可修正的項目：依 Rule 11 重跑後仍有回歸，或有未執行、無法對應的 Example 時，存回後依 Rule 6 停下回報 |
| 全端點層 | 單獨 `/bdd verify`（使用者手動，或 implement 執行 tasks.md 的 `[驗證]` 任務時委派） | 完整 | Phase 5 全部 | 不傳 | 不傳 | 依 Rule 11 重跑後，仍有回歸依 Rule 6 停下回報，不修改任何檔案 |

修正迴圈只在本階段修改過檔案後執行，每次修改後都必須再執行一次。本階段沒有修改任何檔案（refactor 沒有可重構內容、green 範疇已通過且沒有破壞要還原）時不執行：有確認現況的執行就以它的報告存回；現況沿用上次結果時不存回，結果檔已是現況。存回時以 `--run` 傳入最後一次執行與其單獨重跑的執行紀錄（run_suite.py stdout 的 `run_record`）；verify_result.py 在那次執行之後有檔案變動時會拒絕寫入，此時必須重新執行任務指令組，不得改以不帶 `--run` 的寫入繞過。

### Good Example

這個範例在後端 red 的迴圈以任務指令組執行，第一次以整個範疇為預期失敗；破壞產品程式後的執行把因破壞而失敗的 Example 加入預期失敗，它們照常存為失敗、不算回歸，下一個 green 仍看得到紅燈；迴圈結束時以最後一次執行的報告存回，不再執行。

```text
red 範疇：specs/truth/features/backend/改答案.feature（:21 第一次就通過，已破壞扣次數邏輯）
最後一次執行：run_suite.py --step backend backend 600 "uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend -f json -o {out}/backend.json" → run_record {out}/run-20261114T101500000000Z.json
結果：改答案.feature:21 ✗、:60 ✗（同樣依賴改答案後的狀態，因破壞而失敗）
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --behave $TMP/bdd-verify/backend.json backend --ran-scope specs/truth/features/backend --expected-fail specs/truth/features/backend/改答案.feature specs/truth/features/backend/改答案.feature:60 --dry-run
→ regressions 0、in_progress 27（expected_fail: true）、carried 為 database 與前端的 Example
存回：同一指令去掉 --dry-run，加 --run $TMP/bdd-verify/run-20261114T101500000000Z.json
```

### Bad Example

這個範例在 green 的迴圈已經通過後，又為了「結尾任務驗證」以同一指令組再執行一次；兩次之間沒有修改任何檔案，前端範疇多跑 5 分鐘，結果完全相同。

```text
green 範疇：specs/truth/features/frontend/改答案.feature
迴圈執行：bddgen 後 playwright test .features-gen/truth/features/frontend/改答案.feature.spec.js → 31 個通過
結尾：再以 run_suite.py 執行同一指令 → 31 個通過 → 存回
```

### Bad Example

這個範例在 red 的迴圈沒有傳入 `--expected-fail`，範疇內被故意破壞而失敗的 Example 被列為回歸並停下，使用者被要求處理一個 red 本來就要留給 green 的紅燈，還得自己重跑 verify。

```text
red 範疇：specs/truth/features/backend/改答案.feature（:21 第一次就通過，已破壞扣次數邏輯）
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --behave $TMP/bdd-verify/backend.json backend --ran-scope specs/truth/features/backend --dry-run
→ regressions 1（改答案.feature:21）→ 停下回報，建議 /bdd green
```

## Rule 9 -- 任務驗證的回歸依類別修正或停下

**強度：MUST**

修正迴圈的每次執行依 Rule 11 重跑後仍失敗的回歸，視為本階段修改造成，必須依範疇與執行規範的失敗原因類別處理：「測試程式錯誤」或「業務行為尚未實作」（本階段改壞的行為）屬本階段可修正，不得停下，必須回到該階段的修正 Step（red 修正測試程式、green 修正產品程式、refactor 修正或還原重構），修正後再執行一次任務指令組（Step 4 至 Step 8），直到沒有本階段可修正的回歸。red 的迴圈執行若回歸的失敗位置就是這次故意破壞的產品程式，不修正，改以相同報告把它加入 `--expected-fail` 重新執行 verify_result.py。其他類別（feature 或 dsl.md 有問題、其他端點尚未實作、環境問題），以及 `not_run` 或 `unmapped` 不為空時，必須依 Rule 6 與停下回報規範停下。

### Good Example

這個範例在 green 的迴圈執行發現同資料夾的回歸，單獨重跑後仍失敗，判定是本次修改改壞的產品行為，回到綠燈修正後再執行，沒有回歸才存回。

```text
green 範疇：specs/truth/features/backend/改答案.feature:10
迴圈執行（backend 資料夾）：regressions 1（specs/truth/features/backend/改答案.feature:60，上次通過）
單獨重跑 改答案.feature:60 → 仍失敗：Then 系統回報 "3A0B"：AssertionError: '0A0B' != '3A0B'
類別：業務行為尚未實作（本階段改壞的行為）→ 回到 Phase 3 Step 5 修正 replace_answer
修正後再執行：regressions 0 → 以這次執行存回 → green 完成
```

### Bad Example

這個範例在 green 的迴圈執行遇到本階段改壞的產品行為就停下，建議使用者執行 `/bdd green` 再手動跑 verify；這個錯誤本來就在 green 可修改的範圍內，使用者被迫自己來回執行。

```text
迴圈執行：regressions 1（specs/truth/features/backend/改答案.feature:60）
類別：業務行為尚未實作
→ 停下回報：建議 /bdd green specs/truth/features/backend/改答案.feature:60，完成後請執行 /bdd verify
```

## Rule 10 -- 任務驗證只跑範疇與快速端點資料夾

**強度：MUST**

任務層（green、refactor 的確認現況，red、green、refactor 的修正迴圈與 rerun 的執行）只執行範疇與範疇與執行規範 Rule 6 定義的任務指令組：Playwright 的 e2e 與 vitest 元件測試只跑範疇指令；由 behave 執行的端點（不啟動瀏覽器，整個資料夾約 10 至 90 秒，如 backend、database）改跑範疇所在的端點資料夾指令（範圍包含範疇）。任務指令組不得包含範疇以外的 Playwright 端點資料夾指令（前端資料夾 66 個 Example，每個 Example 起點重啟後端約 11 秒，一輪約 10 分鐘）或其他端點的完整指令；範疇本身是 Playwright 端點資料夾時，範疇指令就是該資料夾指令。唯一的例外是 red 改寫既有 step 時：範疇外用到它、不在端點資料夾指令內的 Example，依紅燈規範另以範疇指令一併執行。傳給 verify_result.py 時必須加 `--ran-scope`，列出本次實際執行的每個指令所涵蓋的範疇或端點資料夾（相對於專案根目錄）；範疇外沒有報告的 Example 沿用上次結果（列為 carried），範疇內缺報告的 Example 列為 not_run，讓報告漏項、腳本崩潰與逾時不會被當成沿用。不得改用 `--partial`（以端點資料夾為單位沿用，前端範疇只有部分 Example 有報告時其餘會被判為 not_run），也不得為了補檢查而重用其他指令的報告。單獨 `/bdd verify`、階段開始建立基準用完整指令組且不傳 `--ran-scope`；範疇外的回歸由全端點層的 verify 檢查。

### Good Example

這個範例前端紅燈只跑範疇，後端綠燈跑範疇與 backend 資料夾；兩者都傳 `--ran-scope`，沒有執行的 Example 沿用上次結果，不跑整個前端資料夾。

```text
前端 red 範疇：specs/truth/features/frontend/連猜三次.feature:6
任務指令：cd frontend && npx --no-install bddgen && npx --no-install playwright test --grep "連猜三次 確認使用連猜三次後，連猜剩餘次數必須為 3 " --reporter=json（PLAYWRIGHT_JSON_OUTPUT_NAME={out}/e2e.json）
verify_result.py --playwright {out}/e2e.json --ran-scope specs/truth/features/frontend/連猜三次.feature:6 --expected-fail specs/truth/features/frontend/連猜三次.feature:6
→ 只執行 1 個 Example；前端其他 Example 沿用上次結果（carried）

後端 green 範疇：specs/truth/features/backend/連猜三次.feature:6
任務指令：cd backend && uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend -f json -o {out}/backend.json
verify_result.py --behave {out}/backend.json backend --ran-scope specs/truth/features/backend
→ backend 資料夾逐一比對；其他端點沿用上次結果
```

### Bad Example

這個範例的前端綠燈範疇是單一 feature，迴圈卻執行整個前端資料夾，每次執行約 10 分鐘，修正兩次就是半小時，多跑的 35 個 Example 也不在本階段的檢查範圍。

```text
green 的迴圈執行：cd frontend && npx --no-install bddgen && npx --no-install playwright test .features-gen/truth/features/frontend --reporter=json（66 個 Example，約 10 分鐘）
```

## Rule 11 -- 回歸先單獨重跑排除偶發

**強度：MUST**

verify_result.py 比對出 `regressions` 時（單獨 verify 與修正迴圈的每次執行都適用），必須先把每個回歸的 Example 單獨重跑一次，再判定是否回到修正 Step：用該 Example 的範疇指令（behave 用 `路徑:行號`，Playwright 依範疇與執行規範 Rule 9 以 `--grep`，vitest 用該工具篩選單一情境的機制），JSON 報告輸出到暫存目錄。以 verify_result.py 重新比對時，其他參數與第一次相同，同一種工具的重跑報告接在原報告之後（同一個 Example 以最後傳入的報告為準）；判斷階段（第一次比對與重跑後的比對）一律傳 `--dry-run`，不得讓比對先覆寫 `specs/truth/features/.verify-result.json`，需要保留原基準時另以 `--base <備份檔>` 指定；判定完成後才以相同參數不帶 `--dry-run` 寫入。重跑通過視為偶發：不修正、不停下，在說明中列出偶發的 Example 位置；重跑仍失敗才依 Rule 6 或 Rule 9 處理。

### Good Example

這個範例的回歸是 Playwright 一個 Example，單獨以 `--grep` 重跑通過，用重跑報告覆蓋後 regressions 為 0，視為偶發。

```text
refactor 的迴圈執行：regressions 1（specs/truth/features/frontend/連猜三次.feature:6）
重跑：cd frontend && npx --no-install playwright test --grep "連猜三次 確認使用連猜三次後，連猜剩餘次數必須為 3 " --reporter=json（PLAYWRIGHT_JSON_OUTPUT_NAME={out}/rerun1.json）→ 通過
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" ... --playwright {out}/e2e.json --playwright {out}/rerun1.json --ran-scope specs/truth/features/frontend/連猜三次.feature:6 --dry-run
（確認偶發、迴圈結束後，以同一指令去掉 --dry-run、加 --run 傳入原執行與重跑的執行紀錄寫入結果）
→ regressions 0；說明：連猜三次.feature:6 偶發失敗，重跑通過
```

### Bad Example

這個範例看到回歸就直接回到修正 Step，沒有先重跑；偶發的逾時被當成本階段改壞的產品行為，green 去修改本來正確的產品程式。

```text
迴圈執行：regressions 1（specs/truth/features/backend/改答案.feature:60）訊息：Connection timed out
類別：業務行為尚未實作 → 回到 Phase 3 Step 5 修改 replace_answer
```

## Rule 12 -- 偶發重跑只限回歸的 Example

**強度：MUST**

不得以「可能是偶發」為由跳過 Rule 11 的重跑，也不得為了排除偶發而重跑整輪任務指令組或完整驗證：重跑的範圍只有這次執行的 `regressions` 列出的 Example，每個重跑一次；重跑仍失敗的 Example 在這次執行中不得再重跑第二次。修正後的下一次執行是新的執行，其中的回歸再依 Rule 11 各重跑一次。

### Good Example

這個範例有兩個回歸，各自單獨重跑一次：一個通過視為偶發，另一個仍失敗，直接依 Rule 9 處理。

```text
regressions 2：後端 改答案.feature:60、前端 連猜三次.feature:6
重跑各一次：:60 仍失敗、:6 通過 → :6 為偶發；:60 依 Rule 9 修正
```

### Bad Example

這個範例以偶發為由重跑整輪 e2e，多花 12 分鐘，同一個 Example 若再失敗又重跑一次，驗證時間無上限。

```text
regressions 1 → 懷疑偶發，重新執行 cd frontend && npm run test:e2e（12 分鐘）→ 又失敗 → 再跑一次
```

## Rule 13 -- verify_result.py 的 stdout 只印摘要，完整結果寫檔

**強度：MUST**

呼叫 verify_result.py 時必須以 `--out <暫存>/verify-full.json` 把完整比對結果寫到專案外的暫存目錄，stdout 只讀摘要：各分組數量、`regressions`、`not_run`、`unmapped` 的清單與各端點通過、失敗數。沿用（`carried`）、開發中與已修好等大型分組只以數量判讀，需要逐項內容時才讀 `--out` 的檔案；不得把完整 JSON 直接讀進對話，也不得為了縮短輸出而自行刪減腳本回傳的清單。

### Good Example

這個範例以 `--out` 寫出完整結果，只讀摘要即可判定，約 570KB 的沿用清單不進入對話。

```text
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --behave {out}/backend.json backend --dry-run --out {out}/verify-full.json
摘要：summary.regressions 1、carried 3512、not_run 0、unmapped 0
→ 只處理 regressions 1 個；carried 與開發中不逐項讀取
```

### Bad Example

這個範例沒有 `--out` 也沒有節制輸出，改以重導向把完整結果倒進對話，沿用的 Example 清單約 570KB 擠掉所有任務脈絡。

```text
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/verify_result.py" --behave {out}/backend.json backend | cat
→ 輸出 570KB，其中 carried 3512 筆
```

## Rule 14 -- 驗證前確認紅燈的破壞已全部還原

**強度：MUST**

全端點層的 verify（Phase 5 Step 2）與任何完整指令組執行前，必須以紅燈規範 Rule 3 的破壞標記 `BDD-RED-BREAK` 搜尋產品程式，確認沒有未還原的破壞。仍有標記時，verify 依 Rule 4 不修改檔案，必須停下回報標記位置與註明的範疇，建議先執行該範疇的 `/bdd green` 還原；不得帶著破壞執行 verify、把破壞造成的失敗當成回歸，或自行刪除標記掩蓋。任務層的驗證（red 的任務驗證）預期有本任務的破壞與其連帶失敗，由 `--expected-fail` 涵蓋。

### Good Example

這個範例在 verify 前搜尋標記，發現後端還有一處破壞，停下並建議先執行同範疇的 green。

```text
grep -rn "BDD-RED-BREAK" backend/app frontend/src → backend/app/service.py:88（specs/truth/features/backend/改答案.feature:21）
停下：完整指令組執行前仍有未還原的紅燈破壞
建議下一步：先執行 /bdd green specs/truth/features/backend/改答案.feature 還原，再執行 /bdd verify
```

### Bad Example

這個範例沒有搜尋標記就執行 verify，被破壞的扣次數邏輯讓 backend 與 e2e 共 9 個 Example 失敗，全被列為回歸並停下，使用者要逐一排查才發現是 red 留下的破壞。

```text
/bdd verify → regressions 9（改答案、連猜三次相關）→ 停下回報
（backend/app/service.py:88 的 BDD-RED-BREAK 仍在）
```
