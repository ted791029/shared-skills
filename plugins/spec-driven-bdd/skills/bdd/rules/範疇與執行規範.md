# 範疇與執行規範

## Rule 1 -- step 目錄與執行指令依專案測試設定決定

**強度：MUST**

測試工具依 `specs/truth/techstack.md` 與 `specs/truth/features/用語表.md`「端點」表為該端點資料夾登記的測試工具決定；step 目錄與執行指令必須依專案測試設定判定：找出涵蓋範疇 feature 的測試設定（如 behave runner 依 `-D suite=` 收集的資料夾、`playwright.config.js` 的 `features`、vitest `include` 載入的測試檔所讀取的 feature），以該設定載入的 step 目錄作為 step 目錄，並以該設定的執行方式寫出兩種可直接執行的指令：範疇指令（只跑範疇內的 Example）與端點資料夾指令（跑範疇所在的端點資料夾的全部 Example）。不得取用用語表登記的 step 目錄、依專案標記檔（如 `package.json`、`pyproject.toml`）或個人偏好另選，也不得為特定資料夾結構寫特例判斷。測試工具支援 `路徑:行號` 時以 resolve_scope.py 輸出的 `run_targets`（每個元素一個 `路徑:行號`，各自成為獨立參數）指定範疇；不支援時改用該工具篩選單一情境的機制，例如以情境標題篩選；Playwright 的指定方式依 Rule 9。測試工具不帶路徑、涵蓋整個端點資料夾的完整指令只屬於全端點驗證，不列入本規則的指令。

### Good Example

這個範例讀 behave runner 的 SUITES 判定 backend 由 `-D suite=api` 收集，step 目錄取自該套件，兩種指令都只指向 backend 資料夾。

```text
範疇：specs/truth/features/backend/改答案.feature:10
測試設定：backend/tests/behave_runner.py SUITES = {"api": "backend", "database": "database"}
  → suite=api 收集 specs/truth/features/backend，涵蓋範疇；載入 backend/tests/api/steps
step 目錄：backend/tests/api/steps
範疇指令：cd backend && uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend/改答案.feature:10
端點資料夾指令：cd backend && uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend
```

### Bad Example

這個範例取用用語表登記的 step 目錄，把 step 寫進測試設定沒有載入的 `frontend/tests/steps`；`playwright.config.js` 的 `steps` 只載入 `tests/e2e/steps/**/*.js`，寫完的 step 永遠是 undefined，red 一直以為是自己的 step 寫錯。

```text
用語表「端點」表 frontend 的 step 目錄：frontend/tests/steps
step 目錄：frontend/tests/steps
撰寫：frontend/tests/steps/modules/技能/改答案.js
```

## Rule 2 -- 沿用專案既有慣例

**強度：MUST**

專案已有 step definitions、Driver、測試支援程式或斷言函式庫時，模組格式（CommonJS 或 ESM）、斷言函式庫與支援程式的寫法必須沿用既有做法；step 檔的路徑依 dsl.md 的 Step 檔對照，不另訂。

### Good Example

這個範例發現既有 backend step 使用 Python `assert` 與 `backend/tests/support/drivers/` 的 Driver，新 step 沿用相同寫法。

```text
既有：backend/tests/api/steps/shared/拒絕.py 使用 assert，Driver 在 backend/tests/support/drivers/
決定：新 step 使用 assert，Driver 放在 backend/tests/support/drivers/
```

### Bad Example

這個範例在既有使用 Python `assert` 的專案改用 `pytest` 的斷言輔助，behave 執行時多出未宣告的依賴，step 一載入就 ImportError。

```text
既有：assert
決定：from pytest import approx, raises
```

## Rule 3 -- 測試環境與測試設定的就緒標準

**強度：MUST**

測試環境是否就緒只看兩項：`specs/truth/techstack.md` 列出的端點測試套件已安裝；測試需要的服務（測試資料庫、後端服務、瀏覽器）可連線，或可由測試設定自行啟動。測試設定是否就緒只看兩項：有測試設定涵蓋該 feature；該設定載入了 step 目錄。測試設定未就緒時不得修改測試設定讓它涵蓋或載入，必須依停下回報規範交由使用者；不得為了就緒安裝套件。以下 Example 皆對照此專案測試設定：

```text
frontend/playwright.config.js：features ['../specs/truth/features/frontend/*.feature', ...]；steps ['tests/e2e/support/fixtures.js', 'tests/e2e/steps/**/*.js']
```

### Good Example

這個範例分別判定測試環境與測試設定，兩者都就緒才繼續，不需要用語表登記任何目錄。

```text
範疇：specs/truth/features/frontend/改答案.feature
測試環境：cd frontend && npx --no-install playwright --version → 1.65.0；MySQL 127.0.0.1:3307 可連線，後端由 tests/e2e/support/server.js 啟動 → 就緒
測試設定：features 的 ../specs/truth/features/frontend/*.feature 涵蓋範疇；steps 載入 tests/e2e/steps/**/*.js → 就緒
```

### Bad Example

這個範例的範疇放在 `features/frontend/` 的第二層，`features` 的萬用字元只比對一層，卻自行在 `playwright.config.js` 補上路徑後繼續；使用者不知道共用的測試設定被改了，其他 feature 的收集範圍也跟著變動。

```text
範疇：specs/truth/features/frontend/排行/排行榜.feature
測試設定：features 只比對 ../specs/truth/features/frontend/*.feature → 未涵蓋
處理：在 features 補上 '../specs/truth/features/frontend/**/*.feature'，繼續撰寫 step
```

## Rule 4 -- 檢查環境不得觸發安裝

**強度：MUST**

檢查套件是否已安裝與執行測試時，必須使用不會同步或下載套件的指令，例如 `uv run --no-sync`、`npx --no-install`；不得使用 `uv sync`、`npm install`、未加 `--no-sync` 的 `uv run` 或未加 `--no-install` 的 `npx`。

### Good Example

這個範例以不會安裝的指令確認 behave 與 Playwright 是否存在。

```text
cd backend && uv run --no-sync python -m behave --version
cd frontend && npx --no-install playwright --version
```

### Bad Example

這個範例以一般的 `uv run` 檢查，uv 先依 `pyproject.toml` 同步環境，把尚未安裝的 dev 套件裝了下去，等於未經使用者同意就安裝套件。

```text
cd backend && uv run python -m behave --version
```

## Rule 5 -- 範疇以行號執行且不加 tag

**強度：MUST**

只跑範疇時必須依 resolve_scope.py 輸出的 Example 行號執行，一個場景大綱連同所有例子列只算一個 Example，所有例子列都通過才算通過。不得為了篩選情境而在 feature 加上 tag。範疇可以是端點資料夾、整份 feature（tasks.md 的階段任務多為整份 feature，NFR 重構為端點資料夾）、Rule 行、以 Rule 名稱定位的 Rule（`<feature 路徑> ＞ Rule「<Rule 名稱>」`，多條以「、」接續，修正 Phase 的任務多為這種寫法，名稱與 feature 的 `Rule:` 行逐字相同）或 Example 行；範疇要傳給 resolve_scope.py、baseline.py，或作為 verify_result.py 的 `--ran-scope`、`--expected-fail` 時，照範疇原文傳入，Rule 名稱的寫法含空白，必須整段以引號包成一個參數。範疇是整份 feature 或 Rule 時，必須以 resolve_scope.py 把它換算為其下全部 Example 行：輸出的 `features[].examples` 列出每個 Example 的行號與標題，`features[].run_targets` 是陣列，每個元素是一個 `feature:行號`，必須各自成為 behave 指令的一個獨立參數（`file:9 file:19`）；不得把多個行號串成 `file:9:19`（behave 1.3.3 回 `InvalidFilenameError`），也不得把 Rule 行直接傳給測試工具或手算行號。舊欄位 `run_target`（行號串成單一字串）已移除，因為它的值正是 behave 不接受的寫法，保留只會誘使呼叫者直接使用；Playwright 與 vitest 不使用 `run_targets`，依各自規則以標題篩選（Rule 9、Rule 15）。

### Good Example

這個範例以行號只執行範疇內的兩個 Example，場景大綱以大綱標題行指定。

```text
範疇：specs/truth/features/backend/連猜三次.feature:12（Rule 行）
resolve_scope.py 輸出：run_targets = [連猜三次.feature:14、:21、:29、:40、:48]（Rule 底下的 5 個 Example 行，每個元素一個 feature:行號）
cd backend && uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend/連猜三次.feature:14 ../specs/truth/features/backend/連猜三次.feature:21 ../specs/truth/features/backend/連猜三次.feature:29 ../specs/truth/features/backend/連猜三次.feature:40 ../specs/truth/features/backend/連猜三次.feature:48
→ 場景大綱以標題行指定，所有例子列都通過才算該 Example 通過
```

這個範例的範疇以 Rule 名稱定位，換算為兩條 Rule 底下的 Example 行，傳給腳本時整段範疇是一個參數。

```text
範疇：specs/truth/features/backend/改答案.feature ＞ Rule「確認改答案後，新答案必須生效」、Rule「改答案後，必須仍輪到同一位玩家」（修正 Phase）
resolve_scope.py 輸出：run_targets = [改答案.feature:10、:56]
baseline.py "specs/truth/features/backend/改答案.feature ＞ Rule「確認改答案後，新答案必須生效」、Rule「改答案後，必須仍輪到同一位玩家」" --folder specs/truth/features/backend
```

### Bad Example

這個範例把多個行號串成一個參數，behave 1.3.3 回 InvalidFilenameError，範疇一個都沒有執行。

```text
cd backend && uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend/連猜三次.feature:14:21:29
→ behave.exception.InvalidFilenameError
```

### Bad Example

這個範例在 feature 加上 `@wip` 篩選範疇，dsl-refine 產出的 feature 被改動，下次增量更新時會被當成使用者手改的內容。

```text
在 改答案.feature 第 9 行加入 @wip
cd backend && uv run --no-sync python -m behave -D suite=api --tags=@wip
```

## Rule 6 -- 基準沿用上次結果，可沿用時不重跑

**強度：MUST**

基準必須取自 `specs/truth/features/.verify-result.json`：階段開始時以 baseline.py 讀出範疇每個 Example 與（範疇所屬端點是快速端點時，以 `--folder` 傳入）範疇所在的端點資料夾每個 Example 的上次結果；只有 `specs/truth/features/.verify-result.json` 不存在時，才以全端點驗證規範的完整指令組（Phase 5 Step 4 至 Step 9）建立，不得另以端點資料夾指令重新「建立」基準，也不得沿用不是這個檔案的舊報告。階段開始是否執行一次確認範疇現況，依階段與 baseline.py 的 `reusable` 決定：

- red：一律不確認現況；失敗原因由撰寫 step definitions 之後的第一次執行判定。
- green、refactor：`reusable` 為 true（範疇內每個 Example 都由結果檔記錄的最後一次執行產生，且目前的專案檔案清單摘要與該次執行結束時相同）時，以結果檔儲存的 `status` 與 `message` 作為現況判定進入條件，不執行；`reusable` 為 false、儲存的 `message` 不足以依 Rule 7 判定失敗原因類別，或依儲存的結果會因進入條件不成立而停下時，必須以任務指令組執行一次（全端點驗證規範 Phase 5 Step 4 至 Step 8，`--dry-run`）作為現況。資料庫、服務等環境狀態不在檔案清單摘要內，只憑沿用的結果不得停下。
- rerun：`reusable` 為 true 且範疇內每個 Example 儲存的 `status` 都是通過時，沿用結果，不執行也不存回；`reusable` 為 false，或沿用的結果有失敗時，必須以任務指令組執行一次並存回（全端點驗證規範 Phase 5 Step 4 至 Step 10），以這次的結果判定。

不得以「應該沒變」為由沿用 `reusable` 為 false 的結果，也不得在 baseline.py 判定之前執行會寫檔的指令（bddgen、`--list` 預檢、`npm run build`、測試指令）。快速端點是由 behave 執行（不啟動瀏覽器，整個資料夾約 10 至 90 秒，如 backend、database）的端點資料夾；其他端點（Playwright 的 e2e、vitest 的元件測試）是慢端點。任務指令組：快速端點是範疇所在的端點資料夾指令（範圍包含範疇），慢端點是範疇指令；範疇本身是端點資料夾時，範疇指令就是該端點資料夾指令，慢端點也照跑；red 改寫既有 step 時，慢端點另加範疇外用到它的 Example（紅燈規範）。確認現況與修正迴圈都只執行任務指令組，不得執行完整指令或慢端點的端點資料夾指令；範疇外的回歸由呼叫者指定的 `/bdd verify`（使用者手動或 implement 的 `[驗證]` 任務）檢查。範疇內 Example 依階段範圍規範的完成條件判定，快速端點資料夾內範疇外只要求基準已通過的 Example 仍通過。上次結果沒有的 Example（新增的）以現況為基準；基準中失敗或不在基準內且不在範疇內的 Example 不列入通過標準，也不得因它們修改程式或加 tag 排除。

### Good Example

這個範例的前端 refactor 緊接在同範疇的 refactor 之後，中間只勾選了 tasks.md，baseline.py 判定可沿用，不再花 10 分鐘確認現況；後端 green 緊接在同範疇 red 之後，以儲存的失敗訊息判定進入條件。

```text
refactor 範疇：specs/truth/features/frontend/（前一任務 T024 同範疇）
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/baseline.py" specs/truth/features/frontend/
→ reusable true；scope 66 個 Example 全部通過、run 都是 last_run 20261114T151606096132Z
現況：沿用 → 進入條件成立，不執行

green 範疇：specs/truth/features/backend/改答案.feature（前一任務 T008 red 同範疇）
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/baseline.py" specs/truth/features/backend/改答案.feature --folder specs/truth/features/backend
→ reusable true；scope failed 26 個，message 都是「When "甲" 改答案為 "4567"：POST /api/rooms/r1/skills/change-secret → 404」
現況：沿用 → 本端點路由不存在，業務行為尚未實作，進入條件成立，不執行
```

### Good Example

這個範例的前一任務改了 backend，baseline.py 判定不可沿用，以任務指令組確認現況（前端慢端點，任務指令組就是範疇指令）。

```text
refactor 範疇：specs/truth/features/frontend/（前一任務 T023 改了 backend/app/snapshot.py）
baseline.py → reusable false；reasons：範疇內 66 個 Example 的結果不是最後一次執行（T023 的 backend 資料夾）產生
現況：run_suite.py 執行 cd frontend && npx --no-install bddgen && npx --no-install playwright test .features-gen/truth/features/frontend → verify_result.py --dry-run --ran-scope specs/truth/features/frontend/ → 66 個通過
```

### Bad Example

這個範例不看 baseline.py 的判定，每個階段開始都重跑範疇；前一任務剛以同一指令跑完且之後沒改任何檔案，前端資料夾白白多跑 10 分鐘。

```text
refactor 範疇：specs/truth/features/frontend/（前一任務 T024 同範疇剛存回）
現況：cd frontend && npx --no-install bddgen && npx --no-install playwright test .features-gen/truth/features/frontend（約 10 分鐘，結果與結果檔相同）
```

### Bad Example

這個範例在沿用的結果顯示環境問題時直接停下；使用者啟動 MySQL 後重新呼叫，沒有改任何檔案，結果仍可沿用，於是每次都停在同一個環境問題。

```text
green 範疇：specs/truth/features/database/連猜三次.feature
baseline.py → reusable true；scope failed 2 個，message：pymysql.err.OperationalError (2003, "Can't connect to MySQL server")
處理：停下回報環境問題（沒有實際執行確認）
```

## Rule 7 -- 失敗原因只能歸入一個類別

**強度：MUST**

每個未通過的 Example 必須依失敗的位置與訊息歸入下列其中一類：

| 類別 | 判定依據 |
|---|---|
| 業務行為尚未實作 | Then 的斷言失敗，或本端點資料夾負責的產品入口或結構不存在（如後端路由 404、前端畫面元素不存在且對應程式尚未撰寫、資料表或欄位尚未建立），不論發生在 Given、When 或 Then |
| 測試程式錯誤 | undefined、pending、ambiguous，step 或 Driver 的語法錯誤、TypeError、selector 或請求寫錯，或本端點 step 建立起點失敗，且不是因為本端點或其他端點的入口、結構、回應欄位不存在 |
| 其他端點尚未實作 | 失敗發生在其他端點資料夾負責的介面，且訊息證明該行為在系統中尚未實作：服務可連線但回 404、405，回應缺少 dsl.md 要求的欄位，或 Given 建立起點用到的其他端點行為不存在；例如 frontend 的 Example 呼叫的後端 API 回 404。服務連不上屬環境問題 |
| feature 或 dsl.md 有問題 | Example 互相要求矛盾的結果、Then 無法透過任何產品入口觀察、dsl.md 的句型或測試撰寫語意與 feature 不符、dsl.md 沒標擬定的技術對應與介面文檔矛盾（依 Rule 16 判斷錯在哪一邊），標「（擬定）」的技術對應依 Rule 8 查證不成立，或要沿用的既有 step 與 dsl.md 的測試撰寫語意不一致（同一個句子在其他 feature 有不同的意思；句型的測試寫法改了、由 red 改寫的既有 step 不屬此類） |
| 環境問題 | 測試資料庫、後端服務或瀏覽器無法連線或啟動 |

無法依判定依據確定類別時，必須重新執行並讀完整的錯誤訊息與堆疊後再歸類，不得以猜測歸入「業務行為尚未實作」。

### Good Example

這個範例依失敗位置與訊息把 frontend Example 的 404 歸入其他端點尚未實作：後端服務可連線，只是路由不存在，證明行為尚未實作而不是環境問題。

```text
frontend/改答案.feature:12 失敗
訊息：POST /api/rooms/r1/skills/change-secret → 404（後端服務已由 server.js 啟動，其他 API 正常回應，路由不存在）
類別：其他端點尚未實作（依賴 backend 改答案 POST /api/rooms/{roomId}/skills/change-secret）
```

### Bad Example

這個範例只看到 Then 斷言失敗就判定為業務行為尚未實作，實際原因是後端 API 404 讓畫面顯示錯誤；green 的進入條件因此誤判成立，在後端完成前就去改前端程式，永遠無法通過，也沒有停下寫出依賴的後端行為。

```text
frontend/改答案.feature:12 失敗
訊息：expect(locator).toHaveText("4567") 實際為「操作失敗」
類別：業務行為尚未實作
```

## Rule 8 -- 擬定的技術對應先查證再判定

**強度：MUST**

dsl.md 標「（擬定）」的技術對應，代表介面文檔查不到、由 dsl-refine 推測，不得只因介面文檔沒有就判定 dsl.md 有問題。必須依序查證介面文檔與既有的產品程式、測試支援程式：任一處已有相符的入口、欄位或定位時，照 dsl.md 使用；兩處都沒有，或既有程式與 dsl.md 的寫法矛盾時，才歸入「feature 或 dsl.md 有問題」。範疇內產品入口本來就尚未實作的擬定對應，依 dsl.md 撰寫，失敗歸入「業務行為尚未實作」。

### Good Example

這個範例的 reset 端點在介面文檔查不到，但後端程式碼的測試專用路由已有，照 dsl.md 使用。

```text
frontend/dsl.md:9：每個 Example 先 POST /api/test/reset（擬定）清空資料
contracts/openapi.yaml：沒有（測試專用端點不放產品契約）
backend/app/routes.py:123：@test_router.post("/api/test/reset")，APP_ENV=test 時掛載
判定：查證成立 → 照 dsl.md 撰寫起點，不停下
```

### Bad Example

這個範例只比對介面文檔就停下，後端早已提供這個測試專用端點，使用者被要求去修一份其實正確的 dsl.md，前端紅燈也因此無法開始。

```text
frontend/dsl.md:9：POST /api/test/reset（擬定）
contracts/openapi.yaml：沒有
判定：dsl.md 有問題 → 停下回報，交由 dsl-refine
```

## Rule 9 -- Playwright 範疇以 bddgen 與 --grep 指定

**強度：MUST**

使用 playwright-bdd 的專案（`playwright.config.js` 以 `defineBddConfig` 設定），Playwright 實際執行的是 `bddgen` 產生到 `.features-gen/` 的 `*.feature.spec.js`，其行號與 feature 的行號不同，不認 `路徑:行號`；不得把 feature 或 resolve_scope.py 的 `run_targets` 行號傳給 `playwright test`，也不得拿行號去對產生檔。範疇指令必須先執行 `bddgen`（讓產生檔與目前的 feature、step 一致），再依範疇選擇：範疇是整份 feature 時執行該 feature 的產生檔 `npx --no-install playwright test .features-gen/truth/features/<端點>/<檔名>.feature.spec.js`；範疇是 Rule 或 Example 時以 `npx --no-install playwright test --grep "<以 feature 名稱錨定的 Rule 或 Example 標題>"` 篩選（錨定寫法依 Rule 15），場景大綱用大綱標題，一次跑完所有例子列；不論哪一種，執行前都以相同指令加 `--list` 預檢數量（依 Rule 15）。端點資料夾指令對應產生檔的 `.features-gen/truth/features/frontend`（其下的 `e2e` 子資料夾一併包含），即 `bddgen` 後執行 `npx --no-install playwright test .features-gen/truth/features/frontend`；路徑相對於 `playwright.config.js` 所在目錄，指令必須在該目錄執行。任務層（red、green、refactor）只執行任務指令組（Rule 6：慢端點的任務指令組就是範疇指令）；範疇本身是端點資料夾時，範疇指令就是端點資料夾指令。以下 Example 皆對照此專案：

```text
frontend/playwright.config.js：defineBddConfig features ['../specs/truth/features/frontend/*.feature', '../specs/truth/features/frontend/e2e/*.feature']
frontend/package.json：test:e2e = bddgen && playwright test
產生檔：frontend/.features-gen/truth/features/frontend/改答案.feature.spec.js
```

### Good Example

這個範例以前端的範疇指令先 bddgen 再以 feature 名稱錨定的 Rule 標題 `--grep`，端點資料夾指令指向 `.features-gen/truth/features/frontend`，兩者都在 `frontend` 目錄執行。

```text
範疇：specs/truth/features/frontend/改答案.feature:20（Rule：改答案後，改答案剩餘次數必須減少一次）
範疇指令：cd frontend && npx --no-install bddgen && npx --no-install playwright test --grep "改答案 改答案後，改答案剩餘次數必須減少一次 "
端點資料夾指令：cd frontend && npx --no-install bddgen && npx --no-install playwright test .features-gen/truth/features/frontend
```

### Bad Example

這個範例把 feature 的行號直接傳給 Playwright，playwright 找不到符合的測試檔而回報 No tests found；若改去對產生檔 spec.js 的行號，行號與 feature 不同，跑到的是別的 Example。

```text
cd frontend && npx --no-install playwright test ../specs/truth/features/frontend/改答案.feature:20
→ Error: No tests found
```

## Rule 10 -- 共用測試資料庫的指令必須序列執行

**強度：MUST**

backend、database 的 behave 與 Playwright 的 e2e 共用同一個測試資料庫，Playwright 另外自行啟動後端並占用固定 port，任兩個指令同時執行會互相清除資料、搶 port 而產生假失敗，這些假失敗還會被當成回歸。所有測試指令必須一個結束才啟動下一個，不得背景、平行或在其他指令未結束時重跑，也不得為了加速改測試設定的 `workers`。以 run_suite.py 執行時依 `--step` 的順序序列執行。

### Good Example

這個範例以 run_suite.py 依序執行四個指令，前一個結束才啟動下一個，耗時由腳本記錄。

```text
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/run_suite.py" --out $TMP/bdd-verify --step backend ... --step database ... --step component ... --step e2e ...
→ backend 96 秒 → database 12 秒 → component 6 秒 → e2e 約 4 分鐘，依序完成
```

### Bad Example

這個範例為了省時間把 backend 與 e2e 同時啟動，兩者同時清空與寫入同一個資料庫，e2e 的 Given 起點被 backend 的清理動作刪掉，十幾個 Example 假失敗，被當成回歸。

```text
cd backend && uv run --no-sync python -m behave -D suite=api &
cd frontend && npm run test:e2e
→ e2e 出現 17 個失敗（房間不存在），其實是資料被另一個指令清掉
```

## Rule 11 -- 每個測試指令必須設逾時

**強度：MUST**

每個測試指令都必須有逾時保護，由呼叫者依上次的耗時（約 2 至 3 倍）決定秒數，沒有耗時紀錄時 backend、database、元件測試用 600 秒，Playwright 用 1800 秒。逾時必須結束整個行程樹（含 npm、node、瀏覽器），並視為這個指令沒有產生可用報告：不得把它的部分報告交給 verify_result.py 比對，也不得當成通過；依失敗原因類別規則讀 log 找出卡住的位置後歸類。以 run_suite.py 執行時以 `--step` 的逾時秒數設定。

### Good Example

這個範例的 e2e 因某個 Driver 等不到元素而卡住，1800 秒時被結束，不比對報告，從 log 找到卡住的 step 後歸為測試程式錯誤。

```text
run_suite.py：[e2e] 逾時，1800.2 秒（exit 1）
處理：不執行 verify_result.py 比對 e2e；讀 e2e.log，卡在 When 房主按下「改答案」等待 #answer-input
類別：測試程式錯誤（selector 寫錯）
```

### Bad Example

這個範例沒有逾時保護，Playwright 的單一動作等不到元素，依設定的 `timeout: 300_000` 每個 Example 要等 5 分鐘，二十個 Example 卡一個半小時，使用者以為死當而中斷。

```text
cd frontend && npm run test:e2e   （沒有逾時；每個缺元素的 Example 等 300 秒）
```

## Rule 12 -- Windows 下 Python 輸出必須設 UTF-8

**強度：MUST**

在 Windows 執行會輸出中文的 Python 指令（behave 的 step 名稱與錯誤訊息含中文）時，必須設定環境變數 `PYTHONIOENCODING=utf-8`，否則輸出以 cp950 編碼，JSON 報告與 log 出現亂碼或 UnicodeEncodeError，verify_result.py 無法解析。run_suite.py 已替每個指令設定；不經過 run_suite.py 單獨執行 Python 指令時，必須自己設定。

### Good Example

這個範例單獨執行 backend 的 behave 時先設定編碼，報告中的中文步驟名稱完整。

```text
cd backend && PYTHONIOENCODING=utf-8 uv run --no-sync python -m behave -D suite=api ../specs/truth/features/backend/改答案.feature:10 -f json -o $TMP/rerun.json
```

### Bad Example

這個範例在繁中 Windows 直接執行，輸出編碼是 cp950，含「甲」「祕密」等字元的訊息變成亂碼或直接 UnicodeEncodeError，step 名稱與錯誤訊息無法正確輸出。

```text
cd backend && uv run --no-sync python -m behave -D suite=api -f json -o $TMP/rerun.json
→ UnicodeEncodeError: 'cp950' codec can't encode character
```

## Rule 13 -- 執行 e2e 與負載測試前後必須確認沒有殘留的測試行程

**強度：MUST**

每次執行 e2e（Playwright）或負載測試前，都必須先以 `cleanup_test_processes.py --kill` 結束專案目錄底下殘留的 uvicorn、node、python、瀏覽器行程（沒有殘留時不結束任何行程），執行後再以不帶 `--kill` 的指令列出確認沒有殘留；`--kill` 只結束腳本列出的、位於專案目錄底下由測試啟動的行程，不得結束專案外或其他使用者的行程。被中斷的測試會留下行程占住 8000 埠或 MySQL 連線，出現 `Too many connections`、`address already in use` 或埠被占用時，必須先清理再重跑；這類失敗不算回歸，也不算環境未就緒，清理後仍連不上服務才依環境問題處理。

### Good Example

這個範例在重跑 e2e 前列出殘留行程，結束後再執行，假失敗消失。

```text
uv run "D:/plugins/spec-driven-bdd/skills/bdd/scripts/cleanup_test_processes.py" --kill → residual 3（uvicorn 1、node 1、chrome 1，都在專案 backend 與 frontend 底下）、killed 3
重跑 e2e → 原本 Too many connections 的 12 個 Example 通過，不列為回歸
```

### Bad Example

這個範例遇到 `Too many connections` 就當成回歸停下，或以名稱結束機器上所有 node 行程，連使用者另一個專案的開發伺服器也被終止。

```text
e2e 出現 Too many connections → 12 個回歸，停下回報
（或）taskkill /IM node.exe /F
```

## Rule 14 -- e2e 測的是建置後的前端，改了前端原始碼必須先重建

**強度：MUST**

前端 e2e 使用建置產物（如 `frontend/dist`）時，必須確認它與目前的 `frontend/src` 一致：測試的真實環境輔助程式只在 `dist/index.html` 不存在時才建置（如 `frontend/tests/e2e/support/drivers/shared/真實環境.js` 的 `ensureBuilt`），改了 `frontend/src` 後不會自動重建，e2e 測到的是舊產品。因此前端 red、green、refactor 與 verify 執行 e2e 前，只要 `frontend/src` 有比建置產物新的修改，必須先在 `frontend` 目錄執行專案既有的 `npm run build`（專案既有的 script，不是安裝套件）；沒有修改時不必重建。

### Good Example

這個範例在前端綠燈改了 `frontend/src` 後，先重建再執行範疇指令，e2e 測到新畫面。

```text
前端 green 範疇：specs/truth/features/frontend/改答案.feature:20；修改 frontend/src/components/SkillPanel.vue
cd frontend && npm run build → 成功
cd frontend && npx --no-install bddgen && npx --no-install playwright test --grep "改答案 改答案後，改答案剩餘次數必須減少一次 " → 通過
```

### Bad Example

這個範例改了 `frontend/src` 後直接執行 e2e，`dist/index.html` 已存在而不重建，測到的是舊畫面，green 以為產品程式寫錯而反覆修改。

```text
修改 frontend/src/components/SkillPanel.vue → 直接 playwright test → 仍失敗：getByTestId('skill-change-confirm') 不存在
（dist 是修改前建置的）
```

## Rule 15 -- Playwright 的 --grep 必須以 feature 名稱錨定，執行前預檢數量

**強度：MUST**

Playwright 的 `--grep` 對完整標題路徑（專案、檔案、`feature 名稱`、`Rule 標題`、`Example 標題`，以空白相連，沒有 `Rule:` 前綴）做子字串比對，單用 Rule 標題會比對到標題含有它的其他 Rule 或其他 feature。必須寫成 `"<feature 名稱> <Rule 標題> "`（範疇是單一 Example 時再接 `<Example 標題>`），三者以單一空白相連，Rule 標題緊接在 feature 名稱之後；範疇有多條 Rule（多個 Rule 行號或多個 Rule 名稱）時，每條 Rule 各寫成這個寫法，再以 `|` 接成一個 `--grep`；標題中的正規表示式特殊字元（`. + * ? ( ) [ ] { } | ^ $ \`）必須以反斜線跳脫。以雙引號包住（Windows 的 cmd 與 Git Bash 都可，標題含雙引號時改用 `.` 比對）。範疇是整份 feature 或端點資料夾時以產生檔或產生資料夾路徑執行，不用 `--grep`。不論範疇大小，執行前必須以相同指令加 `--list` 預檢，列出的測試數量必須等於 resolve_scope.py 輸出的 `playwright_list_count`（範疇內每個一般 Example 算 1，場景大綱每個例子列各算 1）；`example_count` 對場景大綱只算 1 個 Example，不可直接拿來比對。換算以 `features[].examples[]` 中 `kind` 為 `outline` 者的 `example_rows`（例子列數，不含表頭）取代 1。不符時修正篩選，不得直接執行。

### Good Example

這個範例以 feature 名稱「改答案」錨定，`--list` 只列出該 Rule 的 3 個測試。

```text
範疇：specs/truth/features/frontend/改答案.feature 的 Rule「猜測必須記入猜測歷史」
cd frontend && npx --no-install playwright test --list --grep "改答案 猜測必須記入猜測歷史 " → Total: 3 tests（全在 改答案.feature.spec.js）
```

這個範例的範疇含場景大綱，換算後再比對。

```text
範疇：specs/truth/features/frontend/連猜三次.feature:279（Rule 內 1 個場景大綱，Examples 表 2 列）
resolve_scope.py：example_count 1、example_rows 2、playwright_list_count 2
--list → Total: 2 tests → 與 playwright_list_count 相符，才執行
```

這個範例的範疇以 Rule 名稱定位兩條 Rule，各自錨定後以 `|` 接成一個 `--grep`。

```text
範疇：specs/truth/features/frontend/改答案.feature ＞ Rule「確認改答案後，新答案必須生效」、Rule「改答案後，必須仍輪到同一位玩家」
cd frontend && npx --no-install playwright test --list --grep "改答案 確認改答案後，新答案必須生效 |改答案 改答案後，必須仍輪到同一位玩家 " → 數量等於 resolve_scope.py 的 playwright_list_count，才執行
```

### Bad Example

這個範例只用 Rule 標題，同時比對到 `連猜三次.feature` 的「連猜中的猜測必須記入猜測歷史」，多執行 4 個不在範疇內的 Example，其中失敗的被當成回歸。

```text
cd frontend && npx --no-install playwright test --list --grep "猜測必須記入猜測歷史" → Total: 7 tests（改答案 3、連猜三次 4）
```

## Rule 16 -- dsl.md 與介面文檔矛盾時先判斷錯在哪一邊

**強度：MUST**

dsl.md 沒標「（擬定）」的技術對應（API 路徑、欄位與型別、錯誤碼、testid、資料表欄位）與介面文檔矛盾時，不得直接認定 dsl.md 有問題，必須讀進行中 plan 的 acceptance 中相關的 AC 與 spec.md 的 FR、NFR，依序判斷錯在哪一邊並寫出依據：一邊違反 PM 核准的 AC、FR 或 NFR 時錯在這一邊；需求沒有決定時，介面文檔自相矛盾（同一份文檔的範例、約束或其他操作對同一事實的定義不同），或與其他文件（其他端點的 dsl.md、資料模型、先前 plan 的介面文檔）對同一事實的定義不同、而這次的需求沒有要求改變它時，錯在介面文檔（只有程式這樣運作不算依據，程式是終端產物，與 dev-finding 修正擁有者規範 Rule 2 相同）；其餘錯在 dsl.md，因為介面文檔是介面事實的家，dsl.md 依它撰寫。判斷只決定交辦對象（依停下回報規範）：錯在 dsl.md 交由 dsl-refine；錯在介面文檔經 dev-finding 的 record 交給該文檔的 Planner，不交 dsl-refine。不得自行修改任何一邊讓兩者一致。

### Good Example

這個範例在後端綠燈發現契約把剩餘次數寫成字串，契約自己的約束與 dsl.md、前端 dsl.md 都把它當整數，判定錯在契約，經 dev-finding 交給 api-plan。

```text
green 範疇：specs/truth/features/backend/改答案.feature
矛盾：contracts/components/schemas/SkillCounts.yaml › change_answer_left 為 type: string（假設），同一個欄位卻有 minimum: 0、maximum: 1；backend/dsl.md「雙方畫面顯示下列技能剩餘次數：」的改答案為整數
需求：AC-02 只寫剩餘次數 1，沒有決定型別
既有：frontend/dsl.md 同一句型以整數比對，backend/app/services/snapshot.py 回傳整數，既有 Example 皆通過
判斷：錯在介面文檔（約束自相矛盾，且與既有程式行為不同，這次的需求沒有要求改變）→ 建議委派 dev-finding 的 record，應修正的擁有者為 api-plan
```

### Bad Example

這個範例一看到矛盾就判定 dsl.md 有問題交給 dsl-refine，dsl-refine 依契約把句型改成字串，錯的型別留在 truth 的契約，前端用到同一欄位的 Example 也跟著改錯。

```text
矛盾：SkillCounts.yaml › change_answer_left 為 string，backend/dsl.md 為整數
判斷：dsl.md 有問題 → 停下回報，交由 dsl-refine
```
