# 綠燈規範

## Rule 1 -- 只實作範疇需要的行為，並依必讀與 NFR 原文實作

**強度：MUST**

產品程式只能加入讓範疇內 Example 通過所需的行為，不得提前實作範疇外 Example 的行為，也不得加入任何 Example 都沒有要求的功能。實作這些行為時，必須依呼叫者附帶的必讀原文與 NFR 約束原文決定做法：範疇需要的資料表、欄位、API 回應或畫面元素，其名稱、型別、約束、錯誤碼與文案照原文完整建立；NFR 約束（如回應時間、雙方畫面一致、鍵盤操作）是實作方式的限制，不是新增功能的理由。產品檔案應放在 plan.md 原始碼結構與呼叫者附帶的預計修改所列的位置。呼叫者沒有附帶必讀、NFR 約束或預計修改時照常執行，改依範疇所屬端點的 dsl.md、介面文檔與 plan.md 原始碼段實作，不得因缺少附帶內容而停下。

### Good Example

這個範例的範疇需要寫入技能紀錄，依附帶的 `data-model.dbml › Table room_events` 原文完整建立欄位與唯一索引，並依 NFR-011 讓快照與推播共用同一份狀態。

```text
green 範疇：specs/truth/features/backend/改答案.feature（附 Phase 4 標頭）
step3_room_events：依 data-model 建立 room_events 的欄位與 uk_room_events_room_seq（原文列出的唯一索引）
service.py：use_change_secret 寫入 room_events 後，GET 快照與 WebSocket 推播都從 snapshot.build_snapshot() 取得（NFR-011 雙方畫面一致）
未實作：openapi.yaml 列出、但範疇內沒有 Example 的 GET /api/rooms/{roomId}/events
```

### Bad Example

這個範例只做到讓 Example 通過，沒有讀附帶的 data-model 原文，room_events 漏掉唯一索引；同時把 openapi.yaml 列出、沒有 Example 驅動的事件查詢端點也寫了出來，之後該行為的紅燈第一次就通過。

```text
step3_room_events：只建 id、room_id、kind 三個欄位（Example 只查 kind）
routes.py：另外新增 GET /api/rooms/{roomId}/events
```

## Rule 2 -- 綠燈必須還原紅燈留下的破壞

**強度：MUST**

green 完成前，必須搜尋範疇對應的 `BDD-RED-BREAK` 標記（標記註明的範疇與本次範疇相同，或標記的 Example 行號落在本次範疇內）並還原那段邏輯，連標記一併移除；還原不得以新增範疇外行為的方式取代。範疇已通過仍有標記時也要還原，並以任務指令組執行確認沒有回歸後存回。

### Good Example

這個範例在實作前搜尋標記，還原被破壞的扣次數邏輯，標記一併移除。

```text
grep BDD-RED-BREAK → backend/app/service.py:88（specs/truth/features/backend/改答案.feature:21）
還原：恢復 change_secret_left -= 1 並刪除標記 → 範疇與 backend 資料夾通過
```

### Bad Example

這個範例繞過破壞另寫一段邏輯讓範疇通過，標記與被改壞的程式留在原處，[驗證] 前的搜尋仍找到未還原的破壞而停下。

```text
backend/app/service.py:88 的破壞保留；在 use_change_secret 外另加 fix_change_secret_left() 讓範疇通過
```

## Rule 3 -- 完成說明列出修改的產品檔案

**強度：MUST**

綠燈完成說明必須列出這次新增或修改的每個產品檔案；呼叫者附帶預計修改時，另列出預計修改以外的檔案與修改原因；並對照進行中 plan 的 plan.md「原始碼（repo 根目錄）」目錄樹，另列「原始碼段以外的產品檔」：新增或修改的產品檔既不是目錄樹列出的檔案，也不在目錄樹中沒有列出子項目的目錄底下，沒有時寫「原始碼段以外的產品檔：無」。範疇已通過而沒有修改時寫「範疇已通過，未修改產品程式」。不得只寫「green 完成」，也不得以檔案在預計修改內為由略過原始碼段的對照，因為後續任務與 bdd 都依原始碼段找模組的位置。

### Good Example

這個範例列出修改的檔案，標出預計修改以外的檔案與原因，並對照原始碼段標出不在其中的產品檔。

```text
green 完成：specs/truth/features/backend/房間聊天.feature
修改：backend/app/routes/api.py、backend/app/services/rooms.py、backend/app/services/snapshot.py、backend/app/services/chat.py
預計修改以外：backend/app/services/chat.py（訊息送出與頻率限制抽成獨立服務）
原始碼段以外的產品檔：backend/app/services/chat.py（plan.md 原始碼的 services/ 只列 rooms.py、snapshot.py）
存回的最後一次執行：regressions 0
```

### Bad Example

這個範例只寫完成，implement 與使用者不知道 services/chat.py 也被改過，[驗證] 出現回歸時無法判斷它是否由這個任務造成。

```text
green 完成，regressions 0
```

### Bad Example

這個範例只對照預計修改，沒有對照原始碼段；新增的 chat.py 不在 plan.md 的原始碼段，implement 沒有交 system-analysis 修正，下一個 Phase 依原始碼段把聊天推播寫進 rooms.py，同一功能的程式分散兩處。

```text
green 完成：specs/truth/features/backend/房間聊天.feature
修改：backend/app/routes/api.py、backend/app/services/rooms.py、backend/app/services/chat.py
預計修改以外：backend/app/services/chat.py（訊息送出抽成獨立服務）
```
