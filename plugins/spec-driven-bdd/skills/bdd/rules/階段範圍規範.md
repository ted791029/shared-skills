# 階段範圍規範

## Rule 1 -- 各階段依定義表判定範圍

**強度：MUST**

red、green、refactor、rerun 開始前必須以現況（範疇與執行規範 Rule 6：沿用的上次結果，或確認現況的執行）確認所選階段的進入條件成立，執行中只能修改「可修改」欄列出的內容，達成「完成條件」欄的全部條件才算完成。進入條件不成立時必須依停下回報規範停下並寫出要先執行的 subcommand，不得開始該階段，也不得先修改程式讓進入條件成立。feature、dsl.md、用語表、介面文檔與測試設定一律不得修改。

| 階段 | 進入條件 | 可修改 | 完成條件 |
|---|---|---|---|
| red | 無（Phase 1 的停下條件都不成立即可開始） | step definitions、Driver 與測試支援程式，句型的測試寫法改了時含既有的 step 與 Driver（依 Step definitions 撰寫規範）；範疇內 Example 第一次就通過時，可破壞負責該 Example Then 結果的產品程式 | 範疇內每個 Example 的失敗原因都是「業務行為尚未實作」或來自這次破壞，且失敗訊息能證明本端點的該行為尚未實作（不得是其他端點尚未實作、環境問題、測試程式錯誤、undefined 或 ambiguous step）；改寫既有 step 時，其他用到它的 Example 都已執行（依紅燈規範）；存回的最後一次執行中，任務指令組涵蓋的基準已通過的 Example（快速端點資料夾內範疇外的 Example）仍通過，且沒有本階段可修正的回歸 |
| green | 現況中範疇內每個 Example 都是「業務行為尚未實作」的紅燈，或已通過（依 Rule 2）；有「其他端點尚未實作」時停下並寫出依賴的端點與行為，有「測試程式錯誤」（含 undefined step）時停下並建議先對同一範疇執行 red | 只有產品程式；不得修改 step definitions、Driver 與測試支援程式，不得放寬或刪除斷言 | 範疇內 Example 全部通過（範疇已通過時不新增產品程式）；紅燈留下的破壞已還原；修正迴圈與任務驗證的條件同 red |
| refactor | 現況中範疇內每個 Example 都通過 | 範疇內句型在 dsl.md Step 檔對照登記的 step 檔、這些 step 呼叫的 Driver、這些 Driver 呼叫的產品程式，以及呼叫者附帶的任務描述指定新增或修改的產品檔案；不得修改斷言，不得把 step 搬離登記的 Step 檔 | 同 green |
| rerun | 無（Phase 1 的停下條件都不成立即可開始） | 無：不得修改 step definitions、Driver、測試支援程式與產品程式，也不得破壞產品程式；只由 verify_result.py 寫入結果檔 | 任務描述列出的句型與參數，既有 step 都判定不用改（依重跑規範）；範疇的結果可沿用且全部通過，或以任務指令組執行一次並存回，存回的結果沒有回歸、未執行或無法對應的 Example |

### Good Example

這個範例確認 red 沒有進入條件後開始，只修改 red 可修改的 step 與 Driver；範疇是整份 feature，後端已在前面的 Phase 完成，所有 Example 都因本端點畫面元素不存在而失敗，最後一次執行沒有回歸、存回後才判定完成。

```text
subcommand：red；範疇：specs/truth/features/frontend/改答案.feature（backend/改答案.feature 的綠燈已完成）
進入條件：無 → 開始
修改：frontend/tests/e2e/steps/modules/技能/改答案.js、frontend/tests/e2e/support/drivers/modules/技能.js；產品程式未修改
範疇：31 個 Example ✗ getByTestId('skill-change-button') 不存在，前端尚未撰寫 → 業務行為尚未實作
任務指令：bddgen 後 playwright test .features-gen/truth/features/frontend/改答案.feature.spec.js（只跑範疇）
最後一次執行（--ran-scope 與 --expected-fail 都是 specs/truth/features/frontend/改答案.feature）：regressions 0 → 存回 → red 完成
```

### Bad Example

這個範例在 green 時讓範疇通過的方式是修改 Driver 的斷言比對，green 不可修改 Driver，範疇看似轉綠，產品程式其實仍回傳錯誤的答案。

```text
subcommand：green；範疇：specs/truth/features/backend/改答案.feature
失敗：AssertionError: my_answer 0123 != 4567
處理：修改 backend/tests/support/drivers/modules/技能.py，讀取 request 送出的 answer 當成目前答案 → 通過
```

## Rule 2 -- 基準失敗但現況已通過時，green 以範疇已通過完成

**強度：MUST**

green 的現況（沿用的上次結果或確認現況的執行）中，範疇內 Example 基準是失敗、現況已通過（同一次執行中較早的綠燈已順帶讓它通過），green 視為「範疇已通過，無需新增產品程式」完成：不新增也不修改產品程式，只還原紅燈留下的破壞；有還原時依全端點驗證規範 Rule 8 以任務指令組執行並存回，沒有修改任何檔案時不再執行。只實作範疇需要的行為，不得為呼叫者附帶的描述或預計修改列出、但沒有範疇內 Example 驅動的功能多寫程式；NFR 約束與必讀原文只約束範疇行為的實作方式，不是新增功能的理由。

### Good Example

這個範例的範疇因前面 Phase 的綠燈已通過，green 沒有新增程式，以確認現況的執行存回後完成。

```text
green 範疇：specs/truth/features/database/連猜三次.feature
基準：specs/truth/features/.verify-result.json 連猜三次.feature:4、:12 ✗（red 時欄位尚未建立）
現況：baseline.py reusable false（最後一次執行後 backend 有改動）→ 確認現況執行 database 資料夾 → :4、:12 ✓（backend/改答案.feature 的綠燈在 step2_guesses 已建立 burst_index）
處理：範疇已通過，無需新增產品程式；搜尋 BDD-RED-BREAK 無殘留；本階段沒有修改檔案 → 以確認現況的報告存回，regressions 0 → green 完成
```

### Bad Example

這個範例因預計修改列出 `snapshot.py`，在範疇已通過時仍新增快照欄位，沒有任何範疇內 Example 驅動它，之後該行為的紅燈第一次就通過。

```text
現況：連猜三次.feature:4、:12 ✓
處理：預計修改有 backend/app/snapshot.py → 新增 burst_left 欄位到快照
```
