# 紅燈規範

## Rule 1 -- 第一次就通過時破壞對應的產品程式並保留到 green

**強度：MUST**

範疇內的 Example 第一次執行就通過時，必須改壞產品程式中負責該 Example Then 結果的那段邏輯，重新執行確認它因斷言失敗並記錄失敗訊息。因這次破壞而失敗的基準已通過 Example，不算被改壞。破壞後 Example 仍通過時，代表斷言抓不到該行為，必須修正 step definitions 的斷言。破壞驗證完成後必須保留破壞，由同範疇的 green 還原；red 不得自行還原。

### Good Example

這個範例改壞扣次數邏輯，Example 因剩餘次數斷言失敗，保留破壞交給同範疇的 green。

```text
第一次執行：specs/truth/features/backend/改答案.feature:21 passed（產品已會扣改答案次數）
破壞：use_change_secret 不扣 change_secret_left
重新執行：AssertionError: change_secret_left 1 != 0 → 紅燈成立
破壞驗證：backend/app/service.py:88、AssertionError: change_secret_left 1 != 0、保留到 green
```

### Bad Example

這個範例在 Example 第一次就通過時直接結束紅燈，這個 Example 的斷言從沒失敗過，無法確定它真的會在扣次數錯誤時失敗。

```text
第一次執行：改答案.feature:21 passed → 行為已存在，紅燈完成
```

## Rule 2 -- 完成說明寫出失敗類別、證據與未執行的 step

**強度：MUST**

紅燈完成說明必須為範疇內每個 Example（範疇大時可依相同失敗原因分組）寫出失敗類別與失敗訊息中的證據（例如 404 的請求、缺少的回應欄位、不存在的畫面元素或資料表欄位）。Example 失敗在較早的 step 時，之後的 step、Driver 在 red 沒有實際執行，必須列出這些 step；它們的錯誤要到 green 才會暴露。有破壞時寫出破壞驗證（位置、失敗訊息、保留到 green）；有改寫既有 step 時依 Rule 4 寫出改寫的 step 與其他用到它的 Example 的結果。不得只寫「red 完成」或只寫失敗數量。

### Good Example

這個範例依失敗原因分組寫出證據，並列出因較早 step 失敗而沒有執行的 step。

```text
red 完成：specs/truth/features/frontend/改答案.feature（31 個 Example）
- 28 個 業務行為尚未實作：When "甲" 開啟改答案 → getByTestId('skill-change-button') 不存在
- 3 個 業務行為尚未實作：Then "甲" 的改答案剩餘次數為 1 → getByTestId('skill-my-change-left') 不存在
未實際執行的 step：When "甲" 送出新答案 {四碼}、Then "乙" 的畫面在 2 秒內開始播放 {技能} 特效（被開啟改答案擋住，其 step 與 Driver 尚未驗證）
破壞：無
存回的最後一次執行：regressions 0
```

### Bad Example

這個範例只寫出完成與數量，沒有證據也沒有列出未執行的 step；green 時暴露 selector 錯誤，implement 與使用者都不知道這些 step 從沒跑過。

```text
red 完成：改答案.feature 31 個 Example 失敗，regressions 0
```

## Rule 3 -- 破壞必須帶標記並預期連帶失敗

**強度：MUST**

破壞產品程式時，必須在被改壞的位置加上註解標記 `BDD-RED-BREAK`（註明對應的範疇、Example 行號與原邏輯），讓 green 與 verify 前的搜尋能找到並還原。破壞可能同時讓其他 Example 失敗，含其他端點、其他 feature 的 Example；紅燈完成說明必須列出破壞標記位置與能判斷的預期連帶失敗，並寫明由同範疇的 green 還原。標記註解寫的範疇與行號必須與破壞當下 feature 的實際行號一致。

### Good Example

這個範例改壞扣次數邏輯並加標記，說明預期連帶失敗的前端 Example 與還原時機。

```text
破壞：backend/app/service.py:88  # BDD-RED-BREAK specs/truth/features/backend/改答案.feature:21 原邏輯 change_secret_left -= 1
預期連帶失敗：specs/truth/features/frontend/改答案.feature:20（畫面剩餘次數，依賴同一邏輯）
還原：T009 green（同範疇）搜尋標記還原
```

### Bad Example

這個範例直接改掉邏輯沒有標記，也沒有說明連帶失敗；green 搜尋不到標記，破壞留在產品程式，到 [驗證] 時前端 Example 失敗被當成回歸，沒有人記得 backend 還有破壞。

```text
backend/app/service.py:88 刪掉 change_secret_left -= 1 → red 完成
```

## Rule 4 -- 改寫既有 step 時其他用到它的 Example 也要執行

**強度：MUST**

依 Step definitions 撰寫規範改寫既有 step 或 Driver 時，必須以 feature 的步驟（含 Background）比對句型，列出範疇所在端點資料夾中所有用到這個 step 的 Example，確認每一個都在這次執行之內：在範疇內，或在任務指令組執行的端點資料夾內（快速端點）；其餘的另以範疇指令一併執行，並列入 `--ran-scope`。這些範疇外的 Example 因改寫後的斷言驗出業務行為尚未實作而失敗時，與破壞產品程式的連帶失敗相同，列入 `--expected-fail` 存為失敗，不得改回舊的 step 讓它通過；其他類別的失敗依全端點驗證規範 Rule 9 處理。紅燈完成說明必須列出改寫的 step 位置，以及這些 Example 的結果（通過，或因改寫而失敗、需要各自的紅燈與綠燈）。

### Good Example

這個範例改寫共用的提示 step 後，把前端範疇外用到它的 Example 一併執行，因新斷言而失敗的列為預期失敗並寫進完成說明。

```text
red 範疇：specs/truth/features/frontend/改答案.feature ＞ Rule「改答案後，對手必須看到寫明技能名稱的使用提示」
改寫：frontend/tests/e2e/steps/shared/提示.js「玩家 {玩家} 看到提示 {提示}」改讀 role=status（truth-changes 記為改測試寫法）
範疇外用到它的 Example：連猜三次.feature:16、:124 等 14 個（前端慢端點，另以 --grep 一併執行，列入 --ran-scope）
結果：12 個通過；連猜三次.feature:16、:124 的提示不在 role=status 而失敗（業務行為尚未實作）→ 列入 --expected-fail，需要各自的紅燈與綠燈
```

### Bad Example

這個範例改寫共用 step 後只執行範疇，其他 feature 用到同一 step 的 Example 在結果檔仍記為通過，沒有人知道它們在新的斷言下會失敗，直到 [驗證] 才以回歸出現。

```text
改寫：frontend/tests/e2e/steps/shared/提示.js 改讀 role=status
執行：只有改答案.feature 的 Rule 3 個 Example → red 完成
（連猜三次.feature:16、:124 也用這個 step，沒有執行）
```
