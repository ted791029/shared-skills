# 停下回報規範

## Rule 1 -- 只有列舉的情況才停下

**強度：MUST**

只有下列情況必須停下。標明階段的情況只在該階段停下；未標明的不論 subcommand 是 red、green、refactor 或 rerun 都同樣停下，不得依階段放行：

- 測試環境未就緒、測試設定未就緒（沒有測試設定涵蓋範疇的 feature，或沒有載入 step），或發生環境問題（例如後端服務沒啟動、連不上）。
- feature、dsl.md 或用語表有問題，包含要沿用的既有 step 與 dsl.md 的測試撰寫語意不一致（同一個句子在其他 feature 有不同的意思），以及 dsl.md 與介面文檔矛盾（不論判斷錯在哪一邊）。
- rerun：任務描述列出的句型或參數，既有 step 需要改（依重跑規範）。
- 失敗原因是其他端點尚未實作：範疇依賴的其他端點行為不存在，代表任務排序有誤、內層綠燈沒有實作到，或內層 feature 缺少驅動它的 Rule。
- green：範疇內 Example 的失敗原因是測試程式錯誤，例如 red 時被較早的 step 擋住而沒有執行到的 step，這次才暴露 selector 寫錯；green 絕不修改測試程式，一旦發現必須停下（依 Rule 4）。
- 所選階段的進入條件不成立（依階段範圍規範）。
- verify 時完整指令組執行前仍有未還原的紅燈破壞標記（`BDD-RED-BREAK`）。
- 單獨 verify 發現回歸；修正迴圈的執行在重跑後仍出現本階段不可修正的回歸（依全端點驗證規範）；verify_result.py 的結果有未執行、無法對應的 Example。

除上面列出的 green 範疇內測試程式錯誤外，測試程式寫錯、產品程式寫錯都不算，包含修正迴圈的執行發現本階段造成的這兩類回歸，必須在本階段可修改的範圍內繼續修正，不得停下。

### Good Example

這個範例在前端 red 遇到 Given 用到的後端連猜三次端點回 404，判定為其他端點尚未實作而停下，寫出依賴的端點與行為。

```text
subcommand：red；範疇：specs/truth/features/frontend/改答案.feature
失敗：:272 Given 系統處於 "加入者下一回合不能行動、輪到房主"：POST /api/rooms/r1/skills/burst → 404（後端服務可連線、路由不存在）
類別：其他端點尚未實作 → 停下回報：依賴 backend 連猜三次.feature（POST /api/rooms/{roomId}/skills/burst）尚未實作
```

### Bad Example

這個範例把 404 當成合格紅燈完成 red，前端其他 step 被擋在 Given 沒有執行；相鄰的 green 仍會在同一處停下，排序錯誤晚一個任務才被發現，期間寫好的 step 也從未實際執行過。

```text
subcommand：red；範疇：specs/truth/features/frontend/改答案.feature
失敗：:272 POST /api/rooms/r1/skills/burst → 404
→ red 完成（其他端點尚未實作也算紅燈）
```

## Rule 2 -- 不得修改 feature、dsl.md、用語表與介面文檔

**強度：MUST**

不論是否停下，都不得修改範疇所屬端點資料夾的 feature、dsl.md、`specs/truth/features/用語表.md` 與介面文檔，包含加 tag、改步驟文字、補上缺少的句型、改寫測試撰寫語意，或改正契約、UI 契約、資料模型的內容。發現它們有問題時只能停下回報。

### Good Example

這個範例發現 dsl.md 沒有收錄 feature 用到的句型、契約的型別寫錯，都停下回報而不自行補上或改正。

```text
backend/改答案.feature:31 使用「乙 本回合不能行動」，backend/dsl.md 沒有這個句型
→ 停下回報，dsl.md 未修改
contracts/components/schemas/SkillCounts.yaml › change_answer_left 的型別與 dsl.md 矛盾，判斷錯在契約
→ 停下回報，契約未修改
```

### Bad Example

這個範例自行在 dsl.md 補上句型與測試撰寫語意後繼續紅燈，dsl-refine 的產生紀錄與 dsl.md 從此不一致，下次增量更新時會把這列當成使用者手改內容而保留錯誤的語意。

```text
backend/dsl.md 沒有「{玩家} 本回合不能行動」
→ 在 Then 句型表新增一列，回應斷言寫 turn != 玩家，繼續撰寫 step
```

## Rule 3 -- 停下說明必須附位置、原文與交辦對象

**強度：MUST**

停下時必須寫出問題所在的檔案與行號、相關內容的原文、問題說明，以及處理對象：feature、dsl.md 或用語表的問題交由 dsl-refine，同一個句子在其他 feature 有不同的意思時寫出這個句子在 dsl.md 的定義、既有 step 的位置與仍依賴原本行為的 feature，請 dsl-refine 換句子；dsl.md 與介面文檔矛盾時寫出兩邊的位置與原文，以及依範疇與執行規範 Rule 16 判斷錯在哪一邊與依據，錯在 dsl.md 交由 dsl-refine，錯在介面文檔時明確寫「建議委派 dev-finding 的 record 記錄，由該文檔的 Planner 修正」，不交 dsl-refine；rerun 的既有 step 需要改時寫出句型或參數、dsl.md 的原文、既有 step 與 Driver 的位置與不符之處，並明確寫「建議改排紅燈：以 task 的增量入口把 <範疇> 改排為修正 Phase 的紅燈、綠燈、重構」，不符之處來自這次句型的異動、而 truth-changes 記為「只改說明：」時，另寫明先交 dsl-refine 把改動摘要改為「改測試寫法：」；環境問題、測試環境或測試設定未就緒交由使用者，測試設定未就緒時寫出哪個設定檔的哪個欄位沒有涵蓋範疇或沒有載入 step；其他端點尚未實作時寫出依賴哪個端點資料夾的哪個介面與行為，依賴的行為在該端點資料夾有 Rule 驅動時寫出要先對哪份 feature 執行 bdd，沒有任何 Rule 驅動時交由 dsl-refine 補上該端點的 Rule；green 範疇內出現測試程式錯誤時寫出錯誤的 step 或 Driver 位置與訊息，並明確寫「建議先執行 /bdd red <同範疇> 修正測試程式，再執行 /bdd green」，`<同範疇>` 填這次 green 的範疇原文；進入條件不成立時寫出要先執行的 subcommand；verify 前仍有破壞標記時寫出標記位置與要先執行的同範疇 green；verify 發現回歸時依全端點驗證規範為每個回歸的 Example 寫出建議下一步。

### Good Example

這個範例在前端 green 時發現乙的畫面等不到特效推播，後端 feature 沒有任何推播的 Rule，交由 dsl-refine 補上。

```text
停下：其他端點尚未實作
位置：specs/truth/features/frontend/改答案.feature:46
原文：Then "甲" 的畫面在 1 秒內、"乙" 的畫面在 2 秒內開始播放 "改答案" 特效 → 乙的畫面 2 秒內沒有收到 skill_effect
問題：依賴 backend 在改答案後推播 skill_effect（contracts/openapi.yaml › connectRoomSocket），specs/truth/features/backend/ 沒有任何 Rule 驅動這個推播
處理：交由 dsl-refine 在 backend/改答案.feature 補上推播的 Rule，task 再排入對應任務
```

這個範例在後端綠燈發現 dsl.md 與契約矛盾，寫出兩邊的原文與判斷依據，錯在契約，交給 dev-finding 而不是 dsl-refine。

```text
停下：feature 或 dsl.md 有問題（dsl.md 與介面文檔矛盾）
位置：specs/truth/contracts/components/schemas/SkillCounts.yaml:6、specs/truth/features/backend/dsl.md:101
原文：change_answer_left：type: string、minimum: 0、maximum: 1（假設）；「雙方畫面顯示下列技能剩餘次數：」的改答案（整數，必填）
判斷：錯在介面文檔，同一欄位的約束只適用於數字，且既有程式與前端 dsl.md 都以整數處理，這次的需求沒有要求改變
處理：建議委派 dev-finding 的 record 記錄，由該文檔的 Planner 修正
```

### Bad Example

這個範例只寫出有問題，沒有位置、原文與交辦對象，implement 無法對回任務，使用者得自己翻 step 與 feature 找原因，也不知道該交給哪個 skill。

```text
停下：前端測試好像有錯，請確認。
```

## Rule 4 -- green 發現測試程式錯誤時絕不自行修改測試程式

**強度：MUST**

green 在範疇內遇到測試程式錯誤（undefined、ambiguous、selector 或請求寫錯、Driver 語法錯誤）時，不得為了讓範疇通過而修改 step definitions、Driver、測試支援程式或斷言，也不得先改了再回報；必須立即停下，依 Rule 3 寫出位置、原文與「建議先執行 /bdd red <同範疇> 修正測試程式，再執行 /bdd green」。由 implement 依這個固定句型自動對同一範疇重跑 red 再 green。

### Good Example

這個範例發現 selector 與 dsl.md 不符，不改 step，直接停下並給出固定句型。

```text
green 範疇：specs/truth/features/frontend/改答案.feature:10
失敗：frontend/tests/e2e/steps/modules/技能/改答案.js:42 page.getByTestId('skill-change-confirm') 逾時（dsl.md 為 skill-change-submit）
處理：不修改 step；停下，建議先執行 /bdd red specs/truth/features/frontend/改答案.feature:10 修正測試程式，再執行 /bdd green
```

### Bad Example

這個範例在 green 直接把 selector 改成 dsl.md 的值再繼續，測試程式的修改沒有經過 red 的完成條件與破壞檢查，implement 也不知道測試程式被改過。

```text
失敗：getByTestId('skill-change-confirm') 逾時
處理：把 steps/modules/技能/改答案.js:42 改成 getByTestId('skill-change-submit') → 重新執行 → 通過
```

## Rule 5 -- 規格沒寫的行為交由 dev-finding

**強度：MUST**

執行中發現某個行為在 feature、dsl.md 與用語表都沒有寫（不是寫錯或互相矛盾），而它的結果使用者看得到時，處理對象是 dev-finding：寫出這個行為在哪裡被觀察到、規格哪裡沒有寫，並建議委派 dev-finding 的 record 記錄。不決定這個行為就無法讓範疇通過時，依 Rule 1 以 feature 有問題停下；不影響範疇時不停下，寫在完成說明中。不得自行決定這個行為該不該存在，不得為它撰寫 step 或產品程式，也不得直接交辦 dsl-refine 補上 Rule。以下 Example 皆對照此情境：

```text
green 範疇：specs/truth/features/backend/改答案.feature:21（改答案後剩餘次數減一）
現象：實作時發現，新答案與對手的答案相同時要不要接受，feature、dsl.md 與用語表都沒有寫；玩家送出後會在畫面上看到結果
```

### Good Example

這個範例的範疇不受影響，照常完成綠燈，並在完成說明寫出觀察到的位置、規格沒有寫的地方與建議委派 dev-finding。

```text
green 完成：specs/truth/features/backend/改答案.feature:21
另外發現：新答案與對手的答案相同時的結果，specs/truth/features/backend/改答案.feature 沒有任何 Rule 規定；目前 backend/app/services/skills.py:57 會接受。這是玩家看得到的行為，建議委派 dev-finding 的 record 記錄，本階段沒有為它撰寫產品程式。
```

### Bad Example

這個範例自行決定要拒絕並寫進產品程式，還直接交辦 dsl-refine 補上 Rule；玩家看得到的行為沒有經過 PM 確認就成為 truth 的 Rule。

```text
green 完成：specs/truth/features/backend/改答案.feature:21
另外處理：新答案與對手的答案相同時改為拒絕並提示「不可與對手的答案相同」（backend/app/services/skills.py:57），請 dsl-refine 補上對應的 Rule。
```
