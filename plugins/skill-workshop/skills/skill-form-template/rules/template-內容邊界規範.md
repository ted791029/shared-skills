# 樣板內容邊界規範

## Rule 1 -- 樣板只能包含產出檔案的內容

**強度：MUST**

骨架與範例的內容必須是產出檔案本身的形態，AI 複製骨架後只需替換填位符號、或照範例寫法即可成為產出。不得在骨架或範例中寫給產生它的 AI 看的填寫說明、注意事項、推理原則、流程說明或背景段落；這些內容屬於 SOP 或 RuleFile。唯一例外是骨架中以產出格式註解語法標示的重複區塊。

### Good Example

這個範例只有產出檔案會出現的結果，「由外而內」的排序原則沒有寫進範例。

```markdown
### 分析 Wave

**Wave 1 — 前端（UI-01～UI-04）**

- 相依：`spec.md`
```

### Bad Example

這個範例在範例中寫入排序原則與推理理由，AI 會把這些句子當成產出的一部分照抄到每份 plan.md，原則本身也沒有進入 SOP 或 RuleFile 被遵守。

```markdown
### 分析 Wave

由外而內分析：越接近使用者的介面越先分析，內層介面的需求由外層介面推導。

**Wave 1 — 前端（UI-01～UI-04）**

- 相依：`spec.md`，是最外層，沒有前置介面。
```

## Rule 2 -- 寫給讀者的理由屬於產出內容

**強度：MUST**

產出檔案本身就有、寫給該檔案讀者看的理由或說明（如決策理由、替代方案、結構決策）屬於產出內容，必須保留在樣板中。判斷一句話是否屬於產出內容，看它是產出檔案的讀者需要的資訊，還是在告訴 AI 如何產生這份檔案。

### Good Example

這個範例保留研究紀錄中寫給讀者的不採用理由，這是產出檔案本身的欄位。

```markdown
- **考慮過的替代方案**：存成 MySQL `LONGBLOB` 會讓資料庫膨脹，查詢記憶體壓力也大，因此不採用。
```

### Bad Example

這個範例把讀者需要的理由當成推理刪掉，產出的研究紀錄只剩結論，讀者無法判斷為什麼不採用該方案。

```markdown
- **考慮過的替代方案**：MySQL `LONGBLOB`。
```
