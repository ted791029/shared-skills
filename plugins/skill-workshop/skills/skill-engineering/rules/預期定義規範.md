# 預期定義規範

## Rule 1 -- 預期必須寫成可判斷的結果

**強度：MUST**

預期必須寫成一段預期產出的樣本，或可逐條判斷是否達成的驗收條件，讓 Phase 5 演練時能直接比對產出是否符合。不得只寫「更好」、「更精準」、「更符合需求」等無法判斷的方向。預期只寫使用者要看到的結果，不得寫達成結果的手段，例如由哪個 skill 處理、衝突交給誰、在哪一步回報；手段屬於根因分析與修改方向，寫進預期會讓根因分析把符合該手段的偏離判為未偏離。

### Good Example

這個範例把預期寫成可逐條比對的結果，沒有指定由哪個 Step 或 skill 達成，根因分析能以它判斷任何一步的產出是否偏離。

```markdown
預期：
- 只為指定 Step 的產出抽樣板，不為未指定的 Step 新增樣板
- 每份骨架都有同名的範例檔
```

### Bad Example

這個範例第一項只寫出方向，無法判斷是否達成；第二項把手段寫成預期，上游產物違反條款時，根因分析會以「已交給下游處理」把上游判為未偏離。

```markdown
預期：
- 抽出的樣板要更精準、更符合需求
- 條款與上游產物衝突時，產出物照條款撰寫，衝突列入回報交上游處理
```

## Rule 2 -- 推論必須標示並逐條確認

**強度：MUST**

每項預期必須標示來源：取自使用者原話、對話中修正動作或使用者提供的範例輸入與產出的，標為證據並引用原文；由我推測的，標為推論。每項推論必須在 Phase 1 的確認閘門逐條請使用者表態納入或不納入，使用者對整份預期的一句同意不能視為對個別推論的表態。

### Good Example

這個範例引用使用者原話作為證據，並把推測的部分單獨標為推論，確認時逐條請使用者表態。

```markdown
預期：只為指定 Step 的產出抽樣板。
- 證據：使用者原話「我只指定 Phase 2 Step 1，怎麼連 Step 2 的掛載連結也抽成樣板了」
- 推論：未指定但適合抽樣板的 Step，在回覆中列為建議、不執行

確認提問：
1. 推論「未指定但適合抽樣板的 Step 列為建議、不執行」是否納入預期？（納入／不納入）
2. 其餘證據預期與演練情境是否確認？
```

### Bad Example

這個範例雖然標出推論，卻只以一句話請使用者確認整份預期，使用者回「好」時沒有對推論表態，錯誤推論會被當成共識帶入後續修改。

```markdown
預期：只為指定 Step 的產出抽樣板。
- 證據：使用者原話「我只指定 Phase 2 Step 1，怎麼連 Step 2 的掛載連結也抽成樣板了」
- 推論：未指定但適合抽樣板的 Step，在回覆中列為建議、不執行

確認提問：以上預期是否正確？
```

## Rule 3 -- 預期不明時必須先詢問

**強度：MUST**

對話中的證據不足以寫出可判斷的預期時，必須先詢問使用者，不得帶著推測的預期進入後續 Phase。

### Good Example

這個範例在證據只說明不滿、沒說明預期時，先詢問使用者再進行分析。

```text
對話中只有「這次抽的樣板不對」，看不出預期的差異。
請問你預期的樣板與現在的差別是什麼？例如抽取範圍、骨架結構或範例內容。
```

### Bad Example

這個範例在預期不明時直接推測並進入根因分析，若推測錯誤，之後的偏離點與根因都建立在錯誤基準上，整份分析白做。

```text
對話中只有「這次抽的樣板不對」，推測使用者希望範例更完整，開始沿 SOP 找出範例缺漏的原因。
```

## Rule 4 -- 預期必須列出演練情境

**強度：MUST**

預期必須列出 Phase 5 演練用的情境，每個情境寫出輸入與預期產出。優化時必須包含原問題情境與至少一個原本產出正確的回歸情境；新建時至少包含一個代表情境。

### Good Example

這個範例是優化時的演練情境，同時列出原問題情境與回歸情境，各自寫出輸入與預期產出。

```markdown
演練情境：
- 原問題：輸入「為 skill-form-sop 的 Phase 2 Step 1 抽樣板」→ 只產出 sop.md 與 sop.example.md，Phase 2 Step 2 列為建議
- 回歸：輸入「為 skill-form-script 的 Phase 2 Step 1 抽樣板」→ 產出 script.py 與 script.example.py
```

### Bad Example

這個範例是優化時的演練情境，只列出原問題情境，修正若破壞了原本正確的產出，驗證時無法發現。

```markdown
演練情境：
- 原問題：輸入「為 skill-form-sop 的 Phase 2 Step 1 抽樣板」→ 只產出 sop.md 與 sop.example.md，Phase 2 Step 2 列為建議
```

## Rule 5 -- 新建時必須界定職責邊界

**強度：MUST**

新建時必須比對既有 skill 的 description，在預期中列出觸發情境相近的 skill 與分界。目標職責已被既有 skill 涵蓋時，必須改為優化該 skill，不得新建。

### Good Example

這個範例列出觸發情境相近的既有 skill，並逐一寫出分界。

```markdown
預期：新增 skill-form-description，負責撰寫 SKILL.md frontmatter 的 name 與 description。
職責邊界：
- skill-form-sop：只撰寫 `## SOP` 區塊，不碰 frontmatter → 不重疊
- skill-engineering：編排整個 skill 的建立，撰寫 description 時委派本 skill → 本 skill 為其下游
```

### Bad Example

這個範例沒有比對既有 skill 就新建，新 skill 與 skill-form-sop 的觸發情境重疊，兩者會爭搶同一個需求，產出互相覆蓋。

```markdown
預期：新增 skill-write-sop，負責撰寫 SKILL.md 的流程與步驟。
```

## Rule 6 -- 新建時必須確認存放位置

**強度：MUST**

新建時預期必須寫出目標 skill 的存放目錄。使用者未指定時，列出專案既有的 skill 目錄（例如 `.claude/skills/`、`.cursor/skills/`、`.agents/skills/`）並推薦一個，標為推論請使用者表態；不得依目前使用的 agent 自行決定。

### Good Example

這個範例在使用者未指定時列出專案既有的 skill 目錄與推薦，並標為推論請使用者表態。

```markdown
預期：新增 skill-review-spec。
- 推論：存放於 `.agents/skills/skill-review-spec/`，專案既有的 skill 目錄為 `.agents/skills/`（8 個 skill）與 `.claude/skills/`（1 個 skill）

確認提問：
1. 推論「存放於 `.agents/skills/skill-review-spec/`」是否納入預期？（納入／不納入）
```

### Bad Example

這個範例沒有寫出存放目錄，agent 依自己的慣例寫進 `.claude/skills/`，使用其他 agent 的成員讀不到這個 skill。

```markdown
預期：新增 skill-review-spec。
```

## Rule 7 -- 優化對象必須是原始檔

**強度：MUST**

優化時目標 skill 若位於 plugin 的安裝目錄（例如 `~/.claude/plugins/cache/`），必須停止並請使用者提供該 plugin 原始 repo 的路徑，改以原始 repo 內的 skill 為目標；不得修改安裝副本，也不得把副本複製到專案後修改。

### Good Example

這個範例發現目標是安裝副本，停止並詢問原始 repo 的路徑。

```text
目標 skill 位於 ~/.claude/plugins/cache/shared-skills/skill-workshop/，這是 plugin 的安裝副本，更新後修改會消失。
請提供 shared-skills 原始 repo 在你電腦上的路徑，我會改原始 repo 內的 skill。
```

### Bad Example

這個範例直接修改安裝副本，plugin 更新後修改被覆蓋，其他成員也拿不到這次修改。

```text
目標 skill 位於 ~/.claude/plugins/cache/shared-skills/skill-workshop/，已修改該目錄的 SKILL.md。
```
