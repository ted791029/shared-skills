# 編排判斷規範

## Rule 1 -- 依 Step 特徵選擇 deriver

**強度：MUST**

逐一檢查目標 SOP 的每個 Step，依下表選擇 deriver。一個 Step 可同時符合多項；都不符合的 Step 不交給任何 deriver。

| Step 特徵 | deriver |
|---|---|
| 含有相同輸入必定得到相同輸出的機械動作 | skill-derive-script |
| 含有 agent 容易偏離的判斷標準或專案慣例 | skill-derive-rule |
| 產出具有固定結構的檔案或內容 | skill-derive-template |
| 掛載的部件要對照的資料符合[基準邊界判斷](../../skill-derive-baseline/rules/基準邊界判斷.md) Rule 1 的型錄條件（例如被其他 Step 的 Rule、樣板或腳本共用，或逐字取自 skill 以外的來源） | skill-derive-baseline |

### Good Example

這個範例依特徵為每個 Step 選擇 deriver：單純讀取的 Step 不交給任何 deriver，被檢查腳本共用的錯誤代碼表交給 skill-derive-baseline。

```markdown
Phase 1 Step 1 READ 讀取 API 規格與錯誤情況清單 → 無
Phase 1 Step 2 THINK 判斷每個錯誤情況的錯誤類別 → skill-derive-rule（類別判斷易偏離）
Phase 2 Step 1 WRITE 撰寫每個錯誤情況的回應 → skill-derive-rule（code 與 message 要照錯誤代碼表）、skill-derive-baseline（錯誤代碼表也被 scripts/check_codes.py 讀取）與 skill-derive-template（回應有固定結構）
```

### Bad Example

這個範例把每個 Step 都交給 skill-derive-rule，單純讀取的 Step 也被展開；錯誤代碼表沒有抽成基準，Rule 與檢查腳本各留一份，新增代碼時只改一處就會分歧；固定結構的回應也沒有抽樣板。

```markdown
Phase 1 Step 1 READ 讀取 API 規格與錯誤情況清單 → skill-derive-rule
Phase 1 Step 2 THINK 判斷每個錯誤情況的錯誤類別 → skill-derive-rule
Phase 2 Step 1 WRITE 撰寫每個錯誤情況的回應 → skill-derive-rule
```

## Rule 2 -- deriver 依 script、rule、baseline、template 順序執行

**強度：MUST**

同一個 Step 需要多個 deriver 時，必須依 skill-derive-script、skill-derive-rule、skill-derive-baseline、skill-derive-template 的順序執行：先抽出腳本，避免為已交給腳本的動作撰寫規則；基準要等宣告它的 RuleFile 掛上 Step 才能抽出；最後抽樣板，讓樣板的連動調整清除與樣板重複的規則，骨架也不再寫死已抽成基準的資料。

### Good Example

這個範例依規定順序排列同一個 Step 的 deriver。

```markdown
Phase 2 Step 1：
1. skill-derive-rule
2. skill-derive-baseline
3. skill-derive-template
```

### Bad Example

這個範例先抽樣板再展開規則，skill-derive-rule 只檢查 `rules/` 不檢查 `templates/`，會寫出與樣板重複的格式規則，且不再有連動調整清除它們。

```markdown
Phase 3 Step 2：
1. skill-derive-template
2. skill-derive-rule
```

## Rule 3 -- 存留部件的 Step 必須交給對應 deriver

**強度：MUST**

存留判定為保留的既有部件，其對應 Step 必須交給該部件類型的 deriver，由 deriver 的既有部件沿用規則重新掛載，不得手動掛載或略過。

### Good Example

這個範例的 Step 雖然不需要新規則，仍交給 skill-derive-rule，由它沿用並掛載存留的 RuleFile。

```markdown
存留：rules/樣板邊界判斷.md → 對應 Phase 1 Step 2
Phase 1 Step 2 → skill-derive-rule（沿用存留的 RuleFile）
```

### Bad Example

這個範例判定 Step 不需要新規則就不交給 deriver，存留的 RuleFile 沒有被重新掛載，在 Phase 5 被檢查為孤兒檔案。

```markdown
存留：rules/樣板邊界判斷.md → 對應 Phase 1 Step 2
Phase 1 Step 2 → 無（不需要新規則）
```

## Rule 4 -- 編排提案必須逐項列出變更

**強度：MUST**

提交使用者確認的編排提案必須包含目標 SOP、每個 Step 的 deriver 與理由、指派給 skill-derive-baseline 的每份資料與目前持有它的所有部件（RuleFile 與 Rule 編號、樣板、腳本與腳本讀取的資料檔）及預計新增的基準，以及刪除清單中每個部件的刪除理由與引用它的其他 skill 的處理方式；沒有其他 skill 引用時標示「無」。不得只列出新增的部分。

### Good Example

這個範例同時列出 deriver 編排、基準的持有部件與刪除清單，刪除項目附上跨 skill 引用的處理方式，使用者可以逐項確認。

```markdown
目標 SOP：（略，見上方）

編排：
- Phase 1 Step 2 → skill-derive-rule：沿用存留的錯誤類別判斷
- Phase 2 Step 1 → skill-derive-rule、skill-derive-baseline 與 skill-derive-template：code 與 message 要照錯誤代碼表、錯誤代碼表被腳本共用、回應有固定結構

基準：
- 錯誤代碼表 → 新增 rules/baselines/錯誤代碼表.md；持有部件：rules/api-錯誤回應規範.md Rule 3、templates/錯誤回應.md 的附錄、scripts/codes.json（由 scripts/check_codes.py 讀取）

刪除：
- rules/api-錯誤回應規範.md Rule 6：新 SOP 已無對應 Step；跨 skill 引用：無
- templates/錯誤清單.md：錯誤清單無固定結構；跨 skill 引用：api-review Phase 1 Step 2 → 移除該連結
```

### Bad Example

這個範例只列出要衍生的部件，沒有寫出錯誤代碼表的持有部件，也沒有刪除清單；使用者確認後才發現腳本的資料檔與既有部件被刪除，失去在閘門審視的機會。

```markdown
編排：
- Phase 1 Step 2 → skill-derive-rule
- Phase 2 Step 1 → skill-derive-rule、skill-derive-baseline 與 skill-derive-template
```

## Rule 5 -- 目標 SOP 只標記有變動的 Step

**強度：MUST**

優化時，編排提案中的目標 SOP 必須依存留判定的新舊 Step 對應，只在有變動的 Step 行尾加標記，未變動的 Step 不加：

| 變動 | 行尾標記 |
|---|---|
| 沒有對應的舊 Step | `〔新增〕` |
| 文字不同 | `〔修改：原為「舊 Step 全文」〕`；多個舊 Step 併入時併列各段舊文 |
| 換了 Phase，或與其他存留 Step 的相對順序改變 | `〔移動：原 Phase N Step M〕`；同時改寫時併寫為 `〔移動：原 Phase N Step M；修改：原為「舊 Step 全文」〕` |

只因前面插入或刪除 Step 造成的序號位移不算移動。沒有對應新 Step 的舊 Step 必須列在目標 SOP 下方的「已刪除 Step」，寫出原位置、原文與刪除理由。新建時不加標記。標記只出現在編排提案，寫入 SKILL.md 的 SOP 不得含標記。

### Good Example

這個範例只標記有變動的 Step；Phase 2 Step 2 因前面刪除一個 Step 而序號位移，內容未變所以不標記；被刪除的 Step 列在下方。

```markdown
目標 SOP：

### Phase 1 --- 判斷需求

1. READ 讀取使用者需求與目標 skill。
2. ASK 依 [需求釐清規範](rules/需求釐清規範.md) 需求不明時詢問使用者。〔修改：原為「ASK 需求不明時詢問使用者。」〕

### Phase 2 --- 撰寫 SOP

1. WRITE 依 [SOP 格式規範](rules/sop-格式規範.md) 撰寫精簡的重點步驟。〔修改：原為「WRITE 依 [SOP 格式規範](rules/sop-格式規範.md) 撰寫重點步驟。」、「WRITE 依 [SOP 精簡規範](rules/sop-精簡規範.md) 刪除多餘說明。」〕
2. WRITE 依 [SOP 檔案掛載規範](rules/sop-檔案掛載規範.md) 在需要使用檔案的 Step 加入連結。
3. THINK 判斷是否需要 SOP。〔移動：原 Phase 1 Step 2〕

已刪除 Step：
- 原 Phase 2 Step 2「THINK 檢查 Step 數量。」：已由 SOP 格式規範涵蓋，指不出防止的失敗
```

### Bad Example

這個範例把序號位移的 Step 也標為移動，又沒有列出被刪除的 Step；真正的改動淹沒在標記中，被刪除的 Step 則無聲消失。

```markdown
目標 SOP：

### Phase 2 --- 撰寫 SOP

1. WRITE 依 [SOP 格式規範](rules/sop-格式規範.md) 撰寫精簡的重點步驟。〔修改〕
2. WRITE 依 [SOP 檔案掛載規範](rules/sop-檔案掛載規範.md) 在需要使用檔案的 Step 加入連結。〔移動：原 Phase 2 Step 3〕
```
