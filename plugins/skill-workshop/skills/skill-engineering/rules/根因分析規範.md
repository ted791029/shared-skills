# 根因分析規範

## Rule 1 -- 必須沿呼叫鏈回推產出步驟

**強度：MUST**

必須從使用者不滿的產出回推到產生它的 skill 與 Step；該 Step 的輸入來自上游 skill 時，必須繼續回推上游。偏離的 Step 或其掛載部件本身也是上游產出：SOP 由 skill-form-sop 產生，RuleFile、樣板與腳本由對應的 skill-derive-* 產生，必須以現行版本重演該 Step 的產生過程。重演產生相同內容時，回推終點在該模組 skill；不產生相同內容時，回推終點在目標 skill 的該 Step 或部件，不需追查當時的產生過程。不得只檢查使用者點名的那一個 skill。以下 Example 皆對照此呼叫鏈：

```text
skill-derive-rule 依規範邊界判斷 → skill-derive-template 的 rules/樣板邊界判斷.md
skill-derive-template Phase 1 Step 3 THINK 依樣板邊界判斷判斷抽取範圍 → 抽取清單
skill-derive-template Phase 2 Step 1 WRITE 撰寫骨架與範例 ← 使用者不滿的產出
```

### Good Example

這個範例發現樣板的輸入已經偏離，回推到產出抽取清單的 Step，再重演產生其規範的 skill-derive-rule，依重演結果決定回推終點。

```markdown
樣板多出未指定 Step 的檔案 ← Phase 2 Step 1 依抽取清單撰寫樣板
抽取清單已包含「Phase 2 與 Phase 3 全部 Step 的產出」 ← Phase 1 Step 3 判斷抽取範圍時已偏離
樣板邊界判斷沒有限制抽取範圍 ← 重演 skill-derive-rule：規範邊界判斷會展開「樣板只涵蓋指定步驟」，不產生相同內容
→ 回推終點：skill-derive-template 的 rules/樣板邊界判斷.md
```

### Bad Example

這個範例停在目標 skill 的規範，沒有重演產生它的 skill-derive-rule，轉而要求當時的對話紀錄；紀錄不存在時根因分析無法完成，即使找到紀錄也無法判斷模組現在是否仍會產生相同規範。

```markdown
樣板多出未指定 Step 的檔案 ← Phase 2 Step 1 依抽取清單撰寫樣板
抽取清單已包含「Phase 2 與 Phase 3 全部 Step 的產出」 ← Phase 1 Step 3 判斷抽取範圍時已偏離
樣板邊界判斷沒有限制抽取範圍 ← 需要當時撰寫規範的對話紀錄才能判斷原因
→ 回推終點：待查
```

## Rule 2 -- 以第一個偏離點為根因候選

**強度：MUST**

必須以原始輸入沿 SOP 逐步演練，記錄每個 Step 的產出是否符合預期：Step 的產出使最終預期無法達成，或與其他產出物衝突時，即判為偏離，即使該 Step 完全遵守自身的規則。不得以「該 Step 已依規則撰寫」判定未偏離；規則本身導致偏離時，根因在該規則。最早偏離預期的 Step 才是根因候選，之後的偏離一律視為症狀，不得各自列為根因。以下 Example 皆對照此呼叫鏈與預期：

```text
預期：所有產出物的資料表都含稽核欄位
上游 Step 依其規則「只套用本產出物的條款」撰寫 plan.md：結構決策寫「沿用的資料表不修改」
下游 Step 依 plan.md 撰寫 data-model.dbml：沿用的資料表缺稽核欄位
```

### Good Example

這個範例以最終預期判斷上游產出，上游雖然遵守自身規則，產出已使預期無法達成，因此判為第一個偏離點，下游偏離標為症狀。

```markdown
上游 Step 撰寫 plan.md：「沿用的資料表不修改」使沿用表無法補上稽核欄位 → 第一個偏離點（根因候選，該 Step 遵守自身規則，根因在規則）
下游 Step 撰寫 data-model.dbml：沿用表缺稽核欄位 → 症狀
```

### Bad Example

這個範例以「是否遵守自身規則」判斷上游，把第一個偏離點錯放在下游；之後使用者每指出一個上游問題，根因就跟著換一次。

```markdown
上游 Step 撰寫 plan.md：依規則不套用 data-model.dbml 的條款 → 未偏離
下游 Step 撰寫 data-model.dbml：沿用表缺稽核欄位 → 第一個偏離點（根因候選）
```

## Rule 3 -- 必須先靜態判定部件掛載狀態與輸入來源

**強度：MUST**

判斷根因前，必須讀取偏離 Step 所屬 skill 的 SKILL.md 與 `rules/`、`templates/`、`scripts/`，確認偏離 Step 應使用的部件屬於哪一種狀態：不存在、存在但未掛載或掛錯 Step、已掛載。部件已掛載時，必須再列出該 Step 的每個輸入，並寫出產生它的 Step 或決定其範圍的規則，例如讀入的條款由哪一步依哪條規則載入；輸入為空或被規則限縮時，回推到該 Step 或規則。不得搜尋對話紀錄檔來判定；問題發生在當前對話時，以對話中實際讀取的檔案作為證據。不得在未確認狀態前直接判定為「缺少規則」。以下 Example 皆對照此 SKILL.md 片段與檔案：

```markdown
### Phase 1 --- 判斷需求

3. THINK 判斷指定步驟中應抽成樣板的格式內容。

### Phase 3 --- 連動調整

1. WRITE 依 [規則連動調整](rules/規則連動調整.md) 刪改已由樣板涵蓋的 Rule。
```

```text
rules/樣板邊界判斷.md   存在
rules/規則連動調整.md   存在
```

### Good Example

這個範例比對 SKILL.md 與檔案，發現樣板邊界判斷存在卻沒有掛載在任何 Step，判定為「存在但未掛載」，修正方向轉向掛載而非新增規則。

```markdown
偏離 Step：Phase 1 Step 3
應使用部件：rules/樣板邊界判斷.md
掛載狀態：存在但未掛載（Phase 1 Step 3 沒有連結此檔）
```

### Bad Example

這個範例沒有判定掛載狀態就判定缺少規則，實際上規則早已存在只是沒掛載，新增的規則同樣不會被讀取，問題依舊。

```markdown
偏離 Step：Phase 1 Step 3
判定：缺少「樣板只涵蓋指定步驟」的規則 → 新增 Rule
```

## Rule 4 -- 已掛載部件依重演結果分流

**強度：MUST**

部件已掛載時，必須以原始輸入依該部件重演偏離 Step：重演仍偏離時，根因在部件內容，依 Rule 5 歸類；重演得到預期產出時，判定為當時未遵守，修改方向只能調整掛載位置、強度或精簡部件，不得新增規則。以下 Example 皆對照此情境：

```text
偏離 Step：skill-form-template Phase 2 Step 2 WRITE 依 [樣板範例規範](rules/template-範例規範.md) 撰寫範例
規範內容：Rule 3 -- 範例必須是完成的產出（強度：SHOULD）
原產出：範例殘留 `{{phase_name}}` 填位符號
```

### Good Example

這個範例依規範重演後產出正確，判定為未遵守，修改方向只調整強度，不新增規則。

```markdown
重演：依 Rule 3 撰寫範例 → 所有填位符號都已替換，符合預期
判定：已掛載但未遵守
修改方向：Rule 3 強度由 SHOULD 改為 MUST
```

### Bad Example

這個範例重演後產出正確，仍判定缺少規則並新增 Rule，新規則與 Rule 3 重複，原本未被遵守的原因沒有處理，規範只會越疊越多。

```markdown
重演：依 Rule 3 撰寫範例 → 所有填位符號都已替換，符合預期
判定：缺少填位符號替換規則
修改方向：在樣板範例規範新增 Rule 5 -- 範例不得殘留填位符號
```

## Rule 5 -- 根因必須定位到部件並分類

**強度：MUST**

根因必須寫出 skill 名稱、部件檔案與 Step 或 Rule 編號，並歸入下表其中一個類別。無法定位到部件層級的描述（如「模型理解不足」）不算根因。

| 類別 | 範圍 |
|---|---|
| SOP 層 | 缺少 Step、順序錯誤、一個 Step 混入多個動作、缺少閘門 |
| 掛載層 | 部件存在但未掛載、掛錯 Step、連結失效 |
| Rule 層 | 缺少規則、描述無法判斷、強度錯誤、Example 誤導、規則互相衝突 |
| Template 層 | 骨架缺少結構、範例粒度錯誤 |
| Script 層 | 程式錯誤、判斷被寫死在腳本 |
| 觸發層 | description 未觸發或觸發錯 skill |
| 介面層 | 上游產出與下游輸入不一致 |
| 非 skill | 使用者輸入不足、預期從未被表達 |

### Good Example

這個範例寫出 skill、檔案與 Step，並歸入掛載層。

```markdown
根因：skill-derive-template 的 rules/樣板邊界判斷.md 未掛載在 Phase 1 Step 3
類別：掛載層
```

### Bad Example

這個範例只描述模型行為，沒有定位到任何部件，後續無法決定要改哪個檔案，只能憑感覺新增規則。

```markdown
根因：AI 在判斷抽取範圍時沒有理解使用者只想抽指定的 Step。
```

## Rule 6 -- 根因必須通過反事實檢驗

**強度：MUST**

提出根因前，必須假設只修正該部件並重新演練：原問題情境必須得到預期產出，且同類的另一個情境也成立；同類情境必須取自與原問題不同的專案、技術堆疊或領域，不得只用原問題同一個專案的變化，目標為專用 skill（見[重構取捨規範](重構取捨規範.md) Rule 3）時改取該專案的其他功能。未通過的只能列為相關因素，不得作為根因。演練預設以推論進行；符合下列任一條件時，必須在撰寫報告前委派子 agent 實際執行：

- 呼叫鏈跨兩個以上 skill
- 有兩個以上互相競爭的修改方向
- 使用者質疑根因，且重新讀檔後仍無法以證據定案

每個候選修改方向委派一個子 agent，最多兩個。提示只能提供原始輸入、症狀、已確認的預期與套用該修改方向後的部件，不得提供預期的根因，也不得夾帶其他修改方向或要求其產出另一個候選所需的內容；子 agent 的結論必須抽查原始檔案後才能採用。執行環境不支援子 agent 時，必須輸出同一份提示，請使用者另開新對話執行並貼回結論，視同子 agent 的結論；不得改以推論演練代替。

### Good Example

這個範例的呼叫鏈跨三個 skill，因此委派子 agent，只提供套用候選修改方向後的規則與原始症狀，再抽查其引用的檔案。

```markdown
觸發條件：呼叫鏈跨 constitution、system-analysis、data-plan
子 agent 提示：症狀、已確認預期、改寫後的根因分析規範 Rule 2；未提供預期根因
- 原情境：第一個偏離點落在最上游產出決策的 Step，根因與是否需修改其他 skill 都有明確結論 ✔
- 同類情境：樣板多抽未指定 Step 的範例結論不變 ✔
抽查：子 agent 引用的 research.md 決策與憲法目錄列數與原始檔案一致
→ 確立為根因
```

### Bad Example

這個範例的呼叫鏈跨三個 skill，卻只以推論演練，漏掉更上游的偏離；使用者質疑後又只改答案、不實際驗證，根因隨每次追問更換。

```markdown
反事實：只改寫 Rule 3 後推論演練 → data-model.dbml 符合條款 ✔ → 確立為根因
使用者質疑 plan.md 也錯 → 改判 Rule 1 為根因
使用者質疑 plan.md 不依憲法撰寫 → 改判 system-analysis 為根因
```

## Rule 7 -- 根因不在 skill 時不得修改 skill

**強度：MUST**

根因歸入「非 skill」類別時，必須據實回報並建議使用者調整輸入或補充預期，不得為了有所產出而修改 skill。

### Good Example

這個範例判定問題出在使用者輸入的範圍與預期不一致，因此只回報並建議調整輸入，不修改 skill。

```markdown
根因：使用者的需求寫「把 skill-form-sop 的 Phase 2 都抽成樣板」，與預期「只抽 Phase 2 Step 1」不一致
類別：非 skill
建議：下次請在需求中指定到 Step；skill 不修改。
```

### Bad Example

這個範例在根因屬於使用者輸入時仍新增規則，規則無法彌補缺少的資訊，只會讓 skill 多一條沒有作用的規範。

```markdown
根因：使用者的需求指定的範圍與預期不一致
處理：在 樣板邊界判斷.md 新增「必須推測使用者實際想抽的 Step」
```
