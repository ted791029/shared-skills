# 重構取捨規範

## Rule 1 -- 既有部件必須舉證才能存留

**強度：MUST**

逐一檢查既有的 Step、Rule、樣板與腳本：必須能對應到目標 SOP 的某個 Step，且能指出它防止了哪一種失敗，才能存留；任一項指不出就刪除。不得因為「原本就有」或「可能有用」而保留。

### Good Example

這個範例對每個部件舉證，指不出對應 Step 或防止的失敗就判定刪除。

```markdown
rules/樣板邊界判斷.md Rule 3 → 對應新 Phase 1 Step 2；防止抽出未指定 Step 的樣板 → 存留
rules/樣板邊界判斷.md Rule 4 → 新 SOP 已無對應 Step → 刪除
templates/抽取清單.md → 對應新 Phase 1 Step 2；但抽取清單無固定結構，指不出防止的失敗 → 刪除
```

### Bad Example

這個範例以「可能有用」為由保留沒有對應 Step 的部件，skill 會累積無人使用的規則，日後修改時還要顧及它們。

```markdown
rules/樣板邊界判斷.md Rule 4 → 新 SOP 已無對應 Step，但之後可能用得到 → 存留
```

## Rule 2 -- 修正層級依優先序選擇

**強度：MUST**

修正根因時依下列順序選擇第一個能解決的層級：刪除或重排 SOP Step、修正掛載、改由樣板或腳本承載、改寫既有 Rule、新增 Rule。選擇較後的層級時，必須說明較前的層級為什麼無法解決。

### Good Example

這個範例的根因是規則未掛載，選擇第二層的修正掛載，不新增規則。

```markdown
根因：rules/樣板邊界判斷.md 未掛載在判斷抽取範圍的 Step（掛載層）
修正層級：修正掛載 → 在新 Phase 1 Step 2 掛載該 RuleFile
```

### Bad Example

這個範例的根因同樣是規則未掛載，卻直接跳到最後一層新增規則，也沒有說明前面的層級為何無效，新規則與未掛載的舊規則內容重複。

```markdown
根因：rules/樣板邊界判斷.md 未掛載在判斷抽取範圍的 Step（掛載層）
修正層級：新增 Rule → 在 skill-form-template 的 template-骨架規範.md 新增「只為指定 Step 撰寫骨架」
```

## Rule 3 -- 修改內容必須在 skill 的服務範圍內通用

**強度：MUST**

新增或修改的 Rule、SOP Step 與腳本判斷，必須描述同類情境的通用判斷標準，不得只針對使用者回報的單一事件。目標 skill 的 description 或 SOP 沒有寫明只服務某個專案時視為共用 skill，只出現在 Example 的專案內容不算寫明；共用 skill 的這些內容不得出現觸發案例特有的工具、套件、路徑、檔名、數值或領域名詞，這些具體值只能放在 Example，流程中其他 skill 定義的概念與名稱不算案例特有。確認的預期含有專案特有的值時，建議登記到該專案的憲法，不寫入共用 skill。description 或 SOP 寫明只服務某個專案的專用 skill，可以直接寫入該專案的值。

### Good Example

這個範例的共用 skill data-plan 把命名慣例寫成來源，專案的 snake_case 建議登記到憲法，具體表名只留在 Example；專用 skill 則直接寫入該專案的路徑與 port。

```markdown
data-plan（description 未寫明專案 → 共用）
- 修改方向：資料表命名規範新增 Rule：資料表與欄位命名必須依憲法登記的命名慣例；Example 以 `guess_records` 示範
- 建議：在該專案的憲法登記「資料表與欄位使用 snake_case」

ch5-test-env（description 寫明「啟動 CH5 專案的 e2e 測試環境」→ 專用）
- 修改方向：Phase 1 Step 1 改為讀取 `frontend/tests/e2e/playwright.config.js`，Step 2 改為等待 port 8001
```

### Bad Example

這個範例的 data-plan 同樣是共用 skill，卻把觸發案例的命名與表名寫進規則內文，換成慣例為 PascalCase 的專案時，規則會逼該專案改名。

```markdown
data-plan（description 未寫明專案 → 共用）
- 修改方向：資料表命名規範新增 Rule：資料表一律使用 snake_case，猜測紀錄表必須命名為 `guess_records`
```

## Rule 4 -- 衝突 Rule 以修改取代覆蓋

**強度：MUST**

新的要求與既有 Rule 衝突時，必須直接修改或刪除既有 Rule，不得新增一條「優先於」、「例外於」既有 Rule 的規則。

### Good Example

這個範例直接改寫衝突的既有 Rule，規範只存在一處。

```markdown
修改前：## Rule 2 -- 必須抽出所有固定格式的產出
修改後：## Rule 2 -- 必須抽出指定 Step 的固定格式產出
```

### Bad Example

這個範例保留衝突的舊 Rule，再新增一條覆蓋它的規則，agent 必須同時理解兩條互相矛盾的規則及其優先順序，容易執行錯誤。

```markdown
## Rule 2 -- 必須抽出所有固定格式的產出

## Rule 5 -- 本規則優先於 Rule 2：只抽出指定 Step 的產出
```

## Rule 5 -- 淨增加必須說明理由

**強度：MUST**

存留判定完成後，必須統計新增與刪除的 Step、Rule、樣板與腳本數量；新增多於刪除時，必須說明增加的部件解決了哪個既有部件無法解決的問題。

### Good Example

這個範例統計增減，並說明唯一的淨增加對應到既有部件無法涵蓋的問題。

```markdown
Step：+1 −2
Rule：+1 −3
樣板：+0 −1
淨增加說明：無，整體淨減少。
```

### Bad Example

這個範例只列出新增內容，沒有統計刪除也沒有說明淨增加，使用者無法判斷優化是在精簡還是在疊加。

```markdown
新增：
- Phase 1 --- 界定抽取範圍
- rules/抽取範圍規範.md（4 條 Rule）
```

## Rule 6 -- 職責錯置時調整 skill 結構

**強度：SHOULD**

根因屬於介面層或觸發層，或目標 SOP 壓縮後仍超過 5 個 Phase 時，應提出拆分、合併 skill 或搬移職責的結構調整，而不是在單一 skill 內增加 Step 補救。

### Good Example

這個範例的根因是上下游介面不一致，因此提出把職責搬到上游 skill。

```markdown
根因：skill-engineering 的編排提案只寫 deriver 名稱、沒寫指派的 Step，skill-derive-template 只能自行推測抽取範圍（介面層）
結構調整：在 skill-engineering 的編排提案寫明每個 deriver 指派的 Step，skill-derive-template 改為直接讀取
```

### Bad Example

這個範例在下游 skill 增加推測步驟補救上游的缺漏，兩個 skill 對抽取範圍各有一套判斷，日後容易不一致。

```markdown
根因：skill-engineering 的編排提案沒寫指派的 Step（介面層）
處理：在 skill-derive-template 新增 Phase「推測抽取範圍」
```
